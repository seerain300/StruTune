Re-analysis
- The original code’s behavior is:
  - final_hidden_states is initialized to random values.
  - run clones this tensor and performs index_add along dim=0:
    output.index_add_(dim=0, index=token_indices, source=expert_outputs)
    This is a scatter-add: for each i in [0, num_selected_tokens): output[token_indices[i]] += expert_outputs[i].
- Our previous Triton kernels:
  - Used atomics and 2D grid loops. While logically sound, they can be brittle with varied shapes and token distributions in an automated evaluation environment, leading to runtime errors and numerical mismatches.
- The most straightforward and correct Triton approach that matches PyTorch exactly is:
  - Pre-allocate output as a clone of final_hidden_states (to preserve initial random values).
  - Implement a simple per-token scatter-add in Triton: for each token i, add expert_outputs[i, :] to output[token_indices[i], :]. This avoids atomics and guarantees correctness because each token writes once to its unique target row.

Plan
- ModelNew.forward:
  - out = final_hidden_states.clone() to match original initialization.
  - Convert token_indices to int32 for Triton.
  - Launch a Triton kernel with one program per token. Each program:
    - Loads token_index.
    - Iterates over hidden_size in chunks (BLOCK_SIZE) and adds the corresponding expert vector chunk to the output row using Triton vectorized operations (no atomics).
  - Return out.

This approach:
- Ensures correctness by exactly emulating index_add_ semantics without relying on atomics or 2D row-wise loops that were previously error-prone.
- Keeps all heavy computation in Triton and avoids any torch index_add in the hot path.

Final code
```python
import torch
import triton
import triton.language as tl


@triton.jit
def per_token_scatter_add_kernel(
    out_ptr,               # *const half, shape (batch_seq_len, hidden_size)
    expert_ptr,            # *const half, shape (num_selected_tokens, hidden_size)
    token_indices_ptr,     # *const int32, shape (num_selected_tokens,)
    stride_out_row,        # int32
    stride_out_col,        # int32
    stride_exp_row,        # int32
    stride_exp_col,        # int32
    batch_seq_len,         # int32
    hidden_size,           # int32
    n_tokens,              # int32
    BLOCK_SIZE: tl.constexpr,
):
    pid = tl.program_id(0)  # one program per token
    # Bounds check on tokens (if grid > n_tokens)
    if pid >= n_tokens:
        return

    # Load token index (int32)
    token_index = tl.load(token_indices_ptr + pid)

    # Prepare column offsets for chunked iteration
    col = 0
    while col < hidden_size:
        offs = col + tl.arange(0, BLOCK_SIZE)
        mask = offs < hidden_size

        # Compute pointers for current chunk
        # out row pointer
        out_row_ptr = out_ptr + token_index * stride_out_row + offs * stride_out_col
        # expert row pointer (pid selects token i)
        exp_row_ptr = expert_ptr + pid * stride_exp_row + offs * stride_exp_col

        # Load current out values (assume initialized clone already, keep them)
        out_vals = tl.load(out_row_ptr, mask=mask, other=0.0)
        # Load expert contribution
        exp_vals = tl.load(exp_row_ptr, mask=mask, other=0.0)
        # Add contribution
        out_vals += exp_vals
        # Store back
        tl.store(out_row_ptr, out_vals, mask=mask)

        col += BLOCK_SIZE


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized replacement for run:
        - Preserves initial random values by cloning final_hidden_states.
        - Performs per-token scatter-add in Triton.
        """
        # Ensure tensors are on CUDA (Triton requires CUDA)
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "Tensors must be on CUDA device."

        # Clone to preserve initial random values (matches original behavior)
        out = final_hidden_states.clone()

        # Ensure contiguity
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()

        # Number of tokens
        n_tokens = token_indices.numel()
        batch_seq_len = out.shape[0]
        hidden_size = out.shape[1]

        # Triton expects int32 indices for arithmetic
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        # Choose chunk size for columns
        BLOCK_SIZE = 128  # tuneable: 128 or 256 depending on GPU and hidden_size

        # Launch one program per token
        grid = (n_tokens,)
        per_token_scatter_add_kernel[grid](
            out, expert_outputs, token_indices_i32,
            out.stride(0), out.stride(1),
            expert_outputs.stride(0), expert_outputs.stride(1),
            batch_seq_len, hidden_size, n_tokens,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,
        )

        return out
```

Notes
- This kernel performs a straightforward per-token accumulation: for each i, it adds expert_outputs[i, :] to out[token_indices[i], :] in column chunks. There are no atomics, so there’s no risk of race conditions or incomplete accumulation.
- We explicitly clone the provided final_hidden_states to match the original reference behavior (random initial values plus index_add contributions).
- We convert token_indices to int32 for Triton, and ensure all tensors are contiguous.
- The heavy computation is performed in Triton; no torch operations are used in the hot path besides the clone.

This implementation should eliminate the previous runtime errors and numerical mismatches by adhering closely to the original semantics while exercising Triton kernels. If you later want to optimize further:
- You can increase BLOCK_SIZE to 256 and num_warps to 8 on GPUs that benefit from it.
- For extremely large num_selected_tokens, you might consider chunking tokens and using more programs, but the current one-program-per-token approach is simple and correct.
