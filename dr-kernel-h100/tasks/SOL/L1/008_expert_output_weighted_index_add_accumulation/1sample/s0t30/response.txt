  output.index_add_(dim=0, index=token_indices, source=expert_outputs)
- This is a scatter-add along the first dimension (rows): for each i in range(num_selected_tokens), output[token_indices[i]] += expert_outputs[i].
- The evaluation harness provides:
  - batch_seq_len = batch_size * seq_len
  - hidden_size = expert_outputs.shape[1] == final_hidden_states.shape[1]
  - num_selected_tokens = expert_outputs.shape[0]
  - token_indices in [0, batch_seq_len)
- We must implement this scatter-add exactly. The accumulation is elementwise add across hidden_size for each token.

Diagnosis of prior failures
- The earlier Triton scatter-add used a 2D grid or dynamic while loops inside the kernel. While theoretically correct, the evaluation reported “INCORRECT_NUMERICAL” for multiple configurations. This strongly suggests a subtle bug in kernel addressing, masking, or dtype handling that was not consistently caught by partial runs. To minimize risk, I will use a simpler, more robust approach: a 2D grid over tokens and hidden-size columns, performing atomic_add for each token-column pair. This removes dynamic loops and reduces the chance of pointer/mask mistakes.

Plan
- Implement two Triton kernels:
  1) zero_init_kernel: Initializes the output buffer to zeros. This is necessary for atomic_add semantics. We’ll use a simple 2D grid over rows and column blocks to write zeros. It is actually launched from ModelNew.forward.
  2) scatter_add_atomic_kernel: Performs the scatter-add. Grid dimension:
     - grid[0] = num_selected_tokens: one program per token.
     - grid[1] = ceil_div(hidden_size, BLOCK_SIZE): each program handles a block of hidden columns. The kernel loads expert_outputs[row, cols] and out[token_index, cols], computes partial += expert_outputs[row, cols], then atomic_adds partial back into out[token_index, cols]. This ensures we cover all columns even when hidden_size is not a multiple of BLOCK_SIZE. Using a 2D grid eliminates dynamic loops and makes masking straightforward.
- Dtypes:
  - out and expert_outputs are bfloat16 (as per get_inputs).
  - token_indices are converted to int32 for Triton.
- Robustness:
  - Ensure tensors are contiguous.
  - Use masks for partial column blocks.
  - Assume token indices are valid in [0, batch_seq_len), as in the original code.

Final code
```python
import torch
import triton
import triton.language as tl


@triton.jit
def zero_init_kernel(out_ptr, stride_row, stride_col, batch_len, hidden_size, BLOCK_SIZE: tl.constexpr):
    # 2D grid: (rows, col_blocks)
    row_id = tl.program_id(0)
    col_block = tl.program_id(1)
    cols = col_block * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = cols < hidden_size

    # Compute linear offsets: out[row_id, cols]
    offs = row_id * stride_row + cols * stride_col
    # Write zeros
    zeros = tl.zeros([BLOCK_SIZE], dtype=tl.bfloat16)
    tl.store(out_ptr + offs, zeros, mask=mask)


@triton.jit
def scatter_add_atomic_kernel(
    out_ptr, stride_row, stride_col,
    expert_ptr, expert_stride_row, expert_stride_col,
    token_indices_ptr,
    batch_len, hidden_size, n_tokens, BLOCK_SIZE: tl.constexpr
):
    # Grid: (tokens, col_blocks)
    token_id = tl.program_id(0)  # which token we process
    col_block = tl.program_id(1)
    cols = col_block * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    col_mask = cols < hidden_size

    # Load token index for this program
    token_index = tl.load(token_indices_ptr + token_id)  # int32

    # Compute base offsets
    # out: out[token_index, cols]
    out_offs = token_index * stride_row + cols * stride_col
    # expert: expert[token_id, cols]
    expert_offs = token_id * expert_stride_row + cols * expert_stride_col

    # Load current out values and expert contributions (bfloat16)
    out_vals = tl.load(out_ptr + out_offs, mask=col_mask, other=0.0)
    expert_vals = tl.load(expert_ptr + expert_offs, mask=col_mask, other=0.0)

    # Accumulate
    partial = out_vals + expert_vals

    # Atomic add into output
    tl.atomic_add(out_ptr + out_offs, partial, mask=col_mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Compute dimensions
        batch_size = final_hidden_states.shape[0]
        seq_len = final_hidden_states.shape[1]  # hidden_size is the second dimension
        hidden_size = final_hidden_states.shape[1]
        batch_seq_len = batch_size * seq_len

        # Allocate output (clone semantics of original: zero-init then add)
        out = torch.empty((batch_seq_len, hidden_size), dtype=torch.bfloat16, device=final_hidden_states.device)

        # Ensure expert_outputs is contiguous
        expert_outputs = expert_outputs.contiguous()

        # Convert token indices to int32 for Triton
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        # Zero-initialize output using Triton
        BLOCK_SIZE_ZERO = 256
        grid_zero = (batch_seq_len, triton.cdiv(hidden_size, BLOCK_SIZE_ZERO))
        zero_init_kernel[grid_zero](
            out, out.stride(0), out.stride(1), batch_seq_len, hidden_size,
            BLOCK_SIZE=BLOCK_SIZE_ZERO,
            num_warps=4,
        )

        # Launch scatter-add kernel: 2D grid over tokens and column blocks
        n_tokens = expert_outputs.shape[0]
        BLOCK_SIZE = 256
        grid_scatter = (n_tokens, triton.cdiv(hidden_size, BLOCK_SIZE))
        scatter_add_atomic_kernel[grid_scatter](
            out, out.stride(0), out.stride(1),
            expert_outputs, expert_outputs.stride(0), expert_outputs.stride(1),
            token_indices_i32,
            batch_seq_len, hidden_size, n_tokens,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,
        )

        return out
```

Why this should fix correctness
- The zero_init_kernel runs and writes zeros across all rows and hidden columns using a straightforward 2D grid and mask. This eliminates any ambiguity about whether the accumulator starts at zero.
- The scatter_add_atomic_kernel processes each token in its own program and covers all hidden columns using a 2D grid over column blocks. Each program:
  - Loads the current out[token_index, cols] and expert_outputs[token_id, cols].
  - Computes partial += expert.
  - Performs atomic_add into out[token_index, cols].
- This approach directly mirrors the index_add_ semantics: for each token, add its expert vector to the corresponding row. It handles duplicates in token_indices correctly (multiple tokens contributing to the same row).
- Using a 2D grid over tokens and column blocks avoids dynamic loops in the kernel, minimizing the risk of masking or pointer arithmetic issues that led to incorrect numerical results in prior submissions.

Performance considerations
- The zero-init kernel is a simple fill and is fast. The scatter-add uses atomics per token per column block. For the given problem sizes (hidden_size up to 1024, num_selected_tokens in a few hundred to a few thousand), this should be performant. You can tune BLOCK_SIZE (128, 256) and num_warps (4, 8) based on your GPU. If profiling shows contention, consider increasing BLOCK_SIZE to reduce the number of atomic operations per token.
- If further speedups are needed after correctness is established, you could:
  - Increase BLOCK_SIZE to 512 on GPUs that handle it well.
  - Use num_warps=8 to improve throughput for larger hidden sizes.
  - However, correctness is the primary priority here.
