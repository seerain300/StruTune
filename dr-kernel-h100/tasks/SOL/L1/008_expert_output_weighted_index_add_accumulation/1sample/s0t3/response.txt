Root cause analysis
- The original PyTorch code does: output.index_add_(dim=0, index=token_indices, source=expert_outputs).
  - This performs a scatter-add: for each i, output[token_indices[i]] += expert_outputs[i].
  - It accumulates across all i, but it does not reorder rows. Each row is the sum of contributions from all tokens that map to it.
- In the prior Triton implementation:
  - I used a 2D grid over (tokens, hidden column blocks) and masked stores into out[token_index, col_block].
  - While masked stores can be used to avoid OOB writes, in Triton, masked stores must be used carefully: the pointer must be valid for all lanes, and the mask must define which lanes are actually written. If the program computes a pointer for a token index >= batch_seq_len (or any other invalid condition), Triton still executes the store for all lanes unless the mask prevents it. If the mask is not correctly applied or if the grid or pointer math is off, it can result in incorrect accumulation (e.g., not adding all contributions, or adding to wrong rows).
  - The reported failures “INCORRECT_NUMERICAL” across multiple configurations suggest the accumulation was not performed correctly for some rows. A common issue is that masked stores might not cover all rows or might incorrectly add contributions to rows (e.g., row 0) when token indices are random and some are 0, or that the 2D grid and pointer math for atomic adds was not robust for all shapes. Another risk is that using masked stores without a second kernel that iterates over all rows might leave some rows unprocessed.

Plan to fix correctness
- Use a two-kernel approach that guarantees each row is processed exactly once:
  1) Triton kernel zero_init_kernel: initialize output to zeros. This guarantees atomic_add has a valid accumulator.
  2) Triton kernel row_accumulator_kernel: one program per output row. Each program loops over all tokens and, for tokens whose token_index equals the row’s index, adds the corresponding expert row to output[row]. This uses atomic_add into the row, handling duplicates correctly (multiple tokens mapping to the same row).
     - Grid: (batch_seq_len,). Each program handles one row r.
     - Loop over tokens in blocks: load token_indices and expert_outputs for a block, compare token_indices == r, and atomic_add those expert rows into out[r, :].
     - This guarantees every row r is updated by all tokens mapping to r, independent of token distribution.
- Keep dtype as bfloat16 and ensure token_indices are int32 for Triton. Operate entirely in Triton; no torch operations on tensors in the hot path beyond trivial conversions.

Optimization considerations
- The row_accumulator_kernel performs work proportional to H*num_selected_tokens (H = hidden_size). It is simple and correct, and in many practical cases, num_selected_tokens is large, making this approach efficient. It also avoids complex 2D masked store logic.
- BLOCK_SIZE for token loop can be set to 256 or 512 to reduce loop iterations; num_warps can be 4 or 8. This is typically fine for these sizes. If hidden_size is large, a 2D grid over (rows, column blocks) plus atomics could be faster, but given the correctness failures reported, the simpler one-program-per-row approach is the most robust.
- The zero_init_kernel writes zeros for all rows and columns. Launching it once is cheap relative to the scatter-add.

Notes on correctness and performance
- Correctness:
  - The zero_init_kernel guarantees the output starts at zero, which is required for atomic_add semantics.
  - The row_accumulator_kernel ensures every row r is processed for all tokens; if multiple tokens have token_index == r, atomic_add accumulates them correctly. This matches the behavior of index_add_.
  - We avoid the previous 2D masked store approach that can be error-prone for arbitrary token distributions; one-program-per-row with atomics is straightforward and robust.
- Performance:
  - This kernel is O(H * n_tokens) with a single program per row. In many practical scenarios, this is efficient and simple. It avoids the complexity of a 2D grid and ensures correctness across all distributions of token indices.
  - You can tune num_warps and BLOCK_SIZE for tokens and columns if you profile on specific GPUs. For these problem sizes, 4 warps and token block of 128 or 256 are reasonable defaults.
