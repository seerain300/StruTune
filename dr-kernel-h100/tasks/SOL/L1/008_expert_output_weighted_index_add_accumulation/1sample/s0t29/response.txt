The persistent “INCORRECT_NUMERICAL” and “RUNTIME_ERROR” indicate our Triton kernel invocation and logic are not matching the original PyTorch semantics under the evaluation harness. To robustly fix correctness and avoid runtime issues, I’ll implement the operation in Triton in a way that exactly mirrors PyTorch’s index_add behavior and ensures the Triton kernel is actually invoked.

Deep analysis
- Original behavior:
  - The provided get_inputs initializes final_hidden_states with random values (torch.randn), not zeros. The run function clones this tensor and then performs index_add along dim=0:
    output.index_add_(dim=0, index=token_indices, source=expert_outputs)
    which is equivalent to: for each i in [0, num_selected_tokens), output[token_indices[i]] += expert_outputs[i].
  - Therefore, the correct output should be the initial random final_hidden_states plus the accumulated contributions from all tokens.

- Issues observed:
  - Earlier Triton kernels either:
    - Used atomic_add and 2D grids with masking, which can be error-prone under varied shapes and token distributions.
    - Attempted to pre-zero and then add, but failed to match the initial random state or had incorrect masking/pointer math.
    - Launched kernels incorrectly (e.g., grid shape issues) causing runtime errors.
  - The evaluation reports numerical mismatches, suggesting our accumulation did not match index_add across all configurations, likely due to masked stores or incorrect grid logic.

Plan to fix correctness
- Ensure output starts as a clone of final_hidden_states so the initial random values are preserved.
- Implement a Triton kernel that performs the per-token accumulation without atomics and without any reliance on pre-zeroing. We will:
  - Launch one Triton program per token i.
  - Compute the row r = token_indices[i].
  - Loop over columns in blocks (BLOCK_SIZE) and add expert_outputs[i, cols] to out[r, cols].
- This approach:
  - Exactly matches index_add semantics (each token adds once to its target row).
  - Avoids atomics and any potential race or masking issues.
  - Ensures the Triton kernel is invoked in ModelNew.forward.

Performance
- One program per token means the kernel is O(n_tokens * hidden_size). For typical sizes (hidden_size up to 1024 and n_tokens a few thousand), this is reasonable. You can tune BLOCK_SIZE (128 or 256) and num_warps (4-8) for your GPU. The per-token approach is simple and robust.

Final code
```python
import torch
import triton
import triton.language as tl


@triton.jit
def per_token_scatter_add_kernel(
    out_ptr,              # *bf16, (B, H)
    expert_ptr,           # *bf16, (N, H)
    token_idx_ptr,        # *int32, (N,)
    out_stride0, out_stride1,
    expert_stride0, expert_stride1,
    B, H, N,
    BLOCK_SIZE: tl.constexpr,
):
    # One program per token
    pid = tl.program_id(axis=0)
    if pid >= N:
        return

    # Load destination row index
    row = tl.load(token_idx_ptr + pid)  # int32

    # Iterate over columns in chunks
    for col in range(0, H, BLOCK_SIZE):
        cols = col + tl.arange(0, BLOCK_SIZE)
        mask = cols < H

        # Load the expert vector chunk for this token
        # out[row, cols] += expert[pid, cols]
        exp_ptrs = expert_ptr + pid * expert_stride0 + cols * expert_stride1
        exp_vec = tl.load(exp_ptrs, mask=mask, other=0.0)  # bf16

        out_ptrs = out_ptr + row * out_stride0 + cols * out_stride1
        out_vec = tl.load(out_ptrs, mask=mask, other=0.0)  # bf16

        # Add and store back
        out_vec = out_vec + exp_vec
        tl.store(out_ptrs, out_vec, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor):
        """
        Triton-based implementation of:
          output = final_hidden_states.clone()
          output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        """
        # Clone to match original behavior (preserve initial random values)
        out = final_hidden_states.clone()
        # Ensure tensors are contiguous
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()

        # Shapes
        B = out.shape[0]         # batch_seq_len
        H = out.shape[1]         # hidden_size
        N = token_indices.numel()  # num_selected_tokens

        # Triton expects int32 indices for pointer math
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        # Choose column chunk size
        BLOCK_SIZE = 128  # tuneable: 128 or 256

        # Launch one program per token
        grid = (N,)
        per_token_scatter_add_kernel[grid](
            out, expert_outputs, token_indices_i32,
            out.stride(0), out.stride(1),
            expert_outputs.stride(0), expert_outputs.stride(1),
            B, H, N,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,  # tune: 4-8 are typical
        )

        return out
```

Why this should now pass correctness
- We start from a clone of final_hidden_states, preserving its initial random values exactly as in the original run.
- The Triton kernel performs per-token additions: out[token_indices[i], :] += expert_outputs[i, :], iterating over columns in chunks. There are no atomics or grid-based masking complexities; each program writes to a distinct row for its token, and any duplicate rows are written multiple times by different tokens, matching index_add semantics.
- The kernel is actually invoked from ModelNew.forward, and the heavy computation is done by Triton. We convert token_indices to int32 and ensure all tensors are contiguous.

If further speed optimization is desired after correctness is verified:
- Increase BLOCK_SIZE to 256 and num_warps to 8 for larger H.
- For extremely large N, consider parallelizing within a program using more warps, but the current design is simple and robust.
