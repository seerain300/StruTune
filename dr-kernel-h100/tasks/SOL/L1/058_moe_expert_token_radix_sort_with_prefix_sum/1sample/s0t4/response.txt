Understanding, analysis, and plan

- Original behavior to match:
  - Given topk_idx of shape (batch_size, seq_len, num_experts_per_tok) on CUDA, int32:
    - Flatten to 1D length N.
    - Perform a stable ascending sort of the flattened indices. The function returns the permutation (sorted positions). In other words, it returns torch.argsort(flat, stable=True).
    - Compute expert_offsets of length num_experts + 1 (num_experts=256 here):
      - counts[i] = number of occurrences of index i in the flattened array, for i in [0..255].
      - offsets[0] = 0
      - offsets[i] = sum of counts[0..i-1] for i in 1..256 (inclusive prefix sum).

- Triton-only requirement:
  - All computation must be done via @triton.jit kernels that are actually launched from ModelNew.forward. No torch.argsort, no torch.cumsum, no torch reductions for the heavy work. Only tensor metadata (reshape, contiguous, view) is allowed in host code.

- Strategy:
  - Implement a Triton kernel to build the histogram of the flattened indices using atomic adds into a counts vector of length 256. This replaces torch.bincount.
  - Implement a Triton inclusive scan (prefix sum) kernel to compute offsets from counts. Since num_experts is fixed at 256, a single program instance looping over 256 elements is efficient and avoids complicated block-wise scans. This replaces torch.cumsum.
  - Implement a Triton bitonic sort kernel for the flattened indices to produce the permutation (sorted positions). This replaces torch.argsort(stable=True). Bitonic sort is deterministic and can be made stable by tie-breaking: for equal values, sort by original index in ascending order, preserving original order. We clone flat to a working buffer to perform in-place compare-and-swap while preserving the original flat.

- Stability and correctness:
  - The bitonic sort kernel uses a standard pattern for permutation sort: maintain a global array values and a parallel array indices. For each bitonic stage, we compute partner indices and perform compare-and-swap on values while updating indices accordingly. For equal values, we choose the smaller original index first to maintain stable order (i < j takes index_i), ensuring stability.
  - The histogram kernel uses tl.atomic_add per element to count occurrences of each index in [0..255]. Since indices are in that range, we can initialize counts to zeros and atomically add 1 for each element.
  - The prefix-sum kernel computes inclusive scan by looping over k from 1 to 255, setting offsets[k] = offsets[k-1] + counts[k-1]. We set offsets[0] = 0.

- Performance:
  - Sorting: Bitonic sort is O(N log^2 N). With N up to ~2,048,000, this is acceptable on modern GPUs. Triton’s parallel compare-and-swap across lanes should perform well.
  - Histogram: One atomic add per element, 256 bins. Fast.
  - Prefix sum: 256 iterations per block. Negligible.

Code: Triton-only ModelNew that launches all kernels

```python
import torch
import triton
import triton.language as tl


@triton.jit
def histogram_kernel(x_ptr, counts_ptr, N: tl.int32, BLOCK: tl.constexpr):
    """
    Build histogram of values in x_ptr (int32) into counts_ptr (int32[256]).
    Each element in x_ptr is in [0, 255]. We do one atomic add per element.
    """
    offs = tl.arange(0, BLOCK)
    grid = tl.num_programs(0)
    base = grid * BLOCK
    # Iterate over the whole array in chunks
    for start in range(0, N, base):
        idx = start + offs
        mask = idx < N
        vals = tl.load(x_ptr + idx, mask=mask, other=0)  # int32
        # Atomic add 1 for each valid value
        tl.atomic_add(counts_ptr + vals, 1, mask=mask)


@triton.jit
def inclusive_scan_prefix_sum(counts_ptr, offsets_ptr, M: tl.constexpr):
    """
    Compute inclusive prefix sum of counts_ptr[0..M-1] into offsets_ptr[0..M].
    offsets[0] must be set to 0 by host.
    """
    acc = tl.zeros((), dtype=tl.int32)
    # Loop over all elements; M is constexpr so Triton can unroll
    for k in range(0, M):
        acc += counts_ptr[k]
        offsets_ptr[k] = acc


@triton.jit
def bitonic_sort_argsort(values_ptr, indices_ptr, N: tl.int32, BLOCK: tl.constexpr):
    """
    Bitonic sort of values_ptr (int32) in ascending order, producing indices_ptr
    as the permutation (sorted positions). Stable tie-breaking by original index:
    for equal values, i < j implies choose (i, j) over (j, i).
    We operate in-place on values_ptr and indices_ptr.
    """
    # Initialize indices to [0..N-1]
    ar = tl.arange(0, BLOCK)
    for start in range(0, N, BLOCK):
        idx = start + ar
        mask = idx < N
        # Initialize local values and indices
        vals = tl.load(values_ptr + idx, mask=mask, other=0)  # values
        idxs = idx  # original positions

        # Bitonic sort network
        k = 2
        while k <= N:
            j = k // 2
            while j > 0:
                partner = idx ^ j
                valid_partner = partner < N
                # load partner's values and indices
                vals_partner = tl.load(values_ptr + partner, mask=valid_partner, other=0)
                idxs_partner = partner  # if valid

                # Determine ascending or descending segment for pair (idx, partner)
                ascending = ((idx & k) == 0)

                # Compare
                cond = vals < vals_partner
                tie = vals == vals_partner
                # Stable tie-breaking: prefer smaller original index
                tie_choice = idxs < idxs_partner

                need_swap = tl.where(
                    ascending,
                    cond | (tie & tie_choice),
                    (cond | (tie & tie_choice)) ^ 1
                )

                # Compute new values/indices for position 'idx' after potential swap
                new_vals = tl.where(need_swap, vals_partner, vals)
                new_idxs = tl.where(need_swap, idxs_partner, idxs)

                # Store back to current position
                tl.store(values_ptr + idx, new_vals, mask=mask)
                tl.store(indices_ptr + idx, new_idxs, mask=mask)

                j //= 2
            k *= 2


class ModelNew(torch.nn.Module):
    def forward(self, topk_idx: torch.Tensor):
        """
        Triton-only implementation of the original run:
        - Compute stable sort permutation of flattened indices using Triton bitonic sort.
        - Compute expert offsets via Triton histogram + inclusive scan.
        """
        assert topk_idx.is_cuda, "topk_idx must be on CUDA for Triton kernels."
        # Flatten indices and ensure contiguous
        flat = topk_idx.reshape(-1).contiguous()
        N = flat.numel()
        device = flat.device

        # 1) Stable sort permutation via Triton bitonic sort
        # Work on a copy to avoid mutating the original indices
        values = flat.clone()
        sorted_token_indices = torch.empty(N, dtype=torch.int32, device=device)
        # Launch bitonic sort with a block size that covers typical N; grid covers all elements
        BLOCK = 1024
        grid = (triton.cdiv(N, BLOCK),)
        bitonic_sort_argsort[grid](values, sorted_token_indices, N=N, BLOCK=BLOCK, num_warps=8)

        # 2) Histogram via Triton
        counts = torch.zeros(256, dtype=torch.int32, device=device)
        grid_hist = (triton.cdiv(N, BLOCK),)
        histogram_kernel[grid_hist](flat, counts, N=N, BLOCK=BLOCK, num_warps=8)

        # 3) Prefix sum (offsets) via Triton inclusive scan
        offsets = torch.empty(257, dtype=torch.int32, device=device)
        offsets[0] = 0
        inclusive_scan_prefix_sum[(1,)](counts, offsets, M=256, num_warps=1)

        return sorted_token_indices, offsets
```

Notes and considerations
- All three heavy operations (sorting permutation, histogram, prefix sum) are implemented as Triton kernels and are actually launched from ModelNew.forward. No torch.argsort, no torch.cumsum, no torch reductions for these tasks.
- Sorting tie-breaking: For equal values, we choose the smaller original index first in ascending segments, which preserves the original order and yields stable behavior consistent with torch.argsort(stable=True).
- Histogram: We assume indices are in [0..255], as per the original get_inputs and run. If inputs ever stray outside this range, histogram_kernel would need adjustment; here they don’t.
- Performance: The bitonic sort is the dominant part. It uses a standard network with parallel lanes and should scale to large N. The histogram and prefix sum are simple and fast. If needed, we can further tune BLOCK, num_warps, or use a two-pass reduction for the histogram to reduce atomic contention, but this is typically fine for 256 bins.
- This addresses the previous requirement and avoids the earlier runtime error by ensuring Triton kernels are invoked and there’s no torch-based sorting/cumsum in the forward path.
