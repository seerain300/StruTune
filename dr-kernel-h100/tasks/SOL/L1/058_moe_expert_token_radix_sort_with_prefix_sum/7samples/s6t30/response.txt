Root-cause analysis
- The original PyTorch function run does:
  - Flatten topk_idx to a 1D vector of length N = batch_size * seq_len * num_experts_per_tok.
  - Compute sorted_token_indices = flat.argsort(stable=True). This is a global permutation across all elements, not per-token sorting.
  - Compute expert_offsets using counts of each expert and a prefix sum. Critically: the original sets offsets[0] = 0 and then offsets[1:] = cumulative sum of per-expert counts. Returning offsets[1:] is the number of tokens assigned to each expert respectively. We must mirror this exactly.

- Why the previous attempts failed:
  - Attempt 1: Implemented a “global counting sort” but incorrectly assumed the kernel logic would yield a valid stable permutation. The kernel likely didn’t place elements correctly or didn’t handle all edge cases (e.g., tokens with same value). The evaluator reported “INCORRECT_NUMERICAL”, meaning the sorted indices did not match the reference torch.argsort result. Also, we used torch operations for offsets, which is not allowed under Triton-only.
  - Attempt 2: Switched to a per-token counting sort; however, the original requires a global sort across the flattened vector. Per-token sorting changes the overall permutation compared to the reference, hence incorrect. In short: we must sort the entire flattened vector, not per tokens.

Plan to fix correctness and comply with Triton-only
- Implement a Triton kernel that performs a stable global counting sort for integer values in [0, 255]:
  - Initialize output index array out_idx = 0..N-1 (int32).
  - For each class c in 0..255:
    - Scan the flat values to find all positions i where flat[i] == c.
    - For stable order, among equal keys, preserve original order by scanning out_idx from low to high (i.e., smaller out_idx first). We can do this by looping over i = 0..N-1 and conditionally storing out_idx[i] into the output at position offset[c], then offset[c] += 1.
  - This produces out_idx as the permutation that sorts flat ascending with stable tie-breaker by original index. The kernel runs for 256 classes, each scan O(N). Given N up to ~8192 in the benchmarks, this is fine and deterministic.
- Compute expert offsets:
  - Histogram per expert on the original flat values using a Triton kernel: counts[c] = number of occurrences of c. This is O(N * 256) and acceptable.
  - Inclusive prefix sum over counts via a simple Triton kernel that computes offsets[k] = sum of counts[0..k]. We return offsets[1:] as in the original (offsets[0] is set to 0 on the host, but we can generate offsets[1:] directly to avoid extra work).

- Forward must only:
  - Reshape, ensure dtype int32, allocate outputs, and launch Triton kernels. No torch.sort, torch.bincount, or torch.cumsum on device tensors. Minor allocations (like zeros for out_idx) are fine.
