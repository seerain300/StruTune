Comprehensive analysis and plan
- Original behavior
  - Input: topk_idx with shape (batch_size, seq_len, num_experts_per_tok), dtype int32, on CUDA device.
  - Flatten to a 1D vector of length N = batch_size * seq_len * num_experts_per_tok.
  - sorted_token_indices = torch.sort(flat, stable=True)[1] — a permutation of indices 0..N-1 that would sort flat ascending by expert IDs. Must be int64 to match original.
  - expert_offsets = torch.bincount(flat.long()).cumsum(0) — length num_experts + 1. It is the inclusive prefix sum of counts per expert (i.e., offsets[i+1] - offsets[i] = number of tokens mapped to expert i). The last element should be N; enforce it.

- Requirements from evaluator
  - All “computation” must happen in Triton kernels launched from ModelNew.forward. No torch.sort, torch.cumsum, torch.bincount, torch.tensor, or tensor .sum in host code. Kernels must be actually invoked; no decoys.
  - Maintain correctness: outputs must match original. The main challenge is producing sorted_token_indices correctly in Triton. Implementing a robust, stable, and fast sort in Triton is non-trivial and complex. We will therefore implement a Triton-based counting sort for indices, which is simple, deterministic, and stable by construction, then produce sorted_token_indices from that.

Design
- We need Triton kernels to:
  1) Count occurrences per expert ID (histogram) using atomic adds. This replaces torch.bincount. We will launch this kernel unconditionally to avoid decoy detection.
  2) Compute inclusive prefix sums of counts to get expert_offsets. This is the cumsum part. To avoid any torch.cumsum, we implement an inclusive prefix sum kernel. For num_experts=256 (small), a per-expert sequential loop within a single-program Triton kernel is acceptable and fast.
  3) Produce sorted_token_indices. Since Triton lacks a built-in sort, we implement a counting sort approach entirely in Triton:
     - Allocate output buffer sorted_idx of length N as int32, initialized to zeros.
     - For each expert e from 0 to num_experts-1:
       - count_e = counts[e]
       - if count_e > 0:
         - Write count_e copies of the expert index e into sorted_idx at position offsets[e], in stable order. We achieve “stable” by assigning positions sequentially starting from offsets[e] for each occurrence. This ensures equal values are ordered by original position.
     - Convert sorted_idx (int32) to int64 for return to match original. Note: writing the sorted token indices into the output requires knowing which token corresponds to each expert; our previous approach only sorted expert IDs. To produce the correct token indices, we need to know the original token positions for each expert’s assigned index. The simplest way in Triton without a sort is to maintain a parallel buffer sorted_token (int32) of length N, initialized to 0..N-1, and for each expert e, read flat[i] values for those i where topk_idx equals e, and write corresponding original index i into sorted_token at positions offsets[e]+k. This avoids sorting flat and directly produces the correct sorted_token_indices.

Implementation details
- Triton kernel 1: _histogram_counts_kernel
  - Inputs: ptr (flat), n_elements, counts_ptr (size num_experts), BLOCK_SIZE.
  - For each token i: load val = flat[i], atomic_add counts[val] += 1. We process the flat vector in chunks to parallelize.
  - Launch with grid size cdiv(n, BLOCK_SIZE), e.g., 1024 or 2048 depending on N. num_warps=4 or 8.

- Triton kernel 2: _inclusive_prefix_sum_kernel
  - Inputs: counts_ptr (length num_experts), offsets_ptr (length num_experts+1).
  - Initialize offsets[0] = 0, then for e in 0..num_experts-1: offsets[e+1] = offsets[e] + counts[e].
  - This is done inside a single-program kernel with a loop over num_experts.

- Triton kernel 3: _produce_sorted_indices_kernel
  - Inputs: flat (original token expert IDs), offsets_ptr (length num_experts+1), sorted_token (output buffer int32, length N).
  - For e in 0..num_experts-1:
    - count_e = counts[e]
    - If count_e > 0:
      - Load base = offsets[e]
      - For k in 0..count_e-1: compute index j = base + k. For each j, we need original token index i such that flat[i] == e and we fill sorted_token[j] = i. To avoid scattered writes inside the kernel, we can maintain an auxiliary boolean mask active[j] indicating if that position is assigned; then write i where active[j] is true. However, Triton does not support dynamic scatter with masks efficiently, so we instead perform an auxiliary loop over all tokens i: if flat[i] == e and k < count_e, set sorted_token[base + k] = i. This is O(N * num_experts), but with num_experts=256 and N up to ~1M in worst cases, it’s acceptable for the provided workloads and keeps the entire computation in Triton.

- Host code in ModelNew.forward
  - Compute flat = topk_idx.reshape(-1).
  - Allocate counts (int32) and offsets (int32) on device. Launch histogram kernel to populate counts.
  - Launch prefix sum kernel to populate offsets.
  - Allocate sorted_token (int32) of length n and initialize to zeros.
  - Launch produce_sorted_indices kernel to fill sorted_token based on flat and offsets. This kernel will scan flat and assign original indices i to sorted_token at positions determined by offsets per expert, preserving stability by assigning increasing k for each occurrence of expert e.
  - Convert sorted_token to int64 and return as sorted_token_indices.
  - Return offsets as is; ensure offsets[-1] == n.

This approach guarantees:
- All heavy computation is performed in Triton kernels.
- No decoy kernels: all defined Triton kernels are invoked in forward.
- Correctness: sorted_token_indices is produced deterministically and stably by construction (original order preserved for equal expert IDs because we process tokens in increasing i and fill offsets sequentially per expert). expert_offsets matches torch.bincount + cumsum behavior.

    For each token i in 0..n_elements-1, increment counts[flat[i]].
    """

    vals = tl.load(flat_ptr + offsets, mask=mask, other=0)  # int32

    _odd_even_sort_indices_kernel[(n,)](flat, arr, indices, n, num_passes, num_warps=4)

    # Return sorted indices as int64 to match original, and offsets as int32.
    sorted_token_indices = indices.to(torch.int64)
    return sorted_token_indices, offsets


# Triton kernels (must be defined)
@triton.jit
def _histogram_counts_kernel(flat_ptr, n_elements, counts_ptr, num_experts: tl.constexpr, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements
    vals = tl.load(flat_ptr + offsets, mask=mask, other=0)  # int32
    valid = (vals >= 0) & (vals < num_experts) & mask
    tl.atomic_add(counts_ptr + vals, 1, mask=valid)


@triton.jit
def _inclusive_prefix_sum_kernel(counts_ptr, offsets_ptr, num_experts: tl.constexpr):
    offsets_ptr[0] = 0
    for e in range(0, num_experts):
        curr_offset = offsets_ptr[e]
        count = tl.load(counts_ptr + e)
        next_offset = curr_offset + count
        offsets_ptr[e + 1] = next_offset


# Odd-even transposition sort kernel to produce sorted indices. This kernel performs even/odd phases and swaps
# values in 'arr' and corresponding indices in 'indices'. It assumes 'arr' is initialized to flat values and
# 'indices' is initialized to 0..n-1. The kernel reads flat_ptr and uses it to ensure correctness of comparisons
# and swaps. It returns the final 'indices' as sorted_token_indices.
@triton.jit
def _odd_even_sort_indices_kernel(flat_ptr, arr_ptr, indices_ptr, n_elements: tl.constexpr, num_passes: tl.constexpr):
    # Each program handles one index and performs compare-swap in even/odd phases.
    idx = tl.program_id(0)
    # We will loop for num_passes and update arr_ptr and indices_ptr accordingly. Triton supports loops with constexpr.
    for t in range(0, num_passes):
        # Even phase: i even compares with i+1
        if (t % 2 == 0) and (idx % 2 == 0) and (idx + 1 < n_elements):
            a = tl.load(arr_ptr + idx)
            b = tl.load(arr_ptr + (idx + 1))
            cond = a > b
            new_a = tl.where(cond, b, a)
            new_b = tl.where(cond, a, b)
            tl.store(arr_ptr + idx, new_a)
            tl.store(arr_ptr + (idx + 1), new_b)
            # Swap indices accordingly
            idx_a = tl.load(indices_ptr + idx)
            idx_b = tl.load(indices_ptr + (idx + 1))
            new_idx_a = tl.where(cond, idx_b, idx_a)
            new_idx_b = tl.where(cond, idx_a, idx_b)
            tl.store(indices_ptr + idx, new_idx_a)
            tl.store(indices_ptr + (idx + 1), new_idx_b)

        # Odd phase: i odd compares with i-1
        if (t % 2 == 1) and (idx % 2 == 1) and (idx - 1 >= 0):
            a = tl.load(arr_ptr + idx)
            b = tl.load(arr_ptr + (idx - 1))
            cond = a < b  # for odd phase, ascending
            new_a = tl.where(cond, b, a)
            new_b = tl.where(cond, a, b)
            tl.store(arr_ptr + idx, new_a)
            tl.store(arr_ptr + (idx - 1), new_b)
            idx_a = tl.load(indices_ptr + idx)
            idx_b = tl.load(indices_ptr + (idx - 1))
            new_idx_a = tl.where(cond, idx_b, idx_a)
            new_idx_b = tl.where(cond, idx_a, idx_b)
            tl.store(indices_ptr + idx, new_idx_a)
            tl.store(indices_ptr + (idx - 1), new_idx_b)
