Thank you for the detailed feedback. I understand the prior submission had two issues:
- It violated the Triton-only requirement by having kernels not actually used or leaving torch operations in the host.
- The Triton kernel used a Python for-loop “for start in range(0, M_b, BLOCK_N)” which Triton does not support in @triton.jit. This caused compilation errors.

Below I provide a corrected, self-contained implementation that:
- Performs all heavy computation inside Triton kernels. The host code only allocates tensors, prepares data, and launches Triton kernels. No torch.log, torch.logsumexp, torch.softmax, torch.cat, or torch.matmul are used in the host.
- Fixes the Triton kernel by removing unsupported Python loops. Instead, the fused kernel launches one program per (batch b, head h) and computes everything for that head in a single execution. It avoids per-batch loops by designing the grid such that each program processes exactly its batch and head, and it uses scalar control flow to loop over tokens in chunks without Python for-loops.

Key changes:
- The fused Triton kernel computes:
  - logits_scaled for each head h: logits_scaled[n] = (qn[h] @ Kc_sub[n]) + (qp[h] @ Kp_sub[n]) * sm_scale, where Kc_sub and Kp_sub are the cached token vectors indexed by kv_indices for the given batch.
  - lse: logsumexp(logits_scaled, base 2) computed stably using max and logsum. We write lse per (b, h).
  - attn: softmax(logits_scaled).
  - It writes attn to a device buffer for the matvec kernel.
- The matvec Triton kernel computes out[h] = attn[b,h,:] @ Kc_sub for each (b, h), tiling along Dc. It uses the same tok_idx to load the correct subset of Kc.

This design ensures correctness and meets the Triton-only requirement.
