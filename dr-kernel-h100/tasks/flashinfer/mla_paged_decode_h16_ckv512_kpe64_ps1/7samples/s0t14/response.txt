Diagnosis, constraints, and plan

- The original PyTorch run function performs per-batch, per-head attention:
  - It gathers selected cached key vectors based on kv_indptr and kv_indices.
  - For each head:
    - Computes logits per token: dot product of qn[h] with Kc_selected and qn[h] with Kp_selected.
    - Applies scaling, computes logsumexp (base-2), and softmax.
    - Produces output as attention-weighted sum over Kc_selected.

- The previous Triton attempts failed to compile due to:
  - Using Python for-loops or vector constructions within @triton.jit kernels that the evaluator’s Triton JIT rejects.
  - Constructing per-token row vectors via pointer arithmetic and tl.arange in ways that caused compilation errors.

- The evaluation requires:
  - ModelNew.forward must invoke Triton kernels. No torch operations should perform the main computation (e.g., no .exp, .log, .sum, .matmul in the host).
  - Triton kernels must be defined, and at least one must be actually launched from ModelNew.forward.

- To satisfy both correctness and Triton-only requirement, we will:
  - Keep host code to minimal setup and launching Triton kernels; no torch compute.
  - Implement Triton kernels that:
    - Compute per-head logits vector across all tokens (no Python loop, vectorized).
    - Compute lse per head using scalar reductions (tl.max, tl.sum).
    - Compute attention-weighted output per head using per-token loads and reductions, without Python loops.
  - Handle dynamic L_TOKENS by using tl.constexpr in kernel meta (Triton JIT specializes per L_TOKENS). Edge case L_TOKENS == 0 is guarded in host: no kernel launch, output zeros, lse initialized.

Design details:
- Inputs per batch b:
  - q_nope[b] → [16, 512] float32 (after casting), each head h uses qn[h, :] and qp[h, :] = q_pe[b][h, :].
  - Gather Kc_selected = ckv_cache[tok_idx] → [L_tokens, 512], Kp_selected = kpe_cache[tok_idx] → [L_tokens, 64] as float32.
- Triton kernel 1 (_compute_logits_and_lse_kernel):
  - Grid: (num_qo_heads,)
  - Each program handles one head h.
  - Vectorized computation of logits[t] = dot(qn[h], Kc_selected[t]) + dot(qp[h], Kp_selected[t]) for t in [0..L_TOKENS).
  - Compute m = max(logits) and s = sum(exp(logits - m * sm_scale)). Then lse[h] = m + log(s) / log(2).
  - Store lse[h] to output tensor. No Python loop; Triton reductions are fine on small vectors.

- Triton kernel 2 (_compute_attention_output_kernel):
  - Grid: (num_qo_heads,)
  - Each program handles one head h.
  - Load lse[h], compute scaling factor scale = sm_scale - lse[h] * (1 / log(2)).
  - For each t: compute attn[t] = exp(scale - logits[t]) where logits[t] is reloaded (or recomputed cheaply via dot, but reusing saved logits would require storing; for simplicity and Triton support, we recompute per token with vectorized reductions). Then out_vec += attn[t] * Kc_selected[t, :].
  - Store out_vec to output[b, h, :]. No Python loop; use per-token tl.load and reductions.

- Host code:
  - Allocate output [B, 16, 512] float32, lse [B, 16] float32.
  - For each batch b:
    - Compute tok_idx slice and L_tokens. If L_tokens == 0: output zeros, lse initialized to -inf; skip kernel launches for that b.
    - Cast q_nope[b], q_pe[b], Kc_selected, Kp_selected to float32.
    - Launch _compute_logits_and_lse_kernel to fill lse[b, :].
    - Launch _compute_attention_output_kernel to fill output[b, :, :].
  - Return output cast to bfloat16, lse as float32, matching original.

This approach avoids any torch computations in the host and uses Triton kernels for the core work, ensuring compliance with the TRITON-ONLY requirement. While Triton’s loop/vector constraints can be finicky, we avoid problematic Python loops and rely on Triton’s supported reductions and vectorized operations.
