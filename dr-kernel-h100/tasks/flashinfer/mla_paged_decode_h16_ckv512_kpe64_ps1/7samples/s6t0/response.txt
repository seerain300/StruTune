Understanding what the original code does, how it should be generalized, and where Triton can help

1) What the original Model.run computes per batch element b:
- It uses q_nope[b] and q_pe[b] which have shapes:
  - q_nope: (num_qo_heads=16, head_dim_ckv=512) in the provided example
  - q_pe: (num_qo_heads=16, head_dim_kpe=64)
- It gathers tokens for this batch element based on kv_indptr and kv_indices:
  - kv_indptr[b] and kv_indptr[b+1] give the start and end indices of the token sequence for batch b.
  - tok_idx = kv_indices[page_beg:page_end] gives L_tokens = number of tokens for that batch.
- It fetches the corresponding cache chunks:
  - Kc_all = ckv_cache.squeeze(1) with shape (num_pages, 512)
  - Kp_all = kpe_cache.squeeze(1) with shape (num_pages, 64)
  - For these L_tokens, we gather Kc = Kc_all[tok_idx] and Kp = Kp_all[tok_idx], which are (L_tokens, 512) and (L_tokens, 64).
- It computes two dot products and adds them:
  - logits = (qn @ Kc.T) + (qp @ Kp.T)
    - qn: (16, 512) dot Kc.T: (512, L_tokens) -> (16, L_tokens)
    - qp: (16, 64) dot Kp.T: (64, L_tokens) -> (16, L_tokens)
    - Then sum across the two contributions. Here head_dim_ckv=512 and head_dim_kpe=64, but we treat these as generic Hc and Hp.
- It scales logits by sm_scale, applies softmax along the token axis (dim=-1), and then computes:
  - output[b] = softmax(logits_scaled) @ Kc  -> (16, 512)
  - lse[b] = logsumexp(logits_scaled) / log(2) for each of the 16 heads, saved as float32.
- It repeats for all batch elements, accumulates outputs, and returns (output, lse).

Important notes:
- In the provided get_inputs(), batch_size is 1, num_pages is 989669, len_indptr=2, and num_kv_indices varies (8, 108, …). The example setup always selects just one token per batch element (L_tokens = len(kv_indices)), which is highly unusual in practice. I will not hardcode or rely on that. The implementation must handle any L_tokens.
- The asserts in the original code are fixed (num_qo_heads == 16, head_dim_ckv == 512, head_dim_kpe == 64, and special asserts that rely on the provided tiny kv_indices). I will keep behavior identical for the provided example (i.e., we only use the given kv_indices, not some random subset) but will implement the general gather based on kv_indptr and kv_indices so that it handles other configurations too.
- The math.log(2) conversion is done on the LSE. For performance, it’s best to avoid computing lse if not requested. Here, since the harness compares outputs, we will compute it, but we’ll keep the kernel focused on the main workload (output). We can add a simple PyTorch computation for lse (which is cheap relative to the GEMMs), or we can compute it in Triton as well.

Where Triton can optimize:
- The heavy work is:
  - logits = qn @ Kc.T + qp @ Kp.T
  - attn = softmax(logits_scaled, dim=-1)
  - output = attn @ Kc
- Both qn @ Kc.T and attn @ Kc are GEMMs. GEMM is Triton’s sweet spot, especially with block tiling and fp32 accumulation.
- The small qp @ Kp.T and the softmax could also be Triton kernels, but given Hp=64 and typical small L_tokens, PyTorch may be fine. Still, for completeness and generality, we can implement those in Triton as well.
- Since output is (num_qo_heads, head_dim_ckv) per batch element and in the common setup num_qo_heads=16, head_dim_ckv=512, we can structure the Triton kernel grid as (batch_size, num_qo_heads), each program computing the entire output vector for that head (length 512). That gives good parallelism across batches and heads, with tiling over K (the number of tokens L_tokens) and N (head_dim_ckv=512).

Design choices for Triton kernels:
- Kernel 1: gemm_logits_kernel
  - Inputs: qn (M=16, K=L_tokens), Kc (K=L_tokens, N=512), and similarly qp (M=16, K=L_tokens), Kp (K=L_tokens, N=64), plus scaling factors.
  - Outputs: two matrices OutQc (M=16, N=512) and OutQp (M=16, N=512), both float32. Then elementwise add to get logits.
  - This avoids recomputing two matmuls in separate kernels; we compute both in one kernel for each head, which is fine because M is small (16) and we can tile over K. For larger M, more complexity is needed, but our case is small. If desired, we can split into two kernels. However, doing both in one kernel reduces overhead.
- Kernel 2: softmax_1d_kernel (to keep the Triton spirit: we’ll implement a Triton softmax along the last dimension of logits_scaled, i.e., along tokens, per (batch, head). This avoids torch.softmax and runs on GPU. It’s a 1D softmax and is straightforward.)
- Kernel 3: gemv_output_kernel
  - Inputs: attn (M=16, K=L_tokens), Kc (K=L_tokens, N=512).
  - Output: output (M=16, N=512), float32.
  - This is a batched GEMV per head. Triton can handle this with a 2D grid (M tiles, N tiles), reducing along K.
- Data types:
  - The original code converts Kc_all, Kp_all to float32 before computation. We’ll keep q_nope and q_pe in float32 as well, and compute logits/output in float32, then cast output to bfloat16 before returning (to match the original’s output dtype). LSE should be float32 as in the original.
- Strides and indexing:
  - We’ll operate on contiguous tensors. In forward, we ensure q_nope, q_pe, Kc_all, Kp_all are contiguous on device. We will not rely on squeeze(1) from the original function; we will pass in tensors shaped as [num_pages, head_dim], and in the kernels we’ll use the appropriate strides and gather via tok_idx. However, the original function actually uses squeeze(1) on cached tensors. To preserve exact behavior, we will implement that in the PyTorch host code, then feed into kernels. Note: squeeze(1) returns a view; but our tensors will be contiguous, and our kernel pointer math will not rely on that view but on the underlying storage with strides, so it’s fine.

Performance considerations and why this Triton version should be faster or at least competitive:
- We move the matmul-heavy work into Triton kernels. Triton allows us to:
  - Use fp32 accumulation for accuracy.
  - Employ tiling (BLOCK_M, BLOCK_N, BLOCK_K) to handle large N (512) and variable K (L_tokens).
  - Fuse operations minimally; here, the main heavy parts are two GEMMs and a GEMV, plus a 1D softmax. The GEMV is small in M (16), and N is 512, which is a good fit for Triton’s matmul templates.
- Although L_tokens is tiny in the given get_inputs (8, 108, etc.), the harness provides a variety of shapes. The Triton kernels will work for any L_tokens > 0 and any batch/heads. For large L_tokens (e.g., 27545 for batch 64), Triton matmul will be beneficial.
- We avoid any host-side PyTorch matmul in ModelNew.forward; all computations are kernel launches. This satisfies the Triton-only requirement.

Correctness details:
- We must match the original behavior:
  - q_nope, q_pe: input dtype bfloat16, but we convert to float32 for compute. Output is returned as bfloat16.
  - Kc_all, Kp_all: original code converts to float32, we’ll do the same.
  - softmax is along dim=-1 (tokens), scale by sm_scale, then logsumexp divided by ln(2). We compute lse using PyTorch after the Triton softmax, to keep things simple and accurate; if needed, a Triton reduction kernel could be written, but given the relative simplicity, PyTorch lse is fine.

Now, let’s create ModelNew with Triton kernels. We’ll include:
- Triton kernels: gemm_logits_kernel, softmax_1d_kernel, gemv_output_kernel.
- ModelNew.forward which:
  - Ensures device, contiguity, dtype conversion.
  - Computes outputs and lse, returning (output bfloat16 tensor), (lse float32 tensor).

Plan and kernel logic:

1) Triton kernel for computing logits:
   - Signature: gemm_logits_kernel(qn_ptr, Kc_ptr, qp_ptr, Kp_ptr, outQc_ptr, outQp_ptr, L_tokens, head_dim, SM_SCALE, BLOCK_M: constexpr, BLOCK_K: constexpr, BLOCK_N: constexpr)
   - Grid: (1, 1) isn’t enough; we need to tile over M (heads) and N (512). Because M can be up to 16, we can set BLOCK_M=16, so one program handles all heads for a given batch; but better is to set grid=(M, ceil_div(N, BLOCK_N)). Since N=512, we can choose BLOCK_N=128 or 64; we’ll pick 128 for good throughput. K is dynamic (L_tokens), so we loop over K in blocks of BLOCK_K=32.
   - For each m in [0, M), we compute C[m, n:n+BLOCK_N] = sum_k qn[m, k] * Kc[k, n:n+BLOCK_N] + sum_k qp[m, k] * Kp[k, n:n+BLOCK_N].
   - We multiply by SM_SCALE and store in outQc/outQp. We can compute both in the same kernel to avoid double launch, but if we want clarity, we can compute qn@Kc.T into outQc and qp@Kp.T into outQp in separate calls; however, Triton kernel invocation is fine either way.

2) Triton kernel for softmax along last dimension (tokens):
   - Signature: softmax_1d_kernel(logits_ptr, attn_ptr, L_tokens, SM_SCALE, BLOCK: constexpr)
   - Each program handles one head and iterates over tokens in chunks of BLOCK (e.g., 64/128). It computes max, subtracts, exponentiates, sums, normalizes, and writes attn. We can use two-pass approach: first pass compute max, second pass compute sum of exp, third pass write normalized.

3) Triton kernel for GEMV output:
   - Signature: gemv_output_kernel(attn_ptr, Kc_ptr, out_ptr, L_tokens, head_dim, BLOCK_M: constexpr, BLOCK_K: constexpr, BLOCK_N: constexpr)
   - Grid: (M, ceil_div(N, BLOCK_N)). We tile over N (512) and K (L_tokens). For each head m and N tile, we accumulate over K and write output.

Given the complexity, I’ll first implement the essential Triton matmul for logits (qn@Kc.T) and output (attn@Kc). The softmax will be done in Triton too (1D softmax). I’ll ensure everything uses contiguous tensors, proper strides, and device handling. I’ll also add checks for device and dtype conversion.

Code follows. Note: Triton code requires triton and triton.language. I’ll import those and define kernels. The ModelNew.forward will be the entry point. I’ll also provide get_inputs and fused_operator functions to mirror the original.

import math
import torch

try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False
    triton = None
    tl = None


# Triton kernels
if TRITON_AVAILABLE:
    @triton.jit
    def matmul_qn_Kc_T_kernel(
        qn_ptr,  # *float32, shape (M, K) where K=L_tokens
        Kc_ptr,  # *float32, shape (K, N) where N=head_dim_ckv
        out_ptr, # *float32, shape (M, N)
        M: tl.constexpr,      # number of heads (e.g., 16)
        K: tl.constexpr,      # number of tokens (L_tokens)
        N: tl.constexpr,      # head_dim_ckv (e.g., 512)
        stride_qm, stride_qk, # strides for qn: (N=K, K)
        stride_kc_k, stride_kc_n, # strides for Kc: (N=K, N)
        stride_out_m, stride_out_n,  # strides for out: (M, N)
        BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr,
    ):
        # We tile over M and N; M is small, so one program can handle all M.
        # Choose grid=(1, ceil_div(N, BLOCK_N))
        pid_n = tl.program_id(1)
        n_start = pid_n * BLOCK_N

        # Accumulator for the entire M x N output
        # We loop over M in chunks to initialize acc; since M is small, we can vectorize over M too.
        # But simpler: handle one M at a time. We will use BLOCK_M=16 and assume M==16.
        # For generality, we keep loop over M.
        # However, Triton requires compile-time loops; since M is provided as constexpr, we can do:
        for m in range(0, M):
            acc = tl.zeros((BLOCK_N,), dtype=tl.float32)
            # Loop over K in blocks
            for k0 in range(0, K, BLOCK_K):
                k_idx = k0 + tl.arange(0, BLOCK_K)
                # Load qn[m, k_idx]
                qn_block = tl.load(qn_ptr + m * stride_qm + k_idx * stride_qk, mask=k_idx < K, other=0.0)  # shape (BLOCK_K,)
                # Load Kc[k_idx, n_start:n_start+BLOCK_N]
                n_idx = n_start + tl.arange(0, BLOCK_N)
                Kc_block = tl.load(Kc_ptr + k_idx[:, None] * stride_kc_k + n_idx[None, :] * stride_kc_n,
                                   mask=(k_idx[:, None] < K) & (n_idx[None, :] < N),
                                   other=0.0)  # shape (BLOCK_K, BLOCK_N)
                # Accumulate: acc += sum_k qn_block[k] * Kc_block[k, :]
                # qn_block is (BLOCK_K,), Kc_block is (BLOCK_K, BLOCK_N)
                # acc is (BLOCK_N,)
                acc += tl.sum(qn_block[:, None] * Kc_block, axis=0)
            # Store acc to out[m, n_start:n_start+BLOCK_N]
            tl.store(out_ptr + m * stride_out_m + (n_start + tl.arange(0, BLOCK_N)) * stride_out_n,
                     acc, mask=(n_start + tl.arange(0, BLOCK_N)) < N)


    @triton.jit
    def matmul_qp_Kp_T_kernel(
        qp_ptr,  # *float32, shape (M, K) where K=L_tokens
        Kp_ptr,  # *float32, shape (K, N) where N=head_dim_kpe (e.g., 64)
        out_ptr, # *float32, shape (M, N)
        M: tl.constexpr,      # number of heads (e.g., 16)
        K: tl.constexpr,      # number of tokens (L_tokens)
        N: tl.constexpr,      # head_dim_kpe (e.g., 64)
        stride_qp_m, stride_qp_k,
        stride_kp_k, stride_kp_n,
        stride_out_m, stride_out_n,
        BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr,
    ):
        pid_n = tl.program_id(1)
        n_start = pid_n * BLOCK_N

        for m in range(0, M):
            acc = tl.zeros((BLOCK_N,), dtype=tl.float32)
            for k0 in range(0, K, BLOCK_K):
                k_idx = k0 + tl.arange(0, BLOCK_K)
                qp_block = tl.load(qp_ptr + m * stride_qp_m + k_idx * stride_qp_k, mask=k_idx < K, other=0.0)
                n_idx = n_start + tl.arange(0, BLOCK_N)
                Kp_block = tl.load(Kp_ptr + k_idx[:, None] * stride_kp_k + n_idx[None, :] * stride_kp_n,
                                   mask=(k_idx[:, None] < K) & (n_idx[None, :] < N),
                                   other=0.0)
                acc += tl.sum(qp_block[:, None] * Kp_block, axis=0)
            tl.store(out_ptr + m * stride_out_m + (n_start + tl.arange(0, BLOCK_N)) * stride_out_n,
                     acc, mask=(n_start + tl.arange(0, BLOCK_N)) < N)


    @triton.jit
    def softmax_1d_kernel(
        logits_ptr,   # *float32, shape (M, K) where M=num_qo_heads, K=L_tokens
        attn_ptr,     # *float32, shape (M, K)
        K: tl.constexpr,          # number of tokens (L_tokens)
        stride_log_m, stride_log_k,
        stride_attn_m, stride_attn_k,
        SM_SCALE: tl.constexpr,   # scaling factor
        BLOCK: tl.constexpr,      # chunk size along K
    ):
        m = tl.program_id(0)  # each program handles one head
        # Compute max across K
        m_val = -float('inf')
        for k0 in range(0, K, BLOCK):
            k_idx = k0 + tl.arange(0, BLOCK)
            logits_block = tl.load(logits_ptr + m * stride_log_m + k_idx * stride_log_k,
                                   mask=k_idx < K, other=-float('inf'))
            m_val = tl.maximum(m_val, tl.max(logits_block, axis=0))
        # Compute sum of exp(logits_scaled - m_val)
        sum_exp = 0.0
        for k0 in range(0, K, BLOCK):
            k_idx = k0 + tl.arange(0, BLOCK)
            logits_block = tl.load(logits_ptr + m * stride_log_m + k_idx * stride_log_k, mask=k_idx < K, other=-float('inf'))
            vals = logits_block * SM_SCALE - m_val
            # exp(-inf) = 0, safe
            exp_vals = tl.exp(vals)
            sum_exp += tl.sum(exp_vals, axis=0)
        # Write normalized attn
        for k0 in range(0, K, BLOCK):
            k_idx = k0 + tl.arange(0, BLOCK)
            logits_block = tl.load(logits_ptr + m * stride_log_m + k_idx * stride_log_k, mask=k_idx < K, other=-float('inf'))
            vals = logits_block * SM_SCALE - m_val
            attn_block = tl.exp(vals) / sum_exp
            tl.store(attn_ptr + m * stride_attn_m + k_idx * stride_attn_k, attn_block, mask=k_idx < K)


    @triton.jit
    def gemv_output_kernel(
        attn_ptr,    # *float32, shape (M, K)
        Kc_ptr,      # *float32, shape (K, N) where N=head_dim_ckv
        out_ptr,     # *float32, shape (M, N)
        M: tl.constexpr,      # number of heads (e.g., 16)
        K: tl.constexpr,      # number of tokens (L_tokens)
        N: tl.constexpr,      # head_dim_ckv (e.g., 512)
        stride_attn_m, stride_attn_k,
        stride_kc_k, stride_kc_n,
        stride_out_m, stride_out_n,
        BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr,
    ):
        # Each program handles a tile of N (BLOCK_N) for a given m
        pid_n = tl.program_id(1)
        n_start = pid_n * BLOCK_N
        # We'll compute output for all m (M is small, e.g., 16), or iterate if needed.
        for m in range(0, M):
            acc = tl.zeros((BLOCK_N,), dtype=tl.float32)
            for k0 in range(0, K, BLOCK_K):
                k_idx = k0 + tl.arange(0, BLOCK_K)
                # Load attn[m, k_idx]
                attn_block = tl.load(attn_ptr + m * stride_attn_m + k_idx * stride_attn_k, mask=k_idx < K, other=0.0)  # (BLOCK_K,)
                # Load Kc[k_idx, n_start:n_start+BLOCK_N]
                n_idx = n_start + tl.arange(0, BLOCK_N)
                Kc_block = tl.load(Kc_ptr + k_idx[:, None] * stride_kc_k + n_idx[None, :] * stride_kc_n,
                                   mask=(k_idx[:, None] < K) & (n_idx[None, :] < N),
                                   other=0.0)  # (BLOCK_K, BLOCK_N)
                acc += tl.sum(attn_block[:, None] * Kc_block, axis=0)
            tl.store(out_ptr + m * stride_out_m + (n_start + tl.arange(0, BLOCK_N)) * stride_out_n,
                     acc, mask=(n_start + tl.arange(0, BLOCK_N)) < N)
