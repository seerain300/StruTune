Understanding the original PyTorch code and its computation
- Inputs:
  - final_hidden_states: shape (batch_size * seq_len, hidden_size), dtype bfloat16, device CUDA
  - expert_outputs: shape (num_selected_tokens, hidden_size), dtype bfloat16
  - token_indices: shape (num_selected_tokens,), dtype long (int64), values in [0, batch_size * seq_len)
- Operation:
  - The reference run(...) does output.index_add_(dim=0, index=token_indices, source=expert_outputs).
    - That is: for each i in [0, num_selected_tokens), output[token_indices[i]] += expert_outputs[i].
    - In other words, it performs a scatter-add (or atomic add) of the row vector expert_outputs[i] into the output row indexed by token_indices[i].
    - This is a pure elementwise scatter-add with no reduction across indices.
- The get_inputs(...) function:
  - Creates random final_hidden_states (not zeros) so there is a value to potentially “overwrite” or add to, depending on token indices (though with random indices, most rows will be seen once, so addition starts from those random values).
  - Creates random expert_outputs.
  - Creates random token_indices in [0, batch_size*seq_len), meaning some tokens will get multiple expert contributions (duplicate indices).
- Important: Model.forward is just a wrapper that calls run(...). The harness will feed get_inputs’ outputs into ModelNew.forward. So we need to implement a Triton version of run(...), i.e., a Triton kernel that performs the same index_add-like scatter-add into the first dimension (rows), not columns.

Optimization analysis and plan
- The operation is a scatter-add across rows of a 2D tensor. In PyTorch, index_add on dim=0 already launches an efficient GPU kernel. However, the task explicitly requires a Triton implementation.
- Scatter-add can be implemented with a Triton kernel by:
  - Launching one program per source row i (i in [0, num_selected_tokens)).
  - Loading the token index idx = token_indices[i].
  - Loading the row vector v = expert_outputs[i, :] (size hidden_size).
  - Performing an atomic add into output[idx, :] for all hidden_size columns. This will correctly handle duplicates in token_indices (multiple rows contributing to the same output row).
- Memory access pattern considerations:
  - Accessing expert_outputs[i, :] uses contiguous columns if the tensor is row-major contiguous (stride over hidden dimension is 1). That’s typical. We should make expert_outputs contiguous before passing to Triton to ensure coalesced loads.
  - Writing into output[idx, :] will read random rows depending on token_indices. Atomic adds introduce non-coalesced writes, but that’s inherent to scatter operations. PyTorch’s index_add also does random row writes.
- Data type:
  - final_hidden_states and expert_outputs are bfloat16. Triton supports bf16. We should perform the atomic add in bf16 to match PyTorch behavior. Triton’s atomic_add for bf16 is available on recent versions. If not, we would need to upcast to fp32 and downcast, but that changes numerics. We’ll target Triton with bf16 atomic support; if not available, this kernel will fail to compile, but the benchmarking harness typically uses recent Triton builds.
- Strides and generality:
  - The example tensors are contiguous. We can make sure to call .contiguous() on inputs. The kernel can still use strides to be robust if inputs are not contiguous, but making them contiguous simplifies and improves performance.
  - We’ll implement the kernel to handle arbitrary strides, but we’ll ensure inputs are contiguous for best performance.
- Grid and performance:
  - One program per i (num_selected_tokens) is simple and correct. For very large hidden_size, a 2D grid (over rows and column tiles) could improve occupancy, but it complicates per-row index selection. Given the provided workloads, hidden_size is moderate (e.g., 128, 512, 1024, etc.), and num_selected_tokens is at most batch_size*seq_len (here num_experts_per_tok is not provided, but the original code uses axes_and_scalars["num_experts_per_tok"] which is not passed in the provided get_inputs; however, the harness uses the provided get_inputs, and it returns expert_outputs with a specific shape. We can infer num_selected_tokens is len(token_indices) which equals batch_size * seq_len in these setups. So num_selected_tokens can be up to 8192 in one case. Launching one program per row is fine.
  - We can set num_warps based on hidden_size (e.g., 4 or 8) for reasonable performance. The kernel is memory bound and simple.

Correctness and edge cases
- Duplicate indices: Our kernel uses atomic_add, so duplicates are correctly accumulated. PyTorch’s index_add also accumulates duplicates.
- Out-of-bounds indices: In the provided get_inputs, token_indices are in [0, batch_seq_len), so they’re valid. We won’t guard against OOB in the kernel (Triton mask won’t help here).
- Device: Triton requires CUDA. The provided get_inputs creates tensors on the given device, typically CUDA. We’ll assert or assume CUDA in ModelNew.
- No autograd: The original run(...) uses @torch.no_grad(). Our Triton implementation is forward-only; that’s fine.

Implementation details
- Triton kernel signature: add_by_token_index_kernel(output_ptr, expert_ptr, indices_ptr, batch_seq_len, hidden_size, strides for output/inputs). We’ll pass base pointers and strides. Since we’ll make tensors contiguous, strides are simple: output.stride(0) = hidden_size, output.stride(1) = 1, and similarly for expert_outputs.
- Each program:
  - i = program_id(0)
  - idx = tl.load(indices_ptr + i)
  - offs = tl.arange(0, hidden_size)
  - v = tl.load(expert_ptr + i * hidden_size + offs)  # row-major contiguous assumption; ensured by .contiguous()
  - tl.atomic_add(output_ptr + idx * output.stride(0) + offs, v)
- Host code:
  - Ensure device is CUDA, make final_hidden_states, expert_outputs, token_indices contiguous.
  - Allocate output as final_hidden_states.clone() to preserve original semantics (clone is not strictly required for correctness since atomic_add will write to the output, but the original run(...), clones first. To match, we’ll clone.)
  - Launch kernel with grid = (num_selected_tokens,) and num_warps tuned (e.g., 4).
  - Return output.

Potential pitfalls and how we handle them
- Triton bf16 atomic_add support: If your Triton version doesn’t support atomic_add for bf16, the kernel won’t compile. Most recent Triton builds do. If compilation fails, consider upcasting to fp32 before the kernel and downcasting after, but that changes numerics and is not ideal. Given the evaluation environment typically uses recent Triton, we proceed with bf16.
- Hidden size variability: The kernel uses hidden_size as a meta parameter (tl.constexpr), so it can specialize per hidden size. That’s fine for multiple workloads.
- Performance: The kernel performs one atomic add per column per row. For large hidden_size and num_selected_tokens, this is fine. PyTorch’s index_add is highly optimized; our Triton version may be similar or slightly slower depending on hardware, but the requirement is to use Triton.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def add_by_token_index_kernel(
    output_ptr,         # *bf16, (B, H)
    expert_ptr,         # *bf16, (T, H)
    indices_ptr,        # *i32,  (T,)
    batch_seq_len: tl.constexpr,  # int, but used for bounds (we assume indices < B)
    hidden_size: tl.constexpr,    # columns in the second dim
):
    pid = tl.program_id(axis=0)
    # Each program handles one source row i
    # Load the token index for this row
    idx = tl.load(indices_ptr + pid)
    # Compute column offsets
    offs = tl.arange(0, hidden_size)
    # Load the row vector from expert_outputs
    # expert_ptr is row-major: row i starts at i * hidden_size
    v = tl.load(expert_ptr + pid * hidden_size + offs)
    # Atomic add into output row at index 'idx'
    # output is row-major with stride (hidden_size, 1) if contiguous
    tl.atomic_add(output_ptr + idx * hidden_size + offs, v)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized version of:
            output = final_hidden_states.clone()
            output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        We implement the index_add via a Triton kernel using atomic adds.
        """
        # Ensure tensors are on CUDA and contiguous
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA for Triton."
        # Clone to match original run semantics (index_add writes into a separate output)
        output = final_hidden_states.clone()
        # Make inputs contiguous for better performance
        output = output.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        # Triton expects int32 for indices in many kernels; convert if necessary
        # We'll keep original indices as int64, but load and cast inside the kernel. Alternatively, convert here:
        # token_indices_i32 = token_indices.to(torch.int32)
        # Note: kernel loads and uses the provided dtype; Triton will accept int64/long too, but int32 is common.
        # If token_indices is int64, Triton can load it; int32 is preferred for smaller footprint.
        # We'll convert to int32 for efficiency:
        token_indices = token_indices.to(torch.int32)

        B = final_hidden_states.shape[0]  # batch_seq_len
        H = final_hidden_states.shape[1]
        T = token_indices.shape[0]  # number of expert outputs to scatter

        # Choose kernel launch parameters
        # One program per row in expert_outputs
        grid = (T,)
        # num_warps can be tuned; for moderate H, 4 is fine
        num_warps = 4

        # Launch Triton kernel
        add_by_token_index_kernel[grid](
            output,          # output_ptr
            expert_outputs,  # expert_ptr
            token_indices,   # indices_ptr
            B,               # batch_seq_len (bounds)
            H,               # hidden_size (columns), constexpr for specialization
            num_warps=num_warps,
        )

        return output
```

import triton
import triton.language as tl


@triton.jit
def add_by_token_index_kernel(
    output_ptr,         # *bf16, (B, H)
    expert_ptr,         # *bf16, (T, H)
    indices_ptr,        # *i64,  (T,)  (we pass long indices, load as int64)
    hidden_size: tl.constexpr,  # columns in the second dim (compile-time constant per launch)
):
    # One program per source row i
    i = tl.program_id(axis=0)
    # Load token index for this row (int64), then cast to int32 for pointer arithmetic
    idx64 = tl.load(indices_ptr + i)
    idx = idx64.to(tl.int32)
    # Column offsets [0..H)
    offs = tl.arange(0, hidden_size)
    # Load the row vector from expert_outputs (row-major contiguous: i * H + offs)
    v = tl.load(expert_ptr + i * hidden_size + offs)
    # Atomic add into output row at index 'idx': output[idx, offs] += v
