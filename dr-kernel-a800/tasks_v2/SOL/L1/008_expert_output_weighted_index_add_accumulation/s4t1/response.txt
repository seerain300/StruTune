```python
    # Store it into the output at row idx, column h
```
```python
    tl.store(output_ptr + idx * H + h, val)

        # num_warps=1 is fine since each program does a single scalar load/store
        scatter_add_dim0_exact_kernel[grid](
            output,          # output_ptr
            expert_outputs,  # expert_ptr
            token_indices,   # indices_ptr
            H=H,             # hidden size as constexpr for specialization
            num_warps=1,
        )

        return output
```

Why this addresses the issue
- No atomics, no vectorized columns: minimal risk of Triton atomic or dtype behavior discrepancies.
- Operates strictly in bfloat16 throughout, avoiding any unintended upcasting to float32.
- Exact match to PyTorch index_add semantics: duplicates are handled by multiple programs writing the same value to the same location.

Performance note
- This 2D per-element kernel will be slower than an atomic-based implementation because it launches T*H programs. However, correctness is paramount. Once confirmed correct, we can consider performance tuning:
  - Process multiple columns per program with a small loop (BLOCK_H), reducing the number of programs.
  - Revisit atomic-based kernel with careful handling and masking, only if the evaluation environment confirms that bf16 atomic_add behaves deterministically.
