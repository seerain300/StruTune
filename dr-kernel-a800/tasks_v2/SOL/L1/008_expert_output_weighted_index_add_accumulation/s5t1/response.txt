- The original PyTorch code does a scatter-add: output.index_add_(dim=0, index=token_indices, source=expert_outputs). That means, for each i, output[token_indices[i]] += expert_outputs[i, :].
- My earlier Triton implementation had several issues:
  - It used a more complex per-row kernel and incorrect accumulation strategy, which led to not reproducing index_add behavior and, consequently, incorrect numerical outputs.
  - It didn’t clearly zero-initialize the output correctly (index_add starts from an already-initialized tensor in the original code, but if you use atomic adds you still must match the initial values).
  - The integration was convoluted and didn’t match the exact semantics.

Correctness requirement recap
- The original Model.run clones final_hidden_states, then performs index_add along dim=0. The cloned final_hidden_states has random values (not zeros). The Triton version must:
  - Clone final_hidden_states (preserve the initial random values).
  - For each i, add expert_outputs[i] to output[token_indices[i]]. This must handle duplicates correctly (use atomic adds).
- Dtypes: The original code uses torch.bfloat16 for final_hidden_states and expert_outputs. We should keep bf16.

Robust Triton approach
- Launch one Triton program per index i (grid = (n_indices,)).
- Inside each program:
  - Read idx = token_indices[i] and vec = expert_outputs[i, :].
  - Atomic-add vec to output[idx, :].
- This exactly mirrors index_add semantics, including duplicates. It’s simple, correct, and avoids host-side reductions.
- Important: Ensure output is a clone of final_hidden_states before launching the kernel. That matches the original behavior and preserves the initial values. The kernel only performs additions; no subtraction or modification of other rows.

Performance considerations
- Atomic per-element updates can have contention if there are many duplicates, but the get_inputs generator produces random indices in [0, batch_seq_len), so duplicates are rare for these sizes. The operation is bandwidth-bound; random row writes are acceptable.
- This approach is a single kernel and avoids complex two-phase reductions. If you later see heavy duplication, you can consider a two-kernel strategy (first group-reduce per index, then scatter once), but that’s beyond the current requirement.

- Provide a Triton kernel _atomic_scatter_add_kernel:
  - Inputs: out_ptr (final output), idx_ptr (int32 token indices), vec_ptr (bf16 expert outputs), n_indices, n_cols, BLOCK_SIZE constexpr.

import torch

# Triton imports
try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False


# Triton kernel: For each i in [0, n_indices):
#   idx = token_indices[i]
#   vec = expert_outputs[i, :]
#   output[idx, :] += vec  (atomic add to handle duplicates)
@triton.jit
def _atomic_scatter_add_kernel(
    out_ptr,         # *bf16, shape (n_rows, n_cols), where n_rows = batch_size * seq_len
    idx_ptr,         # *i32, shape (n_indices,)
    vec_ptr,         # *bf16, shape (n_indices, n_cols)
    n_indices,       # int32
    n_cols,          # int32
    BLOCK_SIZE: tl.constexpr,
):
    pid = tl.program_id(axis=0)
    if pid >= n_indices:
        return

    # Load target row index for this element
    idx = tl.load(idx_ptr + pid)  # int32

    # Iterate over columns in chunks of BLOCK_SIZE and atomic add
    j = 0
    while j < n_cols:
        cols = j + tl.arange(0, BLOCK_SIZE)
        mask = cols < n_cols
        # Load the vector chunk for this i (bf16)
        vec_chunk = tl.load(vec_ptr + pid * n_cols + cols, mask=mask, other=0.0)
        # Atomic add into the output row at row idx
        out_row_ptr = out_ptr + idx * n_cols + cols
        tl.atomic_add(out_row_ptr, vec_chunk, mask=mask)
        j += BLOCK_SIZE
