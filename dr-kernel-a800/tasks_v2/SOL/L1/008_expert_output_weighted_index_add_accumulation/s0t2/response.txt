感谢反馈。当前状态是所有工作负载都正确，但速度远低于 1（平均 0.0076），说明 Triton 实现比 PyTorch 的 index_add 慢得多。我们需要在保持正确性的同时，显著优化 Triton 内核。

问题分析
- 原始操作是 scatter-add 沿 dim=0：
  - output[token_indices[i]] += expert_outputs[i]
  - output 形状为 (M, H), token_indices 长度 N, expert_outputs 形状 (N, H), M = batch_size * seq_len, H = hidden_size, N = num_selected_tokens.
- PyTorch 的 index_add 很可能是经过高度优化的，使用批量原子或更高效的散列策略，因此我们的 Triton 实现需要更聪明地利用 GPU 并行性才能接近或超越它。

之前版本的缺陷与性能原因
- 我的一个早期 Triton 版本采用了对 H 的简单循环，并在每次迭代中执行 atomic_add，虽然正确但效率低下，因为它对 H 每个特征都进行原子操作，增加了控制开销和原子争用。
- 评审反馈中提到“Ensure your kernel isn’t reloading final_hidden_states in a way that would negate prior atomic adds.” 这表明我们之前可能重建了 output 从而丢失了前一步的原子添加效果。但根据我们的模型，我们是 clone final_hidden_states 作为初始 output，因此不应该丢失先前的原子添加。无论如何，速度远低于 1 是事实，我们需要加强并行和减少原子争用。

优化策略
- 我们要使用真正的 2D tiling over (N, H) with atomics, 但关键是要确保每一步 atomic_add 添加的是 expert_outputs 的内容，而不是 output 本身（即避免 “reloading final_hidden_states” 导致的重复添加）。
- 为了减少 atomic 争用并增加并行性，我们将 grid 设计为 (N, H_blocks)：
  - axis 0: 每个 program 处理一个特定的源行 n (即 expert_outputs 中的一行)。
  - axis 1: 每个 program 处理 H 的一个 block (BLOCK_H)。
  - 这样每个 program 只负责更新某一行的一段 hidden 特征，并且可以并行化到 H 维度上。尽管行索引是重复的（token_indices 可能有重复），但同一 program 只更新一段 H，不会覆盖整行，而且多个 program 可以同时更新不同的 H-blocks，从而分散原子压力并提高并行性。
- 选择 BLOCK_N=1 (即每个 program 处理单个源行) 以保证安全性，并且 BLOCK_H=128 以获得较好的 H 并行度。

核函数设计
- Triton @jit kernel:
  - program_id(0) = n: the row index in expert_outputs and source of update.
  - program_id(1) = h_block: which H-block this program handles.
  - Load idx = token_indices[n] (target row in output).
  - Load h_offsets = h_block * BLOCK_H + arange(BLOCK_H).
  - Load vals = expert_outputs[n, h_offsets] for masked h_offsets < H.
  - Compute dest = idx * H + h_offsets.
  - tl.atomic_add(output_ptr + dest, vals, mask=mask_h) where mask_h is h_offsets < H.
- Forward:
  - Clone final_hidden_states to output.
  - Launch kernel with grid = (N, ceil_div(H, BLOCK_H)).
  - Use num_warps=4, num_stages=2, BLOCK_H=128.

这样做的好处
- 每次 atomic_add 都只添加专家输出的那一部分 hidden 数据到目标行的对应部分，不会重新加载 output 导致重复添加的问题。
- 并行性显著提高：H 维被分成多个块，多个 program 同时工作；N 维也并行化，即使有重复 idx，每个 idx 的不同 H-block 由不同的 program 处理，并发更新不会相互干扰（只要不更新同一 H-block 内的相同位置两次）。
- 减少 per-iteration 控制流开销，提升 GPU 执行效率。

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_dim0_2d_per_row_bf16(
    output_ptr,            # *ptr to (M, H) output tensor [bf16]
    expert_outputs_ptr,    # *ptr to (N, H) expert_outputs tensor [bf16]
    token_indices_ptr,     # *ptr to (N,) token indices [int64 or int32]
    M, H, N,               # sizes: M rows, H hidden dim, N number of updates
    BLOCK_H: tl.constexpr, # hidden block size (e.g., 128)
):
    # 2D grid: axis 0 over N (source rows), axis 1 over H in blocks of BLOCK_H
    pid_n = tl.program_id(axis=0)  # which source row n we update
    pid_h = tl.program_id(axis=1)  # which H-block

    # Bounds check: if pid_n >= N, return (grid should ensure this, but safe)
    # Load the destination row index for this source row
    n = pid_n
    idx = tl.load(token_indices_ptr + n)

    # Compute H offsets for this block
    h_offs = pid_h * BLOCK_H + tl.arange(0, BLOCK_H)
    mask_h = h_offs < H

    # Load corresponding expert_outputs row segment: expert_outputs[n, h_offs]
    vals = tl.load(expert_outputs_ptr + n * H + h_offs, mask=mask_h, other=0).to(tl.bfloat16)

    # Compute destination addresses: idx * H + h_offs
    dest = idx * H + h_offs

    # Atomic add into output
    tl.atomic_add(output_ptr + dest, vals, mask=mask_h)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized scatter-add along dim=0:
        output[token_indices[i]] += expert_outputs[i] for all i
        """
        # Ensure CUDA tensors
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, \
            "Triton kernels require CUDA tensors. Move inputs to CUDA device."
        assert final_hidden_states.dtype == torch.bfloat16, "final_hidden_states must be bfloat16"
        assert expert_outputs.dtype == torch.bfloat16, "expert_outputs must be bfloat16"
        assert token_indices.dtype in (torch.int32, torch.int64), "token_indices must be int32 or int64"

        # Sizes
        M = final_hidden_states.shape[0]
        H = final_hidden_states.shape[1]
        N = expert_outputs.shape[0]
        assert expert_outputs.shape[1] == H, "expert_outputs second dimension must equal hidden_size"
        assert token_indices.shape[0] == N, "token_indices length must equal number of expert outputs"

        # Clone to keep original buffer intact (matching reference semantics)
        output = final_hidden_states.clone()

        # Choose hidden block size; 128 is a good default for many H sizes
        BLOCK_H = 128
        grid = (N, triton.cdiv(H, BLOCK_H))

        # Launch Triton kernel
        scatter_add_dim0_2d_per_row_bf16[grid](
            output, expert_outputs, token_indices,
            M, H, N,
            BLOCK_H=BLOCK_H,
            num_warps=4,   # adequate for per-row H-block processing
            num_stages=2,  # modest pipelining
        )

        return output


def get_inputs(
    axes_and_scalars: dict[str, ...], device: torch.device
) -> dict[str, torch.Tensor]:
    """Returns the input arguments for the reference forward pass. Required method."""
    batch_size, seq_len, hidden_size = (
        axes_and_scalars["batch_size"],
        axes_and_scalars["seq_len"],
        axes_and_scalars["hidden_size"],
    )
    num_experts_per_tok = axes_and_scalars["num_experts_per_tok"]

    batch_seq_len = batch_size * seq_len
    num_selected_tokens = batch_seq_len * num_experts_per_tok  # each token can have multiple experts

    # Initialize accumulation buffer with random values (not zeros) to detect no-op
    final_hidden_states = torch.randn(batch_seq_len, hidden_size, dtype=torch.bfloat16, device=device)

    # Expert outputs (weighted outputs from expert computation)
    expert_outputs = torch.randn(num_selected_tokens, hidden_size, dtype=torch.bfloat16, device=device)

    # Token indices (which token position each expert output belongs to)
    token_indices = torch.randint(
        0, batch_seq_len, (num_selected_tokens,), dtype=torch.long, device=device
    )

    return {
        "final_hidden_states": final_hidden_states,
        "expert_outputs": expert_outputs,
        "token_indices": token_indices,
    }
```

  - This increases parallelism by spreading work across H and avoids the serial loop over H.
- Important correctness nuance:

This avoids potential double-counting or overwriting issues.

5) Why this should be faster
- Compared to per-H loop, this parallelizes across H-blocks, significantly increasing throughput and reducing control overhead.

6) Edge cases and robustness
- token_indices are within [0, M) by construction; we rely on input validity.
- We ensure outputs tensor is bfloat16 and on CUDA; inputs must be moved to CUDA before calling forward.
- The kernel uses masked loads/stores to avoid out-of-bounds access for partial blocks.

說明：
- Triton 核心心平行化 H 维度，每个程序处理专家输出某一行的一个 H 块，并原子添加到目标行的相应位置。这比之前的 per-H 循环更高效，并保持了正确的 scatter-add 行为，包括对重复索引的正确处理。
- ModelNew.forward 仅执行 clone 和 Triton 核的启动，没有使用任何 PyTorch 张量操作进行核心计算，符合 Triton-only 的要求。
- 通过调整 BLOCK_H 和 num_warps，可以在不同隐藏大小和硬件上获得更好的性能。

Triton-optimized, correctness-preserving implementation

- We replaced the PyTorch index_add with a Triton kernel that performs atomic scatter-add along dim=0: for each i, output[token_indices[i]] += expert_outputs[i, :]. The Triton kernel processes the hidden dimension in blocks (BLOCK_H), increasing parallelism and reducing control overhead compared to a per-H loop. This maintains correctness (including handling duplicate indices via atomics) and should improve performance.

Code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_dim0_2d_bf16(
    output_ptr,            # *ptr to (M, H) output tensor [bf16]
    expert_outputs_ptr,    # *ptr to (N, H) expert_outputs tensor [bf16]
    token_indices_ptr,     # *ptr to (N,) token indices [int64 or int32]
    M, H, N,               # sizes: M rows, H hidden dim, N number of updates
    BLOCK_H: tl.constexpr, # hidden block size (e.g., 128 or 256)
):
    # 2D grid: axis 0 over N (source rows), axis 1 over H in blocks of BLOCK_H
    pid_n = tl.program_id(axis=0)  # which source row n we update
    pid_h = tl.program_id(axis=1)  # which H-block

    # Load the destination row index for this source row
    idx = tl.load(token_indices_ptr + pid_n)  # int64/int32

    # Compute H offsets for this block
    h_offs = pid_h * BLOCK_H + tl.arange(0, BLOCK_H)
    mask_h = h_offs < H

    # Load corresponding expert_outputs row segment: expert_outputs[pid_n, h_offs]
    vals = tl.load(expert_outputs_ptr + pid_n * H + h_offs, mask=mask_h, other=0).to(tl.bfloat16)

    # Compute destination addresses: idx * H + h_offs
    dest = idx * H + h_offs

    # Atomic add into output
    tl.atomic_add(output_ptr + dest, vals, mask=mask_h)
```

Explanation and performance rationale
- Correctness: The kernel initializes output as a clone of final_hidden_states, then atomically adds each expert_outputs block to the corresponding output row dictated by token_indices. This exactly mirrors torch.index_add along dim=0, and atomics ensure correctness even when indices are duplicated.
- Performance: The previous implementation iterated over H with a per-element loop and many atomic_add calls, which is slower. The 2D tiling over (N, H-blocks) increases parallelism by processing multiple hidden features concurrently per program. This reduces control overhead and improves throughput. Tunable parameters (BLOCK_H, num_warps) allow adaptation to different hidden sizes and hardware.
