Understanding, thinking, and plan

What the original code does:
- Input shapes:
  - query: [batch_size, num_attention_heads, seq_len, head_dim], dtype bfloat16
  - key: [batch_size, num_key_value_heads, seq_len, head_dim], dtype bfloat16
  - value: [batch_size, num_key_value_heads, seq_len, head_dim], dtype bfloat16
- It applies RMSNorm to both query and key:
  - rms_norm(x, weight, eps) = (weight * x / sqrt(mean(x^2) + eps))
  - Here weight is a per-head parameter (head_dim), eps = 1e-6.
- It constructs “rotary embeddings” cos/sin from inv_freq and position_ids:
  - inv_freq is a vector of length head_dim/2: inv = 1 / (rope_theta^(i/HEAD_DIM)), i = 0,2,4,...,HEAD_DIM-2
  - position_ids shape is [batch_size, seq_len] and is used to build frequency vector for each token t: emb = [pos * inv, pos * inv]
  - cos = emb.cos(), sin = emb.sin()
- It applies a rotation to query and key:
  - rotate_half(x) = concat([-x[..., head_dim/2:], x[..., :head_dim/2]])
  - apply_rope(x, cos, sin) = x * cos + rotate_half(x) * sin
- It updates caches:
  - key_cache[:, :, cache_position] = key_rotated
  - value_cache[:, :, cache_position] = value (no rotation for value)
- Note: cache_len and seq_len are dynamic in the evaluation; cache_position is of length seq_len (not seq_len+cache_len), and key/value caches are sized [batch, num_key_value_heads, max_position_embeddings, head_dim]. The code overwrites slice key_cache[:, :, cache_len:cache_len+seq_len, :] with key_rotated and similarly for value_cache.

Where we can optimize with Triton:
- The bulk computation that can be offloaded to Triton are:
  - RMSNorm: per-row (over head_dim) normalization of query and key. This is a reduction + elementwise operation per token/row in the 3rd dimension (seq_len). Triton can be used to compute sqrt(mean), normalization factor, and multiply by weight. This avoids PyTorch’s generic kernel launch overhead and can be tuned per head_dim/seq_len.
  - Rotary embedding application: For each token/row, we need to produce cos and sin and then compute x * cos + rotate_half(x) * sin. This is a per-row transformation over the head_dim. We can write a Triton kernel that:
    - Computes cos and sin on-the-fly from position and inv_freq, using a block of columns for parallelism.
    - Loads x (query or key), computes rotate_half(x) as a vector operation across the row, then writes y = x * cos + rotate_half(x) * sin.
    - We can precompute cos/sin on GPU using torch (which is fast and avoids trig in Triton), or compute them in Triton; given head_dim=128, precomputing with torch is fine. If we wanted maximum performance, Triton can also compute cos/sin, but trig functions are slightly slower. The evaluation harness focuses on Triton usage, so we will compute cos/sin in Triton as well.
- Update of caches: This is a strided assignment (writing a slice into a larger tensor). While Triton can handle strided stores, the pattern is simple and can be done with torch (it’s just assignment). The heavier part is RMSNorm and the rotation, which we’ll do in Triton.

Constraints and correctness:
- We must keep the exact math of the original code:
  - RMSNorm: x / sqrt(mean(x^2) + eps) multiplied by per-column weight (head_dim length).
  - Rotation uses two halves of the last dimension. Since head_dim=128, that’s 64 per half. Rotation is applied equally to query and key.
  - inv_freq is of length head_dim//2 (64 for head_dim=128). The original code uses inv_freq[0:head_dim//2]. We will follow that exactly.
  - Cache update is an overwrite of a slice at positions [cache_len:cache_len+seq_len]. We must ensure indexing uses seq_len, not seq_len+cache_len.
- We must launch Triton kernels and not perform host-side torch computations in ModelNew.forward (except trivial allocations). All reductions and elementwise math should be done by Triton kernels. RMSNorm and rotation will be implemented as Triton kernels.

Kernel design:
- RMSNorm kernel:
  - Grid: (batch, num_q_heads, seq_len) or (batch, num_kv_heads, seq_len). We need both for query and key. We can write a single kernel and call it twice.
  - Each program handles one row (a token in a head): it iterates over head_dim in blocks (e.g., 128), accumulates sum of squares in fp32, computes r = sqrt(1/(mean + eps)) = 1/sqrt((sum/HEAD_DIM) + eps), then loops again to write normalized output: y[i,j] = weight[j] * x[i,j] * r.
  - We will pass weight as a 1D fp32 vector of length head_dim to the kernel. Input x will be converted to fp32 for accumulation and normalization, then cast back to original dtype for storage. This ensures numerical stability. The original run returns tensors with the original dtype (bfloat16), so we cast back to bfloat16.
- Rotary kernel (apply rotation):
  - Grid: (batch, seq_len) -> total of batch*seq_len programs. Each program handles one token and its head_dim-vector for either query or key (we’ll pass a flag to know which input to write to).
  - Precompute cos and sin for that position using inv_freq: emb = pos * inv_freq[:half_dim]; cos = emb.cos(), sin = emb.sin(). Since we may not have sin in the inputs (the original code computes sin via torch), we will compute cos/sin in Triton too. We can make two kernels, one for cos, one for sin, or use a single kernel to compute both scalars (very cheap). For simplicity and clarity, we compute cos/sin in Triton and then apply rotation in a second Triton kernel.
  - Inside the rotation kernel, we load x (query or key), compute x1 = x[..., :half], x2 = x[..., half:], rotate = [-x2, x1], then y = x * cos + rotate * sin, and store into out tensor for that token/row.
  - We will pass per-token pos via tl.program_id(0) and row via tl.program_id(1). We use strides from the input/out tensors to support general contiguous layout [B, H, T, D].

Performance considerations:
- seq_len varies per workload (from 1 to 4096), head_dim is fixed at 128. RMSNorm and rotation are small per-token computations. Triton will be fine for these sizes, but we can tune BLOCK sizes (128 or 256) and num_warps. Given head_dim=128, BLOCK=128 fits well.
- We keep all math in fp32 in kernels for stability; write back in original dtype (bfloat16). This is standard practice for normalization and elementwise ops.
- Avoid Python loops and torch ops inside forward; only Triton kernels and torch allocations.

Plan:
1. Implement two Triton kernels:

Inputs: pos, inv_freq, Out_ptr, head_dim. Grid: (B, T). This avoids torch trig calls in forward; however, trig in Triton is acceptable and performance is fine since head_dim is small.
2. In ModelNew.forward:
   - Accept the same args as original run. Compute q_norm and k_norm using Triton rmsnorm kernels (two launches: one for query, one for key). Ensure q_norm_weight and k_norm_weight are fp32 (cast once).
   - Compute cos and sin tensors using Triton kernels: shape [batch_size, seq_len], dtype float32 (we will cast to bfloat16 before passing to rotation kernel).

We can do this with a Triton kernel that copies (no math required), but torch.copy_ is fine; however, to satisfy Triton-only, we can use a simple Triton copy kernel.    - Finally, update caches by slicing assignment using torch. Triton can also do this, but this is a simple and correct way.

Edge cases:
- Handle any batch_size, seq_len, cache_len passed. We do not depend on them for computations; cache_position length is seq_len, and we only update slice starting at cache_len for key_cache and value_cache. This matches the original code.
