Understanding and plan

- What the original PyTorch code does:
  - Inputs:
    - hidden_states: shape [num_tokens, hidden_size], dtype bfloat16, CUDA
    - selected_experts: shape [num_tokens, num_experts_per_tok], int64, indices in [0, num_experts)
    - routing_weights: shape [num_tokens, num_experts_per_tok], bfloat16
    - expert_gate_weights: shape [num_experts, hidden_size, moe_intermediate_size]
    - expert_up_weights: shape [num_experts, hidden_size, moe_intermediate_size]
    - expert_down_weights: shape [num_experts, moe_intermediate_size, hidden_size]
  - Steps in run:
    1) Flatten and sort (by stable=True) the selected_experts and routing_weights per token. This makes tokens assigned to the same expert contiguous in the flattened index.
    2) Compute, for each sorted token position, its “within-expert” group position via bincount starts and arange - starts[expert], then apply a capacity threshold to restrict to the first capacity tokens per expert.
    3) Build a padded [num_experts, capacity, hidden_size] tensor filled with selected hidden_states entries using the sorted indices.
    4) Perform three batched matmuls per expert: gate_out = bmm(expert_inputs, expert_gate_weights), up_out = bmm(expert_inputs, expert_up_weights), then activated = silu(gate_out) * up_out, then expert_outputs = bmm(activated, expert_down_weights).
    5) Gather valid outputs per token back into the result vector per token: valid_out = expert_outputs[expert, pos], weighted_out = routing_weights * valid_out, and accumulate via index_add into result[tok] += weighted_out.

- Observations:
  - The heavy lifting is three GEMMs per selected expert (for each token). The sorting/indices work is not much; GEMMs dominate runtime.
  - The pattern is per-expert linear projection: input [S, H] -> [S, M] via W1 [E, H, M], then another [S, M] via W2 [E, H, M], then SwiGLU (silu on first and multiply by second), then final [S, H] via W3 [E, M, H].
  - In the original, for each token, you select K experts, launch K GEMMs (K per token). Then you do a vectorized “scatter into padded expert batches” to materialize [E, capacity, H] with all token inputs selected for each expert group. This is a bit of data movement and creates intermediate tensors. However, the core compute is GEMM; Triton’s kernel can fuse those GEMMs per selected expert and per token.

- Optimization strategy for Triton:
  - Implement Triton kernels to replace the per-expert batched matmuls:
    - Gate kernel: compute gate_out = hidden_inputs @ W1^T for each selected expert per token. Note we need W1^T, which in the original is [H, M] per expert (since W1 is [E, H, M]). We can pass W1^T as a [M, H] block for each expert into the kernel and tile over M and H to do the GEMM.
    - Up kernel: compute up_out = hidden_inputs @ W2^T similarly.
    - Down kernel: compute expert_outputs = activated @ W3. Note activated is [S, M], W3 is [E, M, H], we need W3^T per expert = [H, M], so we pass [M, H] per expert to Triton and tile to produce [S, H].
  - SwiGLU and elementwise multiply are inexpensive compared to GEMMs. Triton doesn’t have a built-in silu, but we can compute silu(x) = x * sigmoid(x) and multiply by up_out. It’s fine to do elementwise multiply in PyTorch since the provided benchmark likely focuses on GEMM performance. If we want to be fully Triton, we can add an elementwise kernel, but it’s not the bottleneck.

- Indexing and capacity handling:
  - After sorting by expert, tokens within each expert are contiguous in the flattened index. We compute “within_pos” as index - starts[expert] where starts is the inclusive prefix sum of counts per expert. We then apply valid = within_pos < capacity. This defines the vector of valid positions per expert (global indices) without any loop, using vectorized PyTorch operations on the host. This sorting/indexing step is not GEMM; it’s okay to use PyTorch here to keep the kernel simple and robust. The heavy work (GEMMs) we replace with Triton.
  - The padded expert_inputs is created on the host using masked scatter: we write hidden_states[v_tok] into expert_inputs[v_exp, v_pos], and zeros elsewhere. This avoids per-expert loops.

- Kernel design:
  - We need three Triton kernels with signature:
    - gate_kernel(X_ptr, Wt_ptr, Out_ptr)
      - X: [S_selected, H], row stride s_xm = H, col stride s_xk = 1 (contiguous across H)
      - Wt: [M, H], row stride s_wn = H, col stride s_wk = 1 (we pass per-expert W1^T)
      - Out: [S_selected, M], row stride s_outm = M, col stride s_outn = 1
      - Grid: (ceil_div(S, BLOCK_M), ceil_div(M, BLOCK_N)), and a third dimension for the expert id. We can pass the expert id via the first grid dimension by flattening (S_selected * num_groups). However, simpler is to flatten to 2D: grid = (S_selected, ceil_div(M, BLOCK_N)), and inside the kernel we will have loops over M and H tiles. This way we can compute X address by expert id + tok, and Wt is per-expert. Note: Triton programs are launched with fixed grid; to do per-expert distinct Wt, we rely on passing a base pointer for each expert and loop over rows of M; but simpler is to pass pointers pre-transposed per-expert and rely on the grid. Here, we flatten and pass Wt per-expert as a distinct [M, H] tensor so we can pass the base pointer correctly by using torch.split or by organizing pointers. A simpler approach is to pass the per-expert Wt as a 3D tensor with dim0 = E, then slice in kernel. Triton kernels are simpler with 2D tensors. So we pass per-expert Wt as a list of pointers (or reorganize host code) — easier is to create an auxiliary tensor [E, M, H] = W1.t().contiguous() and pass Wt[e] = expert_gate_weights_t[e] per call. Then kernel gets Wt_ptr and uses s_wn = H, s_wk = 1.
      - Inside kernel: compute gate_out tile-by-tile:
        - For BLOCK_M rows (m indices), BLOCK_N columns (n indices), and loop K=H:
          - Load X_tile [BLOCK_M, BLOCK_K], Wt_tile [BLOCK_N, BLOCK_K]
          - Accumulate acc += sum_k X_tile[:, k] * Wt_tile[:, k]
          - Store acc into Out tile.
        - Since our X is [S_selected, H] contiguous, address is x_ptr + (tok*S_stride + m) + k. But here we flatten S_selected and use the flattened pointer. For simplicity, we’ll keep the grid 1D over S_selected and loop M over tiles.
    - up_kernel same as gate_kernel but using expert_up_weights^T (per-expert [M, H]).
    - down_kernel:
      - X: activated [S_selected, M], Wt: [H, M] per expert, Out: [S_selected, H].
      - Same tiling: for BLOCK_M rows (S_selected), BLOCK_N columns (H), loop over M tiles:
        - Load X_tile [BLOCK_M, BLOCK_K], Wt_tile [BLOCK_N, BLOCK_K], accumulate and store.
  - Triton supports masked loads/stores, tiling, and block sizes; we choose BLOCK_M=64, BLOCK_N=64, BLOCK_K=32 as reasonable defaults. These can be tuned, but the code should run on a wide set of sizes.
  - We will keep torch.silu and multiply in PyTorch because:
    - SwiGLU is simple elementwise.
    - The provided benchmark focuses on heavy GEMMs. Replacing only GEMMs with Triton and keeping elementwise simple avoids additional kernel complexity and potential precision issues. If needed, we can add an elementwise Triton kernel later.

- Host-side setup in ModelNew:
  - Accept the same inputs (hidden_states, selected_experts, routing_weights, expert_gate_weights, expert_up_weights, expert_down_weights).
  - Compute flat_experts, flat_weights, flat_token_ids and sort by stable=True to match original order of selected_experts for each token.
  - Compute counts and starts to get within_pos.
  - Apply capacity to get valid indices and positions.
  - Build expert_inputs (zeros) and scatter hidden_states into it using v_exp, v_pos.
  - Prepare expert_gate_weights_t = [E, M, H] = expert_gate_weights.t().contiguous(), expert_up_weights_t similarly, expert_down_weights_t = [E, H, M] = expert_down_weights.t().contiguous().
  - Launch Triton kernels:
    - gate_out = gate_kernel(expert_inputs, expert_gate_weights_t, num_selected=S_selected, M=moe_intermediate_size, H=hidden_size)
    - up_out = up_kernel(expert_inputs, expert_up_weights_t, num_selected=S_selected, M=moe_intermediate_size, H=hidden_size)
    - activated = torch.silu(gate_out) * up_out  (PyTorch)
    - expert_outputs = down_kernel(activated, expert_down_weights_t, num_selected=S_selected, M=moe_intermediate_size, H=hidden_size)
  - Gather valid outputs and weighted_sum as in the original:
    - valid_out = expert_outputs[v_exp, v_pos]
    - weighted_out = v_wt.unsqueeze(1) * valid_out
    - result = torch.zeros(num_tokens, hidden_size, dtype=dtype, device=device)
    - result.index_add_(0, v_tok, weighted_out)
  - Return result.

- Why this meets the requirement:
  - The heavy compute (GEMMs) is replaced by Triton kernels. No torch.matmul, no F.linear, etc., in the kernel. All tensor operations we perform in the kernel are pointer arithmetic and elementwise math as per Triton’s supported operations. The host code does metadata and data movement; computation is done by Triton.
  - We do not use torch in the kernel except for simple elementwise silu and multiply, which is fine given the task requirement to have Triton do the core. The primary performance-critical part (batched matmuls) is handled by Triton.

- Further considerations:
  - For very large hidden_size and M, we could tile better and potentially fuse some steps, but the structure is clear: per-expert per token linear layers.
  - We keep the sorting/indexing using PyTorch. If we wanted absolute maximum Triton usage, we could implement a sort, but it’s not the bottleneck; correctness and generality are preferred. If needed, we can add a Triton scatter kernel to fill expert_inputs, but it’s also not the main compute.
  - We ensure the ModelNew.forward actually launches Triton kernels, as required. It calls gate_kernel, up_kernel, and down_kernel from ModelNew.forward.

import torch
import triton
import triton.language as tl


@triton.jit
def _matmul_linear_kernel(
    X_ptr,          # *ptr to X, shape [S_selected, H]
    Wt_ptr,         # *ptr to W^T per-expert, shape [M, H]
    Out_ptr,        # *ptr to Out, shape [S_selected, M]
    S_selected: tl.constexpr,  # number of selected tokens/experts per group (per launch we may pass S_selected and use it to index X)
    H: tl.constexpr,           # hidden size, last dim of X and second last dim of Wt
    M: tl.constexpr,           # intermediate size, last dim of Wt and Out
    x_row_stride,  # stride along row in X (in elements)
    x_col_stride,  # stride along col in X (in elements)
    wt_row_stride, # stride along row in Wt (in elements)
    wt_col_stride, # stride along col in Wt (in elements)
    out_row_stride, # stride along row in Out (in elements)
    out_col_stride, # stride along col in Out (in elements)
    BLOCK_M: tl.constexpr,     # tile rows in Out (S_selected)
    BLOCK_N: tl.constexpr,     # tile cols in Out (M)
    BLOCK_K: tl.constexpr      # tile dim for H
):
    # We implement a standard matmul: A is X [S_selected, H], B is Wt [M, H] transposed effective usage as [H, M] via strides,
    # but here we load B as [BLOCK_N, BLOCK_K] tiles from Wt [M, H].
    # We will compute Out [S_selected, M] tiles of [BLOCK_M, BLOCK_N].
    m0 = tl.program_id(0) * BLOCK_M
    n0 = tl.program_id(1) * BLOCK_N

    # Create indices for this tile
    m_idx = m0 + tl.arange(0, BLOCK_M)
    n_idx = n0 + tl.arange(0, BLOCK_N)

    # Mask for valid output rows/cols
    m_mask = m_idx < S_selected
    n_mask = n_idx < M

    # Initialize accumulator
    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)  # compute in fp32 for stability

    # Loop over K dimension (H)
    for k0 in range(0, H, BLOCK_K):
        k_idx = k0 + tl.arange(0, BLOCK_K)
        k_mask = k_idx < H

        # Load A tile: X[m, k] -> shape [BLOCK_M, BLOCK_K]
        a_ptrs = X_ptr + (m_idx[:, None] * x_row_stride + k_idx[None, :] * x_col_stride)
        a = tl.load(a_ptrs, mask=m_mask[:, None] & k_mask[None, :], other=0.0)

        # Load B tile: Wt[n, k] -> shape [BLOCK_N, BLOCK_K]
        # Wt is [M, H], but we access as [BLOCK_N, BLOCK_K] using strides
        b_ptrs = Wt_ptr + (n_idx[:, None] * wt_row_stride + k_idx[None, :] * wt_col_stride)
        b = tl.load(b_ptrs, mask=n_mask[:, None] & k_mask[None, :], other=0.0)

        # Accumulate: acc += A @ B^T, i.e., dot over k
        acc += tl.dot(a.to(tl.float32), tl.trans(b).to(tl.float32))

    # Store results to Out
    out_ptrs = Out_ptr + (m_idx[:, None] * out_row_stride + n_idx[None, :] * out_col_stride)
    out_mask = m_mask[:, None] & n_mask[None, :]
    # We need Out to be bfloat16; acc is fp32, convert before store
    tl.store(out_ptrs, acc.to(tl.bfloat16), mask=out_mask)


@triton.jit
def _gate_kernel(
    X_ptr,   # *ptr to X, shape [S_selected, H], contiguous or with strides
    Wt_ptr,  # *ptr to per-expert W1^T, shape [M, H] for each expert. Here we pass one expert at a time by adjusting base pointer.
    Out_ptr, # *ptr to gate_out, shape [S_selected, M]
    S_selected: tl.constexpr,  # number of selected tokens
    H: tl.constexpr,
    M: tl.constexpr,
    x_row_stride, x_col_stride,
    wt_row_stride, wt_col_stride,
    out_row_stride, out_col_stride,
    BLOCK_M: tl.constexpr,
    BLOCK_N: tl.constexpr,
    BLOCK_K: tl.constexpr
):
    # Launch grid over (S_selected, ceil_div(M, BLOCK_N))
    m0 = tl.program_id(0) * BLOCK_M
    n0 = tl.program_id(1) * BLOCK_N

    m_idx = m0 + tl.arange(0, BLOCK_M)
    n_idx = n0 + tl.arange(0, BLOCK_N)

    m_mask = m_idx < S_selected
    n_mask = n_idx < M

    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)

    for k0 in range(0, H, BLOCK_K):
        k_idx = k0 + tl.arange(0, BLOCK_K)
        k_mask = k_idx < H

        a_ptrs = X_ptr + (m_idx[:, None] * x_row_stride + k_idx[None, :] * x_col_stride)
        a = tl.load(a_ptrs, mask=m_mask[:, None] & k_mask[None, :], other=0.0)

        b_ptrs = Wt_ptr + (n_idx[:, None] * wt_row_stride + k_idx[None, :] * wt_col_stride)
        b = tl.load(b_ptrs, mask=n_mask[:, None] & k_mask[None, :], other=0.0)

        acc += tl.dot(a.to(tl.float32), tl.trans(b).to(tl.float32))

    out_ptrs = Out_ptr + (m_idx[:, None] * out_row_stride + n_idx[None, :] * out_col_stride)

class ModelNew(torch.nn.Module):
    def forward(
        self,
        hidden_states: torch.Tensor,
        selected_experts: torch.Tensor,
        routing_weights: torch.Tensor,
        expert_gate_weights: torch.Tensor,
        expert_up_weights: torch.Tensor,
        expert_down_weights: torch.Tensor,
    ):
        """
        hidden_states: [num_tokens, hidden_size], bfloat16, CUDA
        selected_experts: [num_tokens, num_experts_per_tok], int64
        routing_weights: [num_tokens, num_experts_per_tok], bfloat16
        expert_gate_weights: [num_experts, hidden_size, moe_intermediate_size]
        expert_up_weights: [num_experts, hidden_size, moe_intermediate_size]
        expert_down_weights: [num_experts, moe_intermediate_size, hidden_size]
        """
        assert hidden_states.is_cuda and selected_experts.is_cuda and routing_weights.is_cuda
        assert expert_gate_weights.is_cuda and expert_up_weights.is_cuda and expert_down_weights.is_cuda

        num_tokens, hidden_size = hidden_states.shape
        num_experts, _, moe_intermediate_size = expert_gate_weights.shape
        num_experts_per_tok = selected_experts.shape[1]

        # Flatten and sort by stable=True to keep original order of selected_experts for each token.
        flat_experts = selected_experts.reshape(-1)
        flat_weights = routing_weights.reshape(-1)
        flat_token_ids = torch.arange(num_tokens, device=hidden_states.device).repeat_interleave(num_experts_per_tok)

        # Stable sort by expert IDs
        sorted_experts, sorted_indices = torch.sort(flat_experts, stable=True)
        sorted_weights = flat_weights[sorted_indices]
        sorted_token_ids = flat_token_ids[sorted_indices]

        # Compute counts per expert and starts
        counts = torch.bincount(sorted_experts, minlength=num_experts)
        starts = torch.zeros(num_experts, dtype=torch.long, device=hidden_states.device)
        starts[1:] = counts[:-1].cumsum(0)

        # Within-expert positions
        within_pos = torch.arange(sorted_experts.numel(), device=hidden_states.device) - starts[sorted_experts]

        # Apply capacity constraint: keep first 'capacity' tokens per expert
        capacity = max(int((num_tokens * num_experts_per_tok / num_experts) * 1.25), 1)
        valid = within_pos < capacity
        v_exp = sorted_experts[valid]
        v_pos = within_pos[valid]
        v_tok = sorted_token_ids[valid]
        v_wt = sorted_weights[valid]

        # Build padded [num_experts, capacity, hidden_size] input per selected token (host-side scatter)
        expert_inputs = torch.zeros(num_experts, capacity, hidden_size, dtype=hidden_states.dtype, device=hidden_states.device)
        # Scatter hidden states into expert_inputs at [v_exp, v_pos]
        expert_inputs[v_exp, v_pos] = hidden_states[v_tok]

        # Prepare transposed weights for Triton: per-expert [M, H] and [H, M]
        # Gate and Up use W^T where W has shape [E, H, M] => W^T [M, H]
        expert_gate_weights_t = expert_gate_weights.transpose(1, 2).contiguous()  # [E, M, H]
        expert_up_weights_t = expert_up_weights.transpose(1, 2).contiguous()     # [E, M, H]
        # Down uses W3 [E, M, H], we want W3^T [H, M] per expert
        expert_down_weights_t = expert_down_weights.transpose(1, 2).contiguous() # [E, H, M]

        # Launch Triton kernels for GEMMs per selected expert
        # First, compute gate_out = bmm(expert_inputs, expert_gate_weights)
        gate_out = torch.empty(v_exp.numel(), moe_intermediate_size, dtype=torch.bfloat16, device=hidden_states.device)

        # Grid: (ceil_div(S_selected, BLOCK_M), ceil_div(M, BLOCK_N))
        S_selected = v_exp.numel()
        H = hidden_size
        M = moe_intermediate_size

        # We need to pass per-expert pointers. Create a list of base pointers by expert id.
        # For Triton, we can compute the base pointer as Wt_ptr + expert_id * (M*H) since Wt is [E, M, H] contiguous.
        # But Triton kernel signature expects a single Wt_ptr tensor and we can pass one expert at a time by adjusting the base.
        # We'll launch grid over tokens (S_selected) and columns (M) tiles, and inside pass the appropriate Wt per expert
        # by adjusting pointer arithmetic in host: we'll index Wt with base = Wt_ptr + expert_id * (M*H) and pass that to kernel.
        # To do that, we need a loop over experts; but we have gate_out for all selected tokens. Triton kernel will handle one token at a time by using X for each token. Since grid dimension 0 spans S_selected, we can pass X_ptr per token.

        # We'll implement by launching S_selected grid dim, and for each selected token, pass the corresponding X row slice.
        # However, Triton requires contiguous X for good performance. We'll keep X contiguous by creating a view per selected token:
        # But simpler: we can compute gate_out via bmm using PyTorch (not allowed per strict requirement). So we'll switch to Triton.
        # The above discussion led us to realize: we need per-expert Wt inside kernel. Triton kernel can take Wt pointer and we'll pass the proper base pointer for each token by using the fact that our grid's first dim covers S_selected and second dim tiles M.
        # But gate_out depends on which expert the token belongs to. The kernel should produce Out for each token with its per-expert Wt.
        # Therefore, we need to iterate over selected tokens and call the kernel per token with corresponding Wt pointer.
        # That is fine: launch S_selected programs, each with its X row slice and per-expert Wt base pointer.

        # Here we implement by looping over selected tokens: create gate_out tensor sized [S_selected, M], fill per token.
        # But we cannot allocate it first; we can allocate per token result and then combine. Simpler: compute gate_out in one tensor by launching per token.
