Understanding and goals

- The original PyTorch model performs a per-batch sequence attention:
  - Input q, k, v are slices per batch segment given by qo_indptr and kv_indptr.
  - Grouped-Query Attention (GQA) mapping: num_qo_heads = 32, num_kv_heads = 8, so gqa_ratio = 4. K and V are repeated along the head dimension for Q’s number of heads.
  - Softmax attention: logits = Q @ K^T scaled by sm_scale. Then apply a causal mask: for each query position i, you can attend to key positions j in [0, min(num_kv_tokens, i + 1 + (num_kv_tokens - num_q_tokens))).
  - Output is a [total_q, num_qo_heads, head_dim] tensor (bfloat16), and lse is a [total_q, num_qo_heads] tensor of logsumexp per query head (float32), computed in “base-2” form as logsumexp / ln(2). Note: this “base-2” is unusual; we will preserve it.

Optimization strategy with Triton

- We should avoid per-element PyTorch ops in the hot path. The main cost in the original code is:
  - Building logits with einsum, masking, softmax, and matmul-equivalent einsum for output.
  - Everything is done per batch segment. We can process one batch segment per Triton program to minimize host-side overhead.

- Triton design:
  - Write one Triton kernel per batch segment (grid size = len_indptr - 1). Each program handles one batch b.
  - Within a program:
    - Extract q_batch, k_batch, v_batch using qo_indptr[b] and kv_indptr[b].
    - Compute Q @ K^T to get logits shape [num_q_tokens, num_qo_heads, num_kv_tokens]. Since num_qo_heads = 32 and num_kv_heads = 8, we need to expand K and V to 32 heads: k_expanded = k.repeat_interleave(4, dim=1), v_expanded = v.repeat_interleave(4, dim=1). This is a simple data movement and can be done on device with torch operations before the kernel (it’s not the main bottleneck).
    - Apply causal mask. We can fuse this mask into logits as -inf when forbidden. In Triton, we will build masks with 2D ranges for [Q, K] and apply via tl.load/tl.store or by setting the logits tensor to -inf. To keep kernel simple, we’ll write the logits and then set masked positions to -inf after the kernel; or include mask logic. Given the small sizes, computing logits and then masking is fine.
    - Compute lse per query token and per head via logsumexp of logits (dim=K), then divide by ln(2). We can do this reduction inside the kernel or on host. For simplicity and performance, we’ll perform logsumexp in Triton, and compute the final division on host (cheap).
    - Compute softmax along K dimension: softmax = exp(logits) / sum_exp, where sum_exp = logsumexp(logits, dim=-1). Note: softmax in Triton is straightforward; we’ll compute exp(logits) and divide by sum_exp. Using masked logits (-inf) ensures non-attendance contributes zero to the sum. We’ll then compute output: einsum equivalent is output = softmax @ v_expanded (matmul along K dimension). In Triton, we’ll implement this as a reduction over K for each (q, h).
  - Memory layout: We will store output as a contiguous [num_q_tokens, num_qo_heads, head_dim] and write into the correct region of the output tensor using offsets. lse is a 2D tensor [num_q_tokens, num_qo_heads]; we’ll update using slices.

- Numerical considerations:
  - Compute in float32 for attention operations (Q/K/V cast to float32 in host). Triton will do float32 math inside the kernel. Output will be written as bfloat16, matching the original.
  - logsumexp: We can compute row-wise max over logits for numerical stability, then sum exp(logits - max), then lse = max + log(sum) - ln(2). This matches the original’s “base-2” LSE as lse = logsumexp(logits)/ln(2). We’ll pass ln(2) from host.
  - Causal mask: For each query position i, the valid key range is j in [0, min(num_kv_tokens, i + 1 + delta)) with delta = num_kv_tokens - num_q_tokens. We will compute this in the Triton program and set logits[i, :, j] = -inf when j >= upper_limit.

- Performance considerations:
  - The kernel per segment is modest: num_q_tokens up to tens of thousands, num_kv_tokens up to tens of thousands, heads up to 32, head_dim 128. Triton’s vectorized loads/stores along head_dim and reduction along K should be efficient. We will keep everything contiguous and use block-wise loops for K reduction.
  - Avoid Python loops per token; instead, use Triton programs with vectorized operations over blocks. For small dims, straightforward 2D loops (over K in chunks) are acceptable and keep the kernel simple. For larger dims, we can consider more advanced blocking and shared-memory-like patterns, but here the shapes are moderate and this approach is fine.
  - The original code does einsum ‘qhd,khd->qhk’ and then a second einsum ‘qhk,khd->qhd’. In Triton, we’ll compute logits directly (Q @ K^T), mask, softmax, then output via reduction. This avoids creating intermediate tensors on PyTorch and keeps all attention math inside the kernel.

   - Inputs: pointers to q_batch, k_expanded, v_expanded, and output logits buffer, sizes num_q_tokens, num_kv_tokens, num_qo_heads, head_dim, and sm_scale, ln2, delta, causal constants.
   - Steps:
     - Compute logits[q, h, k] = sum_d Q[q, h, d] * K[k, h, d] for all q,h,k.

        # Launch Triton kernel per batch segment
        n_batches = qo_indptr.shape[0] - 1

        # For simplicity, we call a single kernel that handles one segment. Since Triton expects a grid, we implement a loop in Python over segments.
        for b in range(n_batches):

            v_expanded_batch = v_expanded[kv_start:kv_end]

            q_stride_h = q_batch.stride(1)
            q_stride_d = q_batch.stride(2)

            k_stride_d = k_expanded_batch.stride(2)

            out_stride_h = output_seg.stride(1)
            out_stride_d = output_seg.stride(2)

            lse_stride_q = lse_seg.stride(0)
            lse_stride_h = lse_seg.stride(1)

                sm_scale, ln2, num_kv_tokens - num_q_tokens,  # delta
                BLOCK_K=64, BLOCK_D=16
            )

            # Copy segment results into global output/lse
            output[q_start:q_end] = output_seg
            lse[q_start:q_end] = lse_seg

        return output, lse

Notes on the Triton kernel and implementation

- The above Triton kernel is designed to handle one batch segment per program. It computes the logsumexp per (query token, head) across K with causal masking, then stores lse. For output, it recomputes softmax per (query token, head) and reduces over K via V to produce the final output. This avoids materializing the full [Q, H, K] logits tensor, which would be heavy in Triton.

- Limitations and performance:
  - The output computation path recomputes outer products multiple times. This is acceptable to demonstrate Triton usage and keep the kernel self-contained, but in production you should implement a proper matmul kernel for the Q @ K^T part and a reduction for output, or use Triton’s block matmul templates. The current implementation is primarily to meet the “Triton-only” requirement and to provide a structure. In many benchmarks, the dominant cost is the Q @ K^T and the reduction, so a dedicated Triton matmul kernel plus a Triton reduction would be faster and more standard.

- Correctness:
  - The kernel implements the same causal masking as the original: for each query position q, only key positions k < min(num_kv_tokens, q + 1 + delta) are allowed. The “base-2” logsumexp is preserved by dividing lse by ln(2).
  - All computation is done in float32 inside the kernel; output is bfloat16, matching the original.
