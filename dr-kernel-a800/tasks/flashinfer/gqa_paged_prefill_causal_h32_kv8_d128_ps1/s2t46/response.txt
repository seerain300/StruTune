Final analysis and plan

- The original PyTorch code performs a per-segment, per-query, per-head attention using Grouped Query Attention (GQA). With qo_heads=32 and kv_heads=8, each query head maps to a unique KV head via h // 4. It computes:
  - logits = q_vec @ k_rows.T for a vector q_vec and a slice of k_cache rows selected by kv_indices
  - logits_scaled = logits * sm_scale
  - lse_base2 = logsumexp(logits_scaled) / ln(2)
  - attn = softmax(logits_scaled)
  - out_vec = attn @ v_rows
  - Writes out_vec to output[global_q_idx, h] (bf16) and lse_base2 to lse[global_q_idx, h] (fp32)

- The previous Triton attempt failed due to:
  - Passing an unrecognized constexpr (BLOCK_K) or invalid dynamic 2D Triton tensor construction (expand errors).
  - Attempted decoy kernels that weren’t actually used by forward.
  - Using torch operations for lse and attention, which violates the Triton-only requirement.

- To fix:
  - Implement and launch Triton kernels that perform the core computation, not just atomics.
  - Avoid constructing 2D Triton tensors from runtime indices. Instead, iterate over K (max_kv_idx) in the kernel and load vectors row-by-row, compute dot products, and accumulate the output vector. This is doable because each program instance is uniquely mapped to (b, q_idx, h), and K is small (<=128 here).
  - Compute lse in Triton: loop over K to find max, accumulate sum of exp(logits_scaled - max), and compute logsumexp in base-2. Also compute softmax and multiply by v_row, accumulating the output vector.
  - Do not use any torch.matmul, .max, .matmul, .max, torch.logsumexp, torch.softmax in forward. Only Triton kernels should do the math.
  - Ensure we pass only literal constexpr values in kernel signatures. No dynamic constexpr like BLOCK_K. Use tl.constexpr for H, D, and MAX_K (set to 128), which is the head_dim. Mask out elements beyond max_kv_idx.

- Performance notes:
  - With 10^5 programs across workloads (varying total_q, len_indptr, num_segments), this approach may be slower than PyTorch for small K, but it satisfies correctness and the Triton requirement. If further speed is needed, we could later batch multiple q_idx per program and reuse k_rows in shared memory, but this version prioritizes correctness and compliance.

# Kernel B: For each (b, q_idx, h), compute output vector:
#   - q_vec = q_ptr[global_q_idx, h, :]
#   - k_rows = k_ptr[kv_indices_seg, kv_head], v_rows similarly
#   - logits_scaled = q_vec @ k_rows.T
#   - attn = softmax(logits_scaled)
#   - out_vec = sum_k (attn[k] * v_rows[k, :])
#   - store out_vec to output_ptr[global_q_idx, h, :] as bfloat16
@triton.jit
def compute_out_single(
    q_ptr,           # float32* [T, H, D]
    k_ptr,           # float32* [MAX_K, D] (gathered k_rows for this segment)
    v_ptr,           # float32* [MAX_K, D] (gathered v_rows for this segment)
    output_ptr,      # bfloat16* [T, H, D]
    global_q_idx,    # int32
    sm_scale,        # float32
    H: tl.constexpr,       # 32
    D: tl.constexpr,       # 128
    MAX_K: tl.constexpr,   # 128
):

    # Compute logits_scaled, same as Kernel A

    for i in range(MAX_K):
        k_row = tl.load(k_ptr + i * D + tl.arange(0, D), mask=tl.arange(0, D) < D, other=0.0)  # [D]
        prod = q_vec * k_row
        logits_scaled[i] = tl.sum(prod, axis=0)
    logits_scaled = logits_scaled * sm_scale

    # Softmax in base of e (for attn), we need denominator

    sum_exp = 0.0
    for i in range(MAX_K):

    # Compute output vector: out_vec = sum_k (exp(logits_scaled[k] - m) * v_rows[k, :])

    for i in range(MAX_K):

        v_row = tl.load(v_ptr + i * D + tl.arange(0, D), mask=tl.arange(0, D) < D, other=0.0)  # [D]
        out_vec += attn_i * v_row

    # Store as bfloat16
    out_base = global_q_idx * H * D
    out_offset = out_base + h * D
    tl.store(output_ptr + out_offset + tl.arange(0, D), out_vec.to(tl.bfloat16), mask=tl.arange(0, D) < D)
