Final diagnosis and plan

- The original PyTorch code computes per-segment, per-query, per-head attention using GQA. It does:
  - For each segment b, each query position q_idx, and each query head h:
    - Map to KV head kv_head = h // 4 (since 32 qo heads with 8 kv heads).
    - Gather k_rows = k_cache_flat[kv_indices_seg], slice kv_head -> [K, 128]
    - q_vec = q[b, h, :] -> [128]
    - K_eff = min(q_idx + 1 + (num_kv_tokens - num_q_tokens), num_kv_tokens)
    - logits = q_vec @ k_rows.T -> [K_eff]
    - logits_scaled = logits * sm_scale
    - lse = logsumexp_base2(logits_scaled)
    - attn = softmax(logits_scaled)
    - out_vec = attn @ v_rows (same kv_head slice) -> [128]
    - Store out_vec as bfloat16 at output[global_q_idx, h, :] and lse to lse[global_q_idx, h] as float32.

- The previous Triton submission failed due to:
  - Missing tl.program_id(2) and incorrect Triton kernel signature in launch (TypeError: missing 1 required positional argument: 'T'), meaning the grid and kernel signature were mismatched. Each Triton program must have three program IDs: (b, q_idx, h).
  - The earlier attempt also tried to pass dynamic constexpr or use 2D dynamic Triton tensors from runtime indices, which Triton doesn’t support. We must avoid that and only use compile-time constants like D=128 and iterate with masks.

- Fixes:
  - Define ModelNew.forward to compute q_f32, k_cache_flat, v_cache_flat, and gather kv_indices_seg per segment. Launch a Triton kernel that is explicitly 3D: (len_indptr-1, num_q_tokens, num_qo_heads).
  - In the kernel:
    - Compute global_q_idx = b * num_q_tokens + q_idx.
    - Load q_vec from q_ptr using linear indexing.
    - Iterate over k in 0..MAX_K-1 (MAX_K=128), load k_row and v_row for kv_head, compute q·k_row, track max and sum_exp for logsumexp, and accumulate out_vec = sum_k softmax_k * v_row[k, :].
    - Compute lse_base2 = (max + log(sum_exp)) / ln(2), store to lse_ptr[global_q_idx * H + h].
    - Store out_vec to output_ptr[global_q_idx * H * D + h * D + tl.arange(0, D)] as bfloat16.
  - Ensure no torch operations (no matmul, no .max, no softmax, no logsumexp) are used in forward. The only data movement allowed is allocation, view, and launching Triton kernels.

- Performance considerations:
  - This kernel is per-(b, q_idx, h). For large total_q and many segments, we create many program instances. However, the work per instance is small (128 vector ops). It’s acceptable and correct. Further speedups would require batching multiple q_idx or heads per program, which is more complex; correctness and stability are prioritized here.
