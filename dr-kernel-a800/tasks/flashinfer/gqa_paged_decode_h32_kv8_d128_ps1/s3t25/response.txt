- Tritonでは動的な配列ループとスカラーポインタのトークンIDによる索引がサポートされておらず、プログラムの制限により失敗します。
- さらに、2回のスキャン（まずmaxを求めてからsumを求める）を行うカーネル内でスカラーパラメータの書き込みもサポートされず、エラーとなります。
- 本質的には、各(b, h)について token_ids の長さだけのループが必要で、それをGPU側で実現するのが困難です。

このような制限をクリアするための現実的な解決策は、トークンID全体をバッチ次元に折りたたんで1Dにする方法です：
- token_ids_all_flat: shape [B_total * num_tokens_max] となる1Dテンソルを生成し、各要素にトークンIDを格納します。
- 次に単純なループカーネルを1Dで実装し、各プログラムが複数のトークンを担当します（BLOCKトークンずつ処理）。これはTritonでサポートされます。
- そこで以下の計画を採用します：
  1) ModelNew.forwardは完全にTriton呼び出しを含みます。
  2) トークンIDを1Dにパックし、T_MAX=num_tokens_maxをconstexprとして渡します。各プログラムではBLOCKトークンの範囲を扱い、トークン数を超えたものは無視します。
  3) 2つのTritonカーネルを呼び出します：
     - lse_max_per_bh: 各(b, h)について、トークン0..T_MAX-1をBLOCKずつスキャンし、各トークンのlogits_scaledを計算して最大値l_maxを更新。各(b, h)で一意のスカラーパラメータとしてl_maxを保存します。
     - sum_and_out_per_bh: 同様にl_maxを読み込み、トークンごとのexp(logits_scaled - l_max)を計算し、output[b, h, :]を累積します。またlse[b, h]を計算し、host側に配列として保持します。

このアプローチは、Tritonのループ制限に対処し、全ての計算をTriton内で行います。また、トークンIDを1Dテンソルとして扱い、BLOCKシフトにより継続的な処理が可能です。

    T_MAX: tl.constexpr,   # maximum number of tokens per batch

    BLOCK: tl.constexpr,    # number of tokens handled per program
):

    pid = tl.program_id(0)
    b = pid // H
    h = pid % H

    if b >= B:

    q_base = q_ptr + b * (H * D) + h * D
