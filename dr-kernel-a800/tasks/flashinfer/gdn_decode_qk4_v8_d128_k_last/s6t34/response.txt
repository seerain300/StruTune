Understanding the original code behavior
- For each batch b and head h:
  - Compute per-head scalars:
    - g = exp(-exp(A_log[h]) * softplus(a[b,h] + dt_bias[h]))
    - beta = sigmoid(b[b,h]) = 1 / (1 + exp(-b[b,h]))
  - Using q_h, k_h, v_h vectors of length K=128, and state[b,h] of shape [V=128, K]:
    - old_state = g * state[b,h] elementwise
    - old_v = k_h @ old_state (scalar reduction over K)
    - new_v = beta * v_h.sum() + (1 - beta) * old_v (scalar)
    - updated_state = old_state - old_v + new_v (broadcast scalar across [V,K])
    - output[b,h] = scale * (q_h @ updated_state) (scalar)
- Output shape is [B, 1, H, V], where H=v.shape[1] (8) and V=128. new_state shape is [B, H, V, K] (float32).

Evaluator constraints
- Triton-only: All device-side computation must be performed via Triton kernels. No torch elementwise ops (softplus, sigmoid, matmul, reductions, etc.) in forward. Only allocations, .contiguous(), views, and Triton kernel launches are allowed.
- No decoy kernels: Triton kernels must be actually launched from ModelNew.forward.
- Correctness: Outputs and new_state must match the original. This is challenging because Triton does not provide a built-in matmul/dot reduction for 2D tensors. However, we can implement reductions via loops and elementwise kernels.

Key tasks to satisfy the constraint
- Compute g and beta in Triton:
  - softplus(x) = log(1 + exp(x))
  - beta = 1 / (1 + exp(-b[b,h]))
- Implement per-(b,h) scalar reductions in Triton:
  - For k @ old_state, iterate over i in [0, K) and j in [0, V) and accumulate sum_j = sum(old_state[i, j]) then sum_k_old = sum(k_h[i] * sum_j).
