  - We can compute g and beta in Triton elementwise kernels too. To satisfy “no decoy,” we will define and launch at least one kernel for g and one for beta in forward. Even though these are per-(b,h) scalars, launching these kernels ensures we’re using Triton.

Design details
- Triton kernels:
  1) gate_beta_kernel:
     - Inputs: g_out[B,H], B, H, A_log[HV], a_flat[B*H], dt_bias[HV].
     - For each (b,h), compute A = a[b,h] + dt_bias[h], g = exp(-exp(A_log[h]) * softplus(A)). Store as float32.
     - Note: We’ll allocate g_out as torch.empty([B,H], dtype=float32, device=device) and write results via Triton. Triton does not support torch.randn inside forward, so we cannot initialize this in Triton; we allocate and write values. This avoids using torch elementwise ops to compute anything (we only allocate).
  2) beta_kernel:
     - Inputs: beta_out[B,H], B, H, b_flat[B*H].
     - For each (b,h), compute beta = sigmoid(b[b,h]) and store. We allocate beta_out similarly.
  3) qdot_kernel:
     - Compute q_h @ updated_state for each (b,h). Since Triton lacks matmul, we implement per-(b,h) scalar reduction via elementwise loads. We’ll read q_h and updated_state rows, multiply, and atomically add into a per-(b,h) scalar tensor output[B,H] (float32). This avoids any torch reductions in forward.
     - We’ll construct pointers for q_h and updated_state per (b,h) and run a small grid; although we could use a single program, it’s cleaner to run per (b,h). To avoid torch .sum, we implement the sum in Triton (using atomic_add).
- Forward logic:
  - No torch elementwise ops on device tensors. No torch.randn, no .sum, no .item, no torch constructors for scalars or device tensors in forward. Only allocate outputs and launch Triton kernels.
  - Return output cast to bfloat16 with shape [B,1,H,V], and new_state as float32 [B,H,V,K].

Performance notes
- This approach fully obeys Triton-only constraints and launches at least three Triton kernels (two elementwise for g/beta, one for q @ updated_state). It avoids using any torch elementwise ops in forward.
- Since the output is a single scalar per (b,h), using elementwise Triton to compute q_h @ updated_state (via per-row loads and atomic_add) is acceptable and satisfies correctness.
- While this may not be the most optimal implementation compared to Triton’s matmul optimizations, it adheres to the requirement to use Triton for all computation and avoids prior decoy issues.

    h = tl.program_id(1)

import torch
import triton
import triton.language as tl


@triton.jit
def gate_beta_kernel(g_out_ptr, B, H, A_log_ptr, a_ptr, dt_bias_ptr):
    # Each program handles one (b,h) element
    b = tl.program_id(0)
    h = tl.program_id(1)
    if (b < B) and (h < H):
        # A = a[b,h] + dt_bias[h]
        A = tl.load(a_ptr + b * H + h) + tl.load(dt_bias_ptr + h)
        # softplus(A) = log(1 + exp(A))

        # store to g_out[b, h]
        tl.store(g_out_ptr + b * H + h, g)
