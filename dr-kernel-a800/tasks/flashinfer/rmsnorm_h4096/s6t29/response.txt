Recap of the operation
- For each row:
  - Compute inv_rms = 1 / sqrt(mean(x^2) + eps), with mean over 4096 elements.
  - Output y = (x * inv_rms) * weight.
- Memory traffic is unavoidable: two reads per row and one write. Writing intermediates would only add bandwidth.

Plan
- Keep a single Triton kernel with one program per row, two passes:
  - First pass: accumulate sum of squares to derive inv_rms.
  - Second pass: re-read x, multiply by inv_rms and weight, and store output.
- Tiling and warps:
  - Use BLOCK_SIZE=1024 and num_warps=8 for hidden_size=4096 to minimize loop iterations (4) and hide latency. Keep num_stages=3 for pipelining.
- Dtype handling:
  - Compute in float32 for numerical stability; cast to the desired output dtype at store (fp32/fp16/bf16). This matches original behavior and avoids host-side elementwise casts.
- Robustness:
  - Masked loads/stores ensure correctness for any batch_size and hidden_size (we assert hidden_size==4096 in ModelNew for this benchmark).

```python
import torch
import triton
import triton.language as tl

# Triton kernel: per-row RMS scaling with weight.
# One program per row. We read x twice: once to compute sum of squares, once to write output.
@triton.jit
def _rms_scale_kernel(
    hidden_ptr,        # *float32, pointer to hidden_states (cast to float32)
    weight_ptr,        # *float32, pointer to weight (cast to float32)
    out_ptr,           # *T_out, pointer to output (will store casted result)
    batch_size,        # int32
    hidden_size,       # int32
    eps,               # float32
    out_dtype_code: tl.constexpr,  # 0: fp32, 1: fp16, 2: bf16
    BLOCK_SIZE: tl.constexpr        # e.g., 1024
):
    row_id = tl.program_id(0)  # one program per row

    # Accumulator for sum of squares (float32)
    sum_sq = 0.0

    # First pass: compute sum of squares across the row
    for col_start in range(0, hidden_size, BLOCK_SIZE):
        cols = col_start + tl.arange(0, BLOCK_SIZE)
        mask = cols < hidden_size
        x = tl.load(hidden_ptr + row_id * hidden_size + cols, mask=mask, other=0.0)
        sum_sq += tl.sum(x * x, axis=0)

    mean_sq = sum_sq / hidden_size
    inv_rms = tl.rsqrt(mean_sq + eps)

    # Second pass: scale and write output
    for col_start in range(0, hidden_size, BLOCK_SIZE):
        cols = col_start + tl.arange(0, BLOCK_SIZE)
        mask = cols < hidden_size
        x = tl.load(hidden_ptr + row_id * hidden_size + cols, mask=mask, other=0.0)
        w = tl.load(weight_ptr + cols, mask=mask, other=0.0)
        y = x * inv_rms * w

        # Store with dtype control
        if out_dtype_code == 0:
            # fp32
            tl.store(out_ptr + row_id * hidden_size + cols, y, mask=mask)
        elif out_dtype_code == 1:
            # fp16
            tl.store(out_ptr + row_id * hidden_size + cols, y.to(tl.float16), mask=mask)
        else:
            # bf16
            tl.store(out_ptr + row_id * hidden_size + cols, y.to(tl.bfloat16), mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, hidden_states, weight):
        # Fallback to PyTorch if not CUDA
        if not hidden_states.is_cuda or not weight.is_cuda:
            # Match original behavior
            x = hidden_states.to(torch.float32)
            inv_rms = torch.rsqrt(x.pow(2).mean(dim=-1, keepdim=True) + 1e-5)
            y = (x * inv_rms) * weight.to(torch.float32)
            return y.to(hidden_states.dtype)

        # Ensure contiguity and compute in float32
        hidden = hidden_states.contiguous().to(torch.float32)
        weight = weight.contiguous().to(torch.float32)

        batch_size = hidden.shape[0]
        hidden_size = hidden.shape[1]
        assert hidden_size == 4096, "This optimized kernel expects hidden_size == 4096."

        # Output tensor with same dtype as input hidden_states
        out = torch.empty_like(hidden, dtype=hidden_states.dtype)

        # Encode output dtype for the kernel
        if out.dtype == torch.float32:
            out_dtype_code = 0
        elif out.dtype == torch.float16:
            out_dtype_code = 1
        elif out.dtype == torch.bfloat16:
            out_dtype_code = 2
        else:
            # Fallback: compute in float32 and cast after
            out = torch.empty_like(hidden, dtype=torch.float32)
            out_dtype_code = 0

        grid = (batch_size,)
        # Launch Triton kernel
        _rms_scale_kernel[grid](
            hidden, weight, out,
            batch_size, hidden_size, 1e-5,
            out_dtype_code,
            BLOCK_SIZE=1024,
            num_warps=8,
            num_stages=3,
        )

        return out
```

If you want to experiment, BLOCK_SIZE=2048 (with num_warps=8) can be tried; however, given hidden_size=4096, 1024 is a robust choice.
- We cast to the desired output dtype inside the kernel to match the original code’s dtype behavior without relying on host-side PyTorch elementwise casts.

What the original code does
- For each row in hidden_states (shape [batch_size, 4096]):
  - Compute inv_rms = 1 / sqrt(mean(x^2) + 1e-5) over the 4096 elements.
  - Scale each element by inv_rms, then multiply by weight (shape [4096]), and return the result in the original dtype.

Memory traffic characteristics
- This is memory-bound. The optimal approach is to avoid extra global memory writes and keep everything in a single fused kernel.
- The computation requires a reduction (sum of squares) per row, which means at least one read of the entire row. Writing intermediate x^2 to global memory would add bandwidth. Therefore, the most effective design reads the row twice: once to compute the sum of squares, and a second time to scale and write the output.

Strategy
- Implement a Triton kernel with one program per row.
- Two passes per row:
  1) First pass: accumulate sum of squares to compute inv_rms (scalar per row).
  2) Second pass: re-read x, multiply by inv_rms and weight, and store the output.
- Keep computation in float32 for numerical stability; cast to the desired output dtype only at store time.
- Use BLOCK_SIZE tuned for 4096 (e.g., 1024) to reduce loop iterations and improve throughput. Use num_warps=8 and num_stages=3 to hide latency and pipeline loads.
- Ensure masked loads/stores so the kernel works for any hidden_size, but assert 4096 to match the benchmark.

Why not one pass with shared/global memory?
- RMS scaling requires knowing the mean across the entire row. Without storing partial sums or performing atomics (which would introduce contention), a single pass cannot produce the final scaled output. Thus, two passes are the minimal memory pattern.
