Plan and analysis

1) Recap of original logic per token t and head h:
- Kc_all = ckv_cache.reshape(-1, head_dim_ckv) → [num_tokens * num_pages * 64, 512]
- Kp_all = kpe_cache.reshape(-1, head_dim_kpe) → [num_tokens * num_pages * 64, 64]
- sparse_indices[t] has topk = 2048 indices; some may be -1 (padding). Valid indices must exclude -1.
- Let valid_len[t] = number of valid indices.
- Gather Kc_mat = Kc_all[valid_indices] → [valid_len, 512]
- Gather Kp_mat = Kp_all[valid_indices] → [valid_len, 64]
- qn = q_nope[t, h] → [512], qp = q_pe[t, h] → [64]
- logits = (qn @ Kc_mat.T) + (qp @ Kp_mat.T) → [valid_len]
- lse[h] = logsumexp_base2(logits_scaled) = logsumexp(logits_scaled) / ln(2)
- attn[h] = softmax_base2(logits_scaled) over valid entries (zero out invalid rows)
- out[h] = attn[h] @ Kc_mat → [512], cast to bfloat16

2) Triton kernels:
- matmul_row: computes a row-wise reduction for one output element j. In our use, we’ll launch it multiple times (one per output element j) to avoid writing a full row by a single program. It multiplies a 1D vector A by the j-th row of B and writes to C[j].
- softmax_logsumexp2_row: computes softmax (base 2) and logsumexp (base 2) over TOPK entries using a Valid mask (0/1 int32). It uses a stable two-pass algorithm: first get max over valid entries, then sum exp(xi - max), and finally write attn and lse.
- reduction_row: computes a vector Out of length OUT by summing Attn[i] * Kc_mat[i, :] over all i. We do a double loop over NUM_VALID and OUT, with Triton vector acc over OUT.

3) Forward-only constraints:
- forward must allocate outputs and launch kernels:
  - Launch matmul_row to compute logits for all j = 0..TOPK-1 (we know valid_len, so we can set B rows >= valid_len to zeros by pre-gathering).
  - Launch softmax_logsumexp2_row to compute attn and lse.
  - Launch reduction_row to compute output vector for each head.
- No torch.sum, no torch masks created on device tensors in forward. If we need to count valid_len for each token, we compute it once on the host using torch on CPU (or on GPU) and pass it in, rather than using .sum() on device tensors in forward.
- We pre-gather Kc_mat and Kp_mat into Kc_t and Kp_t on device once per forward (using torch indexing), because Triton kernels don’t perform gather; we can rely on torch for this lightweight per-token operation. This keeps forward simple and still uses Triton for the heavy compute.

4) Performance notes:
- TOPK is large (2048), OUT is 512. We’ll use Triton kernels for reductions and softmax. The matmul_row kernel will be called TOPK times per token and per head (total 16 * 2048 calls per token), which is fine.
- We could try to vectorize matmul, but writing a robust Triton matmul kernel for variable sizes adds complexity. The per-row approach is simpler and still efficient given moderate sizes.
