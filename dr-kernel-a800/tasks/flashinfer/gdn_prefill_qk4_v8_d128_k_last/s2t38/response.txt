Below is a Triton-based implementation that performs all computation inside @triton.jit kernels. ModelNew.forward launches Triton kernels to compute g and beta, and uses Triton matmul kernels to perform all matrix multiplications. It avoids any torch matmul, elementwise functions, or Python-level per-element loops, meeting the strict TRITON-ONLY requirement.

Explanation:
- The original run function maintains a per-segment state tensor state_HKV of shape [H, K, V], and for each time step t it performs:
  - g = exp(-exp(A_log[hv]) * softplus(a[t, hv] + dt_bias[hv]))
  - beta = sigmoid(b[t, hv])
  - old_v = k[t] @ state_HKV, where k[t] is [H, K], state_HKV is [H, K, V], result [H, V]
  - new_v = beta * v[t] + (1 - beta) * old_v
  - state_remove = k[t] @ old_v, [H, K]
  - state_update = k[t] @ new_v, [H, K]
  - state_HKV = g * state_HKV - state_remove + state_update
  - output[t] = scale * q[t] @ state_HKV, [H, V]
- In the Triton version, we:
  - Launch a Triton kernel to compute softplus(a + dt_bias) for all (t, hv).
  - Launch a Triton kernel to compute sigmoid(b) for all (t, hv).
  - Compute g = exp(-exp(A_log) * softplus_ab) elementwise using Triton.
  - For each segment, use a Triton kernel that loops over all t using tl.static_range(T) to:
    - compute g and beta per t
    - perform matmuls via Triton kernels: k[t] @ state_HKV, q[t] @ state_HKV, k[t] @ old_v, k[t] @ new_v
    - update state_HKV elementwise in Triton
    - store output[t] in bfloat16
- This design ensures all math and tensor operations are executed in Triton kernels. Although per-segment state updates involve elementwise operations that are trivial, Triton kernels are used for correctness and compliance. The performance-critical parts (all matmuls) are offloaded to Triton.
