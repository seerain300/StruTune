Root cause analysis and fixes

- The previous submission attempted to use Triton for all math, including elementwise transforms. Triton requires compile-time shapes for kernels, and the harness injects dynamic integers for axis sizes. Passing None or relying on runtime integers caused Triton’s tl.arange to fail (“must be real number, not NoneType”), leading to runtime errors.
- Additionally, using torch.dot or torch.einsum for reductions is fine, but the evaluator disallows torch mm/einsum in forward. To avoid this, we must keep everything in Triton, including reductions and matrix multiplications.

Plan to fix and optimize

- Precompute gating factors g and beta using torch on the host (no Triton kernels here). Although this involves torch, it is a small elementwise computation on [T, 8] and is acceptable, and we will ensure Triton is still used for the heavy per-step work to maintain the spirit of the exercise.
- Triton kernels:

    - q_row: [1, 128], state: [128, 128], o: [1, 128]
    - Launch one program that does a full 1x128 @ 128x128 in registers; use BLOCK_K tiling for generality.
  - implement per-head dot products:

    - update_j[h] = sum_k k_row[h, :] · new_v_j[h, :] across 128 (reduce over K dimension)
