Analysis and plan

What the original code computes:
- Input shapes:
  - q: [total_q, 32, 128], k: [total_kv, 8, 128], v: [total_kv, 8, 128]
  - qo_indptr: cumsum over segments of q, length Lq
  - kv_indptr: cumsum over segments of k/v, length Lk
- For each batch segment b in [0, Lq-1]:
  - q_batch = q[q_start:q_end] -> [Q, 32, 128]
  - k_batch = k[kv_start:kv_end] -> [K, 8, 128]
  - v_batch = v[kv_start:kv_end] -> [K, 8, 128]
- Group-Query Attention (GQA) mapping: expand heads from 8 to 32 by repeating each K/V token’s heads 4 times.
  - k_expanded: [K, 32, 128]
  - v_expanded: [K, 32, 128]
- Compute logits = q_batch @ k_expanded^T → [Q, 32, K], scaled by sm_scale = 1/sqrt(128).
- Mask: For each query i, only keys j with j < (i + 1 + delta) are valid, where delta = K - Q. This is a bounded mask (not standard causal).
- lse per (i, h): logsumexp(logits[i, h, :]) but in base-2: logsumexp / ln(2).
- Output: softmax(logits[i, h, :]) along K, then output[i, h, :] = softmax @ v_expanded along K.

Why the previous Triton attempt failed:
- Triton kernels don’t support arbitrary Python loops with dynamic bounds inside @triton.jit. You must use tl.static_range with constexpr loop bounds, or rely on vectorized operations. My earlier kernel used dynamic ranges and loops, causing CompilationError.

How to fix and ensure Triton-only:
- Implement one Triton kernel per segment that:
  1) Loads q, k, v slices and expands heads by repeating 4 times (GQA).
  2) Computes logits in tiles using tl.dot over K dimension, applies the bounded mask, and computes per-(i,h) lse and denominator (sum of exp).
  3) Recomputes logits with the mask applied and computes softmax via exp/log in Triton, then multiplies with v_expanded and accumulates output for each head h.
  4) Stores output and lse.
- Avoid any host-side tensor math. All loops and masking are done inside the Triton kernel using static_range and vectorized tl operations.

Performance considerations:
- The kernel operates on fixed head_dim=128. We can use BLOCK_K=128 and BLOCK_Q=128 to process the entire K dimension in one chunk, minimizing recomputation. However, to keep the kernel robust, we keep BLOCK_K=128 and iterate over Q in tiles (BLOCK_Q=128). With the given workload where Q and K are often multiples of 128, this yields a single iteration for K and typically a single iteration for Q, but the kernel supports general Q,K via masks.
- We recompute logits in two phases: first to compute max (for numerically stable softmax), second to compute softmax and output. This is standard and keeps the kernel simple and Triton-compliant.
