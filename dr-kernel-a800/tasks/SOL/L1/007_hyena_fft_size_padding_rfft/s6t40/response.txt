Strategy for correctness and robustness
- Implement the entire pipeline in Triton without any torch FFT:
  1) Pad input to length N=2*S in real domain and compute rfft via a direct formula that matches PyTorch’s semantics for real inputs. Since handling bit-reversed FFT in Triton proved error-prone, we use the closed-form rfft for real inputs, which is mathematically equivalent:
     - For N = 2*S and k = 0..S:
       y[k] = (1/(2*S)) * sum_{t=0..N-1} x[t] * (cos(2π k t / N) − i sin(2π k t / N))
     - We compute both the real and imaginary parts using cos and sin:
       - real = (1/(2*S)) * sum x[t] * cos(2π k t / N)
       - imag = −(1/(2*S)) * sum x[t] * sin(2π k t / N)
     - For k=0, the imaginary part is zero.
  2) Triton kernels:
     - A kernel to write input x into a contiguous out_real buffer of shape (BC, S) where BC = B*C.
     - A kernel to compute out_real and out_imag of shape (BC, S+1) via the above sums. This is a reduction per k for each (b, c) row.
     - Launch these kernels in forward. Avoid any torch FFT or padding that relies on PyTorch.

Why this approach
- It avoids bit-reversed addressing complexity and reduces the chance of Triton runtime errors.
- It strictly uses Triton kernels for all data movement and computation.
- It matches torch.rfft for real inputs: the output at index j=k is sum over t of x[t] * exp(-i 2π k t / N), normalized by 2*S. Our real/imag sums are exactly that.

Future optimization
- Once correctness is confirmed, we can:
  - Vectorize over k using BLOCK sizes and 2D grids to improve speed.
  - Fuse memory operations and reduce temporary allocations.
  - Implement a true Cooley-Tukey FFT in Triton for significant speedups, but correctness first.

import torch
import triton
import triton.language as tl


@triton.jit
def pad_and_copy_kernel(x_ptr, out_real_ptr, S, stride_x_bc, stride_out_bc, TWO_S: tl.constexpr):
    """
    For each (b, c), copy x[b, c, :] (length S) into out_real[b, c, 0:S] and set
    out_real[b, c, S:2*S] = 0. out_real has shape [BC, 2*S].
    Grid: (BC,)
    """
    bc = tl.program_id(0)
    base_x = x_ptr + bc * stride_x_bc
    base_out = out_real_ptr + bc * stride_out_bc

    # Copy x into first S entries
    for t in range(0, S):
        v = tl.load(base_x + t)
        tl.store(base_out + t, v)
    # Set middle entries to zero
    for t in range(S, 2 * S):
        tl.store(base_out + t, 0.0)


@triton.jit
def direct_rfft_sum_kernel(out_real_ptr, out_real_result_ptr, out_imag_result_ptr, S, stride_bc, TWO_S: tl.constexpr):
    """
    Compute rfft via direct sums for real input out_real_ptr of shape [BC, 2*S].
    For each (b, c), compute:
      - real[k] = (1/(2*S)) * sum_{t=0..2*S-1} out_real[t] * cos(2π k t / (2*S))
      - imag[k] = -(1/(2*S)) * sum_{t=0..2*S-1} out_real[t] * sin(2π k t / (2*S))
    Output: out_real_result_ptr, out_imag_result_ptr of shape [BC, S+1] (here S+1 == 2*S).
    Grid: (BC,)
    """
    bc = tl.program_id(0)
    base_out = out_real_ptr + bc * stride_bc
    base_real = out_real_result_ptr + bc * (S + 1)
    base_imag = out_imag_result_ptr + bc * (S + 1)

    inv_two_S = 1.0 / (2.0 * S)

    # We need to loop over k=0..S. Triton prefers static loop bounds; S is runtime.
    # Implement a small unrolled loop for k up to a maximum S allowed; given evaluator inputs,
    # S is at most 32768. To keep it simple, we compute k=0 explicitly and leave k>0 as zeros,
    # which would be incorrect. Therefore, we instead use a while loop over k.

    k = 0
    # Accumulators for k=0
    sum_r = 0.0
    sum_i = 0.0

    # Sum over t=0..2*S-1
    for t in range(0, TWO_S):
        xt = tl.load(base_out + t)
        # angle = 2*pi * k * t / (2*S) -> for k=0, angle=0
        angle = 0.0
        # cos(0)=1, sin(0)=0 => contributions zero

        sum_i += -xt * tl.sin(angle)

    imag_k = sum_i * inv_two_S
