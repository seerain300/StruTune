深度调查失败原因及根本纠正

- 问题表现：最新的 Triton-only 实现持续报告 “INCORRECT_NUMERICAL” 对所有 workload。这意味着我们的计算结果与 PyTorch 参考存在系统性差异，而不仅仅是数值精度或边界情况错误。

- 根本原因分析：
  1) compute_mean_std_fp32 kernel 中的 while 循环逻辑存在缺陷：虽然我们对 masked lanes 使用了 other=0.0 来 load，但在累加时没有将 masked lanes 的贡献清零，而是错误地将 masked lanes 的 0.0 加入到了 sum/sum_sq 中。这会导致 mean/std 的计算错误，进而使得 threshold 和激活结果与 PyTorch 的参考不同。例如，当 H 不是 BLOCK 的整数倍时，这部分误差被放大，并导致明显不正确的结果。
  2) apply kernel 中虽然使用了 mask，但之前的版本也有可以改进的地方，不过最明显的错误是在统计 kernel 中未能排除 masked lanes 的影响。

- 修复策略：
  - 修正 compute_mean_std_fp32 kernel 中的两遍 pass：
    - 第一遍：使用 masked load 保护越界的 lanes，并且在累加之前通过 tl.where(mask, x, 0.0) 将无效 lanes 的贡献置为零，确保 sum 和 sum_sq 只包含有效的 H 项。
    - 第一遍完成后计算 mean = sum / H 和 var = sum_sq / H - mean^2 (population std, unbiased=False)。
    - 第二遍：重新遍历 H 以应用阈值 y = max(x - (mean + std*z), 0) 到 out_ptr，并使用相同的 mask 保护。
  - icdf approximation kernel 保持 A&S 5th-order rational approximation 传回标量 z (fp32) 在 device，forward 中 host 不做任何 tensor math。
  - apply kernel 严格基于合法 offsets < H 进行 load, compute, store，并且不修改 out_ptr 中无效位置。

- 性能考虑：
  - keep BLOCK=2048 来平衡并行度和向量化效率，在 H 较大时减少循环次数。
  - 两遍遍历对统计和应用来说是标准做法，并且已经展示出良好的性能 (前一次提交取得了 10.98x)。只要保证统计正确，apply 步骤也很高效。

最终的 Triton-only 代码

```python
import torch
import triton
import triton.language as tl


@triton.jit
def compute_mean_std_fp32(in_ptr, mean_ptr, std_ptr, B, S, H, BLOCK: tl.constexpr):
    # One program per (b, s) row, pid in [0, B*S)
    row = tl.program_id(0)
    b = row // S
    s = row % S

    # Base offset for this row in flattened [B, S, H] layout
    base = b * S * H + s * H

    # First pass: accumulate sum and sum of squares (fp32), excluding masked lanes
    sum_val = 0.0
    sum_sq = 0.0
    offsets = tl.arange(0, BLOCK)
    i = 0
    while i < H:
        idx = i + offsets
        mask = idx < H
        x = tl.load(in_ptr + base + idx, mask=mask, other=0.0)
        x = x.to(tl.float32)
        x_masked = tl.where(mask, x, 0.0)  # ensure masked lanes contribute 0
        sum_val += tl.sum(x_masked, axis=0)
        sum_sq += tl.sum(x_masked * x_masked, axis=0)
        i += BLOCK

    # Compute mean and std (population, unbiased=False)
    n = H
    mean = sum_val / n
    var = sum_sq / n - mean * mean
    std = tl.sqrt(var)

    # Store per-row mean and std
    tl.store(mean_ptr + row, mean)
    tl.store(std_ptr + row, std)


@triton.jit
def compute_icdf_scalar(out_ptr, p_val, p_low, p_high, BLOCK: tl.constexpr):
    # Abramowitz & Stegun 5th-order rational approximation for standard normal inverse CDF
    a1 = -3.969683028665376e+01
    a2 = 2.209460984245205e+02
    a3 = -2.759285104469687e+02
    a4 = 1.383577518672690e+02
    a5 = -3.066479806614716e+01
    a6 = 2.506628277459239e+00

    b1 = -5.447609879822406e+01
    b2 = 1.615858368580409e+02
    b3 = -1.556989798598866e+02
    b4 = 6.680131188771972e+01
    b5 = -1.328068155288572e+01

    c1 = -7.784894002430293e-03
    c2 = -3.223964580411365e-01
    c3 = -2.400758277161838e+00
    c4 = -2.549732539343734e+00
    c5 = 4.374664141464968e+00
    c6 = 2.938163982698783e+00

    d1 = 7.784695709041462e-03
    d2 = 3.224671290700398e-01
    d3 = 2.445134137142996e+00
    d4 = 3.754408661907416e+00

    # piecewise selection
    p_low_scalar = 0.02425
    p_high_scalar = 1.0 - p_low_scalar

    if p_val <= p_low_scalar:
        q = tl.sqrt(-2.0 * tl.log(p_val))
        poly = -(((((c1 * q + c2) * q + c3) * q + c4) * q + c5) * q + c6)
        den = (((((d1 * q + d2) * q + d3) * q + d4) * q + 1.0))
        nd = poly / den
    elif p_val >= p_high_scalar:
        q = tl.sqrt(-2.0 * tl.log(1.0 - p_val))
        poly = -(((((c1 * q + c2) * q + c3) * q + c4) * q + c5) * q + c6)
        den = (((((d1 * q + d2) * q + d3) * q + d4) * q + 1.0))
        nd = poly / den
    else:
        q = p_val - 0.5
        r = q * q
        poly = (((((a1 * r + a2) * r + a3) * r + a4) * r + a5) * r + a6)
        den = (((((b1 * r + b2) * r + b3) * r + b4) * r + b5))
        nd = poly * q / den

    tl.store(out_ptr, nd)


@triton.jit
def apply_threshold_relu_to_bf16(in_ptr, out_ptr, mean_ptr, std_ptr, B, S, H, z_ptr, BLOCK: tl.constexpr):
    # One program per (b, s) row
    row = tl.program_id(0)
    b = row // S
    s = row % S

    # Load per-row mean and std (fp32)
    mean = tl.load(mean_ptr + row)
    std = tl.load(std_ptr + row)
    # Load scalar z (icdf) from z_ptr[0]
    z = tl.load(z_ptr)

    # Compute threshold
    thr = mean + std * z  # fp32

    # Base offset for this row
    base = b * S * H + s * H

    # Second pass: apply y = max(x - thr, 0) over H, store as bfloat16
    offsets = tl.arange(0, BLOCK)
    i = 0
    while i < H:
        idx = i + offsets
        mask = idx < H
        x = tl.load(in_ptr + base + idx, mask=mask, other=0.0).to(tl.float32)
        y = x - thr
        y = tl.maximum(y, 0.0)
        tl.store(out_ptr + base + idx, y.to(tl.bfloat16), mask=mask)
        i += BLOCK


class ModelNew(torch.nn.Module):
    def forward(self, input_tensor: torch.Tensor, target_sparsity: float) -> torch.Tensor:
        """
        Triton-only implementation of Gaussian-based top-k sparse activation:
        - Compute per (batch, seq) row mean and std in fp32 over feature dim H (population, unbiased=False).
        - Compute z = inverse-normal CDF(target_sparsity) as scalar on device (A&S approximation).
        - Apply thresholding: y = max(input - (mean + std*z), 0) and return in bfloat16.
        """
        assert input_tensor.is_cuda, "Input must be a CUDA tensor for Triton version."
        assert target_sparsity >= 0.0 and target_sparsity <= 1.0, "target_sparsity must be in [0, 1]"

        # Ensure contiguous [B, S, H] layout
        input_bf16 = input_tensor.to(torch.bfloat16).contiguous()
        B, S, H = input_bf16.shape

        # Allocate output tensor (bfloat16), and stats buffers (fp32) per row
        out = torch.empty_like(input_bf16)
        mean = torch.empty((B * S,), dtype=torch.float32, device=input_bf16.device)
        std = torch.empty((B * S,), dtype=torch.float32, device=input_bf16.device)

        # Launch compute_mean_std_fp32
        grid_stats = (B * S,)
        compute_mean_std_fp32[grid_stats](
            input_bf16, mean, std, B, S, H, BLOCK=2048,
            num_warps=4, num_stages=2
        )

        # Compute icdf scalar z and store to 1-element fp32 tensor
        z_tensor = torch.empty((1,), dtype=torch.float32, device=input_bf16.device)
        compute_icdf_scalar[(1,)](
            z_tensor, target_sparsity, 0.02425, 1.0 - 0.02425, BLOCK=1,
            num_warps=1, num_stages=1
        )

        # Launch apply kernel
        apply_threshold_relu_to_bf16[grid_stats](
            input_bf16, out, mean, std, B, S, H, z_tensor, BLOCK=2048,
            num_warps=4, num_stages=2
        )

        return out
```

关键修正总结
- compute_mean_std_fp32 kernel 第一遍中加入了 tl.where(mask, x, 0.0) 来确保无效 lanes 不计入 sum/sum_sq，彻底消除之前遗漏导致的 mean/std 误差。
- apply kernel 严格使用 mask 来 load/compute/store，并且不向 out_ptr 中写入无效位置的值，防止任何副作用。
- host 代码仅做 allocation, launch, grid 选择和 scalar 传递，符合 Triton-only 规则。

冷静分析、复盘及纠正

- 问题现象：最新的 Triton-only 实现持续报告 “INCORRECT_NUMERICAL” 对所有 workload。这表明我们的 Triton kernels 存在系统性偏差，而不仅仅是轻微的数值精度问题。

- 根本原因排查：
  1) compute_mean_std_fp32 kernel 中的两遍 pass 设计理论上是正确的，但在之前的提交中出现了不一致性失败。最常见的陷阱是在 while 循环内使用向量 masked load 时，如果没有将 masked lanes 的贡献置为零就进行 tl.sum，可能会在某些情况下引入微小偏差，尤其是在 H 不是 BLOCK 的整数倍时。此外，即使 masked load 用了 other=0.0，如果不显式地置零再求和，某些 Triton 编译路径下可能无法完全排除无效 lanes 的影响。
  2) apply kernel 本身也是基于正确的 offsets<H 来做 load, compute, store，并使用 mask 保护，之前 failure 更有可能来自于 stats 的偏差。

- 为了彻底消除不确定性，我决定对统计计算进行更严格的保护，并且简化应用步骤：
  - 重构 compute_mean_std_fp32 为严格的 per-element iteration (for i in range(0, H, BLOCK)) 而不是 while 循环，确保每次迭代都是完整的 BLOCK 区间，mask 只用于最后不足 BLOCK 的部分，并且显式地置零无效 lanes 后求和。这样可以最大程度地避免循环控制带来的问题。
  - keep icdf approximation 为 A&S 5th-order rational approximation，传回 fp32 标量 z (device tensor) 给 host 作为参数，在 host 中只负责 scalar 传递。
  - apply kernel 也改用 for i in range(0, H, BLOCK) 结构，严格使用 mask 来 load/compute/store。

- Triton-only 规则：ModelNew.forward 只负责 allocation, launch, grid 设定，以及 scalar 传递，不做任何 torch tensor math (no torch.mean, torch.std, F.relu, torch.tensor(...))。所有的 per-element math 和 reductions 都在 Triton kernels 中完成。

- 性能考虑：
  - keep BLOCK=2048 以及 num_warps=4, num_stages=2 来达到较好的并行度，并减少 H 较大时的循环次数。
  - 两遍计算（统计 + 应用）之前有较好的 speedup (10.98x)，只要确保 stats 正确，应用步骤也很高效。

    base = b * S * H + s * H
