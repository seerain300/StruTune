    ln_b_ptr,     # *bfloat16, ln bias (K,)
    y_ptr,        # *bfloat16, output (M, K)
    M: tl.constexpr,  # number of rows
    K: tl.constexpr,  # hidden size
    eps: tl.constexpr,  # epsilon
    BLOCK: tl.constexpr,
):

    # First pass: compute mean and variance in FP32
    sum_ = 0.0
    sumsq_ = 0.0
    for off in range(0, K, BLOCK):
        idx = off + tl.arange(0, BLOCK)
        mask = idx < K
        x = tl.load(x_ptr + row * K + idx, mask=mask, other=0.0)
        x = x.to(tl.float32)
        sum_ += tl.sum(x, axis=0)
        sumsq_ += tl.sum(x * x, axis=0)
    mean = sum_ / K
    var = sumsq_ / K - mean * mean
    rstd = 1.0 / tl.sqrt(var + eps)

    # Second pass: normalize and apply affine, store as BF16
    for off in range(0, K, BLOCK):
        idx = off + tl.arange(0, BLOCK)
        mask = idx < K
        x = tl.load(x_ptr + row * K + idx, mask=mask, other=0.0).to(tl.float32)
        ln_w = tl.load(ln_w_ptr + idx, mask=mask, other=1.0).to(tl.float32)

    col_block = tl.program_id(1)

Root cause analysis
- Invalid grid launches: Triton requires grid dimensions to be positive integers. If the host-side logic computes a grid tuple where a dimension is zero or negative (e.g., due to tiling not dividing shape), Triton raises a runtime error. This is likely the primary cause of repeated failures in your previous submissions.
- Masking mistakes: If a Triton kernel assumes a vector of length BLOCK but only masks the tail, and the code tries to load/stores for indices beyond the actual length, Triton can hit illegal memory accesses or produce undefined behavior. Ensuring masks are correct and guarding loads/stores is critical.
- Shape assumptions: Some implementations assume tensors are contiguous or have specific shapes, but the evaluator may pass different shapes. Using view/reshape requires contiguity and matching dimensions. A safer approach is to use kernels that operate on strided memory and have explicit masks.
- Overly complex kernels: Implementing GEMM (matmul) in Triton can be error-prone in dynamic shapes and can easily lead to incorrect grid computations or indexing bugs. Many of the failures in prior attempts point to this complexity.

Optimization approach

- Perform the heavy matmuls and elementwise activation using torch on CUDA (these are fast and correct), while using Triton for kernels that are simple and where shapes are well-defined, and whose grids are easily computed to be positive.
