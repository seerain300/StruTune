詳細な解析、既存の問題、そして改善計画

元のコードの挙動と目標
- get_inputs は、ランダムな専門家インデックス topk_idx を生成し、その shape は (batch_size, seq_len, num_experts_per_tok) です。
- run では：
  - flat = topk_idx.reshape(-1) で 1D 配列を作ります。
  - sorted_token_indices = torch.sort(flat, stable=True)[1] つまり、flat の値を昇順にソートしたときの各要素の元のインデックスの並び（stable=True は値が同じとき元の順序を保持）。
  - expert_offsets = torch.bincount(flat.long(), minlength=num_experts).cumsum(0).to(int32)
    → 各専門家 ID の出現回数の exclusive prefix sum で、length は num_experts + 1 です。

TRITON-ONLY 要件
- ModelNew.forward で行われるすべての計算は @triton.jit 定義の Triton キャンプから実行しなければなりません。
- torch.sort や torch.bincount を使用してはいけません。
- 定義した Triton キャンプが実際に forward 内で起動される必要があります（デコイは拒否）。

前回の問題とその原因
- 前のサブミッションでは、「decoy kernel」の理由で拒否されました：定義だけあって実行されていなかった。
- さらに、ビットソートなどの実装が誤り、評価環境でランタイムエラーが出ました。
- これらは、トランプ内での変数スコープ、配列の同期化、ループ制御の誤りからくる可能性が高いです。

正しい実装の方針
1) sorted_token_indices の計算:
   - torch.sort は強力ですが、ここではそれを避ける必要があります。代わりに、元のフラット配列の値に対し、「stable count-per-value」で安定な順序を決定します。その方法として、各桁について counting sort を用いて stable な並び替えを実現できます。
   - topk_idx の値の範囲が [0, num_experts-1] であり、num_experts=256 なので、ビット幅は 8 で十分です。各桁 d=0..7 について以下の動作を行う：
     - counts[d] = (flat[i] >> d) & 1
     - exclusive prefix sum of counts[d] を計算し、各 i に対して destination position を決定します。
     - stable な並び替えのために、各桁ごとに flat[i] に対応する position[i] を配列で保持し、途中で値を書き換えながら並び替えを行います。これは「レジストリー内での並び替え」のようなメソッドで行うことができ、元の順序（並び替え前の位置 i）を基準にすることで安定性が保持されます。

2) expert_counts (bincount) の計算:
   - Triton キャンプ count_histogram_atomic で、flat をスキャンし、各要素を専門家 ID に対応する counts[ID] に atomic_add で加算します。counts は長さ num_experts (256) の int32 配列を予めゼロ初期化します。

3) expert_offsets (cumulative sum):
   - Triton キャンプ exclusive_prefix_sum_kernel で、counts の exclusive prefix sum を計算し、length は num_experts + 1 として出力します。

詳細な Triton 実装の説明
- counting_sort_by_bits_kernel:
  - grid=(1,) で 1 つのプロセスが全要素を並び替える。各桁 d について、counts[d] を計算し、exclusive prefix sum を求め、position[i] に destination index を書き込みます。
  - 安定性のために、同一ビットで 0 と 1 を区別し、position が smallest から順に決定されるようにします。

- count_histogram_atomic:
  - grid=M を設定し、flat をスキャンして各専門家 ID に対し counts[ID] += 1 とする。初期化は counts=torch.zeros(256, device=device, dtype=torch.int32) で行う（これは forward で行うので許容）。

- exclusive_prefix_sum_kernel:
  - offsets[0] = 0; その後、for i in 1..N_bins-1: offsets[i] = sum_{k=0..i-1} counts[k] とする。O(N_bins^2) だが N_bins=256 なので許容範囲内。

重要な設計ポイント
- Triton 内で並び替えは Bitonic などではなく、ビット別 counting sort を採用し、stable=True に準じた挙動を保証します。
- counts のゼロ初期化は forward で行いますが、その後の bincount と prefix sum は Triton で行われます。
- sorted_token_indices は output に直接書き込むのではなく、position[i] を使って後で gather するようにします。もしくは直接書き込むことも可能ですが、トランプでは配列同期の扱いが簡単なので position[i] を使って実装します。
