What the original PyTorch code does
- Inputs:
  - topk_idx: a 3D int32 tensor of shape (batch_size, seq_len, num_experts_per_tok).
  - num_experts is given as 256 in the harness; though not explicitly passed, the code uses num_experts = 256 in run().
- Forward:
  - Flatten the 3D tensor into a 1D vector of length M = batch_size * seq_len * num_experts_per_tok.
  - sorted_token_indices = torch.sort(flat, stable=True).values. This returns a stable permutation of [0..M-1] in increasing order of the values in flat (for ties, original order is preserved).

Key observation: The stable sort must be performed on the flattened values in the input vector, not on the indices of the 3D structure. My previous attempt mistakenly tried to sort by a “topk_idx” tensor and by keys extracted from topk_idx values; that changes semantics and causes incorrect results. The correct stable sorting is on the values of flat.

Why previous submissions failed
- The evaluation environment reported “INCORRECT_NUMERICAL” for multiple workloads, meaning the computed sorted_token_indices did not match torch.sort(..., stable=True) exactly. The most likely root cause was misinterpreting what is being sorted (sorting on indices vs. values), and also possibly subtle tie-handling bugs.
- Another earlier warning “decoy kernel” suggests that at least one Triton kernel did not perform any meaningful computation or was unused. We must ensure that all Triton kernels launched actually do the work (counts, stable permutation, offsets).

Strategy to fix correctness and satisfy Triton-only requirement
- Implement three Triton kernels that are actually launched and do the necessary work:
  1) counts_and_bases_kernel:
     - For each key k in [0..NUM_EXPERTS), count how many elements in flat equal k.
     - Compute the inclusive prefix sums of counts into offsets_incl (length NUM_EXPERTS). Also store the total_count in a device scalar total_count_ptr.
     - This kernel is launched once, reads flat once, and writes offsets_incl. No torch.bincount is used on the host.
  2) stable_permutation_kernel:
     - For each j in [0..M), compute key_j = flat[j]. Since values are in [0..NUM_EXPERTS-1], key_j is an expert id.
     - base_excl = offsets_incl[key_j - 1] if key_j > 0 else 0. For key 0, base is 0.
     - tie_count = number of previous indices t < j with same key and flat[t] < flat[j] (to preserve original order for ties).
     - rank = base_excl + tie_count. Write sorted_token_indices[j] = rank.
     - This kernel implements torch.sort(stable=True) semantics for sorting by values in flat: ranks are assigned in increasing value order, and for equal values, earlier indices come first.
     - This kernel must be launched once for the entire flat array. It reads flat and produces the permutation. The tie_count loop is O(M) but efficient for typical sizes; it’s correct and simple.
  3) finalize_offsets_kernel:
     - Read counts_and_bases_kernel’s offsets_incl and total_count, and write expert_offsets as:
       - offsets[:NUM_EXPERTS] = offsets_incl[:]
       - offsets[NUM_EXPERTS] = total_count + 1
     - This kernel is launched once, writes the final offsets. No torch.cumsum is used on the host.

- Important points:
  - We must sort by the values in flat, not by indices. The stable permutation is computed solely from flat[j] values, matching torch.sort(stable=True).
  - The tie_count loop uses a vectorized approach per j: for each j, it counts elements before j that have equal key and smaller value. This is simple and deterministic.
  - No torch.sort, torch.bincount, or torch.cumsum is used in forward; only Triton kernels and device-aware allocations.

Performance considerations
- The stable permutation is O(M) with an inner loop that depends on j, but for the typical sizes here (M up to tens of thousands) this is fine and deterministic. We ensure Triton kernels are used and correctness is guaranteed.
- If needed for larger M, we could implement a block-wise parallel scan or a two-pass ranking approach, but correctness is the priority given the evaluation failures.

     - This kernel is launched once with grid = (NUM_EXPERTS,). It reads flat and writes offsets_incl and total_count.

2) Compute the stable permutation indices (sorted_token_indices) without torch.sort:
   - Implement a Triton kernel stable_permutation_kernel that computes ranks for each j in [0..M) using:
     - base_excl = offsets_incl[key_j - 1] if key_j > 0 else 0, where key_j = flat[j].
     - tie_count = number of previous indices t < j with same key and flat[t] < flat[j]. This preserves stable order for ties.
     - rank = base_excl + tie_count. Then sorted_token_indices[j] = rank.
   - Triton does not easily support per-element cross-reduction across the entire array in a single kernel; however, we can avoid that complexity by using the counts_and_bases to get offsets_incl and computing the permutation using torch.sort (which is correct and fast). But the evaluation insists on Triton-only; thus, we implement tie_count via Triton with a block-wise scan:
     - Per chunk of indices handled by a program, compute base_excl, and then for each element j in that chunk, scan the entire flat in fixed-size chunks to count ties:
       - For each chunk, count number of elements t where t < j, key_t == key_j, and vals_t < vals_j. Accumulate into a per-chunk vector acc of size BLOCK. Atomic add into a per-j global tie counter (one int32 per j).
     - This approach avoids looping over M with dynamic bounds inside Triton but uses chunked scanning; it’s correct and deterministic. It is O(M * M_chunk) per element j, but given M in provided workloads is modest (e.g., 2048), and num_experts_per_tok is moderate, it is acceptable. Crucially, this kernel does all heavy work in Triton.
   - The stable_permutation_kernel is launched with grid = (ceil_div(M, BLOCK),) and processes indices in chunks.

3) Finalize expert_offsets:
   - Kernel finalize_offsets_kernel:
     - Copy offsets_incl into expert_offsets[:NUM_EXPERTS].
     - Write total_count + 1 at the end (offsets[NUM_EXPERTS]) using the scalar total_count_ptr.
     - Launch as a tiny 1-program kernel.

This plan ensures:
- All three Triton kernels are launched and perform meaningful work.
- sorted_token_indices and expert_offsets are both produced by Triton. No torch.sort or torch.bincount is used in the forward path.
- Stable sort semantics are matched: equal values preserve original order (ties broken by j), which is exactly torch.sort(stable=True) behavior on the flattened values.

Performance
- counts_and_bases_kernel is O(M + K) (K=256) and very fast.
- finalize_offsets_kernel is O(K) and trivial.
- stable_permutation_kernel does chunked scans and per-element tie counting; while not optimal, for the provided sizes it is acceptable and deterministic. If needed, a more optimized version can be added later (e.g., multi-pass scans, shared-memory block scans), but correctness and compliance with Triton-only are prioritized here.
