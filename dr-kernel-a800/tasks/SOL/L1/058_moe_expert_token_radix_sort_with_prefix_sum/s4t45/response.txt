    - expert_offsets: number of tokens assigned to each expert i, inclusive prefix sum over i in [0..255].

- Optimization strategy:
  1) Sorting in Triton: PyTorch’s GPU sort is highly optimized and robust. Since the evaluation has shown correct results and modest speedup with PyTorch sort, we keep sorting in PyTorch to maintain correctness and avoid in-kernel sorting pitfalls. However, the “no PyTorch data-dependent computation” requirement is challenging for a stable sort in Triton. A robust Triton stable sort is non-trivial and can be error-prone. To strictly adhere to “no PyTorch data-dependent ops,” we will implement a Triton sort for the flattened array. We can use an odd-even transposition sort (bubble sort variant) which is simple and stable: perform NUM_TOKS passes; in each pass, compare adjacent pairs (even phase: (0,1),(2,3)...; odd phase: (1,2),(3,4)...), swap when out of order. We maintain stability by not swapping on equality. This avoids dynamic loops by unrolling via Python loops with compile-time bounds. We pass NUM_TOKS as a constexpr meta-parameter to Triton so the loop bounds are compile-time, which Triton supports.

    We’ll implement two Triton kernels:
    - _odd_even_sort_stable_asc kernel: sorts ascending and returns permutation indices p such that output = indices[p]. We perform NUM_TOKS passes, in each pass load i and i+1, compute min/max with stability (on equal values, do not swap to keep original order), store to out indices, then copy back to indices for the next pass. We maintain p by tracking positions of original indices.
    - After sorting, sorted_token_indices = p.

  2) Per-expert offsets in Triton:
     - First kernel (_hist_kernel): compute counts of each expert id via a Triton histogram. Each program instance processes BLOCK_SIZE elements and atomically increments counts[i] for each element i. This reduces atomics vs per-element atomics.
     - Second kernel (_prefix_sum_inclusive_kernel): compute inclusive prefix sums of counts to produce expert_offsets. Implement a simple two-pass scan with O(NUM_EXPERTS^2) work, which is acceptable for NUM_EXPERTS=256. We initialize offsets[0]=0, then loop i from 0 to NUM_EXPERTS-1 and set offsets[i+1] = offsets[i] + counts[i]. Triton supports scalar loops with constexpr bounds, so this is valid.

- Trade-offs:
  - The Triton sort is O(N^2) but with N up to 2,080,000 in worst cases it’s acceptable and correct. It satisfies the requirement to avoid PyTorch data-dependent ops. The histogram and prefix sum are efficient and Triton-based.
  - Full PyTorch sort was already giving 16/16 correct results. The goal now is to further optimize and strictly avoid PyTorch data-dependent computation. The odd-even sort with compile-time loops should be correct and predictable.
