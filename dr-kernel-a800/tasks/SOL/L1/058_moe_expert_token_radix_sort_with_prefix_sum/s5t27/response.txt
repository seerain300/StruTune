Understanding the original behavior
- Inputs:

- Outputs:

  - expert_offsets: torch.bincount(flat).cumsum(0) + 1, i.e., inclusive counts per expert id plus 1. The expected dtype is torch.int32 with shape (num_experts + 1).

Why the previous attempts failed
- “INCORRECT_DTYPE” on multiple workloads indicates the returned tensors had wrong dtypes: sorted_token_indices was not torch.long (int64), and expert_offsets was not torch.int32 (int32). This is a clear mismatch.
- Earlier “decoy kernel” warnings indicated Triton kernels were defined but not actually doing meaningful work or were not launched. We must ensure:
  - counts_kernel is launched and computes counts of each expert id.
  - scan_inclusive_kernel is launched and computes offsets_incl (inclusive prefix sums of counts).
  - finalize_offsets_kernel is launched and writes expert_offsets correctly.
  - A Triton kernel (stable_permutation_kernel) is launched to produce sorted_token_indices with correct dtype.

Implementation strategy
- Compute counts and prefix sums with Triton:
  - counts_kernel: For each k in [0..NUM_EXPERTS), iterate over flat in BLOCK-sized chunks, count occurrences of k, and store counts[k].
  - scan_inclusive_kernel: Inclusive prefix sum over counts[0..NUM_EXPERTS-1], writing offsets_incl[i] = sum(counts[0..i]).
  - finalize_offsets_kernel: Write expert_offsets of length (NUM_EXPERTS + 1) such that:
    - offsets[0..NUM_EXPERTS-1] = offsets_incl[:]
    - offsets[NUM_EXPERTS] = total_count + 1, where total_count is sum of counts (stored by counts_kernel to a device scalar).
- Produce sorted_token_indices:
  - Implement a Triton kernel stable_permutation_kernel that assigns ranks to each j in [0..M-1] using:
    - key_j = flat[j]
    - base_excl = offsets_incl[key_j - 1] if key_j > 0 else 0
    - tie_count = number of previous indices t < j with same key and flat[t] < flat[j] (this enforces stable ordering by original index for ties).
    - rank = base_excl + tie_count; write sorted_token_indices[j] = rank.
  - Since stable ranks are in [0..M-1] (ascending), convert to torch.long and return.

Performance considerations
- Computing counts and offsets is O(M + K), with K=256, which is efficient.
- Stable ranking is O(M * K) in the worst case but K is small. We can do it in Triton with fixed loops to avoid dynamic loops that previously caused runtime errors.

Caveat: Triton’s best practice avoids dynamic loops over runtime bounds; we use fixed compile-time loops (with known NUM_EXPERTS=256) to ensure robustness and avoid crashes. If needed, further optimizations can use chunked block loops, but for correctness and evaluation, fixed loops with NUM_EXPERTS as constexpr are straightforward and reliable.

    # flat_ptr points to 1D tensor of length M (int32).
    # counts_ptr is length NUM_EXPERTS (int32).
    for e in range(0, NUM_EXPERTS):
        count = tl.zeros((), dtype=tl.int32)
        # Loop over flat in chunks of BLOCK
        for start in range(0, M, BLOCK):
            offs = start + tl.arange(0, BLOCK)
            mask = offs < M
            vals = tl.load(flat_ptr + offs, mask=mask, other=0)  # int32

            count += tl.sum(eq.to(tl.int32), axis=0)
        tl.store(counts_ptr + e, count)
