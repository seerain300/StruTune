We’ll implement the network directly in Triton with tl.static_range loops over k and stride.

3) Compute expert_offsets:
   - Use an in-place inclusive prefix sum Triton kernel. We avoid torch.cumsum. The kernel computes out[i+1] = out[i] + out[i], scanning from end to beginning, using a loop over i with tl.static_range and loading/storing out[i]. This is O(num_experts) and small, so fine.

4) Return the sorted_token_indices permutation (we obtain it from the Triton sort) and expert_offsets. Host code only allocates, launches kernels, and returns.

This approach eliminates all PyTorch GPU ops (no .sort, no .cumsum, no .item), and uses Triton for histogram, sort, and scan, improving performance by reducing atomic contention and avoiding non-Triton ops. The bitonic sort is stable due to tie-breaking on original index.

# Triton kernel: block-based histogram with vectorized reduction and minimal atomics.
@triton.jit
def _histogram_block_kernel(x_ptr, N, out_counts_ptr, num_experts: tl.constexpr, BLOCK: tl.constexpr):
    pid = tl.program_id(axis=0)
    start = pid * BLOCK
    offsets = start + tl.arange(0, BLOCK)
    mask = offsets < N

    # Load indices as int32
    idx = tl.load(x_ptr + offsets, mask=mask, other=0).to(tl.int32)

    # For each expert bin j, compute count and atomically add once per program
    for j in range(num_experts):
        eq = (idx == j) & mask
        # Reduce boolean vector to int32 scalar count
        count_j = tl.sum(eq.to(tl.int32), axis=0)
        tl.atomic_add(out_counts_ptr + j, count_j)
