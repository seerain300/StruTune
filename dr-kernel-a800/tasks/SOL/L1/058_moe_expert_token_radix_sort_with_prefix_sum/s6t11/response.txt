- Design details:

      - For each value j in 0..L-1 (L=num_experts=256), atomically add 1 to local_rank[i] if v == j and local_rank[i] == 0 (to avoid double-counting).
    - Compute counts[j] = number of elements equal to j. We can do this by summing contributions inside the kernel using block-level atomics (per j loop).

However, Triton doesn’t provide dynamic loops over N in a straightforward way for each program; a robust vectorized approach is:
      - First, compute counts for all values (counts is a small vector of size L).
      - Then, compute exclusive prefix sums for counts to get base position per value.
      - Third, iterate j in [0..L-1] in a loop (since L is constexpr 256), and for each index i, if v == j, compute base = sum_{k<j} counts[k], then write out[i] = base + local_rank[i]. This guarantees stability because we process values in increasing order and break ties by local_rank.

    - exclusive_scan_kernel(counts_exp, expert_offsets, 256, N) to produce inclusive offsets and set the last element to N.

- Performance:
  - The Triton sort kernel uses three passes over the data:
    - Pass 1: counts accumulation (atomic add per element).
    - Pass 2: compute exclusive offsets for each value.
    - Pass 3: place each element using counts and local_rank.
  - The complexity per element in pass 3 is O(L) where L=256. With N up to 4096*2080 ~ 8.4M in worst case, this is acceptable and typical for such kernels. The expert offsets use small vectors and are fast.

- Correctness:
  - This approach mirrors a stable counting sort: stable because we process values in increasing order and resolve ties by local_rank (i preserved for duplicates). It will match the original torch.sort(stable=True) behavior for values in [0..255], which is the setup here.
