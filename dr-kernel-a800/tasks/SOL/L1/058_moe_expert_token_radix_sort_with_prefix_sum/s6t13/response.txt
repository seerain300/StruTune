Final analysis, diagnosis, and plan

- Original behavior:
  - topk_idx is generated as int32 with values in [0, num_experts-1], where num_experts=256 by assertion. get_inputs produces tensors on the device.
  - run flattens topk_idx to 1D length N.
  - sorted_token_indices = torch.sort(flat, stable=True)[1] returns the permutation of indices [0..N-1] that would sort the flattened values ascending. With stable=True, ties are broken by original order (i.e., lower original index comes first).
  - expert_offsets = torch.bincount(flat.long(), minlength=num_experts).cumsum(0).to(torch.int32) with expert_offsets[0]=0 gives offsets[e] = inclusive count of elements strictly less than e. offsets[num_experts] == N.

- Constraints:
  - ModelNew.forward must launch Triton @triton.jit kernels for all numerical work. No torch operations (torch.sort, torch.bincount, torch.cumsum, .sum, etc.) in the forward host code.
  - Previously flagged “decoy kernels” occurred because Triton kernels were defined but not launched. We must actually call each Triton kernel from forward.

- Strategy:
  - Implement Triton kernels to:
    1) Produce sorted_token_indices using a stable global counting sort approach:
       - count_values_kernel: counts occurrences of each value 0..255 in flat (since topk_idx values are in [0, 255]).
       - compute exclusive prefix sums to get per-value starting positions.
       - For each index i, read v = flat[i], compute stable local rank r (how many elements with value <= v come before index i). r = sum_{j<i and flat[j] <= v} 1. This preserves stability. This is computed with a block-local reduction using tl.sum and tl.atomic_add.
       - Place index i at position out_pos = offsets[v] + r in the output sorted_token_indices. This yields a stable ascending sort without data-dependent swaps.
    2) Compute expert_offsets:
       - histogram_original_experts_kernel: counts occurrences per expert id 0..255 in the original topk_idx tensor (not in sorted order, but we need counts per expert in the original indices). This histogram is computed from the original topk_idx, not from sorted flat values.
       - exclusive_scan_kernel: compute exclusive prefix sums of these counts to produce offsets[e] for e in 0..255. Set offsets[num_experts] = N. This uses inclusive prefix sum; we initialize the last element to N to satisfy offsets[num_experts] == N.

- Important correctness points:
  - The stable rank r ensures the sort is stable by original index: within equal values, lower original index appears first. We compute r per element using a reduction over the block; ties are handled correctly.
  - The expert offsets must be computed from the original topk_idx, not from the sorted values. Therefore, histogram_original_experts_kernel reads original topk_idx and produces counts; then exclusive_scan_kernel computes prefix sums and writes to offsets.

- Performance:
  - The stable sort approach uses:
    - One global read of flat.
    - One pass of counting per value and computing offsets.
    - One pass to compute stable ranks (atomic per element).
    - One pass to write the output permutation. This is O(N) with reasonable work per element. Triton’s atomics are used for local rank aggregation; this is acceptable and avoids a more complex global sorting network.
  - The expert offsets use two kernels (histogram and scan), both O(N) and simple.

- Integration:
  - ModelNew.forward will:
    - Flatten original topk_idx to orig_flat (int32 1D).
    - Launch count_values_kernel to produce counts_values (int32[256]).
    - Launch compute_exclusive_prefix_sums for values to produce offsets_values (int32[256]).
    - Launch stable_rank_kernel to produce local ranks and write sorted_token_indices (int32[N]).
    - Launch histogram_original_experts_kernel to produce counts_experts (int32[256]) from original topk_idx.
    - Launch exclusive_scan_kernel to produce offsets_experts (int32[257]) from counts_experts, with offsets[256] set to N.
    - Return sorted_token_indices and offsets_experts.

- This plan ensures:
  - All computation is in Triton kernels.
  - No torch operations in forward host code.
  - No decoy kernels: each Triton kernel is actually launched.
  - Correctness for both outputs.
