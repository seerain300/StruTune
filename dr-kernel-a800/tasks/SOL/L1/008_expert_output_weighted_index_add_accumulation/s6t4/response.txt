- What went wrong previously:

  - Perform the clone (copy) explicitly using a Triton kernel: out[i, :] = final_hidden_states[i, :] for all i in [0, batch_seq_len). This ensures the output buffer starts with the same values as the clone.
  - Then perform scatter-add via a simple per-token kernel: out[token_indices[i], :] += expert_outputs[i, :]. This avoids atomics and ensures each token’s contribution is added exactly once to the correct row. Even if token_indices has duplicates, this matches torch.index_add semantics (each source row is added at its index).

- Design choices:
  - Dtypes: keep bfloat16. Triton supports bf16 loads/stores; we’ll use bf16 throughout.
  - Index dtype: Triton prefers int32 for indexing. token_indices are int64 by default; we cast to int32 (safe because batch_seq_len fits in int32 for these workloads).
  - Robustness: The copy kernel uses a straightforward 2D grid (rows, hidden-size tiles) with masking, avoiding any atomic operations and minimizing risk.
  - Performance: While two kernels (copy + scatter-add) may not be as fast as a single atomic-add approach, correctness is paramount. After verifying correctness, we can later optimize by fusing per-token processing or using atomics if the evaluator confirms stability.

import torch
import triton
import triton.language as tl


@triton.jit
def _copy_rows_kernel(
    out_ptr,  # *bf16
    src_ptr,  # *bf16
    M: tl.constexpr,    # number of rows (batch_seq_len)
    N: tl.constexpr,    # hidden_size
    stride_m: tl.constexpr,  # row stride in elements (usually N for contiguous [M, N])
    stride_n: tl.constexpr,  # col stride in elements (usually 1 for contiguous [M, N])
    BLOCK_N: tl.constexpr,   # tile size for columns
):
    row = tl.program_id(0)  # each program handles one row
    col_block = tl.program_id(1)  # each program also handles one column tile
    start = col_block * BLOCK_N
    offs = start + tl.arange(0, BLOCK_N)
    mask = offs < N

    # Compute pointers for source and destination
    src_row_ptr = src_ptr + row * stride_m + offs * stride_n
    out_row_ptr = out_ptr + row * stride_m + offs * stride_n

    # Load and store with masking
    vals = tl.load(src_row_ptr, mask=mask, other=0.0)
    tl.store(out_row_ptr, vals, mask=mask)

def _scatter_add_rows_kernel(
    out_ptr,           # *bf16
    expert_ptr,        # *bf16
    indices_ptr,       # *int32
    M: tl.constexpr,   # batch_seq_len
    N: tl.constexpr,   # hidden_size
    BLOCK_N: tl.constexpr,
):
    pid = tl.program_id(0)  # each program handles one token
    # Load index (row destination) and expert row
    row = tl.load(indices_ptr + pid)  # int32
    # Columns tile
    col_block = tl.program_id(1)
    start = col_block * BLOCK_N
    offs = start + tl.arange(0, BLOCK_N)
    mask = offs < N

    out_row_ptr = out_ptr + row * N + offs

        batch_size, seq_len = None, None  # not needed directly; we can infer batch_seq_len from out

        hidden_size = final_hidden_states.shape[1]
        num_selected_tokens = expert_outputs.shape[0]
        assert expert_outputs.shape[1] == hidden_size, "expert_outputs second dim must match hidden_size"

Summary of the operation
- Original behavior:
  - Clone the accumulation buffer: output = final_hidden_states.clone()
  - Scatter-add along dim=0: output.index_add_(dim=0, token_indices, expert_outputs)
  - This is equivalent to, for each token i:
    output[token_indices[i]] = final_hidden_states[token_indices[i]] + expert_outputs[i]
- In other words, we must first initialize the output with the clone (copy all rows of final_hidden_states into output), and then add each expert_outputs[i] row into the target row indexed by token_indices[i].

Root cause of previous failures
- The earlier Triton attempt relied on atomic_add or vectorized updates across hidden_size. While logically sound, atomic behavior and vectorized masking can be fragile across different Triton versions and shapes, leading to runtime errors and numerical mismatches in some configurations (e.g., hidden_size = 541 or 1879).
- Additionally, ensuring exact behavior with atomics across variable hidden sizes and dtypes (bf16) can be subtle.

Fix: two-kernel approach for robust correctness
- Kernel 1: Copy final_hidden_states into output. This matches the clone semantics exactly and is simple, avoiding any atomics.
- Kernel 2: Scatter-add each expert_outputs[i] row into out[token_indices[i]]. We do this without atomics by using a simple per-token kernel that loads the token index and adds the expert row into the corresponding output row. While duplicates in token_indices will result in multiple additions (which matches torch.index_add behavior), this approach ensures correctness and avoids atomic pitfalls.

Design details
- Device and dtype: All tensors are bfloat16 and on CUDA. Triton kernels use bf16 loads/stores.
- Indexing: token_indices default is int64. Triton prefers int32 for indexing; we cast to int32.
- Tiling: For performance, we tile the hidden dimension with BLOCK_N (e.g., 128 or 256). The grid for each kernel is (rows or tokens, tiles over hidden dimension). Masks ensure we don’t write out-of-bounds.
- No torch computation in host code: only tensor allocation, shape checks, and kernel launches.
