Diagnosis, lessons, and optimization plan

- Behavior recap:
  - We need to implement output = final_hidden_states.clone(); output.index_add_(0, token_indices, expert_outputs). That is, for each i, add the H-vector expert_outputs[i] to the row output[token_indices[i]] using atomic adds. This must be done with Triton (no fallback to torch.index_add).

- What happened:
  - The first correct submission used a simple per-element atomic_add over H within each program. It was robust and correct, but very slow (only ~0.05x speedup).
  - The next attempt tried a more complex tiling strategy (vectorize across hidden dimension, split across tiles). It failed numerical correctness on some workloads, likely due to subtle mask/stride/dtype issues in Triton’s atomic_add across vector lanes for bfloat16 scatter.
  - The latest submission reverted to the simple per-element approach, preserving correctness, but performance remained poor.

- Constraints and choices:
  - We MUST use Triton and actually perform the scatter-add via atomic adds. No torch.index_add in the forward.
  - Maintain correctness across all 16 provided configurations. The earlier “vectorized” attempt shows Triton atomic_add over vector lanes can be fragile with bfloat16 and non-trivial index patterns. Robustness takes priority.

Given the evaluation’s strict correctness requirement, the safest path is to keep a simple, reliable Triton kernel that does per-element atomic adds along the hidden dimension for each source row. While it’s not the fastest, it consistently passes. Once this is solid, future iterations can refine tiling and dtype handling under careful testing.

- Planned kernel:
  - Grid: one program per source row (N programs). Inside each program, loop j from 0 to H-1:
    - Load val = expert_outputs[row, j] as bfloat16.
    - Atomic add to output[token_indices[row], j].
  - This avoids vector masking and ensures correctness. It’s slower but reliable. We can tune num_warps and num_stages slightly, but the dominant cost is atomics.

- Performance notes:
  - This approach issues H atomics per row. While not optimal, it’s consistent. We will choose num_warps=4 and num_stages=2 to improve throughput a bit while keeping code simple.
  - The evaluator has previously shown >1.5x speedup with a different kernel configuration, but it failed on some workloads. We will prioritize correctness and stable behavior. Once verified correct, further tuning can attempt vectorized tiles guarded by meticulous masking and dtype alignment.

Final code: Triton-based ModelNew that performs scatter-add correctly

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_atomic_kernel(
    out_ptr,            # *bfloat16, shape (M, H)
    src_ptr,            # *bfloat16, shape (N, H)
    idx_ptr,            # *int32,    shape (N,)
    M: tl.constexpr,    # rows in output
    H: tl.constexpr,    # hidden size
    N: tl.constexpr,    # number of source rows
):
    # One program handles one source row 'row'
    row = tl.program_id(0)
    # If row >= N, do nothing (defensive; Triton grid will ensure row < N)
    if row >= N:
        return

    # Iterate over hidden dimension and perform atomic add per element
    # H is a constexpr; Triton will unroll or loop as needed.
    for j in range(0, H):
        # Load source value (bfloat16)
        val = tl.load(src_ptr + row * H + j)
        # Load destination row index (int32)
        dst_row = tl.load(idx_ptr + row)
        # Compute output pointer and atomic add
        out_ptr_ij = out_ptr + dst_row * H + j
        tl.atomic_add(out_ptr_ij, val)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton implementation of:
            output = final_hidden_states.clone()
            output.index_add_(0, token_indices, expert_outputs)
        """
        # Ensure contiguity and dtypes
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA"
        out = final_hidden_states.clone()  # mimic original semantics: clone before index_add

        # Triton expects int32 for indices; convert if necessary
        if token_indices.dtype != torch.int32:
            idx_i32 = token_indices.to(torch.int32)
        else:
            idx_i32 = token_indices

        # Ensure expert_outputs is contiguous
        src = expert_outputs.contiguous()
        out = out.contiguous()

        M = out.shape[0]
        H = out.shape[1]
        N = src.shape[0]

        # Launch: one program per row
        grid = (N,)
        scatter_add_rows_atomic_kernel[grid](
            out, src, idx_i32,
            M=M, H=H, N=N,
            num_warps=4, num_stages=2
        )
        return out
```

Notes:
- This kernel uses per-element atomic_add, which is robust and matches PyTorch’s index_add semantics for duplicates. It avoids tricky vectorized atomic patterns that previously caused numerical inconsistencies.
- We clone final_hidden_states and write into out, preserving the original behavior.
- Tensors are made contiguous and indices converted to int32 for Triton.
- The grid is a 1D launch with one program per source row, which is simple and correct. num_warps and num_stages are set modestly; further tuning can attempt vectorization if correctness is validated, but this version prioritizes correctness and stability.
