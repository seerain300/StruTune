We’re consistently correct. The latest speed is ~1.63x. The earlier best was ~2.0x. The slight regression likely came from kernel configuration choices for some shapes. We can try to stabilize and further improve performance by tuning BLOCK and num_warps deterministically at launch and keeping the correct, robust one-program-per-row design.

Recap of the operation
- We must implement: output = final_hidden_states.clone(); then output.index_add_(dim=0, index=token_indices, source=expert_outputs).
- That means for each selected token i (N rows), add expert_outputs[i, :] into output[token_indices[i], :]. Duplicates in token_indices must accumulate.

What we’ve used that is correct
- Launch one Triton program per selected token row (N programs). Each program:
  - Reads its hidden vector (H elements) in BLOCK chunks.
  - Atomically adds those values into the destination row out[token_indices[i], :] in the same BLOCKed chunks.
- This avoids per-element atomics, preserves correctness, and performed well in earlier runs (~2.0x).

Why performance can vary
- BLOCK size and num_warps affect how efficiently each program processes its row. If BLOCK is too large, it increases register pressure and reduces occupancy. If too small, loop overhead and atomics per chunk increase.
- Different H (hidden size) across workloads demand different BLOCK/num_warps settings.

Optimization plan
- Keep the robust “one row per program” approach.
- Choose BLOCK deterministically at launch:
  - BLOCK = next_power_of_two(H), but clamp to a maximum of 128. This balances the number of chunks and per-program resource usage. For typical H up to 1024, this yields 1, 2, 4, 8, 16, 32, 64, 128.
  - For example, H=1024 -> BLOCK=128 -> 8 chunks; H=72 -> BLOCK=128 -> 1 chunk; H=16 -> BLOCK=16 -> 1 chunk.
- Set num_warps based on BLOCK:
  - num_warps=2 for BLOCK<=64
  - num_warps=4 for BLOCK<=128
- Keep num_stages=2 for pipelining.
- Ensure out is a clone of final_hidden_states, token_indices are int32, and tensors are contiguous.

This stabilizes the configuration and should improve or at least maintain speed while preserving correctness.

Final code (ModelNew)
```python
import torch
import triton
import triton.language as tl


@triton.jit
def _index_add_rows_kernel(
    out_ptr,        # *half, final_hidden_states clone (we will write into it)
    expert_ptr,     # *half, expert_outputs (N, H)
    indices_ptr,    # *int32, token_indices (N,)
    N,              # int32, number of selected tokens
    H,              # int32, hidden size
    BLOCK: tl.constexpr,
):
    pid = tl.program_id(axis=0)
    if pid >= N:
        return

    # Destination row index for this selected token
    idx = tl.load(indices_ptr + pid)
    # idx is expected to be in [0, N). We assume token_indices is valid.

    # Process the hidden dimension in BLOCK-sized chunks
    num_chunks = tl.cdiv(H, BLOCK)
    for r in range(0, num_chunks):
        cols = r * BLOCK + tl.arange(0, BLOCK)
        mask = cols < H
        # Load expert vector for this row
        vals = tl.load(expert_ptr + pid * H + cols, mask=mask, other=0.0)
        # Compute destination addresses for this row
        dest_addrs = out_ptr + idx * H + cols
        # Atomic add into output
        tl.atomic_add(dest_addrs, vals, mask=mask)


def _next_power_of_two(n: int) -> int:
    # Returns the next power of two >= n, with n >= 1
    if n <= 1:
        return 1
    return 1 << ((n - 1).bit_length())


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure inputs are on the same device and contiguous
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA"
        # Clone final_hidden_states for accumulation
        out = final_hidden_states.clone()
        # Ensure dtype consistency (inputs are bfloat16 per get_inputs)
        out = out.to(expert_outputs.dtype)
        expert_outputs = expert_outputs.contiguous()
        # Token indices must be int32 for Triton
        if token_indices.dtype != torch.int32:
            token_indices = token_indices.to(torch.int32)
        token_indices = token_indices.contiguous()

        N = expert_outputs.shape[0]
        H = expert_outputs.shape[1]

        # Choose BLOCK deterministically to balance performance and resource usage
        BLOCK = min(_next_power_of_two(H), 128)
        num_warps = 2 if BLOCK <= 64 else 4
        grid = (N,)

        _index_add_rows_kernel[grid](
            out, expert_outputs, token_indices, N, H, BLOCK,
            num_warps=num_warps, num_stages=2
        )
        return out
```

Notes
- This keeps the exact semantics of index_add along dim=0 with accumulation, using Triton for the heavy scatter-add.
- The deterministic BLOCK and num_warps selection aims to improve or stabilize performance across the varied shapes without risking correctness.
- We keep everything Triton-only on the kernel; host code does only necessary tensor setup and launches the kernel.
