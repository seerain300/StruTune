您好。再次感謝評估報告。目前所有工作負載都正確，但速度平均仍然約為 0.65（即 Triton 實現比 PyTorch index_add 慢約 35%）。為了在保持正確性的前提下進一步優化，我們需要減少原子爭用並提高 GPU 並行性。

問題分析
- 操作：給定 output 形狀為 (M, H), expert_outputs 形狀為 (N, H), token_indices 長度 N (值在 [0, M))，執行 scatter-add: output[token_indices[i]] += expert_outputs[i]。這等價於 torch.index_add(dim=0, index=token_indices, source=expert_outputs)。
- 現有 Triton 實現正確，但性能仍低於 PyTorch。主要原因：
  - 2D tiling 没有充分分散同一行的更新，導致同一目標行 (由 token_indices 指定) 上的原子競爭加劇，尤其是在 token_indices 中存在大量重複索引的情況下。
  - 原子操作頻率較高，控制開銷大，尤其是 N 和 H 都不小的情況下。

優化策略
1) 將 grid 的第一維改為直接覆蓋 N (而非 tiling N)：
   - axis 0 = each unique source row n (i.e., each i in [0, N)).
   - axis 1 = tile over H in blocks of BLOCK_H.
   - 這樣每個 program 只處理一行和一段 hidden 特徵，可以更有效率地分散更新並減少與其他行的原子競爭。

2) 調整 BLOCK_H 和 num_warps 以適應不同的 H：
   - H 大時使用較大的 BLOCK_H (如 128), 並設置更多的 warps 來提高並行性。
   - H 小時使用較小的 BLOCK_H (如 64 或 32) 以避免過多無效 masked 加載。

3) 保持 num_stages = 2 作為合理預設，可根據 H 進一步調整，但這裡主要優化並行性和減少原子衝突。

4) 原始 token_indices 是 int64 的，為了在 Triton 中加速索引運算，可以提前轉換為 int32 (由於 M = batch_size * seq_len 通常 <= 2^31 - 1，int32 網址安全)。這不會影響正確性，並且可以加快 Triton 中的地址計算。

核心 Triton 核心
```python
@triton.jit
def scatter_add_n_h_kernel(
    output_ptr,          # *const bfloat16, shape (M, H)
    expert_ptr,          # *const bfloat16, shape (N, H)
    indices_ptr,         # *const int32,     shape (N,)
    N: tl.constexpr,     # number of updates
    H: tl.constexpr,     # hidden size
    BLOCK_H: tl.constexpr,
):
    # Each program handles one source row n, and a block of H features.
    n = tl.program_id(0)
    h_block = tl.program_id(1)

    # Compute the hidden offsets for this block
    h_offsets = h_block * BLOCK_H + tl.arange(0, BLOCK_H)
    mask_h = h_offsets < H

    # Load token index for this row (cast to int64 for address arithmetic)
    idx = tl.load(indices_ptr + n)  # int32
    idx = idx.to(tl.int64)          # target row in output

    # Compute pointers
    # expert row base
    src_base = n * H
    src_ptrs = expert_ptr + src_base + h_offsets
    vals = tl.load(src_ptrs, mask=mask_h, other=0.0)

    # output row base
    out_base = idx * H + h_offsets  # int64 offsets
    out_ptrs = output_ptr + out_base

    # Atomic add the values into output
    tl.atomic_add(out_ptrs, vals, mask=mask_h)
```

ModelNew.forward
```python
class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized scatter-add:
          output[token_indices[i]] += expert_outputs[i] for i in [0, N)
        output has shape (M, H), expert_outputs (N, H), token_indices (N,).
        """
        # Ensure device compatibility: Triton requires CUDA tensors
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be CUDA for Triton"

        # Clone to initialize output; no in-place modifications to the input
        output = final_hidden_states.clone()

        # If token_indices is int64, convert to int32 for faster Triton indexing (safe as long as M < 2^31)
        if token_indices.dtype != torch.int32:
            token_indices = token_indices.to(torch.int32)

        N = expert_outputs.shape[0]
        H = final_hidden_states.shape[1]

        # Heuristic tuning for BLOCK_H and warps
        if H >= 256:
            BLOCK_H = 128
            num_warps = 4
            num_stages = 2
        elif H >= 128:
            BLOCK_H = 128
            num_warps = 4
            num_stages = 2
        elif H >= 64:
            BLOCK_H = 64
            num_warps = 2
            num_stages = 2
        else:
            BLOCK_H = 32
            num_warps = 2
            num_stages = 2

        # Grid: each program handles one source row and one H-block
        grid = (N, triton.cdiv(H, BLOCK_H))

        scatter_add_n_h_kernel[grid](
            output, expert_outputs, token_indices,
            N=N, H=H,
            BLOCK_H=BLOCK_H,
            num_warps=num_warps, num_stages=num_stages,
        )

        return output
```

為什麼這能更快
- 降低原子爭用：每個 program 處理的是不同的 source row (n)，而不是將同一行的多個更新交給不同的 H-blocks 來處理，這有助於減少同一行上的原子競争。尤其是當 token_indices 存在大量重複時，這種設計讓每個重複的行被一個 program 處理，從而減少沖突點。
- 提高 H 方向的並行性：使用較大的 BLOCK_H (如 128) 可以讓每個 program 處理更多的隱藏特徵，在 H 大的場景下提高吞吐量。
- 減少控制開銷：相比於先前逐個 H 特徵進行原子操作的方式，我們採用向量化的 loads 和 atomic_add，一次處理一個 H-block，減少了控制和 loop 開銷。
