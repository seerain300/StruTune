Deep analysis, root cause, and optimization plan

1) What the original PyTorch code computes
- Shapes:
  - final_hidden_states: [M, H], where M = batch_size * seq_len
  - expert_outputs: [N, H], where N = M * num_experts_per_tok
  - token_indices: [N], with values in [0, M)
- Operation:
  - output = final_hidden_states.clone()
  - For each i in [0, N): output[token_indices[i]] += expert_outputs[i]
  - This is exactly torch.index_add(dim=0, index=token_indices, source=expert_outputs) with atomic add semantics when indices repeat.

2) What went wrong in the last attempt
- We changed the Triton mapping to have each kernel program handle multiple source rows (to reduce launch overhead). That increases the number of atomic_add operations and can lead to subtle races or omissions depending on how loops are structured and how Triton schedules work across rows.
- The evaluation shows 0/16 workloads correct with numerical mismatches. The most likely causes are:
  - Duplicate indices and non-associativity of floating-point adds. With multiple rows per program, if partial sums are combined in a different order than PyTorch’s index_add, small numerical differences can accumulate and fail strict correctness checks.
  - Masking/looping logic error in the multi-row loop. Even if rare, mistakes in masked loads/stores or row iteration can cause silent mismatches on some shapes.

3) Fix: revert to the robust, correct per-row mapping
- Revert to a kernel that assigns one Triton program to one source row (grid = N). This approach previously produced 16/16 correct workloads with strong speedups and avoids complex inner loops and multi-row atomics. It matches index_add’s atomic semantics one addition per row.
- Keep the vectorized approach across the hidden dimension H in tiles (BLOCK_H) with masked atomic_add, which is both correct and performant for typical H ≤ 1024.
- Preserve data types and contiguity:
  - final_hidden_states and expert_outputs: torch.bfloat16
  - token_indices: torch.int32 (PyTorch’s index_add typically uses int64; Triton loads int32 efficiently. The test inputs use int64, but Triton will accept int64; we can cast to int32 inside the kernel or convert on host. Casting to int32 is fine for M ≤ 2^31; our M is much smaller. We’ll cast on host to ensure efficiency and avoid any Triton int64 load issues.)
- Heuristics:
  - BLOCK_H: use 256 or 512, num_warps 4 or 8. Earlier results showed 256 with 4 warps gave the best geomean (~2.02x). We’ll use BLOCK_H=256 and num_warps=4, num_stages=2 for consistent performance.
  - Ensure tensors are contiguous and flattened where needed; operate on the 2D [N, H] grid with simple program_id(0) indexing.

4) Performance notes
- While per-row mapping may launch more programs than a multi-row kernel, it proved both correct and fast (~2x speedup). The simplicity reduces risk of subtle bugs and ensures correctness. If needed later, we can revisit multi-row with careful per-dimension atomics, but correctness is the immediate priority.

Final Triton implementation (ModelNew)

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,       # *const bfloat16, shape [M, H]
    src_ptr,       # *const bfloat16, shape [N, H]
    indices_ptr,   # *const int32,    shape [N]
    M: tl.constexpr,   # total rows in output
    H: tl.constexpr,   # hidden size (columns)
    N: tl.constexpr,   # number of source rows to add
    BLOCK_H: tl.constexpr,  # tile size across hidden dim
):
    # One program handles one source row i
    row_i = tl.program_id(0)
    if row_i >= N:
        return

    # Load token index for this row (int32)
    tok = tl.load(indices_ptr + row_i)  # tok in [0, M)

    # Iterate across hidden dimension in tiles
    for col_start in range(0, H, BLOCK_H):
        offs = col_start + tl.arange(0, BLOCK_H)
        mask = offs < H

        # Load source row vector for this tile
        src_vals = tl.load(
            src_ptr + row_i * H + offs,
            mask=mask,
            other=0.0
        )  # bfloat16 vector

        # Atomic add into output at the target row
        tl.atomic_add(
            out_ptr + tok * H + offs,
            src_vals,
            mask=mask
        )


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized scatter-add equivalent of:
            output = final_hidden_states.clone()
            output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        Assumes:
          - final_hidden_states: [M, H], bfloat16, device CUDA
          - expert_outputs: [N, H], bfloat16, device CUDA
          - token_indices: [N], int64 or int32, values in [0, M)
        """
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "Tensors must be on CUDA device"
        assert final_hidden_states.dtype == torch.bfloat16 and expert_outputs.dtype == torch.bfloat16, "dtype must be bfloat16"

        # Make inputs contiguous and prepare dtypes
        out = final_hidden_states.clone()  # clone to match original semantics
        src = expert_outputs.contiguous()
        # Triton prefers int32 indices for atomic addressing; cast safely
        M = out.shape[0]
        N = src.shape[0]
        # token_indices may be int64; cast to int32 (safe for typical M)
        indices_i32 = token_indices.to(torch.int32).contiguous()

        H = out.shape[1]
        # Launch one program per source row
        grid = (N,)

        # Choose tile size and warps
        BLOCK_H = 256  # good balance for H up to 1024
        num_warps = 4
        num_stages = 2

        scatter_add_rows_kernel[grid](
            out, src, indices_i32,
            M, H, N,
            BLOCK_H,
            num_warps=num_warps, num_stages=num_stages
        )

        return out
```

Notes
- This kernel assigns exactly one Triton program per source row and performs masked atomic_add across the hidden dimension in BLOCK_H-sized tiles. It avoids multi-row loops and their potential race/loop issues, which is why it fixes the incorrect numerical results observed.
- It preserves correctness while maintaining strong performance for typical shapes. If later runs still show variance, we can experiment with BLOCK_H=512 and num_warps=4/8, but the above setup previously achieved ~2.0x speedup in correct runs.
- We cast token_indices to int32 for Triton. Given M = batch_size * seq_len and typical sizes in your workloads, M is far below 2^31, so int32 is safe. If you anticipate extremely large M, you can keep indices as int64 and modify the kernel to load int64, but Triton’s atomic_add expects integer addressing and int32 is standard for GPU indices.

Key insight for optimization:
- The operation is a scatter-add along the first dimension: output[index[i]] += src[i] for each i. In your setup, index[i] ∈ [0, M), M = batch_size * seq_len, and src[i] has shape [H] (hidden size).
- Our previous “one program per row” kernel does exactly one atomic add per hidden tile per row, which is correct but may leave performance on the table for some shapes due to high launch count (grid = N). However, attempting to process multiple rows per program risks correctness due to atomic accumulation order and register pressure.
- To improve speed without risking correctness, we can:
  - Keep the per-row mapping (one program per row), but reduce loop iterations by choosing BLOCK_H adaptively as the next power-of-two of H, clamped to [128, 1024]. This makes typical H ≤ 1024 fit in a single tile (one atomic_add vector per row), minimizing loop overhead.
  - Match num_warps to BLOCK_H to maximize parallelism: 4 for ≤256, 8 for 512 or 1024. Use num_stages=2 to pipeline memory operations.
  - Ensure inputs are contiguous and indices are int32 for efficient addressing.

This approach keeps the robustness of the per-row kernel (which already passed all tests) and reduces loop work, yielding better performance consistency.

```python
import torch
import triton
import triton.language as tl


def _select_block_h_and_warps(H: int):
    # Choose BLOCK_H as next power-of-two >= H, clamped to [128, 1024]
    if H <= 128:
        block_h = 128
    else:
        block_h = 1 << (H - 1).bit_length()  # next power of two
        block_h = min(max(block_h, 128), 1024)
    # Heuristic for warps: more warps for larger tiles
    if block_h <= 256:
        num_warps = 4
    elif block_h <= 512:
        num_warps = 8
    else:  # 1024
        num_warps = 8
    return block_h, num_warps


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,       # *const bfloat16, shape [M, H]
    src_ptr,       # *const bfloat16, shape [N, H]
    indices_ptr,   # *const int32,    shape [N]

    H: tl.constexpr,   # hidden size (columns)
    N: tl.constexpr,   # number of source rows to add
    BLOCK_H: tl.constexpr,  # tile size across hidden dim

        mask = offs < H

            mask=mask,
            other=0.0
        )  # bfloat16 vector

            out_ptr + tok * H + offs,
            src_vals,
            mask=mask
        )

    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized scatter-add equivalent of:
            output = final_hidden_states.clone()
            output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        Assumes:
          - final_hidden_states: [M, H], bfloat16, device CUDA
          - expert_outputs: [N, H], bfloat16, device CUDA
          - token_indices: [N], int64 or int32, values in [0, M)
        """
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "Tensors must be on CUDA device"
        assert final_hidden_states.dtype == torch.bfloat16 and expert_outputs.dtype == torch.bfloat16, "dtype must be bfloat16"

        # Make inputs contiguous
        out = final_hidden_states.clone()  # clone to match original semantics
        src = expert_outputs.contiguous()
        M = out.shape[0]
        N = src.shape[0]
        # Triton prefers int32 indices for atomic addressing; cast safely
        indices_i32 = token_indices.to(torch.int32).contiguous()

        H = out.shape[1]
        # Launch one program per source row
        grid = (N,)

        # Choose tile size and warps to minimize loop iterations and maximize parallelism
        BLOCK_H, num_warps = _select_block_h_and_warps(H)
        num_stages = 2

        scatter_add_rows_kernel[grid](
            out, src, indices_i32,
            M, H, N,
            BLOCK_H,
            num_warps=num_warps, num_stages=num_stages
        )

        return out
```

- Adaptive BLOCK_H: We pick the next power-of-two of H, clamped between 128 and 1024. For typical H ≤ 1024, this makes the loop across the hidden dimension run exactly once, reducing atomic operations and loop overhead. For very large H, the loop still handles it correctly.
- Adaptive num_warps: 4 for ≤256, 8 for 512 or 1024. This matches parallelism to tile size and can improve throughput on larger H while maintaining correctness.
- Kept the per-row mapping: This avoids correctness pitfalls from multi-row loops and maintains atomic semantics identical to torch.index_add along dim=0.
