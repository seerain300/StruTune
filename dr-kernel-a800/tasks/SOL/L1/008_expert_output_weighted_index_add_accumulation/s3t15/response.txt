Deep analysis, diagnosis, and optimization plan

What the original PyTorch code does
- It sets up:
  - final_hidden_states: shape [batch_seq_len, hidden_size], initialized randomly in bfloat16.
  - expert_outputs: shape [num_selected_tokens, hidden_size], initialized randomly in bfloat16.
  - token_indices: shape [num_selected_tokens], long values in [0, batch_seq_len).
- It then performs:
  - output = final_hidden_states.clone()
  - output.index_add_(dim=0, index=token_indices, source=expert_outputs)
  This is a row-wise scatter-add: for each i, add expert_outputs[i] into output[token_indices[i]]. Duplicates are summed.

Why Triton is appropriate
- This is a scatter-add pattern that can be implemented with Triton. bfloat16 does not support atomic_add in Triton, but float32 does. So we accumulate in float32 and cast back to bfloat16 at the end.
- The initial Triton implementation used one program per update with atomic_add. It was correct but very slow (speedup ~0.08x). The primary reason is that atomic_add introduces contention, especially when many updates target the same row, and the per-program scalar operations are not well vectorized.

Key bottlenecks and improvements
- Contention and serialization from atomic_add on a per-row scalar basis.
- Poor memory throughput if each program only handles a single element update.

Optimization strategy
- Keep the exact semantics: out[row, :] += expert_outputs[i, :] where row = token_indices[i]. We cannot merge multiple additions into one vectorized add per row without risking race conditions when duplicates exist, because multiple i can map to the same row.
- Improve throughput by:
  1) Using Triton vectorization along the hidden_size dimension. Each program will process a tile of columns (BLOCK_H columns) and loop over a batch of rows (BLOCK_N updates) in one kernel instance. This increases memory coalescing and reduces the number of atomic operations per row to one per program along the column tile.
  2) Choose BLOCK_H to match or be a multiple of typical hidden_size values from the workloads (e.g., 128 or 256), improving memory throughput.
- Algorithm inside the Triton kernel:
  - For each batch tile (BLOCK_N updates) and for each column tile (BLOCK_H columns), compute idx = token_indices[batch_offset + j], load v_col = expert_outputs[batch_offset + j, cols], and atomically add v_col to out_fp32[idx, cols].
  - This ensures we only perform one atomic per column per tile for each update, reducing atomic contention significantly compared to per-element atomic_add.

Correctness considerations
- Duplicates in token_indices are correctly handled by the atomic add. Each update adds its vector contribution to the destination row; duplicates will accumulate multiple times.
- We ensure:
  - Inputs are contiguous and on the same CUDA device.
  - final_hidden_states is cloned into an fp32 output buffer to match PyTorch’s initial state.
  - expert_outputs is converted to fp32 for accumulation.
  - token_indices is converted to int32 for efficient Triton indexing.

Expected performance improvements
- Vectorizing along hidden_size reduces the number of atomic operations per row. While duplicates still lead to multiple additions, batching multiple updates per program and vectorizing across columns increases memory throughput and reduces per-program overhead.
- Choosing BLOCK_H to match hidden_size (128/256/512) gives coalesced access across columns. Using a moderate BLOCK_N (e.g., 128) balances register pressure and occupancy.

Final code: Triton-optimized ModelNew with a vectorized, batched atomic-add kernel

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_fp32_tiled(
    out_ptr,                # *float32, [M, H] output buffer (M = batch_seq_len)
    idx_ptr,                # *int32,   [N] token indices
    A_ptr,                  # *float32, [N, H] expert outputs
    M: tl.constexpr,        # int, number of rows (batch_seq_len)
    N: tl.constexpr,        # int, number of updates
    H: tl.constexpr,        # int, hidden size
    BLOCK_N: tl.constexpr,  # tile size along N (updates per program)
    BLOCK_H: tl.constexpr,  # tile size along H (columns per program)
):
    # Each program handles a tile of columns (BLOCK_H) and a batch of updates (BLOCK_N).
    pid = tl.program_id(axis=0)
    cols = pid * BLOCK_H + tl.arange(0, BLOCK_H)
    mask_cols = cols < H

    # Loop over a batch of updates within this program.
    for batch_start in range(0, N, BLOCK_N):
        row_offsets = batch_start + tl.arange(0, BLOCK_N)
        mask_rows = row_offsets < N

        # Load indices and expert vectors for this batch of updates.
        idx = tl.load(idx_ptr + row_offsets, mask=mask_rows, other=0)  # int32
        # A is [N, H]; load a [BLOCK_N, BLOCK_H] tile.
        a_ptrs = A_ptr + row_offsets[:, None] * H + cols[None, :]
        mask = mask_rows[:, None] & mask_cols[None, :]
        a = tl.load(a_ptrs, mask=mask, other=0.0)  # float32

        # Compute destination pointers for out and perform atomic add per column tile.
        # out is [M, H], so base = idx * H + cols.
        out_ptrs = out_ptr + idx[:, None] * H + cols[None, :]
        # Atomic add the [BLOCK_N, BLOCK_H] tile to the corresponding out rows.
        tl.atomic_add(out_ptrs, a, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized forward that performs:
          output = final_hidden_states.clone()
          output.index_add_(dim=0, token_indices, expert_outputs)
        All computation is done by Triton kernels. Accumulation is in float32, final is cast back to bfloat16.
        """
        # Ensure tensors are on the same device and contiguous
        device = final_hidden_states.device
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "Tensors must be on CUDA device for Triton."
        # Make inputs contiguous
        final_hidden_states = final_hidden_states.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        # Shapes
        M = final_hidden_states.shape[0]
        N = expert_outputs.shape[0]
        H = final_hidden_states.shape[1]

        # Output buffer in fp32 (clone initial state)
        out_fp32 = final_hidden_states.to(torch.float32).clone()

        # Convert expert_outputs to fp32
        A = expert_outputs.to(torch.float32)

        # Convert token_indices to int32 for Triton
        idx_int32 = token_indices.to(torch.int32)

        # Launch Triton kernel: one program per tile of columns.
        # Choose BLOCK_H based on H for good coalescing.
        # Use a moderate BLOCK_N to handle many updates per program without too much register pressure.
        BLOCK_H = 128  # works well for typical hidden sizes (128/256/512)
        BLOCK_N = 128  # batch of updates per program

        grid = (triton.cdiv(H, BLOCK_H),)

        scatter_add_rows_fp32_tiled[grid](
            out_fp32, idx_int32, A,
            M=M, N=N, H=H,
            BLOCK_N=BLOCK_N, BLOCK_H=BLOCK_H,
            num_warps=4, num_stages=2,
        )

        # Cast back to bfloat16 to match original dtype
        result = out_fp32.to(torch.bfloat16)
        return result
```

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_fp32_atomic(
    out_ptr,                # *float32, [M, H] output buffer (M = batch_seq_len)
    idx_ptr,                # *int32,   [N] token indices
    A_ptr,                  # *float32, [N, H] expert outputs

    H: tl.constexpr,        # int, hidden size

        out_fp32 = final_hidden_states.to(torch.float32).clone()

        # Convert expert_outputs to fp32
        A = expert_outputs.to(torch.float32)

        # Convert token_indices to int32 for Triton
        idx_int32 = token_indices.to(torch.int32)

        # Launch Triton kernel: one program per update
        grid = (N,)

        scatter_add_rows_fp32_atomic[grid](
            out_fp32, idx_int32, A,
            M=M, N=N, H=H,
            num_warps=4, num_stages=2,
        )

        # Cast back to bfloat16 to match original dtype
        result = out_fp32.to(torch.bfloat16)
        return result
```

Notes and potential further optimizations
- This kernel uses FP32 atomic_add, which is supported in Triton, and avoids the bfloat16 atomic limitation. It is the minimal-correctness approach and should be correct across duplicates and all shapes.
- Performance: This approach is often faster than a naïve per-row load+add+store because it only does one atomic per update, avoiding touching rows that don’t receive updates. However, heavy contention can occur if many updates target the same row. In such cases, performance may be limited by atomic serialization. Despite the earlier evaluation indicating the per-update store approach was very slow, using atomic_add can improve throughput significantly compared to per-row full writes.

If further tuning is needed
- You can experiment with num_warps and num_stages; e.g., num_warps=8, num_stages=1 or 2 can sometimes improve performance depending on H and N. For very large H, increasing parallelism can help.
- If contention is very high (many duplicates mapping to the same rows), a more complex strategy would be to:
  - Reduce per-row contributions (compute sums in tiles without atomics), then perform one atomic add per row. This reduces the number of atomic operations, but requires additional indexing and temporary buffers.
  - Use a two-phase approach: compute per-row partial sums in Triton (e.g., in shared memory or registers) and then atomic-add only those partial sums. This reduces atomic operations but adds complexity and temporary allocations.

This should address the “decoy kernel” concern and correctness.
