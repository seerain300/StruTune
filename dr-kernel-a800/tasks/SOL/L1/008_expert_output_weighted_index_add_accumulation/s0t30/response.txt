Analysis and optimization plan
- Operation recap: output[token_indices[i]] += expert_outputs[i]. Output is of shape (M, H) where M = batch_size * seq_len; expert_outputs is (N, H) and token_indices is length N.
- Prior kernel: one Triton program per source row n, iterates over H in chunks (BLOCK_H), and performs tl.atomic_add for each chunk. This avoids a 2D grid and keeps code simple. It was faster than baseline and robust, but performance varies with H and distribution of token_indices.
- Bottleneck: atomic contention when many indices point to the same output row. We can’t fully avoid this unless we implement a two-phase reduction per row (block-local reduction + second pass), but that adds complexity and risk. The simpler approach is to increase per-program work and tune launch parameters to better utilize the GPU and reduce loop overhead.
- Improvements:
  - Adaptive BLOCK_H: pick larger chunks for larger H to reduce loop iterations and improve memory throughput. Use 256 for H >= 1024, 128 for H >= 256, 64 otherwise. This keeps vectorized loads/stores efficient without over-allocating registers.
  - Tune num_warps and num_stages based on H: more warps for larger H to improve throughput; modest staging to pipeline loads/stores.
  - Keep the while loop over H; it’s safe with runtime termination and avoids Triton compile-time issues when H varies.
  - Ensure contiguous memory for expert_outputs (row-major) to maximize coalesced loads. In this benchmark setup, expert_outputs is already contiguous; our kernel expects that.
  - Use int32 for token_indices and do address arithmetic in 32-bit; this is fine since M and H in the provided workloads are within int32 range.

Why this helps
- Larger BLOCK_H reduces the number of loop iterations, which decreases control overhead and can reduce the number of atomics issued per program, improving overall performance.
- num_warps/num_stages tuning keeps SMs well-occupied and pipelines memory operations.

Final code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_row_kernel(
    output_ptr,            # *fp16/bf16 pointer, shape [M, H]
    expert_ptr,            # *fp16/bf16 pointer, shape [N, H]
    index_ptr,             # *int32 pointer, shape [N]
    N: tl.constexpr,       # number of source rows
    H: tl.constexpr,       # hidden size (columns)
    BLOCK_H: tl.constexpr  # chunk size over H
):
    pid = tl.program_id(0)  # one program per source row n
    if pid >= N:
        return

    # Load token index for this source row
    idx = tl.load(index_ptr + pid)
    # If idx is out of range (shouldn't happen with provided data), skip
    if idx < 0:
        return

    # Iterate over H in chunks of BLOCK_H
    start = 0
    while start < H:
        offs = start + tl.arange(0, BLOCK_H)
        mask = offs < H

        # Load the corresponding expert_outputs row chunk
        vals = tl.load(expert_ptr + pid * H + offs, mask=mask, other=0.0)

        # Compute linear destination addresses: out[idx, offs] -> idx * H + offs
        dest = idx * H + offs

        # Atomic add into output
        tl.atomic_add(output_ptr + dest, vals, mask=mask)

        start += BLOCK_H


def _choose_launch_params(H: int):
    # Adaptive tuning for performance
    if H >= 1024:
        return 256, 8, 3
    elif H >= 256:
        return 128, 4, 2
    else:
        return 64, 2, 2


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure device and dtypes
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA"
        assert final_hidden_states.shape == (final_hidden_states.shape[0], final_hidden_states.shape[1]), "final_hidden_states must be 2D (M, H)"
        assert expert_outputs.shape[0] == token_indices.shape[0], "expert_outputs and token_indices lengths must match"
        M, H = final_hidden_states.shape
        N = token_indices.shape[0]

        # Make sure expert_outputs is contiguous row-major for coalesced loads
        expert_outputs = expert_outputs.contiguous()

        # Triton kernel expects int32 indices
        if token_indices.dtype != torch.int32:
            token_indices = token_indices.to(torch.int32)

        # Allocate output (clone input to match reference behavior)
        output = final_hidden_states.clone()

        # Launch Triton kernel: one program per source row
        BLOCK_H, num_warps, num_stages = _choose_launch_params(H)
        grid = (N,)

        scatter_add_row_kernel[grid](
            output, expert_outputs, token_indices,
            N=N, H=H, BLOCK_H=BLOCK_H,
            num_warps=num_warps, num_stages=num_stages
        )

        return output
```

Notes
- The kernel uses one program per source row and iterates over H in chunks for coalesced loads and vectorized atomic adds. It avoids 2D grids and compile-time loops over H by using a runtime while loop, which is robust across varying hidden sizes.
- We tune BLOCK_H, num_warps, and num_stages based on H to balance throughput and occupancy. This should further improve the geomean speedup without sacrificing correctness.
- The forward only clones the input and launches the Triton kernel. No PyTorch tensor operations are used in the forward path for computation, satisfying the Triton-only requirement.
