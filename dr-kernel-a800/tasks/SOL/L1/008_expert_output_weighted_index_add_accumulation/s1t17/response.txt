Analysis and plan

- Behavior to implement:
  - We must clone final_hidden_states (shape [M, H], M = batch_size * seq_len) into output and then perform a scatter-add along dim=0 using token_indices (shape [N], N = M * num_experts_per_tok): output[token_indices[i]] += expert_outputs[i], which is equivalent to torch.index_add(dim=0, index=token_indices, source=expert_outputs). Duplicates in token_indices are handled by atomic adds.

- Current status:
  - The Triton kernel that maps one program per source row and vectorizes across the hidden dimension in tiles (BLOCK_H=256), using masked tl.atomic_add, is correct and achieves a strong speedup (~2.02x). This is the best result so far.

- Optimization opportunities:
  - The per-row vectorized approach is robust and fast. Further micro-optimizations that don’t change semantics include:
    - Keep BLOCK_H at 256, which provides one iteration for typical H ≤ 1024 and avoids excessive register pressure. Larger tiles sometimes hurt performance.
    - Use num_warps=4 and num_stages=2, which previously provided best performance for these workloads.
    - Ensure inputs are contiguous and indices are int32. Use masked vector loads/stores and atomic adds to avoid out-of-bounds and maintain correctness for any H.
  - Avoid more complex 2D tiling across M to prevent correctness pitfalls observed earlier; the per-row mapping is already efficient and simple.

- Expected impact:
  - Maintaining the best-performing configuration should keep correctness and performance at or above the current ~2.02x speedup without risking regressions.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,          # *const bfloat16, shape [M, H]
    src_ptr,          # *const bfloat16, shape [N, H]
    indices_ptr,      # *const int32,    shape [N]
    M: tl.constexpr,  # total rows in out_ptr/src_ptr
    H: tl.constexpr,  # hidden size
    BLOCK_H: tl.constexpr,  # tile size along H
):
    # One program per source row
    row = tl.program_id(0)  # 0 <= row < N
    # Load the destination row index (token position)
    dest_idx = tl.load(indices_ptr + row)  # int32

    # Loop over hidden dimension in tiles
    # Triton will unroll this small loop since H is constexpr
    for j in range(0, H, BLOCK_H):
        offsets = j + tl.arange(0, BLOCK_H)  # vector [0..BLOCK_H)
        mask = offsets < H

        # Compute base pointers
        # src_row_ptr: *const bfloat16, length H, starts at src_ptr + row * H
        src_row_ptr = src_ptr + row * H
        out_row_ptr = out_ptr + dest_idx * H

        # Load vector from source row
        vals = tl.load(src_row_ptr + offsets, mask=mask, other=0.0)  # bfloat16

        # Atomic add into output at the selected destination row
        tl.atomic_add(out_row_ptr + offsets, vals, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(
        self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor
    ) -> torch.Tensor:
        # Clone to initialize output with the same values as final_hidden_states
        output = final_hidden_states.clone()

        # Ensure dtypes/devices/contiguity
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "Tensors must be on CUDA for Triton."
        assert final_hidden_states.dtype == torch.bfloat16 and expert_outputs.dtype == torch.bfloat16, "Expected bfloat16 dtype."
        # Make inputs contiguous
        output = output.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous().to(torch.int32)

        M = output.shape[0]  # batch_seq_len
        H = output.shape[1]
        N = expert_outputs.shape[0]

        # Grid: one program per source row
        grid = (N,)

        # Launch Triton kernel; tune for good performance
        scatter_add_rows_kernel[grid](
            output, expert_outputs, token_indices,
            M, H,
            BLOCK_H=256,
            num_warps=4,
            num_stages=2,
        )

        return output
```

Notes:
- The kernel uses one program per source row and vectorized processing along H in tiles of size BLOCK_H=256. This approach balances vectorization and register pressure, achieving strong performance and preserving correctness.
- We ensure proper masking for tails when H is not a multiple of BLOCK_H.
- We keep indices as int32 and bfloat16 for both outputs and inputs, matching the original behavior.
