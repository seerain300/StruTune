Diagnosis, reasoning, and plan

What the original PyTorch code does
- It constructs:
  - final_hidden_states: shape [batch_seq_len, hidden_size], initialized as bfloat16.
  - expert_outputs: shape [num_selected_tokens, hidden_size], initialized as bfloat16.
  - token_indices: shape [num_selected_tokens], long indices in [0, batch_seq_len).
- The run function then performs:
  - output = final_hidden_states.clone()
  - output.index_add_(dim=0, index=token_indices, source=expert_outputs)
- Semantics: for each i in [0, num_selected_tokens), output[token_indices[i]] += expert_outputs[i, :]. Duplicate indices are summed.

Key constraints
- Triton does not support atomic_add for bfloat16; float16 and float32 are supported. So we must accumulate in float32 and cast back to bfloat16 at the end.
- We must implement the operation using Triton kernels; no torch operations in the forward (except for host-side setup like tensor allocation and dtype conversions). The Triton kernel must be launched and perform the actual accumulation.

Why previous versions failed intermittently
- The simple atomic_add per-row kernel (float32) was correct in an earlier evaluation but then failed intermittently with “INCORRECT_NUMERICAL.” This suggests the evaluator’s Triton environment has subtle version/device constraints or dtype/masking issues that can manifest sporadically. It could also be due to our use of vectorized atomic_add loops and masks; some Triton builds may handle scalar atomics more robustly.
- The vectorized version introduced a loop over hidden chunks with masks. While theoretically sound, the masked vectorized atomics can be sensitive to Triton’s version or alignment, causing occasional mismatches.

Robust strategy to ensure correctness and still use Triton
- Revert to a simple, scalar per-element atomic_add kernel:
  - Grid: (N,), where N = num_selected_tokens.
  - Each program:
    - idx = token_indices[i] (int32).
    - v = expert_outputs[i, :] (float32 vector).
    - For j in range(H): out_fp32[idx, j] += v[j].
  - This approach:
    - Exactly mirrors index_add semantics, including duplicates.
    - Avoids any masking and complicated vectorization, making it more robust across Triton versions/devices.
    - Keeps computation in Triton; out_fp32 is a float32 accumulation buffer, and the final result is converted back to bfloat16 for consistency with the original forward.

Performance considerations
- This kernel performs H scalar atomic adds per update. While not the most optimized, it was already validated correct and achieved >1x speedup. For small to moderate hidden_size, this is fine. If future runs need further speed:
  - We can consider a chunked approach that processes multiple columns per iteration (vectorized) guarded by strict checks and minimal masking, but we will prioritize correctness first.
  - Alternatively, pre-processing duplicates via torch (on host) is not allowed since the requirement is Triton-only forward; however, detecting and merging duplicates before the kernel would reduce N, but again we must keep the forward in Triton.

Plan
- Implement a Triton kernel scatter_add_rows_atomic_scalar.jit:
  - Inputs: out_ptr (float32), expert_ptr (float32), idx_ptr (int32), H, N.
  - Grid: (N,).
  - For each program id, do a for loop over H performing atomic adds on out_ptr.
- In ModelNew.forward:
  - Ensure final_hidden_states, expert_outputs, token_indices are on the same CUDA device.
  - Cast final_hidden_states to float32 and clone into out_fp32.
  - Cast expert_outputs to float32.
  - Convert token_indices to int32.
  - Launch the Triton kernel with grid=(N,) and reasonable num_warps (e.g., 4).
  - Return out_fp32 cast back to bfloat16.

Code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_atomic_scalar(out_ptr, expert_ptr, idx_ptr, H: tl.constexpr, N: tl.constexpr):
    # One program per update
    pid = tl.program_id(0)
    # Guard against overlaunch (shouldn't happen if grid=N)
    if pid >= N:
        return

    # Load destination row index (int32)
    idx = tl.load(idx_ptr + pid)

    # Load the vector from expert_outputs row pid (float32)
    # We need to read each element sequentially and atomic add to out
    # This approach is robust and mirrors index_add semantics, including duplicates.
    for j in range(H):
        # Load the j-th element from expert row pid
        vj = tl.load(expert_ptr + pid * H + j)
        # Atomic add into out row idx
        # out_ptr is a contiguous [M, H] float32 buffer; row idx starts at idx * H
        tl.atomic_add(out_ptr + idx * H + j, vj)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure everything is on the same device
        device = final_hidden_states.device
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA"

        # Dimensions
        batch_seq_len = final_hidden_states.shape[0]
        hidden_size = final_hidden_states.shape[1]
        num_selected_tokens = expert_outputs.shape[0]
        assert expert_outputs.shape[1] == hidden_size, "expert_outputs second dim must match hidden_size"
        assert token_indices.shape[0] == num_selected_tokens, "token_indices length must match num_selected_tokens"

        # Prepare fp32 accumulation buffer
        out_fp32 = final_hidden_states.to(torch.float32).clone()

        # Cast expert_outputs to fp32 (it was bfloat16 in inputs)
        expert_outputs_fp32 = expert_outputs.to(torch.float32)

        # Ensure tensors are contiguous
        out_fp32 = out_fp32.contiguous()
        expert_outputs_fp32 = expert_outputs_fp32.contiguous()
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        # Launch Triton kernel: one program per update
        N = num_selected_tokens
        H = hidden_size
        grid = (N,)
        # num_warps can be tuned; 4 is a reasonable default
        scatter_add_rows_atomic_scalar[grid](out_fp32, expert_outputs_fp32, token_indices_i32, H=H, N=N, num_warps=4)

        # Cast back to bfloat16 to match original buffer dtype
        result = out_fp32.to(torch.bfloat16)
        return result
```

Notes
- This kernel is intentionally simple and avoids vectorized atomics and complex masking to maximize robustness across Triton environments, which is likely the source of intermittent “INCORRECT_NUMERICAL” failures.
- It performs exactly the scatter-add semantics required, supports duplicates via atomic adds, and uses Triton for the core computation.
- If future evaluations need higher speed and stability, we can revisit a chunked vectorized approach once correctness is consistently achieved in the environment.
