Given the evaluator’s sensitivity, the safest path is to revert to a proven kernel structure and ensure correctness while making modest performance improvements without risking Triton features that caused previous failures.

What went wrong

- The last version used a large BLOCK_SIZE and relied on tl.program_id(0) + tl.arange(0, BLOCK_SIZE) for row indexing. If BLOCK_SIZE exceeds N (number of rows), pid*BLOCK_SIZE can exceed N-1, and although we guarded with mask, using int32 offsets for very large N can cause undefined behavior or compilation problems. The environment reported runtime errors, which align with exceeding valid bounds and Triton’s pointer arithmetic limitations.

- Earlier, a much simpler kernel with a per-row loop over hidden_size compiled and produced correct results. Although performance was poor, it was stable. We should go back to that approach and improve only safely.

Correctness-first plan

- Ensure we exactly match the PyTorch reference:
  - Clone final_hidden_states before any accumulation. This was crucial for correctness and must be preserved.
  - output.index_add_(dim=0, index=token_indices, source=expert_outputs) semantics are implemented as out[index[i]] += expert_outputs[i, :].

- Triton kernel:
  - Use a 1D grid over rows (N = batch_size * seq_len).
  - For each row i:
    - Compute row_idx = token_indices[i] (assumed int64). We’ll cast to int32 for pointer arithmetic (safe for typical hidden_size and N).
    - Loop j from 0 to hidden_size-1:
      - src_ptr = expert_outputs + i * hidden_size + j
      - dst_ptr = out + row_idx * hidden_size + j
      - atomic_add(dst_ptr, load(src_ptr))
  - This avoids any vectorized pointer arithmetic with tl.arange that previously caused Triton compilation failures. It’s simple and robust.

- Performance considerations:
  - This kernel does one atomic per element. For duplicate indices, that’s necessary. For unique indices, atomics are still executed but only update once per index, which is fine. Given the evaluator previously accepted this structure as correct, we will keep it and ensure compilation stability.
  - We can tune num_warps moderately (e.g., 4) and BLOCK_SIZE default to 1 to keep the kernel simple and avoid over-large grid issues.
  - If future runs permit, a non-atomic scatter kernel for the case where duplicates are rare can be added. However, correctness comes first.

- Strict Triton-only requirement:
  - The forward only allocates tensors, ensures contiguity, and launches the Triton kernel. No PyTorch elementwise operations or index_add_ are used in forward.

Final code (ModelNew)

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,              # *bf16
    expert_ptr,           # *bf16
    indices_ptr,          # *int64 (token_indices)
    N,                    # int32: number of rows to process (sum of token_indices)
    hidden_size,          # int32: size of each row
    BLOCK_SIZE: tl.constexpr,
):
    # Each program handles one row
    pid = tl.program_id(0)
    # Bounds check: if pid >= N, do nothing (defensive, though grid will match N)
    if pid >= N:
        return

    # Load destination row index (token position) for this row
    # indices_ptr is int64 in the input; cast to int32 for pointer arithmetic
    row_idx = tl.load(indices_ptr + pid).to(tl.int32)

    # Loop over hidden dimension and do atomic add
    # This preserves correctness for duplicate row_idx (atomics)
    for j in range(0, hidden_size):
        src_off = pid * hidden_size + j
        dst_off = row_idx * hidden_size + j
        # Atomic add of a single element
        tl.atomic_add(out_ptr + dst_off, tl.load(expert_ptr + src_off))


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor):
        # Match reference: clone the input before accumulation
        out = final_hidden_states.clone()

        # Ensure contiguity and device placement
        # Triton kernels require CUDA tensors
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, \
            "All inputs must be on CUDA for Triton execution."

        # Make sure tensors are contiguous
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        # Shapes
        N = token_indices.numel()  # number of expert outputs
        hidden_size = expert_outputs.shape[1]

        # Launch kernel: one program per row
        grid = (N,)
        scatter_add_rows_kernel[grid](
            out, expert_outputs, token_indices,
            N, hidden_size,
            BLOCK_SIZE=1,  # one row per program; avoid over-large BLOCK_SIZE
            num_warps=4,   # moderate parallelism
        )

        return out
```

Notes

- This kernel uses a per-row loop over hidden_size and performs atomic_add for each element. It avoids the problematic tl.arange vectorization over pointers that previously caused Triton compilation/runtime issues in your environment.
- We keep BLOCK_SIZE=1 to prevent any risk of exceeding row bounds when computing pid * BLOCK_SIZE. The grid is set to (N,), so each program handles exactly one row. This makes the kernel simple and reliable.
- We cast token_indices to int32 for pointer arithmetic. Given typical hidden_size and N from your workloads, this is safe. If you expect extremely large N (e.g., > 2^31 - 1), consider passing indices as int64 and computing offsets in int64; Triton’s atomic_add support is best demonstrated with int32 offsets in this environment. If you do that, you can still load int64 indices and cast to int64 for offsets. However, the provided workloads (e.g., N up to 8192) are well within int32 range.

This version prioritizes correctness and stability based on the evaluator’s previous feedback. If later runs allow, we can add a non-atomic fast path for the case where duplicates are rare, or increase BLOCK_SIZE safely (e.g., up to 1024) if grid is defined per-row, but the above is the safest to avoid runtime errors.
