Analysis and plan

- Task recap
  - We need to implement a scatter-add along the first dimension:
    - output = final_hidden_states.clone(), shape [M, H], M = batch_size * seq_len
    - expert_outputs: shape [N, H], N = M * num_experts_per_tok
    - token_indices: shape [N], values in [0, M)
    - For each i in [0, N): output[token_indices[i]] += expert_outputs[i]
    - Equivalent to torch.index_add(dim=0, index=token_indices, source=expert_outputs), which uses atomic adds when there are duplicates in token_indices.

- Current status
  - The previous submission reverted to a robust, per-row Triton kernel (one program per source row), vectorizing across H with BLOCK_H=256, num_warps=4, num_stages=2, and masked atomic_add. It is correct and delivered ~1.64x speedup.

- Why performance may vary
  - Performance depends on H and the GPU’s SM occupancy. Using BLOCK_H=256 processes one tile per row. If H is small (e.g., 128), this leads to a lot of masked work (loading/storing zeros for out-of-range lanes). If H is large (e.g., 1024), it performs two iterations (BLOCK_H=256), incurring loop overhead.
  - The earlier best result (~2.02x) used BLOCK_H=256 as well, but exact performance can fluctuate with the evaluation harness and the specific workload. Our goal is to keep correctness and further improve performance without risking regressions.

- Optimization strategy
  - Keep the per-row mapping for correctness and simplicity.
  - Dynamically select BLOCK_H and launch parameters to reduce loop iterations when H is large, and avoid excessive masked lanes when H is small:
    - Choose BLOCK_H as the smallest power of two from a set {256, 512, 1024} that is ≥ H, capped at 1024. This reduces the number of loop iterations and masked lanes. For example:
      - H ≤ 256 → BLOCK_H=256 (1 iteration)
      - H ≤ 512 → BLOCK_H=512 (1 iteration)
      - H ≤ 1024 → BLOCK_H=1024 (1 iteration)
      - Otherwise → fallback to 1024 and loop over tiles.
    - Select num_warps based on BLOCK_H to balance occupancy:
      - BLOCK_H ≤ 256 → num_warps=4
      - BLOCK_H ≤ 512 → num_warps=4 (some variants use 8; we keep 4 to avoid over-subscription on small tiles)
      - BLOCK_H ≤ 1024 → num_warps=8
    - Keep num_stages=2 to improve pipelining.
  - Maintain contiguity and dtypes:
    - final_hidden_states and expert_outputs: bfloat16
    - token_indices: int32
    - Proper masks for the H tail when H is not divisible by BLOCK_H.

- Expected impact
  - For H=1024, this reduces to a single tile per row (no loop iterations), which should improve throughput compared to BLOCK_H=256 (two iterations). For smaller H, the overhead is minimized. Overall, we should see performance closer to the earlier ~2.02x speedup while preserving correctness.

Final code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,          # *const bfloat16, shape [M, H]
    src_ptr,          # *const bfloat16, shape [N, H]
    indices_ptr,      # *const int32,    shape [N]
    M: tl.constexpr,  # total rows in out_ptr/src_ptr
    H: tl.constexpr,  # hidden size
    BLOCK_H: tl.constexpr,  # tile size along H
):
    # Each program handles one source row (i in [0, N))
    row = tl.program_id(0)  # index i
    if row >= N:
        return

    # Load target index for this row
    tok = tl.load(indices_ptr + row)  # int32
    # Compute base offsets for output and source rows
    # out is [M, H], src is [N, H]
    # We need to add src[row, :] to out[tok, :]
    # But we process along H in tiles

    # Loop over H in tiles
    for h_start in range(0, H, BLOCK_H):
        offs = h_start + tl.arange(0, BLOCK_H)  # vector of H offsets
        mask = offs < H

        # Load src[row, offs] with masking
        src_vals = tl.load(src_ptr + row * H + offs, mask=mask, other=0.0)  # bfloat16
        # Atomic add into out[tok, offs]
        out_add_ptr = out_ptr + tok * H + offs
        tl.atomic_add(out_add_ptr, src_vals, mask=mask)


def _select_block_h_and_warps(H: int):
    # Choose BLOCK_H and num_warps heuristically to minimize loop iterations
    # Prefer single-tile for H <= 1024
    if H <= 256:
        block_h = 256
    elif H <= 512:
        block_h = 512
    elif H <= 1024:
        block_h = 1024
    else:
        # For very large H, still use 1024 tiles; loop in kernel
        block_h = 1024

    # Heuristic for num_warps
    if block_h <= 256:
        num_warps = 4
    elif block_h <= 512:
        num_warps = 4
    else:
        num_warps = 8

    return block_h, num_warps


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure dtypes and contiguity
        assert final_hidden_states.dtype == torch.bfloat16 and expert_outputs.dtype == torch.bfloat16
        assert token_indices.dtype == torch.int32, "token_indices must be int32"
        out = final_hidden_states.clone()
        # Make tensors contiguous to simplify pointer arithmetic
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        M = out.shape[0]
        N = expert_outputs.shape[0]
        H = out.shape[1]
        assert expert_outputs.shape[1] == H, "expert_outputs second dimension must match hidden size"

        # Launch Triton kernel: one program per source row
        BLOCK_H, num_warps = _select_block_h_and_warps(H)
        grid = (N,)
        scatter_add_rows_kernel[grid](
            out, expert_outputs, token_indices,
            M, H, BLOCK_H,
            num_warps=num_warps,
            num_stages=2,
        )
        return out
```

Notes:
- The kernel uses one program per source row and vectorizes across H in tiles. This preserves correct atomic semantics and avoids cross-row dependencies.
- We dynamically choose BLOCK_H to minimize the number of loop iterations when possible (e.g., H=1024 → single tile). The heuristics for num_warps aim to keep good occupancy without oversubscribing for small tiles.
- Tensors are made contiguous and dtypes are enforced for correctness. The masking ensures no out-of-bounds access in the H tail.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,          # *const bfloat16, shape [M, H]
    src_ptr,          # *const bfloat16, shape [N, H]
    indices_ptr,      # *const int32,    shape [N]
    M: tl.constexpr,  # number of rows in output (not used but kept for clarity)
    H: tl.constexpr,  # hidden size
    BLOCK_H: tl.constexpr,  # tile size along H
):
    # Each program handles one source row (i in [0, N))
    row = tl.program_id(0)
    if row >= N:
        return

    # Load the target token index for this row
    tok = tl.load(indices_ptr + row)  # int32

    # Iterate over H in tiles of size BLOCK_H
    for h_start in range(0, H, BLOCK_H):
        offs = h_start + tl.arange(0, BLOCK_H)  # vector of H offsets
        mask = offs < H

        # Load expert outputs for this row at these H offsets
        src_vals = tl.load(src_ptr + row * H + offs, mask=mask, other=0.0)  # bfloat16

        # Atomic add into the output at row tok
        out_add_ptr = out_ptr + tok * H + offs
        tl.atomic_add(out_add_ptr, src_vals, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Validate dtypes and contiguity
        assert final_hidden_states.dtype == torch.bfloat16, "final_hidden_states must be bfloat16"
        assert expert_outputs.dtype == torch.bfloat16, "expert_outputs must be bfloat16"
        assert token_indices.dtype == torch.int32, "token_indices must be int32"

        # Ensure tensors are contiguous
        out = final_hidden_states.clone()
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        M = out.shape[0]
        N = expert_outputs.shape[0]
        H = out.shape[1]
        assert expert_outputs.shape[1] == H, "expert_outputs second dimension must match hidden size"

        # Launch Triton kernel: one program per source row
        BLOCK_H = 256  # fixed tile size for robust performance
        grid = (N,)
        scatter_add_rows_kernel[grid](
            out, expert_outputs, token_indices,
            M, H, BLOCK_H,
            num_warps=4,   # good balance for BLOCK_H=256
            num_stages=2,  # pipeline loads/stores
        )
        return out
```

- Fixed configuration (BLOCK_H=256, num_warps=4, num_stages=2) is chosen to deliver consistent speedups across varied H, M, and N without risking correctness
