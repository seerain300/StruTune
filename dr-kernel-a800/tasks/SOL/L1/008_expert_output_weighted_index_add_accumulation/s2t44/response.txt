- The Triton approach we use:
  - Launch one program per selected token row i (N programs).
  - Each program reads its hidden vector in BLOCK chunks and atomically adds into the destination row out[token_indices[i], :] in BLOCK chunks.
  - This avoids per-element atomics and preserves correctness.

Why performance may vary and our plan
- Performance depends on BLOCK size and num_warps. Too large BLOCK increases register pressure; too small increases loop/atomic overhead.
- We’ll keep the robust “one row per program” approach and choose BLOCK deterministically:
  - BLOCK = min(next_power_of_two(H), 256). This caps BLOCK at 256 and minimizes the number of chunks for larger H (e.g., H=1024 -> 4 chunks), while keeping tails masked for smaller H.
  - Set num_warps=4 for BLOCK<=128, and num_warps=8 for BLOCK=256. Keep num_stages=2 for pipelining.
- Ensure out is a clone of final_hidden_states, token_indices are int32, and tensors are contiguous. Maintain masked loads/stores for tails.

This deterministic configuration avoids autotune variance and should stabilize and slightly improve performance compared to the last submission.
