Careful diagnosis and plan

- Operation recap: The original forward does a row-wise scatter-add:
  - final_hidden_states has shape [batch_seq_len, hidden_size].
  - expert_outputs has shape [num_selected_tokens, hidden_size].
  - token_indices has shape [num_selected_tokens], with values in [0, batch_seq_len).
  - Output is created by cloning final_hidden_states, then for each i: output[token_indices[i]] += expert_outputs[i].

- Triton suitability: This is a classic scatter-add, ideal for a GPU kernel. The main constraint is atomic_add support: Triton supports atomic_add for float32 and float16, not bfloat16. So we should accumulate in float32, and cast back to bfloat16 at the end.

- Why previous submissions failed: The evaluator reported “RUNTIME_ERROR” for all workloads. Even though the kernel logic looked correct, different Triton versions/devices can be sensitive to:
  - Using atomic_add with fp32, while pointer types are fp32. In some Triton versions, explicit atomic_add might not be as robust across environments. A safer pattern is to load the destination vector, add, and store it back — avoiding atomics. Since we are performing the operation once per row (no overlaps), a load-add-store per row is correct and avoids atomic pitfalls.
  - Kernel signature requirements, constexpr usage, type mismatches, and pointer arithmetic can cause Triton to fail at JIT time or runtime. To minimize risk, we’ll use a simple kernel with explicit int64 indexing and keep the grid size one program per update.

- Strategy to fix correctness first:
  - Do not use tl.atomic_add. Implement a Triton kernel that:
    - Iterates per token i (one program per token).
    - Loads the hidden vector for that token (output_row = output[token_indices[i]]), adds the corresponding expert_output vector (A[i, :]), and stores it back.
    - We will handle bfloat16 by upcasting to float32 for computation, and then returning float32. However, the original code returns bfloat16. We can simply cast the final output to bfloat16 at the end. This avoids any Triton dtype limitations and keeps the Triton kernel simple and robust.
  - This ensures the Triton kernel computes the exact result without atomics and is less likely to fail. Once correctness is established, we can revisit an atomic-based kernel for performance.

- Performance note:
  - One program per token means we launch N programs (N = num_selected_tokens). Each program does a vector load and store of length H. This is fine and should be fast, especially because N can be large but H is typically moderate. It avoids atomics and should be robust across evaluator setups. If later needed, we can optimize to group updates or use atomics once correctness is confirmed.

Implementation details

- Host code:
  - Ensure tensors are on CUDA and contiguous.
  - Convert final_hidden_states to fp32 and allocate out_fp32 as a clone of final_hidden_states in fp32.
  - Convert expert_outputs to fp32.
  - Convert token_indices to int32 for the Triton kernel (Triton’s indexing typically works with int32; we’ll cast to int64 inside the kernel to address row offsets).
  - Launch a Triton kernel with grid size (N,), each program handles one token.
  - Return out_fp32 cast to bfloat16 to match original behavior.

- Triton kernel (no atomics):
  - Parameters: out_ptr (fp32), A_ptr (fp32), idx_ptr (int32), N, H.
  - Use pid = tl.program_id(0).
  - Load idx = idx_ptr[pid].
  - Compute offsets = pid * H + arange(0, H).
  - Load out_vec = tl.load(out_ptr + idx * H + offsets).
  - Load A_vec = tl.load(A_ptr + offsets).  # A is [N, H], contiguous, so offsets suffice.
  - out_vec += A_vec.
  - Store tl.store(out_ptr + idx * H + offsets, out_vec).

This avoids any atomic_add and should be more stable. It also upcasts computation to fp32 to avoid Triton dtype limitations.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,        # *fp32, shape [batch_seq_len, H]
    A_ptr,          # *fp32, shape [N, H]
    idx_ptr,        # *int32, shape [N]
    N, H,           # int32
):
    # One program per token (row addition)
    pid = tl.program_id(0)
    # Bounds check is not needed because grid is exactly N
    # Load destination row index
    row_idx = tl.load(idx_ptr + pid)
    # Cast row_idx to 64-bit for pointer arithmetic
    row_idx64 = row_idx.to(tl.int64)
    H64 = tl.full((), H, tl.int64)

    # Vector of column offsets for this hidden size
    cols = tl.arange(0, H)
    cols64 = cols.to(tl.int64)

    # Compute base pointers
    out_row_ptr = out_ptr + row_idx64 * H64
    A_row_ptr = A_ptr + pid * H  # A is [N, H] contiguous

    # Load current row values from out and add A_row, then store back
    out_vec = tl.load(out_row_ptr + cols64)
    A_vec = tl.load(A_row_ptr + cols64)
    out_vec = out_vec + A_vec
    tl.store(out_row_ptr + cols64, out_vec)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure we are on CUDA
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA for Triton."
        # Shapes
        batch_size, seq_len = final_hidden_states.shape[0] // 0, final_hidden_states.shape[1]  # hidden_size is second dim
        H = final_hidden_states.shape[1]
        N = expert_outputs.shape[0]
        assert token_indices.numel() == N, "token_indices length must equal number of expert outputs."

        # Make inputs contiguous
        final_hidden_states = final_hidden_states.contiguous()
        token_indices = token_indices.contiguous()

        # Allocate fp32 output buffer: clone final_hidden_states in fp32 for correctness
        out_fp32 = final_hidden_states.to(torch.float32).clone()

        # Convert expert_outputs to fp32 for computation
        A_fp32 = expert_outputs.to(torch.float32).contiguous()

        # Triton expects int32 indices; we keep them in device memory
        idx_i32 = token_indices.to(torch.int32).contiguous()

        # Launch one program per token
        grid = (N,)
        scatter_add_rows_kernel[grid](
            out_fp32, A_fp32, idx_i32,
            N, H,
            num_warps=1,
        )

        # Cast back to bfloat16 to match original
        output = out_fp32.to(torch.bfloat16)
        return output
```

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_atomic_rows_kernel(
    out_ptr,        # *fp32, shape [batch_seq_len, H]
    A_ptr,          # *fp32, shape [N, H]
    idx_ptr,        # *int32, shape [N]
    N,              # int32
    H: tl.constexpr # compile-time hidden size for vectorization
):

    # Load destination row index for this token
    row_idx = tl.load(idx_ptr + pid)

    row_idx64 = row_idx.to(tl.int64)

    # Column offsets
    cols = tl.arange(0, H)
    cols64 = cols.to(tl.int64)

    # Base pointers for output row and A row
    out_row_ptr = out_ptr + row_idx64 * H
    A_row_ptr = A_ptr + pid * H  # A is [N, H] contiguous

    # Load current values of out row and add A row (vector)
    out_vec = tl.load(out_row_ptr + cols64)
    A_vec = tl.load(A_row_ptr + cols64)
    out_vec = out_vec + A_vec

    tl.atomic_add(out_row_ptr + cols64, A_vec)
```
