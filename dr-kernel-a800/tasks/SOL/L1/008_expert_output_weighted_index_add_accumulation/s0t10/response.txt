- Reducing the number of atomics: Instead of issuing an atomic add per hidden element, process multiple hidden elements per program in vectorized blocks and perform a single atomic add for the whole block when possible. This reduces contention and improves throughput.
- Increasing parallelism and tiling: Use a 2D grid that tiles over both the N (num_selected_tokens) and H (hidden_size) dimensions, handling many rows and hidden chunks concurrently. Ensure proper masking for boundaries.
- Autotuning: Provide multiple Triton configurations with different BLOCK_N, BLOCK_H, num_warps, and num_stages to allow Triton to pick the best-performing kernel based on input shapes at runtime.

Design and plan

Operation recap:
- Output shape: (M, H), where M = batch_size * seq_len.
- expert_outputs shape: (N, H), where N = M * num_experts_per_tok.
- token_indices: 1D int64 of length N, values in [0, M).
- We need output[row, :] += expert_outputs[i, :] for each i where row = token_indices[i]. PyTorch’s index_add performs this with atomics.

Optimization strategy:
- Kernel grid:
  - axis 0 over N in blocks of BLOCK_N.
  - axis 1 over H in blocks of BLOCK_H.
- Each program handles a tile of size (BLOCK_N, BLOCK_H). For each row n in the tile:
  - Load idx = token_indices[n], the destination row in output.
  - Load vals = expert_outputs[n, h_offsets], where h_offsets = h_block * BLOCK_H + arange(BLOCK_H), masked by h_offsets < H.
  - Compute dest_offsets = idx * H + h_offsets.
  - Use tl.atomic_add(output_ptr + dest_offsets, vals, mask=mask_h) to add the entire block at once. This reduces the number of atomics by BLOCK_H compared to per-element atomic adds.
- Autotune:
  - Provide several configurations like (BLOCK_N, BLOCK_H, num_warps, num_stages): (64, 128, 8, 2), (64, 64, 4, 2), (128, 64, 8, 2), (32, 128, 4, 2), (128, 128, 8, 2).
  - Triton will pick the best based on runtime performance.

Why this should help:
- Vectorized block additions dramatically reduce the number of atomic operations, which are typically the bottleneck in scatter-add. Processing BLOCK_H features at a time per program yields fewer atomics and better GPU throughput.
- Autotuning adapts the kernel to varying H and N sizes across workloads, improving performance robustly.

Final code (ModelNew with Triton-optimized scatter-add)

```python
import torch
import triton
import triton.language as tl


@triton.autotune(
    configs=[
        triton.Config({"BLOCK_N": 64, "BLOCK_H": 128, "num_warps": 8, "num_stages": 2}),
        triton.Config({"BLOCK_N": 64, "BLOCK_H": 64, "num_warps": 4, "num_stages": 2}),
        triton.Config({"BLOCK_N": 128, "BLOCK_H": 64, "num_warps": 8, "num_stages": 2}),
        triton.Config({"BLOCK_N": 32, "BLOCK_H": 128, "num_warps": 4, "num_stages": 2}),
        triton.Config({"BLOCK_N": 128, "BLOCK_H": 128, "num_warps": 8, "num_stages": 2}),
    ],
    key=["N", "H"],
)
@triton.jit
def scatter_add_blocks_kernel(
    output_ptr,          # *pointer* to output [M, H] in bfloat16
    expert_ptr,          # *pointer* to expert_outputs [N, H] in bfloat16
    indices_ptr,         # *pointer* to token_indices [N] int64
    N: tl.constexpr,     # number of source rows
    H: tl.constexpr,     # hidden size (columns)
    BLOCK_N: tl.constexpr,
    BLOCK_H: tl.constexpr,
):
    # program ids
    pid_n = tl.program_id(axis=0)  # over N tiles
    pid_h = tl.program_id(axis=1)  # over H tiles

    # offsets for rows and hidden
    n_offs = pid_n * BLOCK_N + tl.arange(0, BLOCK_N)              # [BLOCK_N]
    h_offs = pid_h * BLOCK_H + tl.arange(0, BLOCK_H)              # [BLOCK_H]

    # masks
    mask_n = n_offs < N                                           # [BLOCK_N]
    mask_h = h_offs < H                                           # [BLOCK_H]

    # load token indices for these rows
    # indices are int64 in input; Triton will load them as 64-bit
    idx = tl.load(indices_ptr + n_offs, mask=mask_n, other=0)     # [BLOCK_N], int64
    # derive destination addresses: idx * H + h_offs
    # broadcasting: [BLOCK_N, BLOCK_H]
    dest_offsets = idx[:, None] * H + h_offs[None, :]             # [BLOCK_N, BLOCK_H]

    # load expert outputs for these rows and hidden offsets
    vals = tl.load(
        expert_ptr + n_offs[:, None] * H + h_offs[None, :],
        mask=mask_n[:, None] & mask_h[None, :],
        other=0.0,
    )  # [BLOCK_N, BLOCK_H], bfloat16

    # atomic add into output
    tl.atomic_add(output_ptr + dest_offsets, vals, mask=mask_n[:, None] & mask_h[None, :])


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Perform output[row] += expert_outputs[i] for each i, where row = token_indices[i].
        Triton kernel does the scatter-add with block-wise atomics. Entry point expected to be 'forward'.
        """
        # Ensure dtype and device compatibility
        assert expert_outputs.dtype == torch.bfloat16, "expert_outputs must be bfloat16"
        assert final_hidden_states.dtype == torch.bfloat16, "final_hidden_states must be bfloat16"
        assert token_indices.dtype in (torch.int32, torch.int64), "token_indices must be int32 or int64"
        # Clone to preserve original buffer semantics (index_add starts from scratch)
        output = final_hidden_states.clone()

        # Shapes
        M, H = output.shape
        N = expert_outputs.shape[0]

        # Launch Triton kernel over tiles of N and H
        # Note: Triton grid depends on meta-parameters BLOCK_N, BLOCK_H provided via autotune
        def grid(meta):
            return (triton.cdiv(N, meta["BLOCK_N"]), triton.cdiv(H, meta["BLOCK_H"]))

        scatter_add_blocks_kernel[grid](
            output, expert_outputs, token_indices,
            N, H,
        )

        return output
```

Notes
- The Triton kernel processes a tile of BLOCK_N rows and BLOCK_H hidden features per program. It loads the token indices, computes destination offsets, loads the expert outputs for the block, and performs a single atomic_add for the entire block. This reduces the number of atomic operations compared to per-element atomics, which should improve performance while preserving correctness.
- Autotuning provides multiple configurations so Triton can pick the best performing one based on N and H, which vary across the evaluator’s workloads.
- We do not use any PyTorch tensor ops (like index_add) in the forward path; the main computation is done by the Triton kernel. The clone is required to match the original semantics where the accumulation buffer starts from the random initialization rather than zeros.

This approach targets the primary bottleneck (atomic contention and per-element overhead) and should further improve performance without compromising correctness.
