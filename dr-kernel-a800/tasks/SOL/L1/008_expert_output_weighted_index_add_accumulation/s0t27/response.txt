Thank you for the feedback. We have correctness across all 16 workloads, but performance is still below 1.0. The current kernel uses atomic_add for each tile across N and H. While simple and correct, it can suffer from atomic contention when many indices map to the same output row and from per-tile control overhead. To improve speed, we should reduce atomic operations and increase per-program work, while still supporting arbitrary shapes without runtime errors.

Performance diagnosis and plan
- Operation: output[token_indices[i]] += expert_outputs[i], with output shape (M, H), expert_outputs shape (N, H), token_indices length N. This is scatter-add along dim=0.
- Prior kernel: 2D tiling over (N, H tiles), each program atomically adds one H-block for a given n. Correct, but each program does relatively little work and uses atomics per element. When there are duplicates in token_indices, many programs contend on the same output row.
- Optimization strategy:
  - Use a single-program-per-source-row kernel: each Triton program processes one source row n and performs atomic adds for all H in that row. This reduces the number of programs (grid size becomes N) and increases per-program work. It also enables us to vectorize across H in chunks (BLOCK_H), improving memory throughput. It still relies on atomics per H element, but with fewer programs, the GPU can execute each program faster, potentially improving overall performance.
  - Avoid using H as a compile-time constant in Triton; we will loop over H in chunks using a runtime-controlled while loop: start = 0; while start < H: load H-chunk, compute destinations, atomic_add. Triton supports while loops with runtime conditions. This avoids the previous runtime error and keeps correctness.
  - Choose BLOCK_H and num_warps based on H to balance occupancy and memory bandwidth.

Why this should be faster
- Fewer programs (N instead of N*ceil_div(H, BLOCK_H)) reduce scheduling overhead.
- Each program handles an entire source row and performs vectorized loads/stores across H chunks, which improves throughput and reduces per-element overhead.
- Atomic contention is still present if many indices are the same, but with fewer programs, each program has more work to do, and the GPU’s vector lanes can process multiple H chunks efficiently.

Final code
- We implement a Triton kernel that:
  - For each program_id(0) = n (source row), loads idx = token_indices[n] and processes H in chunks of BLOCK_H.
  - Loads vals = expert_outputs[n, h_offsets] for a vector of H offsets, computes dest = idx * H + h_offsets, and performs tl.atomic_add into output.
  - Uses a while loop to iterate over H in chunks, with a mask for the last partial chunk.

Code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_row_atomic_kernel(
    output_ptr,            # *fp16/bf16 pointer to output tensor [M, H]
    expert_outputs_ptr,    # *fp16/bf16 pointer to expert_outputs tensor [N, H]
    token_indices_ptr,     # *int32 pointer to token_indices tensor [N]
    N: tl.int32,           # number of source rows (N)
    H: tl.int32,           # number of hidden features (H)
    BLOCK_H: tl.constexpr, # tile size for H dimension
):
    pid_n = tl.program_id(0)  # program processes one source row n = pid_n
    if pid_n >= N:
        return

    # Load the destination row index for this source row
    # token_indices are int64 in PyTorch; cast to int32 for Triton math
    idx = tl.load(token_indices_ptr + pid_n)
    idx = idx.to(tl.int32)

    # Base pointer for this row in output: output[idx, :]
    # We'll compute addresses as idx * H + h_offsets
    start = 0
    # Process H in chunks of BLOCK_H
    while start < H:
        h_offsets = start + tl.arange(0, BLOCK_H)  # vector of H offsets
        mask = h_offsets < H

        # Load vals from expert_outputs[n, h_offsets]
        vals = tl.load(expert_outputs_ptr + pid_n * H + h_offsets, mask=mask, other=0.0)

        # Compute output addresses and perform atomic add
        dest = idx * H + h_offsets
        tl.atomic_add(output_ptr + dest, vals, mask=mask)

        start += BLOCK_H


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-only forward that performs scatter-add:
          output[token_indices[i]] += expert_outputs[i]
        Input tensors:
          - final_hidden_states: (M, H) fp16/bf16
          - expert_outputs: (N, H) fp16/bf16
          - token_indices: (N,) int64
        """
        # Ensure device and dtype compatibility
        if final_hidden_states.device != expert_outputs.device or final_hidden_states.device != token_indices.device:
            raise RuntimeError("All tensors must be on the same device.")
        if token_indices.dtype != torch.long:
            token_indices = token_indices.to(torch.long)

        # Clone to preserve original buffer (like the original run)
        output = final_hidden_states.clone()

        M, H = output.shape
        N = expert_outputs.shape[0]

        # Triton grid: one program per source row
        grid = (N,)

        # Choose BLOCK_H and kernel config based on H
        if H >= 2048:
            BLOCK_H = 256
            num_warps = 8
            num_stages = 3
        elif H >= 1024:
            BLOCK_H = 256
            num_warps = 4
            num_stages = 3
        elif H >= 512:
            BLOCK_H = 128
            num_warps = 4
            num_stages = 2
        else:
            BLOCK_H = 64
            num_warps = 2
            num_stages = 2

        # Triton kernel expects int32 indices for better performance; token_indices are long, we can pass as-is (Triton loads int64 and we cast)
        scatter_add_row_atomic_kernel[grid](
            output, expert_outputs, token_indices,
            N, H,
            BLOCK_H=BLOCK_H,
            num_warps=num_warps, num_stages=num_stages,
        )

        return output
```

Notes
- Correctness: This kernel initializes output as a clone of final_hidden_states and atomically adds expert_outputs[n, :] into output[token_indices[n], :] for all n. This matches torch.index_add(dim=0, index=token_indices, source=expert_outputs), including handling duplicate indices via atomic adds.
- Performance: Reduces the number of Triton programs to N and processes H in vectorized chunks, which should improve throughput compared to the previous 2D-tiled kernel that created many small programs. The while loop over H is a Triton-supported runtime loop, avoiding the previous compile/runtime issues.
- Robustness: Avoids using H as a compile-time constant in problematic ways; masks ensure we don’t read/write out of bounds in partial chunks.

If needed, we can further tune BLOCK_H, num_warps, and num_stages for specific workloads. However, this version aims to strike a good balance and should improve speed beyond the previous 0.57 average while keeping correctness intact.
