Great news: the last Triton implementation is both correct and faster than the PyTorch baseline (geomean ~1.83). We can still try to squeeze more performance without risking correctness. The operation remains a scatter-add along dim=0: output[token_indices[i]] += expert_outputs[i], with output shape (M, H), expert_outputs shape (N, H), and token_indices length N.

Performance analysis and plan
- Operation characteristics:
  - Scatter-add is inherently parallel but suffers from atomic contention when many indices map to the same output row. PyTorch’s index_add uses optimized kernels to mitigate this, but our Triton version can still get faster by increasing per-program work and reducing the number of atomics per element.
- Current kernel approach:
  - One Triton program per source row n. Inside the program, it iterates over H in chunks (BLOCK_H), loads token_indices[n], expert_outputs[n, h_block], and performs tl.atomic_add to output at the computed destination. This design was robust and achieved a good speedup.
- Optimization opportunities:
  - Increase BLOCK_H for larger H to reduce loop iterations and atomics per row. This improves memory throughput and reduces kernel control overhead.
  - Tune num_warps and num_stages based on H to balance occupancy and throughput.
  - Keep the while loop over H with runtime condition to avoid Triton compile-time issues and allow handling arbitrary H.

We will refine the kernel launch parameters:
- If H is large (>= 1024), use BLOCK_H=256, num_warps=8, num_stages=3.
- If H is medium (>= 256), use BLOCK_H=128, num_warps=4, num_stages=2.
- Else, use BLOCK_H=64, num_warps=2, num_stages=2.
- Grid remains one program per source row, i.e., (N,).

This keeps correctness intact and should further improve performance for larger hidden sizes while maintaining efficiency for smaller ones.

Final code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_row_kernel(
    output_ptr,            # *bf16 or *fp16 pointer, shape [M, H]
    expert_ptr,            # *bf16 or *fp16 pointer, shape [N, H]
    index_ptr,             # *int32 pointer, shape [N]
    N, H,                  # runtime sizes
    BLOCK_H: tl.constexpr  # compile-time tile size for H
):
    # One program per source row n
    n = tl.program_id(axis=0)
    if n >= N:
        return

    # Load target row index for this source row
    idx = tl.load(index_ptr + n)

    # Iterate over hidden features in chunks of BLOCK_H
    start = 0
    while start < H:
        h_offsets = start + tl.arange(0, BLOCK_H)
        mask = h_offsets < H

        # Load the corresponding hidden values from the expert output row n
        vals = tl.load(
            expert_ptr + n * H + h_offsets,
            mask=mask,
            other=0.0  # zero for out-of-range elements
        )

        # Compute output destinations: each element goes to output[idx, h_offsets]
        dest = idx * H + h_offsets

        # Atomic add to output
        tl.atomic_add(output_ptr + dest, vals, mask=mask)

        start += BLOCK_H


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-only forward that performs scatter-add: output[token_indices[i]] += expert_outputs[i]
        """
        # Clone input buffer to initialize output; we'll modify this clone.
        output = final_hidden_states.clone()

        # Ensure device and dtype consistency
        if not output.is_cuda or not expert_outputs.is_cuda or not token_indices.is_cuda:
            # If tensors are not on CUDA, fall back to torch implementation (for safety)
            # Note: This forward method is expected to run on CUDA devices for Triton performance.
            raise RuntimeError("ModelNew requires CUDA tensors for Triton execution.")

        # Shapes
        M, H = output.shape
        N = expert_outputs.shape[0]

        # Ensure token_indices are int32 for Triton
        if token_indices.dtype != torch.int32:
            token_indices_i32 = token_indices.to(torch.int32)
        else:
            token_indices_i32 = token_indices

        # Choose tile size and warps based on H
        if H >= 1024:
            BLOCK_H = 256
            num_warps = 8
            num_stages = 3
        elif H >= 256:
            BLOCK_H = 128
            num_warps = 4
            num_stages = 2
        else:
            BLOCK_H = 64
            num_warps = 2
            num_stages = 2

        # Launch Triton kernel: one program per source row
        grid = (N,)

        scatter_add_row_kernel[grid](
            output, expert_outputs, token_indices_i32,
            N, H,
            BLOCK_H=BLOCK_H,
            num_warps=num_warps, num_stages=num_stages,
        )

        return output
```

Notes
- Correctness: The kernel initializes output as a clone of final_hidden_states and atomically adds each expert_outputs[n, :] to output[token_indices[n], :]. This matches torch.index_add(dim=0, index=token_indices, source=expert_outputs) semantics, including handling duplicate indices safely.
- Performance: The one-program-per-row design with larger BLOCK_H reduces loop iterations and atomics per row, improving throughput. Tuning num_warps and num_stages helps occupancy. This version aims to further improve speed over the previous submission while preserving robustness and correctness.
- Safety: The kernel uses masks for out-of-range H elements in the last chunk. We ensure token_indices are int32 for Triton and assume all tensors are on CUDA. If not, we raise an error to avoid silent CPU fallback that would compromise the Triton-only requirement.
