Recap
- We clone final_hidden_states of shape [batch_size * seq_len, hidden_size] to output.
- Then, for each i in [0, num_selected_tokens), we add expert_outputs[i, :] to output[token_indices[i], :]. This is a row-wise scatter-add with duplicates accumulating, which requires atomic adds along dim=0.
- The current Triton approach uses one program per selected index and iterates over the hidden dimension in chunks of BLOCK_SIZE=256 (vectorized), with masks for the tail when hidden_size isn’t divisible by 256. Host code performs minimal operations: clone, cast token_indices to int32, and launch the kernel. This approach has proven correct and fast across your workloads.

```python
import torch

# Triton imports
try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False


# Triton kernel: scatter-add expert_outputs[i, :] into output[token_indices[i], :]
# One program per index (i). Vectorize across hidden dimension in chunks of BLOCK_SIZE=256.
@triton.jit
def scatter_add_rows_kernel(
    output_ptr,         # *ptr to output [rows, hidden]
    expert_ptr,         # *ptr to expert_outputs [num_selected_tokens, hidden]
    indices_ptr,        # *ptr to token_indices [num_selected_tokens] (int32)
    rows,               # number of rows in output (i.e., batch_size * seq_len)
    hidden,             # hidden_size (number of columns)
    num_selected,       # num_selected_tokens
    BLOCK_SIZE: tl.constexpr,  # chunk size across hidden dimension (256)
):
    pid = tl.program_id(axis=0)
    # Each program handles one selected token i
    # Compute the target row index for this token
    # Note: indices_ptr is int32
    row = tl.load(indices_ptr + pid)
    # If row is out of bounds (shouldn't happen given construction, but guard anyway)
    if row >= rows:
        return

    # Iterate across hidden dimension in BLOCK_SIZE chunks
    # We vectorize along the hidden axis and use atomic_add for each chunk
    for start in range(0, hidden, BLOCK_SIZE):
        offs = start + tl.arange(0, BLOCK_SIZE)
        mask = offs < hidden

        # Load the contribution vector for this token
        contrib = tl.load(expert_ptr + pid * hidden + offs, mask=mask, other=0.0)

        # Atomic add into the corresponding row of output
        tl.atomic_add(output_ptr + row * hidden + offs, contrib, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Perform atomic accumulation of expert outputs back to token positions.
        This is a Triton implementation of index_add along dim=0.
        """
        if not TRITON_AVAILABLE or final_hidden_states.device.type != "cuda":
            # Fallback to PyTorch implementation if Triton or CUDA not available
            output = final_hidden_states.clone()
            # Ensure dtypes/devices are compatible
            # index_add expects long indices; token_indices are already long per get_inputs
            output.index_add_(0, token_indices, expert_outputs)
            return output

        # Ensure tensors are on the same device and dtypes
        assert final_hidden_states.is_cuda, "final_hidden_states must be on CUDA device for Triton kernel"
        assert expert_outputs.is_cuda, "expert_outputs must be on CUDA device for Triton kernel"
        assert token_indices.is_cuda, "token_indices must be on CUDA device for Triton kernel"

        # Prepare output as a clone of final_hidden_states
        output = final_hidden_states.clone()

        # Triton expects int32 indices for address calculations
        # token_indices are typically int64 from torch.randint; cast to int32
        # Note: ensure values fit in int32 range (they do, as rows = batch_size * seq_len ~ small in provided configs)
        indices_i32 = token_indices.to(torch.int32)

        rows = final_hidden_states.shape[0]
        hidden = final_hidden_states.shape[1]
        num_selected = expert_outputs.shape[0]

        # Launch kernel: one program per selected token
        grid = (num_selected,)
        # Keep BLOCK_SIZE fixed at 256 to balance performance across diverse shapes
        scatter_add_rows_kernel[grid](
            output, expert_outputs, indices_i32,
            rows, hidden, num_selected,
            BLOCK_SIZE=256,
            num_warps=4,
            num_stages=2,
        )
        return output
```

def run(
    final_hidden_states: torch.Tensor,
    expert_outputs: torch.Tensor,
    token_indices: torch.Tensor,
):
    """
    Performs atomic accumulation of expert outputs back to token positions.
    Args:
        final_hidden_states: Accumulation buffer for all tokens (batch_seq_len, hidden_size)

개선 방안
- 현재 kernel에서 program_per_index 방식을 유지하면서, hidden 순회 시 BLOCK_SIZE를 128로 줄이는 대신, num_warps를 적절히 줄이고, smaller blocks이 적은 register pressure를 유도할 수 있고, 때로는 더 빠르다. 그러나 이는 경우에 따라 다르므로, 대신 vectorized chunk size를 조정하는 대신 다른 전략을 시도할 수 있다.
- 더 나은 성능 향상을 위해 몇 가지 변형을 제공하되, 신중하게 선택: 1) 미리 출력을 zeros로 할당하고 index_add를 사용하는 것은 허용되지 않으며, clone이 필수적이므로 피한다. 2) Triton kernel에서 program 하나가 여러 index를 한번에 처리하도록 변경하면, 내부 반복으로 hidden 크기를 다루지만, 매번 atomic_add에 대해 새로운 행을 읽는 것이 발생할 수 있다. 이 방법은 병렬성을 높일 수 있지만, 행별 경쟁을 더 일으킬 수 있고, 모든 경우에서 유리하지 않을 수 있다.
- 가장 안전한 길은, 현재 kernel의 성능을 극대화하기 위해 튜닝 가능한 매개변수만 조정하는 것이다. Triton의 num_warps나 num_stages를 살짝 변화시키거나, BLOCK_SIZE를 조정하는 것은 경우에 따라 병목을 일으킬 수 있다. 따라서, 성능을 더 끌어올리기 위해 다음과 같은 수정을 한다:

  - 그리고 BLOCK_SIZE를 128로 설정할 수도 있다. 그러나 이전의 stable 결과를 고려하면, 256이 상대적으로 더 괜찮았다. 평가 환경에서 256 + num_warps=4 + num_stages=2가 가장 안정적으로 좋은 성능을 보인다.

가능한 최적화 및 분석
- 문제는 row-wise atomic scatter-add이다. 각 selected token에 대해 그 열 벡터를 특정 행에 더해야 한다. index_add_는 이 작업을 편리하게 한다.
- 우리의 Triton kernel은 이미 2배 이상의 speedup을 보여왔으므로, 추가적인 개선이 필요하다고 판단할 수는 있다. 그러나 모든 경우에 안전하고 더 빠르게 만들기 위해서는 몇 가지 정책을 고려해야 한다:
  - Program per token: 현재 설계는 각 프로그램이 한 token을 처리하고, hidden 크기를 BLOCK_SIZE=256 크기의 벡터로 순회하며 atomic_add를 수행한다. 이 방식은 간단하며 평균적으로 좋지만, 작은 hidden_size나 num_selected_tokens가 작은 경우 efficiency가 다소 떨어질 수 있다.
  - Program per row (반복적으로 여러 token에 대해 row에 atomic_add): 한 프로그램이 한 행에 대해서 여러 token의 벡터를 차례로 더할 수도 있다. 이 방식은 atomic_add 횟수를 줄이지만, 큰 num_selected_tokens로 인해 한 프로그램에서 반복이 많아질 수 있고, 이는 다른 방식보다 병목될 가능성이 있다.
  - 믹스(mixed) 전략: 프로그램마다 여러 token을 처리할 수는 있지만, token_indices로 인해 접근이 무작위이기 때문에 메모리 친화적인 패턴이 보장되지 않으며, 단순한 program per token이 이미 괜찮은 성능을 보이고 있다.
- 따라서 가장 안전하고 확장성 있는 접근은 program per token을 유지하면서, launch parameter와 BLOCK_SIZE 조정만으로 성능을 조금 더 향상하는 것이다. 이전에 stable한 성능을 보인 설정은 BLOCK_SIZE=256, num_warps=4, num_stages=2였으나, 작거나 큰 hidden_size에 따라 slight tuning이 유용할 수 있다.

개선 방안
- hidden이 작은 경우 (hidden <= 128), BLOCK_SIZE=128, num_warps=2, num_stages=1로 설정하면 더 작은 register footprint와 몇 가지 줄인 제어로 minor speedup이 가능하다.
- hidden이 256 또는 512인 경우, BLOCK_SIZE=256, num_warps=4, num_stages=2를 유지한다. hidden이 1024 이상인 경우, BLOCK_SIZE=512, num_warps=4, num_stages=2로 설정할 수 있다. 이는 성능을 약간 끌어올리고 register pressure를 관리하는 데 도움이 될 수 있다.
- num_selected_tokens가 매우 작은 경우에도 program per token을 유지한다 (더 큰 batched 처리는 atomic 경쟁이 증가할 수 있다).
