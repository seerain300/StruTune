Final code (ModelNew)
```python
import torch
import triton
import triton.language as tl


@triton.jit
def _index_add_rows_kernel(
    out_ptr,         # *half (final_hidden_states clone)
    expert_ptr,      # *half (expert_outputs)
    indices_ptr,     # *int32 (token_indices)
    N,               # int32: number of selected tokens (rows in expert_outputs)
    H,               # int32: hidden size (columns)
    BLOCK: tl.constexpr,  # chunk size for hidden dimension, e.g., 256
):
    pid = tl.program_id(axis=0)
    if pid >= N:
        return

    # Destination row index for this selected token
    idx = tl.load(indices_ptr + pid)

    # Iterate over hidden columns in chunks of BLOCK, with masking for tail
    for off in range(0, H, BLOCK):
        cols = off + tl.arange(0, BLOCK)
        mask = cols < H

        # Load expert vector chunk
        # expert_ptr is a contiguous [N, H] tensor; row pid starts at 0..N-1
        expert_row_ptr = expert_ptr + pid * H
        vals = tl.load(expert_row_ptr + cols, mask=mask, other=0.0)

        # Compute output row pointer: out_ptr is [BATCH*SEQ, H], row idx
        out_row_ptr = out_ptr + idx * H
        out_vec_ptr = out_row_ptr + cols

        # Atomically add into output
        tl.atomic_add(out_vec_ptr, vals, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Ensure dtype matches the reference (bfloat16)
        if final_hidden_states.dtype != torch.bfloat16:
            final_hidden_states = final_hidden_states.to(torch.bfloat16)
        if expert_outputs.dtype != torch.bfloat16:
            expert_outputs = expert_outputs.to(torch.bfloat16)

        # Prepare output as a clone of the original buffer (to match reference behavior)
        output = final_hidden_states.clone()

        # Ensure contiguity and correct dtypes/devices
        output = output.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()
        if token_indices.dtype != torch.int32:
            token_indices = token_indices.to(torch.int32)

        N = expert_outputs.shape[0]  # number of selected tokens
        H = expert_outputs.shape[1]  # hidden size

        # Launch Triton kernel: one program per row
        # Using BLOCK=256 ensures we cover all hidden columns via masked loop.
        grid = (N,)
        _index_add_rows_kernel[grid](
            output,               # out_ptr
            expert_outputs,       # expert_ptr
            token_indices,        # indices_ptr
            N,                    # N
            H,                    # H
            BLOCK=256,            # chunk size for hidden dimension
            num_warps=4,          # good balance for vector operations
            num_stages=2,         # pipelining
        )

        return output
```

  That means: for each i in [0, N):
    add expert_outputs[i, :] into output[token_indices[i], :].
  Duplicates in token_indices must accumulate, which is atomic-add semantics.

Current kernel structure (working and correct):
- One Triton program per selected token row (N programs).
- Inside each program, iterate over hidden columns in chunks of BLOCK=256 using a masked loop. For each chunk:
  - Load a vector of size BLOCK from expert_outputs for row i.
  - Atomic add into out[token_indices[i], cols].
- This guarantees correctness regardless of H, because the loop covers all columns with masks.

Where we can still optimize:
- Reduce atomic_add per chunk. The kernel is memory-bound; atomics cost some overhead, but with H <= 1024 and N moderate, atomics are acceptable. The big win is to reduce the number of iterations, which equals reducing BLOCK size. However, reducing BLOCK increases the number of iterations; so we need to strike a balance.
- Avoid autotune and keep deterministic launch. Autotune can pick a suboptimal BLOCK for some H or cause overhead, and previously caused a correctness failure.
- Ensure inputs are contiguous and token_indices int32, output is clone of final_hidden_states.

Optimization approach without risking correctness:
- Keep BLOCK=256 (previously best-performing among safe strategies). It balances register pressure and reduces iteration count. The masked loop ensures correctness for any H.
- Adjust num_warps based on grid size (N) rather than H. For very small N, fewer warps reduce overhead; for large N, more warps increase occupancy. This heuristic keeps the kernel efficient across workloads.
  - If N < 2048: num_warps=2
  - Else: num_warps=4
- Keep num_stages=2 for pipelining. On this simple per-row accumulation, further increasing stages may not help much.

Why not switch to BLOCK=128 or BLOCK=H:
- BLOCK=128 increases the number of iterations (2–8 depending on H), which can reduce performance due to more loop/mask overhead.
- BLOCK=H is tempting (one iteration), but Triton generally requires BLOCK to be a compile-time constant and using H directly as BLOCK can vary per launch and may not be ideal for codegen. The masked loop with a fixed BLOCK is robust and safe.

Why not per-element atomics:
- That would massively increase atomic operations (N*H), likely slowing down the kernel and risking illegal memory accesses if not perfectly guarded. The current approach of per-chunk vectorized atomics is the right tradeoff.
