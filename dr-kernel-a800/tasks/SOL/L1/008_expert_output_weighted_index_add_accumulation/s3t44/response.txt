The current Triton kernel is simple and robust: one program per update, iterating over the hidden dimension in BLOCK_H chunks and performing a single atomic_add per chunk. That reduces atomics from H per update to roughly H / BLOCK_H, which yields good speed while preserving correctness.

Goal now: improve performance further without risking correctness. The main levers are:
- Choosing BLOCK_H based on hidden_size to reduce the number of atomic operations per update. Larger BLOCK_H reduces atomics but increases per-program work; smaller BLOCK_H reduces per-program work but increases atomics. We need a balance.
- Keep the kernel simple and avoid introducing multi-update-per-program complexity, since the proven single-update kernel is already correct and fast.

Concrete plan
- Use the same single-program-per-update structure, but select BLOCK_H heuristically:
  - If hidden_size (H) is large (≥ 1024), use BLOCK_H = 1024 (num_warps = 8). This minimizes the number of atomic operations and is ideal for common hidden sizes like 1024.
  - If H ≥ 512, use BLOCK_H = 512 (num_warps = 4).
  - Else, use BLOCK_H = 256 (num_warps = 2).
- Keep accumulation in float32 for atomic_add (bfloat16 atomics are not supported), but do not change the dtype of final_hidden_states on host. Only ensure contiguity and cast expert_outputs to float32 for the kernel. This preserves original dtype behavior and avoids dtype-related runtime issues.
- Maintain masks for tail handling and ensure indices are int32 in the kernel.

This keeps the kernel robust while optimizing the number of atomic operations depending on hidden_size. It should provide incremental speedups over the previous version.

Final code (ModelNew)
```python
import torch
import triton
import triton.language as tl

@triton.jit
def _scatter_add_chunks_kernel(
    out_ptr,            # *fp32, shape [batch_seq_len, H]
    token_indices_ptr,  # *int32, shape [N]
    expert_outputs_ptr, # *fp32, shape [N, H]
    N,                  # int: number of updates
    H,                  # int: hidden size
    BLOCK_H: tl.constexpr,
):
    pid = tl.program_id(0)
    # Each program handles one update
    if pid >= N:
        return

    # Load token index (row in output)
    idx = tl.load(token_indices_ptr + pid)

    # Iterate over hidden dimension in chunks of BLOCK_H
    h = 0
    while h < H:
        offs = h + tl.arange(0, BLOCK_H)
        mask = offs < H

        # Load source vector for this update (fp32)
        v = tl.load(expert_outputs_ptr + pid * H + offs, mask=mask, other=0.0)

        # Compute output pointer for this row and chunk
        out_row_ptr = out_ptr + idx * H
        tl.atomic_add(out_row_ptr + offs, v, mask=mask)

        h += BLOCK_H


def _run_triton_scatter_add(final_hidden_states: torch.Tensor,
                            expert_outputs: torch.Tensor,
                            token_indices: torch.Tensor) -> torch.Tensor:
    """
    Triton-optimized scatter-add:
      out = final_hidden_states.clone()
      out.index_add_(dim=0, index=token_indices, source=expert_outputs)
    Returns updated out (bfloat16).
    """
    # Ensure tensors are on CUDA
    assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA for Triton."

    # Make inputs contiguous
    final_hidden_states = final_hidden_states.contiguous()
    expert_outputs = expert_outputs.contiguous()
    token_indices = token_indices.contiguous()

    # Triton requires int32 indices
    token_indices_i32 = token_indices.to(torch.int32)

    # Prepare output buffer in float32 for atomic accumulation
    out_fp32 = final_hidden_states.to(torch.float32).clone()

    # Cast expert outputs to float32 for accumulation
    expert_outputs_fp32 = expert_outputs.to(torch.float32)

    N = expert_outputs_fp32.shape[0]
    H = expert_outputs_fp32.shape[1]

    # Heuristic for BLOCK_H and num_warps based on hidden size
    if H >= 1024:
        BLOCK_H = 1024
        num_warps = 8
    elif H >= 512:
        BLOCK_H = 512
        num_warps = 4
    else:
        BLOCK_H = 256
        num_warps = 2

    grid = (N,)

    _scatter_add_chunks_kernel[grid](
        out_fp32,
        token_indices_i32,
        expert_outputs_fp32,
        N,
        H,
        BLOCK_H=BLOCK_H,
        num_warps=num_warps,
        num_stages=2,
    )

    # Cast back to bfloat16 to match original API
    return out_fp32.to(torch.bfloat16)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor):
        # The reference forward clones and uses index_add in bfloat16.
        # Our Triton kernel accumulates in fp32 and returns fp32 cast to bfloat16.
        return _run_triton_scatter_add(final_hidden_states, expert_outputs, token_indices)
```

Notes
- Correctness: The kernel performs atomic adds into a float32 copy of the original bfloat16 buffer, and the returned tensor is cast back to bfloat16. This preserves the original semantics and handles duplicate indices correctly via atomics.
- Performance: The heuristic selection of BLOCK_H reduces the number of atomics per update, improving throughput, especially when H is 1024 or larger. The kernel remains simple and robust, avoiding the multi-update-per-program complexity that previously caused runtime issues.
- Safety: We do not change the dtype of final_hidden_states on the host; we only prepare a float32 accumulation buffer and cast the result back to bfloat16, which is acceptable for evaluation since the original run also used a float32 buffer. The key is that the returned tensor matches the original dtype and behavior. If your environment requires strictly bfloat16 throughout, consider accumulating in bfloat16 directly (Triton atomic_add on bf16 may not be available), hence the fp32 intermediate is used for performance and reliability.

This should maintain the ~1.20x speedup and potentially yield small additional improvements due to larger BLOCK_H on common H=1024 workloads, while keeping correctness intact.
