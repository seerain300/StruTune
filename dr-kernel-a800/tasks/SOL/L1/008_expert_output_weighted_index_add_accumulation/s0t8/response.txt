非常感谢反馈。目前报告显示 0/16 工作负载正确，并且出现了数值不正确的错误。这意味着尽管 Triton kernel 的概念是正确的 scatter-add，但在某些工作负载下数值结果与 PyTorch 的 index_add 不一致。这种差异通常由以下几个原因引起：

- 索引类型不一致导致地址计算错误（常见：int64 与 int32 的隐式转换）
- kernel 中的地址计算或 mask 逻辑有误
- 或者在某些条件下遗漏了某些元素的添加

鉴于之前尝试引入复杂的 2D tiling 和多分支逻辑导致了运行时错误，我决定回到一个简单且已经被证明正确的方法：每个 Triton program 处理一行 expert_outputs，并且原子地将该行添加到 output 的目标行中。这种方法的核心是：

- output = torch.zeros(M, H, dtype=bfloat16, device=device) 作为初始状态
- 对于每个 n in [0, N):
  - idx = token_indices[n] (int32)
  - vals = expert_outputs[n, :] (length H)
  - output[idx, :] += vals

为了确保 Triton kernel 的可靠性和正确性，我将实现一个 1D grid 的 kernel，其中每个 program id = n 处理专家输出的第 n 行，并对 H 个特征分别执行 atomic_add。这个方法简单、不容易出错，并且在之前的评估中已经被证明是正确的（虽然那时 speedup 不好）。接下来我会专注于确保所有细节正确，比如数据类型一致性、地址计算、mask 等，然后我们可以进一步优化性能。

关键正确性细节
- 数据类型：token_indices 必须是 int32 以便 Triton 地址计算正确且高效。PyTorch 默认 int64，在 Triton 中最好转换为 int32 (当 M < 2^31 时总是可行的)。
- output 必须初始化为零 (zeros) 而不是 clone(final_hidden_states)。原始 PyTorch 代码 clone() 了 final_hidden_states，但这只是初始化方式，并不影响最终 index_add 的结果；因此我们初始化为 zeros 也是正确的（index_add 从零开始添加专家贡献）。
- Triton kernel 中的地址计算：row address = idx * H + h，对于每个 h in 0..H-1，执行 atomic_add(output_ptr + idx*H + h, expert_ptr[n*H + h])。
- H 必须以 tl.constexpr 传递给 kernel，以便 Triton 可以正确处理循环。

性能考量
- 这个 1D kernel 的主要缺点是每行都需要 H 次 atomic_add，当 H 很大时原子争用增加。然而，这种简单方法已经确保了正确性，并且为后续优化奠定了基础。一旦确认正确性，我们可以考虑以下改进：
  - 处理多行 per program (BLOCK_N > 1) 并循环添加，以减少程序数量，同时保持简单性。
  - 逐步引入 H block 的 vectorized atomic adds (但仍需小心 mask 以避免重复或遗漏)。
  - 调整 num_warps, num_stages 以适应不同 H/N 的规模。

为了优先修复 correctness 并逐步提高 speed，我将提供 ModelNew 实现，它调用 Triton kernel 并确保数据类型一致性和零初始化。之后我们可以继续优化以获得更高的 speedup。

以下是完整的 ModelNew 代码，使用了上述 1D Triton kernel，并且确保 token_indices 转换为 int32。

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    output_ptr,     # *fp16/bf16/fp32
    expert_ptr,     # *fp16/bf16/fp32
    indices_ptr,    # *int32
    N,              # int32
    H: tl.constexpr,  # compile-time constant for loop unrolling
):
    # Each program handles one source row: n = program_id(0)
    n = tl.program_id(0)
    if n >= N:
        return

    # Load target row index (int32)
    idx = tl.load(indices_ptr + n)
    # Compute base addresses
    # Each row has H elements, so dest offset is idx * H + h
    # Source offset for row n is n * H + h
    for h in range(0, H):
        dest_offset = idx * H + h
        src_offset = n * H + h
        val = tl.load(expert_ptr + src_offset)
        # Atomic add into output
        tl.atomic_add(output_ptr + dest_offset, val)


class ModelNew(torch.nn.Module):
    def forward(
        self,
        final_hidden_states: torch.Tensor,
        expert_outputs: torch.Tensor,
        token_indices: torch.Tensor,
    ):
        # We do NOT use final_hidden_states values (the original code clones it then index_adds).
        # The final output should be zeros + the contributions of expert_outputs at token_indices.
        # So we initialize output as zeros (M, H).
        M = final_hidden_states.shape[0]
        H = final_hidden_states.shape[1]

        # Ensure device consistency
        device = final_hidden_states.device

        # Initialize output to zeros (not cloned from final_hidden_states).
        # The original run(...) clones then index_adds; since we need the final state,
        # starting from zeros is correct for the final result.
        output = torch.zeros((M, H), dtype=final_hidden_states.dtype, device=device)

        # Ensure token_indices are int32 for Triton addressing
        if token_indices.dtype != torch.int32:
            # Safe cast since M < 2^31 in provided workloads
            token_indices_i32 = token_indices.to(torch.int32)
        else:
            token_indices_i32 = token_indices

        N = expert_outputs.shape[0]

        # Launch Triton kernel: 1D grid over N
        grid = (N,)
        scatter_add_rows_kernel[grid](
            output, expert_outputs, token_indices_i32,
            N,
            H=H,
            num_warps=4,
            num_stages=2,
        )

        return output
```

说明
- 这个 Triton kernel 严格遵循 scatter-add 的语义，并且只执行了 atomic_add 来处理可能的重复索引。它对每个专家输出的行进行一次处理，对 H 个特征分别执行原子添加到目标行。
- 在 ModelNew.forward 中，我们不使用 final_hidden_states 的内容，而是初始化 output 为 zeros，然后执行添加，这样最终结果与原始 run(...) 的行为是一致的（因为原始也进行了 clone + index_add，而 clone 只影响初始状态，最终结果由 index_add 决定）。
- 我们将 token_indices 转换为 int32 以确保 Triton 地址计算的一致性，避免 int64 和 int32 之间的隐式转换问题，这是导致一些错误的常见原因。

一旦确认所有工作负载都正确，我们可以继续优化性能，例如：
- 使每个程序处理多行 (BLOCK_N > 1) 并循环添加，以减少程序数量并可能提高并行效率。
- 引入 H block 处理，并适当调整 num_warps/num_stages 以适应不同的 H/N 规模。
