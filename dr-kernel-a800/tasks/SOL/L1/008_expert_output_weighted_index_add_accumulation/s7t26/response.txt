Let’s carefully diagnose and then fix the issues before optimizing.

What the original PyTorch code does
- It clones final_hidden_states and then performs index_add along dim=0: output.index_add_(0, token_indices, expert_outputs).
- That means, for each i in [0, num_selected_tokens), output[token_indices[i]] accumulates (atomically) the row expert_outputs[i]. Duplicates in token_indices must be summed correctly.

Why the previous Triton attempts failed
- The vectorized version (using tl.arange across the hidden dimension and atomic adds) crashed Triton in your environment. The evaluator reported compilation/runtime errors and then later reported “INCORRECT_NUMERICAL,” which implies the kernel compiled but produced wrong results.
- The non-vectorized per-row scalar loop version we used earlier did produce correct results in the same environment. So the safest path is to restore that logic and then try to reintroduce vectorization only when we can do it in a way that is robust for all shapes. However, Triton’s vectorized pointer arithmetic for atomics appears fragile here. We will prioritize correctness.

Constraints to respect
- Triton-only computation: ModelNew.forward must invoke a Triton kernel. No torch.index_add or Python-side accumulation.
- Must handle arbitrary batch_size, seq_len, num_experts_per_tok (M), and hidden_size (H). These are runtime values per workload.
- Device is CUDA, dtype is bfloat16, and token_indices are in [0, N), N=batch_size*seq_len.

Plan for a robust, correct Triton kernel
- Host:
  - out = final_hidden_states.clone()  (to mirror the reference behavior)
  - Ensure out and expert_outputs are contiguous on the same CUDA device.
  - Cast token_indices to int32 for Triton.
- Triton kernel:
  - 1D grid over rows i in [0, M).
  - For each row i, compute the destination row index dst = token_indices[i].
  - Loop over the hidden dimension j = 0..H-1 and perform tl.atomic_add(out_ptr + dst * H + j, src_ptr + i * H + j).
  - This avoids any vectorized pointer math and has previously passed correctness in this evaluation setting.

Note: This kernel is correct but not fast. We keep it to restore correctness first. Once correctness is solid, we can attempt small safe optimizations (e.g., BLOCK over j with tl.arange but guarded to avoid Triton fragility), but given the evaluator’s sensitivity, we’ll prioritize correctness here.

Final code (ModelNew)

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_per_row_kernel(
    out_ptr,        # *bf16, shape (N, H), contiguous
    src_ptr,        # *bf16, shape (M, H), contiguous
    indices_ptr,    # *int32, shape (M,), contiguous
    M,              # int32, number of expert outputs to scatter (batch_size * seq_len * num_experts_per_tok)
    N,              # int32, number of rows in out (batch_size * seq_len)
    H,              # int32, hidden size
):
    pid = tl.program_id(axis=0)
    if pid >= M:
        return

    # Load destination token index for this row
    dst = tl.load(indices_ptr + pid)  # int32

    # Loop over hidden dimension and do atomic add
    # We avoid any vectorized pointer arithmetic to stay robust.
    for j in range(0, H):
        out_offset = dst * H + j
        src_offset = pid * H + j
        # Atomic add to handle duplicates
        tl.atomic_add(out_ptr + out_offset, tl.load(src_ptr + src_offset))


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Clone to match reference behavior
        out = final_hidden_states.clone()

        # Ensure tensors are on CUDA and contiguous
        assert out.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA"
        out = out.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.to(torch.int32).contiguous()

        # Compute shapes
        M = expert_outputs.shape[0]  # number of rows to scatter
        N = final_hidden_states.shape[0]  # number of rows in output buffer

        # Launch Triton kernel: one program per row i
        grid = (M,)
        scatter_add_per_row_kernel[grid](
            out,                  # out_ptr
            expert_outputs,       # src_ptr
            token_indices,        # indices_ptr
            M, N, expert_outputs.shape[1],  # pass M, N, H
        )
        return out
```

Explanation of choices
- We use a 1D grid over the M rows. Each program handles one row’s contribution. This keeps code simple and robust, avoiding Triton’s tricky vectorized pointer operations that previously failed.
- We loop over H and perform one atomic_add per element. This exactly matches index_add_ behavior for duplicates.
- We assert device and ensure contiguity. We cast token_indices to int32 for Triton pointer arithmetic.

Performance
- This kernel is correct and stable, but not fast compared to PyTorch’s optimized index_add_. If later runs confirm stability, we can attempt to vectorize across the hidden dimension in a very conservative manner (e.g., with small BLOCK values that ensure bounds), but given the evaluator’s history, the above is the safest path to correctness first.
