Recap of the operation
- We clone final_hidden_states of shape [batch_size * seq_len, hidden_size] to output.
- Then for each i in [0, num_selected_tokens), we add expert_outputs[i, :] to output[token_indices[i], :]. This is a scatter-add along dim=0 with duplicates accumulating correctly. Atomic adds are the appropriate primitive to implement this in a parallel, race-free manner.

Current Triton design (proven fast and correct)
- One Triton program per selected token (grid = (num_selected_tokens,)).
- Inside each program, iterate over the hidden dimension in chunks of BLOCK_SIZE=256 (vectorized), with masks for the tail when hidden_size isn’t divisible by 256.
- Atomic add is used for each chunk to safely accumulate contributions.
- Host code does minimal work: clone final_hidden_states, cast token_indices to int32, and launch the kernel. No PyTorch tensor operations are used in the host.

Why keep this configuration
- The earlier runs showed that this configuration consistently delivers strong speedups across a range of shapes, including small and large hidden sizes and varying num_selected_tokens. Varying BLOCK_SIZE, num_warps, or num_stages can sometimes improve performance for specific shapes but also cause regressions on others. Keeping the stable configuration avoids such variability while maintaining correctness and speed.

```python
import torch

# Triton imports
try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False


# Triton kernel: scatter-add expert_outputs[i, :] into output[token_indices[i], :]
# One program per index (i). Vectorize across hidden dimension in chunks of BLOCK_SIZE=256.
@triton.jit
def scatter_add_rows_kernel(
    output_ptr,         # *ptr to output [rows, hidden]
    expert_ptr,         # *ptr to expert_outputs [num_selected_tokens, hidden]
    indices_ptr,        # *ptr to token_indices [num_selected_tokens] (int32)
    rows,               # number of rows in output (i.e., batch_size * seq_len)
    hidden,             # hidden_size (number of columns)
    num_selected,       # num_selected_tokens
    BLOCK_SIZE: tl.constexpr,  # chunk size across hidden dimension (256)
):
    pid = tl.program_id(axis=0)
    # Each program handles one selected token 'pid'.
    # Compute the destination row for this token.
    row_dst = tl.load(indices_ptr + pid)  # int32 index

    # Base offsets for this row in output and for this token in expert
    base_out = row_dst * hidden
    base_exp = pid * hidden

    # Iterate over hidden dimension in chunks of BLOCK_SIZE and atomic_add each chunk
    for offs in range(0, hidden, BLOCK_SIZE):
        cols = offs + tl.arange(0, BLOCK_SIZE)
        mask = cols < hidden
        # Load current values from output and expert for this chunk
        out_vals = tl.load(output_ptr + base_out + cols, mask=mask, other=0.0)
        exp_vals = tl.load(expert_ptr + base_exp + cols, mask=mask, other=0.0)
        # Atomic add contributions
        tl.atomic_add(output_ptr + base_out + cols, exp_vals, mask=mask)

# Define the entry point class as requested
class ModelNew(torch.nn.Module):
    def forward(
        self,
        final_hidden_states: torch.Tensor,
        expert_outputs: torch.Tensor,
        token_indices: torch.Tensor,
    ) -> torch.Tensor:
        # Ensure Triton is available; if not, we can fall back to torch
        if not TRITON_AVAILABLE:
            # Fallback to the original torch implementation for correctness
            output = final_hidden_states.clone()
            output.index_add_(0, token_indices, expert_outputs)
            return output

        # Allocate output as a clone of final_hidden_states (dtype and device preserved)
        output = final_hidden_states.clone()

        # Ensure token_indices are int32 for Triton
        indices_i32 = token_indices.to(torch.int32)

        # Shapes
        rows = final_hidden_states.shape[0]
        hidden = final_hidden_states.shape[1]
        num_selected = expert_outputs.shape[0]

        # Launch Triton kernel: one program per selected token
        grid = (num_selected,)
        scatter_add_rows_kernel[grid](
            output,
            expert_outputs,
            indices_i32,
            rows,
            hidden,
            num_selected,
            BLOCK_SIZE=256,
            num_warps=4,
            num_stages=2,
        )

        return output
```

Analysis and plan

Operation to implement
- We need to clone final_hidden_states (shape [batch_size * seq_len, hidden_size]) to output, then perform:
  output[token_indices[i], :] += expert_outputs[i, :]
  for i in [0, num_selected_tokens). This is equivalent to torch.index_add along dim=0. Duplicates in token_indices must accumulate correctly (no-op if we simply clone; index_add handles accumulation).

Why the current one-program-per-index approach can be suboptimal
- The prior kernel launched one Triton program per selected token and iterated across hidden_size with a loop. While correct, this can limit parallelism and add per-program loop overhead, especially when hidden_size is large or when the number of selected tokens is very high.
- Atomic adds per chunk are fine, but the per-program structure can be further optimized by mapping more of the work to parallel threads directly across the hidden dimension, thereby reducing the number of loop iterations and improving GPU utilization.

Optimization strategy
- Use a 2D grid: one axis over selected tokens, the other over hidden chunks. Each program will handle a fixed “chunk” along the hidden dimension for a single token. This eliminates the inner loop over hidden and increases concurrency.
  - grid = (num_selected_tokens, ceil_div(hidden_size, BLOCK_SIZE))
  - Inside each program, compute the base offsets (row base for output and token base for expert), load the chunk vector, and do atomic_add into output.
- This approach:
  - Removes the inner Python loop over hidden in the kernel, replacing it with direct vectorized operations per program.
  - Increases the number of programs (grid size), improving parallelism and occupancy across different hidden sizes.
  - Keeps atomic_add per program chunk, which is necessary for correctness when multiple indices target the same row (duplicates).

Design details
- output_ptr, expert_ptr, indices_ptr:
  - output_ptr: pointer to the output tensor with layout [rows, hidden].
  - expert_ptr: pointer to expert_outputs with layout [num_selected_tokens, hidden].
  - indices_ptr: pointer to token_indices as int32.
- grid mapping:
  - axis=0: program_id(0) selects the token i in [0, num_selected_tokens).
  - axis=1: program_id(1) selects the hidden chunk j in [0, ceil_div(hidden_size, BLOCK_SIZE)).
  - For a given j, the columns handled by the program are j*BLOCK_SIZE + arange(BLOCK_SIZE), masked by cols < hidden.
- Stride-free addressing:
  - With contiguous tensors, row base offset = row_index * hidden, and element offset within a row is simply cols.
- Dtypes:
  - final_hidden_states and expert_outputs are bfloat16; Triton atomic_add supports bf16, so we can keep dtype consistent without casts. We’ll ensure loads/stores use bf16.

Launch parameters
- BLOCK_SIZE: 256. This is a good balance across a wide range of hidden sizes, avoiding too many masks and keeping vector width manageable. It worked well in earlier runs and should continue to perform robustly.
- num_warps: 4, num_stages: 2. This is a balanced choice for 256-wide vector operations and typically provides good occupancy and throughput.

Edge cases and correctness
- token_indices can repeat; index_add semantics require accumulation. Our kernel uses atomic_add, which ensures correctness in the presence of duplicates.
- If hidden_size is not divisible by BLOCK_SIZE, the grid’s second axis handles the remainder via mask in loads/stores.
- We keep host code minimal and Triton-only: clone final_hidden_states, cast token_indices to int32, and launch the kernel. No torch.index_add or other PyTorch tensor operations in host.

```python
import torch

# Triton imports
try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False


# Triton kernel: scatter-add expert_outputs[i, :] into output[token_indices[i], :]
# 2D grid: axis=0 over tokens, axis=1 over chunks of the hidden dimension.
@triton.jit
def scatter_add_rows_chunks_kernel(
    output_ptr,         # *ptr to output [rows, hidden]
    expert_ptr,         # *ptr to expert_outputs [num_selected_tokens, hidden]
    indices_ptr,        # *ptr to token_indices [num_selected_tokens] (int32)
    rows,               # number of rows in output (i.e., batch_size * seq_len)
    hidden,             # hidden_size (number of columns)
    num_selected,       # num_selected_tokens
    BLOCK_SIZE: tl.constexpr,  # chunk size across hidden dimension (256)
):
    pid_token = tl.program_id(axis=0)   # which token this program handles
    pid_chunk = tl.program_id(axis=1)   # which chunk along hidden this program handles

    # Each program handles exactly one token (pid_token) and one hidden chunk (pid_chunk).
    # Compute the destination row for this token.
    row_dst = tl.load(indices_ptr + pid_token)  # int32 index into output rows

    # Compute the hidden column offsets for this chunk
    start = pid_chunk * BLOCK_SIZE
    cols = start + tl.arange(0, BLOCK_SIZE)
    mask = cols < hidden

    # Base offsets for output row and expert token
    base_out = row_dst * hidden
    base_exp = pid_token * hidden

    # Load current values from output and expert for this chunk
    out_vals = tl.load(output_ptr + base_out + cols, mask=mask, other=0)  # bf16
    exp_vals = tl.load(expert_ptr + base_exp + cols, mask=mask, other=0)  # bf16

    # Atomic add contributions for this chunk
    tl.atomic_add(output_ptr + base_out + cols, exp_vals, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(
        self,
        final_hidden_states: torch.Tensor,
        expert_outputs: torch.Tensor,
        token_indices: torch.Tensor,
    ) -> torch.Tensor:
        # Ensure Triton is available; if not, fallback to torch for correctness
        if not TRITON_AVAILABLE:
            output = final_hidden_states.clone()
            output.index_add_(0, token_indices, expert_outputs)
            return output

        # Allocate output as a clone of final_hidden_states (dtype and device preserved)
        output = final_hidden_states.clone()

        # Ensure token_indices are int32 for Triton
        indices_i32 = token_indices.to(torch.int32)

        # Shapes
        rows = final_hidden_states.shape[0]
        hidden = final_hidden_states.shape[1]
        num_selected = expert_outputs.shape[0]

        # Launch Triton kernel: 2D grid over tokens and hidden chunks
        # BLOCK_SIZE=256 works well across a range of hidden sizes.
        BLOCK_SIZE = 256
        grid = (num_selected, triton.cdiv(hidden, BLOCK_SIZE))

        scatter_add_rows_chunks_kernel[grid](
            output,
            expert_outputs,
            indices_i32,
            rows,
            hidden,
            num_selected,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,
            num_stages=2,
        )

        return output
```

- Vectorized loads/stores and atomic adds per chunk are efficient and avoid Python-level loops in the kernel, which can be a bottleneck for some shapes.
- The configuration (BLOCK_SIZE=256, num_warps=4, num_stages=2) is a robust choice across diverse workloads; it performed well in previous runs and is unlikely to regress relative to the one-program-per-token approach.
