We are consistently correct across all 16 workloads. The latest speedup is ~1.65x, which is solid but below our earlier ~2.0x. The operation is a scatter-add along rows (dim=0): for each selected token i, output[token_indices[i], :] += expert_outputs[i, :]. Duplicates in token_indices must accumulate, which is exactly what atomic_add semantics provide.

Current approach and why it’s robust
- We launch one Triton program per selected token row (N programs). Each program:
  - Loads its hidden vector (H elements) in BLOCK chunks.
  - Atomically adds those values into the destination row out[token_indices[i], :] in BLOCKed chunks.
- This design avoids per-element atomics, keeps correctness (accumulation for duplicates), and previously achieved higher speedups.

Why performance varied and plan to improve
- Performance can vary depending on BLOCK size and num_warps. If BLOCK is too large for a given H, it can increase register pressure and reduce occupancy; if too small, loop overhead and atomics per chunk can increase.
- We’ll refine BLOCK selection to reduce the number of chunks while keeping resource usage manageable. We’ll cap BLOCK to 256 and pick it as the next power-of-two of H, but clamp to 256. This minimizes chunks for larger H (e.g., H=1024 -> BLOCK=256 -> 4 chunks) and keeps the kernel simple and masked for tails. We’ll keep num_warps=4 for BLOCK<=128 and num_warps=8 for BLOCK=256, with num_stages=2.

This deterministic configuration avoids autotuning overhead and instability while tailoring BLOCK to H.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def _index_add_rows_kernel(
    out_ptr,        # *half, output buffer (final_hidden_states clone)
    expert_ptr,     # *half, expert_outputs (N, H)
    indices_ptr,    # *int32, token_indices (N,)
    N,              # int32, number of selected tokens
    H,              # int32, hidden size
    BLOCK: tl.constexpr,
):
    pid = tl.program_id(axis=0)
    if pid >= N:
        return

    # Destination row index for this selected token
    idx = tl.load(indices_ptr + pid)
    # Assume idx is valid in [0, N). We do not clamp for correctness here.

    # Iterate over the hidden dimension in chunks of BLOCK
    # out_ptr is laid out as (N_rows, H_cols) with strides, but since we're atomically adding
    # to a specific row, we compute the base address and then add column offsets.
    base = idx * H  # because we will assume out is (N_rows_out, H), and idx is a row index
                    # Note: we do not need to map idx to output row index; we just add into the
                    # destination row 'idx' of the output. idx here is token_indices[i].

    # We need to get N_rows_out to know how many rows exist in output. However, Triton kernel
    # does not have access to Python-side variables. Instead, we rely on host code to ensure
    # out_ptr points to a tensor of shape (N_rows_out, H). Since we don't have N_rows_out here,
    # we compute offsets relative to the base row 'idx' and assume out has at least idx row.
    # In practice, out is cloned from final_hidden_states which has N_rows_out = batch_seq_len.
    # token_indices is in [0, batch_seq_len), so idx is valid. Thus base points to the start
    # of destination row.

    # We iterate columns in BLOCK chunks
    # Note: Triton requires loops over constexpr ranges. We emulate by using a static range
    # and masking with a runtime condition. Instead, we use a while loop style by iterating
    # over tl.arange and using a runtime loop counter.
    # But Triton supports Python 'for' loops with tl.arange, and masking with runtime variables.
    # Here, we implement a for loop over start from 0 to H in steps of BLOCK using a Python
    # for construct. Triton will unroll or handle this per launch.

    # Better: use a dynamic loop with tl.arange and tl.static_range by creating a range with
    # runtime start and BLOCK size. Triton supports for start in range(0, H, BLOCK) with BLOCK
    # as constexpr. We'll do that.

    # We'll write a for loop over start from 0 to H in steps of BLOCK, using tl.arange
    for start in range(0, H, BLOCK):
        cols = start + tl.arange(0, BLOCK)
        mask = cols < H

        # Load the corresponding expert values for this row
        expert_vals = tl.load(expert_ptr + pid * H + cols, mask=mask, other=0.0)

        # Compute the output addresses: out_ptr + base + cols
        out_addrs = out_ptr + base + cols

        # Atomically add to the destination row
        tl.atomic_add(out_addrs, expert_vals, mask=mask)


def _run_triton_index_add(final_hidden_states: torch.Tensor,
                           expert_outputs: torch.Tensor,
                           token_indices: torch.Tensor) -> torch.Tensor:
    """
    Triton implementation of output.index_add_(dim=0, index=token_indices, source=expert_outputs)
    where output is a clone of final_hidden_states.
    """
    assert expert_outputs.dim() == 2, "expert_outputs must be 2D (N, H)"
    assert token_indices.dim() == 1, "token_indices must be 1D (N,)"
    N, H = expert_outputs.shape
    # Ensure contiguous tensors
    out = final_hidden_states.clone().contiguous()
    expert = expert_outputs.contiguous()
    indices = token_indices.to(torch.int32).contiguous()

    # Choose BLOCK based on H: next power of two, capped at 256
    # Helper to compute next power of two
    # Note: Triton doesn't see Python variables, so we compute BLOCK here and pass as constexpr.
    def _next_power_of_two(x: int) -> int:
        # For x > 0, next power of two
        return 1 << (x - 1).bit_length()

    BLOCK = min(_next_power_of_two(H), 256)

    # num_warps heuristic: 4 for <=128, 8 for 256
    num_warps = 4 if BLOCK <= 128 else 8
    num_stages = 2

    # Launch grid: one program per row
    grid = (N,)

    _index_add_rows_kernel[grid](
        out, expert, indices,
        N, H,
        BLOCK=BLOCK,
        num_warps=num_warps,
        num_stages=num_stages,
    )
    return out


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor) -> torch.Tensor:
        # Only Triton computation allowed; no torch ops in host code.
        return _run_triton_index_add(final_hidden_states, expert_outputs, token_indices)
```
