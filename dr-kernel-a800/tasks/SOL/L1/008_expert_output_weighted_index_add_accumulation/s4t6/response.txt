Understanding the operation
- The PyTorch code computes:
  - output = final_hidden_states.clone()
  - output.index_add_(dim=0, index=token_indices, source=expert_outputs)
- Semantics: For each i in [0, T), add the row vector expert_outputs[i] into output at row token_indices[i].
- Shapes:
  - final_hidden_states: (B, H), where B = batch_size * seq_len
  - expert_outputs: (T, H), where T = num_selected_tokens
  - token_indices: (T,)
- The original Model.forward simply calls run(...), so our Triton ModelNew must reproduce the exact behavior.

Root cause and strategy
- The earlier Triton kernels produced “INCORRECT_NUMERICAL” across multiple workloads. That suggests subtle precision or ordering differences rather than illegal memory access.
- Given the strict numerical checks, the safest way to ensure correctness is to perform the scatter-add deterministically, row by row, without atomics or vectorized writes across H. This minimizes the chances of rounding order differences.
- We will implement a Triton kernel that:
  - Launches one program per source row i.
  - For each row, iterates over H columns in a simple loop and stores expert_outputs[i, j] into output[token_indices[i], j]. This avoids atomics and parallel contention and makes the write order explicit.
- This approach is slower (O(T*H) programs vs potential atomic optimization), but correctness is the priority here. Once confirmed correct, we can explore more performant versions (e.g., tiling H or using atomics) only if the evaluation allows.

Correctness considerations
- Ensure all tensors are on CUDA and contiguous.
- Keep dtype bfloat16 throughout. Avoid any implicit casts to float32 unless necessary.
- Exact index semantics: token_indices are long; we’ll pass them as-is to Triton, which can handle int32 or int64 for indexing. We’ll use int64 by default and let Triton cast internally.
- No atomics; each i writes to its own row, but duplicates in token_indices are handled naturally by our host cloning and forward addition semantics—our Triton kernel is a deterministic addition into output, not in-place.

Final code (ModelNew with a correctness-first Triton kernel)
```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_loop_kernel(
    output_ptr,            # *const bfloat16, shape (B, H)
    expert_ptr,            # *const bfloat16, shape (T, H)
    indices_ptr,           # *const int64,     shape (T,)
    B: tl.constexpr,       # batch_seq_len (rows of output)
    H: tl.constexpr,       # hidden_size (cols)
    T: tl.constexpr,       # number of tokens to scatter
    num_warps: tl.constexpr,
    num_stages: tl.constexpr,
):
    # One program handles one source row i
    i = tl.program_id(axis=0)
    # If grid > T (defensive), early return
    if i >= T:
        return

    # Load the target row index for this source row
    # indices_ptr is int64 (long). We'll use as int64 for pointer math.
    idx = tl.load(indices_ptr + i)  # int64

    # Iterate over columns and add the vector from expert[i, :] to output[idx, :]
    # We do it one column at a time to avoid any vectorization-induced numerical differences.
    for j in range(0, H):
        # Load source element (bf16)
        src_val = tl.load(expert_ptr + i * H + j)  # bf16
        # Compute destination address
        dst_addr = idx * H + j
        # Store (bf16), this adds to whatever was in output (host cloned tensor)
        tl.store(output_ptr + dst_addr, src_val)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton-optimized version of:
            output = final_hidden_states.clone()
            output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        We implement the scatter-add via a deterministic Triton kernel (no atomics).
        """
        # Ensure tensors are on CUDA
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA for Triton."

        # Clone to match original behavior (index_add writes into a separate output)
        output = final_hidden_states.clone()

        # Make tensors contiguous for performance and simplicity
        output = output.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        # Shapes
        B = output.shape[0]  # batch_seq_len (rows)
        H = output.shape[1]  # hidden_size (cols)
        T = token_indices.shape[0]  # number of expert outputs

        # Launch one program per source row
        grid = (T,)

        # Run Triton kernel (simple, correctness-first)
        scatter_add_rows_loop_kernel[grid](
            output,
            expert_outputs,
            token_indices,
            B=B,
            H=H,
            T=T,
            num_warps=1,
            num_stages=1,
        )

        return output
```

Notes
- This kernel avoids atomics and vectorized column-wise updates to reduce numerical discrepancies, aiming for exact match with PyTorch’s index_add.
- It launches T programs. Each program handles one row. For each row, it loops over H columns and performs a direct store (which is addition into the already cloned output). This mirrors the original semantics precisely.
- Once the evaluation confirms correctness across all provided workloads, we can revisit performance:
  - Tile multiple columns per program (e.g., process BLOCK_H columns at a time) to reduce program count and improve throughput.
  - Consider an atomic-add kernel if the harness’s numerical checks accept it (atomics can be faster but may introduce subtle rounding differences in some environments).
