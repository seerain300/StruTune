Re-analysis of the task
- The PyTorch code performs a scatter-add along dim=0:
  - output = final_hidden_states.clone()
  - output.index_add_(dim=0, index=token_indices, source=expert_outputs)
  - This means: for each i in [0, T), output[token_indices[i]] += expert_outputs[i, :].
- Shapes:
  - output: (B, H), where B = batch_size * seq_len, H = hidden_size
  - expert_outputs: (T, H)
  - token_indices: (T,), int64
- get_inputs creates random tensors, so results are stochastic; any implementation must match the PyTorch index_add behavior exactly.

Why earlier submissions failed correctness
- The evaluation repeatedly reports “INCORRECT_NUMERICAL” across different workloads, which means our Triton implementation produced outputs that differ from the reference in a way the checker detects. Since the data is random, the differences aren’t due to logic; they’re due to subtle numerical discrepancies (e.g., order of additions, dtype casting on load/store, or non-deterministic behavior).
- The most plausible cause is the usage of tl.atomic_add and/or vectorized loads/stores across the H dimension, which can lead to different accumulation order for bf16 and thus different rounding results.

Plan for correctness and Triton compliance
- Implement a Triton kernel that:
  - Launches one program per source row i.
  - Iterates serially over the hidden dimension h from 0 to H-1.
  - Loads idx = token_indices[i] (as int64 then int32 for pointer arithmetic).
  - Loads the scalar expert_outputs[i, h] in bf16.
  - Adds it to output[idx, h] in bf16 and stores back.
- This avoids atomics and any parallel write hazards and ensures that each contribution is written exactly once, matching index_add semantics (including duplicates, which will be written multiple times due to separate programs).
- Be careful with dtypes: keep everything in bfloat16, avoid any implicit casting to float32. Use tl.load/tl.store with correct pointer arithmetic and explicit bf16 handling.
- After correctness is verified, we can revisit performance (e.g., processing multiple columns per program or revisiting atomic-add with precise semantics), but the primary goal is to get correct outputs.

Triton implementation (ModelNew)
Below is a Triton kernel and a ModelNew forward that launches this kernel. The kernel performs the scatter-add without atomics, iterating over the hidden dimension to minimize numerical differences and ensure correctness.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_serial_kernel(
    output_ptr,          # *bf16
    expert_ptr,          # *bf16
    indices_ptr,         # *int64
    B: tl.constexpr,     # batch_seq_len (rows of output)
    H: tl.constexpr,     # hidden_size (cols of output)
    T: tl.constexpr,     # number of source rows (token_indices length)
):
    # One program per source row i
    i = tl.program_id(0)
    # Bounds check
    if i >= T:
        return

    # Load token index as int64 then cast to int32 for pointer arithmetic
    idx64 = tl.load(indices_ptr + i)
    idx = idx64.to(tl.int32)

    # Iterate over hidden dimension serially to minimize numerical differences
    for h in range(0, H):
        # Load the value from expert_outputs[i, h] as bfloat16
        val = tl.load(expert_ptr + i * H + h)  # bf16 scalar
        # Load the corresponding output row element
        out_val = tl.load(output_ptr + idx * H + h)  # bf16 scalar
        # Add and store back
        out_val = out_val + val
        tl.store(output_ptr + idx * H + h, out_val)


class ModelNew(torch.nn.Module):
    def forward(
        self,
        final_hidden_states: torch.Tensor,
        expert_outputs: torch.Tensor,
        token_indices: torch.Tensor,
    ):
        """
        Triton implementation of:
            output = final_hidden_states.clone()
            output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        We perform the scatter-add via a Triton kernel that iterates over the hidden dimension
        serially for each source row to minimize numerical discrepancies.
        """
        # Ensure CUDA tensors
        assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, \
            "All tensors must be on CUDA for Triton."

        # Clone to match original behavior
        output = final_hidden_states.clone()

        # Ensure contiguity (row-major)
        output = output.contiguous()
        expert_outputs = expert_outputs.contiguous()
        token_indices = token_indices.contiguous()

        # Shapes
        B = output.shape[0]  # batch_seq_len
        H = output.shape[1]  # hidden_size
        T = token_indices.shape[0]  # number of expert outputs

        # Launch one program per source row
        grid = (T,)

        # Run Triton kernel; use small num_warps/num_stages for numerical stability
        scatter_add_rows_serial_kernel[grid](
            output, expert_outputs, token_indices,
            B=B, H=H, T=T,
            num_warps=1,
            num_stages=1,
        )

        return output
```

Notes
- This kernel avoids atomics and processes each hidden column one by one, which should make our results very close to PyTorch’s index_add for bf16. It ensures that each expert contribution is added at the exact target row.
- If you need to optimize performance later (once correctness is confirmed), we can:
  - Process a small tile of columns per program (e.g., BLOCK_H = 8 or 16) and use vectorized loads/stores while carefully controlling accumulation order.
  - Consider a two-phase approach: first mark duplicates and then perform batched adds, but this complicates the kernel and may not help unless duplicates are frequent.
- The current approach prioritizes correctness and adheres to the Triton-only requirement: all computation is done inside Triton kernels launched from ModelNew.forward.
