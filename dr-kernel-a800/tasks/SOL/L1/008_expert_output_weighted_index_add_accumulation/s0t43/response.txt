Analysis
- Operation: output[token_indices[i]] += expert_outputs[i] with output shape (M, H), expert_outputs shape (N, H), token_indices length N, M = batch_size * seq_len. This is a scatter-add along rows (dim=0).
- Current kernel: one Triton program per source row i. Inside, it iterates over H in chunks of BLOCK_H, loads token_indices[i], expert_outputs[i, h_block], and performs atomic_add to the appropriate row in output. This approach is simple, robust, and already faster than PyTorch’s baseline.

Bottlenecks and opportunities
- Atomic contention: If many indices map to the same output row, multiple programs contend on the same address. We can’t fully avoid atomics in a single pass without a per-row reduction (two-phase approach), which increases complexity and risk. The current approach is therefore reasonable.
- Per-program efficiency: Increasing the work per program reduces loop overhead and can improve throughput. However, we must choose BLOCK_H carefully to balance register pressure and occupancy across different H sizes. The last adaptive change improved performance in some cases but regressed in others. We can keep the adaptive strategy but slightly refine thresholds and warps/stages to better suit common sizes.

Plan
- Keep one program per source row i (grid size = N).
- Use adaptive BLOCK_H:
  - If H >= 2048, use BLOCK_H=256, num_warps=8, num_stages=2. For very large H, larger chunks reduce loop iterations.
  - Else if H >= 512, use BLOCK_H=128, num_warps=4, num_stages=2. This is a balanced choice for medium H.
  - Else, use BLOCK_H=64, num_warps=2, num_stages=2. For small H, smaller chunks keep register usage low and occupancy high.
- Ensure all tensors are contiguous and token_indices is int32. Perform address arithmetic in 64-bit for safety.
- Keep the while loop over H with runtime condition; this avoids Triton compile-time limitations and has proven robust.

This should further stabilize and potentially improve performance across diverse shapes while maintaining correctness.

Final code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_row_kernel(
    output_ptr,     # *bf16, shape [M, H], contiguous
    expert_ptr,     # *bf16, shape [N, H], contiguous
    index_ptr,      # *int32, shape [N]
    M: tl.int32,    # total rows in output
    H: tl.int32,    # hidden size (columns)
    N: tl.int32,    # number of source rows to add
    BLOCK_H: tl.constexpr,  # chunk size along H
):
    # One program per source row i
    i = tl.program_id(0)
    # guard in case grid > N (though we set grid=N)
    if i >= N:
        return

    # Load token index for this source row (int32)
    token = tl.load(index_ptr + i)  # int32

    # Iterate over H in chunks of BLOCK_H
    start = 0
    while start < H:
        h_offsets = start + tl.arange(0, BLOCK_H)          # [BLOCK_H], int32
        mask = h_offsets < H                                # mask for valid columns

        # Compute row addresses for output and expert rows
        # Cast to 64-bit for pointer arithmetic safety
        M64 = tl.full((), M, tl.int64)
        i64 = tl.full((), i, tl.int64)
        token64 = tl.full((), token, tl.int64)
        H64 = tl.full((), H, tl.int64)
        start64 = tl.full((), start, tl.int64)

        # Output dest addresses: output[token, h_offsets]
        dest_row_offset = token64 * H64                     # row offset
        dest_col_offset = h_offsets.to(tl.int64)            # column offset (vector)
        dest_addr = output_ptr + (dest_row_offset + dest_col_offset)  # [BLOCK_H], int64

        # Expert addresses: expert[i, h_offsets]
        src_row_offset = i64 * H64
        src_addr = expert_ptr + (src_row_offset + h_offsets.to(tl.int64))  # [BLOCK_H], int64

        # Load values with mask
        vals = tl.load(src_addr, mask=mask, other=0.0)      # [BLOCK_H] bf16
        # Atomically add into output
        tl.atomic_add(dest_addr, vals, mask=mask)

        start += BLOCK_H


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        """
        Triton implementation of:
          output = final_hidden_states.clone()
          output.index_add_(dim=0, index=token_indices, source=expert_outputs)
        """
        # Ensure contiguity and dtypes
        output = final_hidden_states.contiguous()
        expert_outputs = expert_outputs.contiguous()
        # Make token_indices int32 for Triton
        if token_indices.dtype != torch.int32:
            token_indices = token_indices.to(torch.int32)

        M = output.shape[0]
        H = output.shape[1]
        N = token_indices.shape[0]

        # Choose BLOCK_H, num_warps, num_stages adaptively based on H
        if H >= 2048:
            BLOCK_H = 256
            num_warps = 8
            num_stages = 2
        elif H >= 512:
            BLOCK_H = 128
            num_warps = 4
            num_stages = 2
        else:
            BLOCK_H = 64
            num_warps = 2
            num_stages = 2

        # Launch one program per source row
        grid = (N,)
        scatter_add_row_kernel[grid](
            output,
            expert_outputs,
            token_indices,
            M,
            H,
            N,
            BLOCK_H=BLOCK_H,
            num_warps=num_warps,
            num_stages=num_stages,
        )

        return output
```

Notes
- The kernel processes one source row per program and iterates over H in chunks of BLOCK_H, performing atomic adds to the appropriate output row. This avoids cross-row coordination and keeps correctness.
- The adaptive BLOCK_H selection aims to improve throughput for larger H while keeping efficiency for smaller H. num_warps/num_stages are set to balanced values for common GPUs.
- We ensure inputs are contiguous and token_indices are int32. Address arithmetic is done in 64-bit for safety.
- This approach preserves correctness across all provided workloads and should provide stable or improved performance compared to the previous version.
