Analysis, root cause, and plan

- Behavior to implement:
  - output = final_hidden_states.clone() where final_hidden_states has shape [M, H] and M = batch_size * seq_len.
  - For each i in [0, N), where N = M * num_experts_per_tok, perform output[token_indices[i]] += expert_outputs[i]. token_indices[i] are in [0, M). This is equivalent to torch.index_add(dim=0, index=token_indices, source=expert_outputs) with atomic adds for duplicates.

- What went wrong in the last attempt:
  - The “dynamically tuned” kernel selected BLOCK_H as a power of two of H and used masked atomic_add across tiles. While previously this approach produced correct results and good speedups, the latest evaluation showed numerical mismatches in multiple workloads. The most plausible causes are:
    - Masking bugs in the vectorized H-tiling loop (e.g., loading/storing with incorrect masks or using “other” values that could subtly affect accumulation).
    - Launch configuration (block size, num_warps, num_stages) interacting with H and the atomic path in a way that is not reproducible or consistent across the test harness.
  - Earlier, we achieved 16/16 correctness with a simpler configuration (BLOCK_H=256, num_warps=4, num_stages=2). The numerical mismatches appeared after changing the tiling logic.

- Fix and strategy:
  - Revert to the robust, previously validated per-row kernel:
    - One Triton program per source row (grid = N).
    - Vectorize across H using a fixed tile size BLOCK_H=256 and use masked tl.atomic_add across the hidden dimension.
    - num_warps=4 and num_stages=2, which performed well and yielded 2.02x speedup earlier.
  - Ensure tensors are contiguous, token_indices are int32, and dtypes are bfloat16.
  - Keep masked loads/stores for the H tail, with the “other=0” pattern for masked loads/stores that is consistent with previous correct submissions.
  - Avoid dynamic power-of-two tiling or multi-row per program, which introduced correctness issues.

- Expected impact:
  - This restores correctness across all workloads. Performance may slightly vary but should remain consistently above ~1.45x speedup and potentially approach the earlier ~2.0x, given the reliable configuration.

Final code

```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_rows_kernel(
    out_ptr,          # *const bfloat16, shape [M, H]
    src_ptr,          # *const bfloat16, shape [N, H]
    indices_ptr,      # *const int32,    shape [N]
    M: tl.constexpr,  # total rows in out_ptr/src_ptr (batch_seq_len)
    H: tl.constexpr,  # hidden size
    N: tl.constexpr,  # total source rows (M * num_experts_per_tok)
    BLOCK_H: tl.constexpr,  # tile size across hidden dim (e.g., 256)
):
    # One program handles one source row i
    i = tl.program_id(0)
    # Guard in case grid > N (not needed if grid == N, but safe)
    if i >= N:
        return

    # Load destination row index for this source row
    dest_row = tl.load(indices_ptr + i).to(tl.int32)

    # Base offsets for source and output rows
    # out_ptr is laid out as row-major [M, H]
    # src_ptr is laid out as row-major [N, H]
    # We process hidden dimension in tiles of BLOCK_H
    for h_start in range(0, H, BLOCK_H):
        h_offsets = h_start + tl.arange(0, BLOCK_H)
        mask = h_offsets < H

        # Load source values for this row i across H tile
        src_row_ptr = src_ptr + i * H
        vals = tl.load(src_row_ptr + h_offsets, mask=mask, other=0.0)  # bfloat16

        # Compute output pointer for the destination row and atomic add
        out_row_ptr = out_ptr + dest_row * H
        # Atomic add: for masked positions, 'vals' is zero so it's a no-op
        tl.atomic_add(out_row_ptr + h_offsets, vals, mask=mask)


def _run_triton_scatter_add(final_hidden_states: torch.Tensor,
                            expert_outputs: torch.Tensor,
                            token_indices: torch.Tensor) -> torch.Tensor:
    """
    Triton implementation of index_add along dim=0:
    output[token_indices[i]] += expert_outputs[i]
    with output initialized to final_hidden_states.clone().
    """
    assert final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, \
        "All tensors must be on CUDA device for Triton execution."

    # Ensure dtypes and contiguity
    out = final_hidden_states.clone()
    # Shapes
    M = out.shape[0]  # batch_seq_len
    H = out.shape[1]
    N = expert_outputs.shape[0]

    # Make sure inputs are contiguous
    out = out.contiguous()
    expert_outputs = expert_outputs.contiguous()
    token_indices = token_indices.to(torch.int32)

    # Launch configuration: one program per source row
    grid = (N,)

    # Use a fixed tile size and warps that previously gave best performance
    BLOCK_H = 256
    # Heuristic: 4 warps for 256 tile, 2 stages for pipelining
    scatter_add_rows_kernel[grid](
        out, expert_outputs, token_indices,
        M, H, N,
        BLOCK_H=BLOCK_H,
        num_warps=4,
        num_stages=2,
    )
    return out


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor) -> torch.Tensor:
        # The Triton kernel performs the atomic scatter-add.
        # final_hidden_states is cloned and modified in-place by the kernel.
        # Ensure tensors are on CUDA; if not, we can fallback to PyTorch for correctness.
        if final_hidden_states.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda:
            return _run_triton_scatter_add(final_hidden_states, expert_outputs, token_indices)
        else:
            # Fallback: pure PyTorch implementation for non-CUDA tensors
            out = final_hidden_states.clone()
            out.index_add_(dim=0, index=token_indices, source=expert_outputs)
            return out
```

Notes:
- The kernel maps one Triton program to each source row i, which is robust for correctness and has previously achieved strong speedups (~2.0x).
- We use masked loads/stores with other=0 and perform tl.atomic_add on each tile across the hidden dimension. Since masked positions have vals = 0, they are no-ops, preserving correctness for any H not divisible by BLOCK_H.
- We keep dtype as bfloat16, indices as int32, and ensure contiguity. This avoids prior masking/other-related issues and should restore the 16/16 correctness seen
