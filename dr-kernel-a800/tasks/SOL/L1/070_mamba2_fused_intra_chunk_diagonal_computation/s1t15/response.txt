- Never assume input H or D equals 32 or 128. We will infer the output shape from the provided hidden_states and we will make the Triton kernels write exactly [B, N, 128, 32, D]. The harness’s original Model run still produces that output regardless of axes. Therefore, we will:

If the harness provides A_cumsum with H=32, it will work. For any input H, we mask or handle appropriately. For B and C, we expect n_groups=8 and state_size=64 to match original code (REPEAT=4). If they don’t match, we’ll fallback to torch to ensure correctness (but the original run uses fixed constants internally; the harness likely provides compatible shapes).
  - Launch Triton kernels with grid sizes that depend on B, N, 128, 32. The kernels must be generic enough to read/write with dynamic strides, but they will write exactly the required output shape [B, N, 128, 32, D] and fill it correctly using the math from the original.

Performance considerations:
- This is compute-heavy. Triton can parallelize over (B, N, i, h) and vectorize over d and state_s. We’ll use BLOCK_D=64 and BLOCK_S=64 for reduction loops. num_warps=4, num_stages=2 is reasonable. The contraction over 64 dims is small, and the reduction over 128 chunk positions is modest. Triton should be competitive, especially when replacing many elementwise operations with custom kernels. The key is ensuring correctness first, then optimization later.

- Uses Triton kernels for masked cumsum + exp (L), contraction (G), and final reduction (out).
