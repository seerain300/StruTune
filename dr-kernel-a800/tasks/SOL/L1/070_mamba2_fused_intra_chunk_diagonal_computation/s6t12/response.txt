- The earlier attempts either defined Triton kernels that were not launched, or used host-side PyTorch operations for cumsum/exp (which violated the Triton-only requirement). The evaluation showed runtime errors across workloads. The most likely issues are:

Design for robust Triton implementation
- Implement three main Triton kernels:
  1) cumsum_exp_tril_kernel: computes L[b, h, n, i, j] = exp(cumsum(masked A)) where masked A has j>i set to 0. We will pass B,H,N,S as constexpr so the kernel can loop over i and j in compile-time known ranges (S=128). We’ll create A_masked by reading A and writing to L, setting L to 0 for j>i. cumsum along i: for each fixed (b,h,n,j), compute prefix = sum_{ii=0..S-1} A[b,h,n,ii] * (ii <= j), then L[b,h,n,i,j] = exp(prefix) if i<=j else 0. This matches torch.tril(diagonal=-1) and cumsum + exp.
  2) g_contract_kernel: computes G[i,j,h] = sum_d C[b,n,i,h,d] * B[b,n,j,h,d]. We launch over (b,n,i,j) and loop over h and D (D=64). This kernel will be simple and robust for small sizes.
  3) y_diag_reduce_kernel: computes Y[b,n,i,h] = sum_j M[b,n,i,j,h] * hidden[b,n,j,h], reducing over j (and also D). We launch over (b,n,i) and loop over h and j.
- Forward will:
  - Ensure tensors are contiguous and on device.
  - Create A_masked via torch.zeros([B,H,N,S,S]) for safety and pass its pointer to the Triton kernel; the kernel will fill it according to logic above.
  - Launch cumsum_exp_tril_kernel for (B,H,N) grid.
  - Launch g_contract_kernel for (B,N,S,S) grid with loops over H and D.
  - Launch m_mul_kernel (elementwise multiply) with L permuted to [B,N,S,S,H].
  - Launch y_diag_reduce_kernel for (B,N,S) grid with loops over H and D.

Performance notes
- This implementation is correct-first and avoids any host-side torch cumsum/exp. The kernels loop over compile-time known sizes (S=128, D=64), which are common in the provided setup.
