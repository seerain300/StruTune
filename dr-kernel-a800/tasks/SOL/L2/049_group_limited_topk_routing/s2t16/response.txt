I fully understand the strict Triton-only requirement: all numerical computation must be performed inside @triton.jit kernels invoked by ModelNew.forward. The previous submissions failed because:
- They relied on torch operations in the host (e.g., torch.topk, torch.gather, torch.sum).
- They either didn’t invoke Triton kernels at all (in earlier attempts), or didn’t cover all computation in Triton.

To fix correctness and satisfy the evaluation, I will provide a single, integrated Triton kernel that:
- Computes logits per token and expert (F.linear equivalent via dot product).
- Applies sigmoid to logits, then adds expert_bias to form scores_for_routing.
- Reshapes to groups [num_tokens, 8, 32], computes top-2 per group, sums to get group scores [num_tokens, 8].
- Selects top-4 groups per token.
- Builds group_mask [num_tokens, 8] (1 for selected groups, 0 otherwise), expands to per-expert mask, and applies it to scores_for_routing: non-selected group elements are set to -inf using a Triton reduction/masked_fill emulation (i.e., elementwise tl.where on GPU).
- Selects top-8 from masked scores (duplicates allowed) using a Triton top-k reduction that iteratively picks the maximum index and removes it by setting to -inf.
- Gathers original logits for those selected indices and normalizes by sum(original_selected_scores + 1e-20) using Triton reductions.
- Applies routed_scaling_factor and stores topk_idx and topk_weight.

All heavy computations (logits, masks, top-k selection, sums) will be performed inside Triton kernels. Host code will only:
- Prepare input tensors (cast to float32).
- Allocate outputs.
- Launch Triton kernels.
- Perform minimal tensor operations (e.g., creating -inf scalar, converting int32 indices to int64).
