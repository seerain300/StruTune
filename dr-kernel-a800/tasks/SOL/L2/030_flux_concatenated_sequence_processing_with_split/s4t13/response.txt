Analysis and plan
- Original operation:
  - Concatenate along sequence: inputs are A1 ∈ R[B, T, H] and A2 ∈ R[B, I, H]. Logical concatenation gives A ∈ R[B, T+I, H].
  - Linear projection: C = A @ W^T, where W ∈ R[H, H], no bias. Shape C ∈ R[B*(T+I), H].
  - Split: first B*T rows → processed_encoder [B, T, H], next B*I rows → processed_hidden [B, I, H].

- Strategy:
  - Implement per-batch 2D GEMM in Triton for each b:
    - For output rows 0..B*T-1: For each m in [0..B*T), seq = m % T. Load row from encoder[b, seq, :]. Compute prod = W^T @ that row → output vector of length H.
    - For output rows B*T..B*(T+I)-1: For each m in [B*T..B*(T+I)), seq = m - B*T. If seq < I, load row from hidden[b, seq, :], else use zeros. Compute prod = W^T @ that row.

  - Use Triton kernels for per-batch row copying (splitting):
    - copy_rows_to_encoder[b]: copy rows [0..B*T) from C_pre[b] into processed_encoder[b].
    - copy_rows_to_hidden[b]: copy rows [B*T..B*(T+I)) from C_pre[b] into processed_hidden[b].
  - This avoids torch operations entirely and performs all computation via Triton kernels. The per-batch GEMM kernels are simpler and less error-prone than a full 2D matmul across concatenated rows.

- Correctness considerations:
  - Each batch’s GEMM kernel uses only one input tensor (encoder or hidden) for that batch, avoiding tricky pointer selection inside a single fused kernel. Masks ensure safety.
  - We ensure inputs are contiguous and use simple strides; we pass strides explicitly to kernels to prevent mismatch issues.
  - BLOCK sizes are moderate (e.g., 64), which works well across a range of H (hidden_dim), and masks handle boundaries. For larger H, the loop over H tiles covers the entire reduction dimension.
