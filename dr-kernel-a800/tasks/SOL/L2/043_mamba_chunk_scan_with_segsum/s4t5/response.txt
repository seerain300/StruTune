Strict TRITON-ONLY analysis and plan

Issue recap:
- The evaluator flagged “decoy kernels”: kernels defined but not launched. That is strictly forbidden. Every Triton kernel we provide must be actually launched from ModelNew.forward for the heavy computation.
- Previously, some kernels were unused or used PyTorch for math (F.pad, cumsum, einsum, exp). We must eliminate all PyTorch math from the host and ensure Triton kernels cover:
  - Padding along the last dimension (F.pad), implemented by a Triton kernel.
  - Cumulative sum (torch.cumsum) along a dimension, implemented by a Triton prefix-sum kernel.
  - Segment sum with triangular mask (torch.tril(diagonal=-1)), implemented by Triton via cumsum with a mask.
  - Contraction einsum-like operations with fixed state_size=256. Implement both needed einsums in Triton:
    - einsum('bcihs,bcjhs->bcijh') where H=num_heads, I=chunk_size, J=chunk_size, S=state_size (256).
    - einsum('bcths,bchds->bcthd') with the same S=256.
  - exp for decays and any per-element exponential must be implemented in Triton elementwise kernels and launched.

Mathematical structure to implement:
- The original forward does:
  - Pad hidden_states to make seq_len multiple of chunk_size=256.
  - Reshape hidden and A into chunks. We can keep reshape in PyTorch (metadata), but compute heavy einsums in Triton.
  - Compute L = exp(segment_sum(A_perm)) with lower-tri mask (diagonal=-1).
  - Compute G = sum over state_size of C[b,nc,i,h,s] * B[b,nc,j,h,s] (einsum('bcihs,bcjhs->bcijh')).
  - M = G * L.
  - Y_diag = sum over j of M[b,nc,i,j,h] * hidden[b,nc,j,h,d] (einsum('bcijh,bcjhd->bcihd')). Implement this in Triton reduction kernel.
  - Inter-chunk recurrence uses einsum('bcths,bchds->bcthd'); implement Triton reduction kernel for S=256.
  - Add D residual and return [B, seq_len, H*D] cast to bfloat16.

Design decisions:
- Implement Triton kernels:
  1) pad_last_dim_3d: pad last dimension of a 3D tensor (hidden_states) to desired padded length.
  2) cumsum_last_dim_4d: prefix sum along the last dimension for a 4D tensor [B, Nc, I, J].
  3) segment_sum4D_lower: compute cumsum along last dimension with lower-tri mask, producing L = exp(segment_sum) with tril(diagonal=-1).
  4) einsum_bcihs_bcjhs_to_bcijh: Triton reduction kernel to compute G, looping over S=256 and accumulating over H, I, J.
  5) einsum_bcths_bchds_to_bcthd: Triton reduction kernel to compute inter-chunk term, looping over S=256 and accumulating.
  6) elementwise_exponential: general exp for any tensor; will be used to compute exp of decays (for inter-chunk propagation). In the original, final_state uses exp; however, the evaluator focuses on forward’s output. We avoid computing final_state and ensure no torch math is used. If final_state were required, we’d add an exp kernel for it, but given constraints, we prioritize the heavy ops that produce the output and avoid any tensors that the original helper didn’t return.

- Ensure all kernels are launched from ModelNew.forward. No PyTorch operations (no torch.cumsum, no F.pad, no torch.exp, no torch.einsum). Only tensor allocations, launches, and simple metadata handling in host code.

- Handle device and dtype: keep float32 for compute; cast output to bfloat16 at the end. Triton kernels can operate on float32 tensors.

- Safety: Triton kernels assume contiguous inputs. We’ll make tensors contiguous before passing to kernels.

- Note: The original helper uses final_state which isn’t returned; our ModelNew.forward will return only the output tensor, which the evaluator compares against. We avoid defining kernels that are not launched to prevent “decoy kernel” flags. Therefore, we will not define unused kernels and will launch every Triton kernel we implement.
