Understanding the failure and constraints

- The evaluator keeps flagging “decoy kernel” rejections, which means we must actually launch each Triton kernel from ModelNew.forward. Any Triton kernel defined must be invoked, and no torch operations should be used for numerical compute.
- The heavy compute in the original code consists of:
  - Generating inputs via torch.randn (we must replace this with Triton).
  - Preprocessing (sorting selected_experts with stable order, bincount, cumsum to determine capacity and grouping).
  - Per token-expert pair:
    - Build expert_inputs of shape [capacity, hidden_size] (mask invalid rows with zeros).
    - Perform three GEMMs: hidden_input @ gate, hidden_input @ up, and activated @ down, where activated = SiLU(gate) * up.
    - Weight contributions and aggregate into the final output.

Given the strict Triton-only requirement, we cannot rely on torch for preprocessing or matmul. We must implement the entire pipeline in Triton:
- Replace torch.randn with a Triton kernel that fills input tensors (selected_experts, routing_logits, hidden_states, expert weights) with random values.
- Implement stable sorting (bitonic) for selected_experts and routing_logits in Triton (we pass arrays as pointers, compare-swap in-kernel, use stable tie-breaking).
- Implement bincount (counts per expert) in Triton (atomic add per element).
- Implement inclusive cumsum (starts per expert) in Triton (pass cumsum output buffer, kernel computes prefix sums via loop).
- Implement mask computation (valid positions within capacity) in Triton.
- Implement building expert_inputs (2D arrays) in Triton (initialize zeros, then copy hidden_input into selected rows using in-kernel loops).
- Implement GEMMs in Triton (row-wise matmul kernels; since Triton lacks high-level torch.bmm, we implement a per-row matmul and loop over K in chunks).
- Implement SiLU and elementwise multiply in Triton.
- Implement weighted aggregation into result via atomic adds (Triton atomic_add).

Note: While this approach ensures all computation is done in Triton and no torch operations are used for numerical compute, implementing stable sort and 2D masked batched GEMMs in Triton is non-trivial. In practice, the evaluator’s previous feedback suggests that “decoy” classification is common unless we provide real Triton launches. Therefore, we will:
- Provide fully self-contained Triton kernels for each major step (random fill, sorting, bincount, cumsum, mask, expert_inputs creation, GEMMs, SiLU, multiply, aggregation).
- Launch these kernels in ModelNew.forward so none are considered decoys.

Potential pitfalls:
- Triton does not support Python for-loops with dynamic ranges. For array-length loops, we use while loops with tl.load/tl.store with masks, or atomic operations where available (tl.atomic_add). For sorting, we perform a bitonic sort network with compile-time known BLOCK size; if N is not a power of two, we pad with sentinel values for correct network behavior.
- Triton atomic_add supports float32 and int32; we will use float32 for atomic accumulation and cast at the end.

Performance considerations:
- This Triton-only implementation will be slower than the original torch implementation due to lack of highly optimized GEMMs and sorting. However, the evaluator’s primary requirement is correctness with Triton launches; we prioritize correctness and proper kernel invocations.

# We assume N is provided and BLOCK is the next power of two >= N (for bitonic network).
@triton.jit
def bitonic_sort_pairs_stable(keys_ptr, vals_ptr, N, BLOCK: tl.constexpr):
    # Each program handles one element i
    i = tl.program_id(0)
    idx = tl.arange(0, BLOCK)
    x = keys_ptr + i
    y = vals_ptr + i

    k_i = tl.load(x)
    v_i = tl.load(y)

    # Bitonic sort network on BLOCK lanes; i is the lane index
    size = 2
    while size <= BLOCK:
        j = size // 2
        while j > 0:
            ixj = i ^ j
            # Load partner lanes
            k_j = tl.load(keys_ptr + ixj)
            v_j = tl.load(vals_ptr + ixj)

            # Decide whether to swap based on direction of current block (i & size) == 0 for ascending
            ascending = (i & size) == 0
            # Stable tie-break: if equal, keep original order (i < ixj)
            swap = tl.where(k_i > k_j, not ascending, tl.where(k_i == k_j, (i < ixj), ascending))

            new_k_i = tl.where(swap, k_j, k_i)
            new_v_i = tl.where(swap, v_j, v_i)

            k_i = new_k_i
            v_i = new_v_i

            j = j // 2
        size = size * 2

    tl.store(x, k_i)
    tl.store(y, v_i)

@triton.jit
def cumsum_inclusive_kernel(out_ptr, in_ptr, length, BLOCK: tl.constexpr):
    # out_ptr and in_ptr are int32, length is int
    # We do an exclusive scan on 'in_ptr' and write inclusive sum into 'out_ptr'.
    # Implement scan using a vectorized approach per BLOCK: compute prefix sums for a chunk.
    for start in range(0, length, BLOCK):
        acc = tl.zeros([BLOCK], dtype=tl.int32)
        offs = start + tl.arange(0, BLOCK)
        mask = offs < length
        # Load counts chunk
        x = tl.load(in_ptr + offs, mask=mask, other=0).to(tl.int32)
        # Compute prefix sums: For each lane j, sum previous lanes
        for j in range(0, BLOCK):
            lane_mask = (start + j) < length
            # acc[j] += x[j]
            acc = tl.where(lane_mask, acc + x[j], acc)
            # Store inclusive sum at (start + j)
            tl.store(out_ptr + (start + j), acc, mask=lane_mask)
