            selected_experts_i64.reshape(-1),
            routing_weights_fp32.reshape(-1),
            expert_gate_weights_fp32.reshape(-1),
            expert_up_weights_fp32.reshape(-1),
            expert_down_weights_fp32.reshape(-1),
            result_fp32,
            num_tokens,
            hidden_size,
            num_experts_per_tok,
            intermediate_size,
            num_warps=1,
            num_stages=1,
        )

        # Return result cast to bfloat16 to match original code's output dtype
        return result_fp32.reshape(num_tokens, hidden_size).to(torch.bfloat16)
```

Notes:
- Forward only allocates, ensures contiguity, casts to float32, and launches the Triton kernel. No torch tensor operations are used in forward, satisfying the evaluator’s constraints.
- The Triton kernel performs all computations: loading hidden state rows, computing gate and up via element-wise loops, applying SiLU, multiplying, and computing the final output via a dot product, then atomic-adding the weighted contribution.
- This should fix the previous runtime errors by removing any torch operations in forward and using Triton exclusively.

Performance:
- This implementation uses explicit loops for GEMMs and is not optimized. It focuses on correctness and adhering to Triton-only constraints. Once correctness is verified, we can optimize by:
  - Implementing Triton matmul kernels for gate, up, and down.
  - Fusing operations to reduce memory traffic.
  - Using 2D grids and vectorization. However, the current priority is to ensure correctness under the evaluator’s strict rules.
