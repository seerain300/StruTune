## 1. What the operation actually computes

### 1.1 Literal reference
Signature: `run(x, x_mask, reverse, {transform_i_conv{0,1,2}_{weight,bias}}_{i=0..3})`.

- `x`: `[B, C=192, T]` float32, contiguous → strides `(C*T, T, 1)`.
- `x_mask`: `[B, 1, T]` float32.
- `reverse`: python `bool` scalar (per-workload).
- Per transform `i` (4 of them): three `Conv1d`, all `kernel_size=5`, `padding=2` (`k//2`), zero-padded:
  - conv0: `(hidden=192, half=96, 5)` + bias → ReLU
  - conv1: `(192, 192, 5)` + bias → ReLU
  - conv2: `(half=96, 192, 5)` + bias  (no activation after)
- `half_channels = 96`.

Reference loop (forward; reverse is the same body with `-` and layers iterated in reverse order):
```
x0 = x[:, :96, :]; x1 = x[:, 96:, :]
h  = conv2(relu(conv1(relu(conv0(x0)))))
h  = h * mask
x1 = x1 ± h
x  = cat([x0, x1], dim=1)
x  = x * mask
```

### 1.2 The critical algebraic simplification
Only the **upper half** `x1` is ever written; `x0 = x[:, :96, :]` is re-sliced from the (unchanged) lower half every iteration, so **`x0` is a constant shared input across all 4 layers**. Because the per-layer updates are pure additions/subtractions, layer order is irrelevant. Therefore the entire block collapses to:

```
S    = Σ_{i=0}^{3} transform_i(x0)            # 4 independent 3-conv stacks on the SAME x0
out0 = x0                                      # lower half is copied verbatim
out1 = x1 ± S                                  # + for forward, − for reverse
out  = mask * cat([out0, out1])                # mask idempotent (0/1)
```
Since `mask` is applied every layer and is 0/1, `mask^2 = mask`, so `out = mask * cat([x0, x1 ± S])` exactly. **Forward vs. reverse differ only by the sign of `S`.**

Consequence: `out[:, :96, :]` is byte-for-byte a copy of the input lower half (mask=1). The only real compute is `S` (a `[B,96,T]` tensor) plus a masked residual add on the upper half.

### 1.3 Reformulating 12 convs → 3 convs (channel stacking)
All 4 `conv0` take the identical input `x0` (96 ch). Stack their weights along the output dim:
1. **conv0_all**: `W0 ∈ [768, 96, 5]`, `x0[96,T] → H0[768,T]`, ReLU. Dense.
2. **conv1_all**: block-diagonal / **grouped conv, groups=4**, each group `192→192`, `W1` as `[768,192,5]` in group form, `H0 → H1[768,T]`, ReLU.
3. **conv2_all**: `W2 ∈ [96, 768, 5]` (the 4 conv2 weights concatenated along the *input* channel dim), `H1[768,T] → S[96,T]`. A dense conv that sums all 768 inputs — this folds the "sum over the 4 transforms" directly into the contraction, since `out[co] = Σ_{ci=0}^{767} Σ_k W2cat[co,ci,k]·H1[ci,·] = Σ_i conv2_i(h1_i)`.

Same total FLOPs as the reference, but reorganized into 3 large, regular ops with better occupancy and far fewer launches. Bias handling: conv0/conv1 biases stack along output; conv2's summed output takes `Σ_i conv2_i_bias` (the four 96-vectors added) as its single bias.

> Weight packing caveat: physically `cat`/`stack`-ing weights with torch is a *computational* op and the contract restricts torch to "metadata and launch plumbing." Safer options (decide in plan): (a) index the 4 separate weight tensors directly inside the Triton kernels via a transform-index grid axis, or (b) pack once per call with a trivial Triton copy kernel. Packing cost is `O(weights)` (~a few MB), independent of `T`, so negligible either way — but I will avoid torch math to respect the rule.

### 1.4 FLOP accounting (per time position, per batch element)
- conv0_all: `768·(96·5)` = 368,640 MAC
- conv1_all: `4·(192·(192·5))` = 737,280 MAC
- conv2_all: `96·(768·5)` = 368,640 MAC
- Total ≈ **1.475M MAC/pos ≈ 2.95 MFLOP/pos**. conv1 is ~50% of the work; it is the tuning priority.

Two clearly distinct regimes drive strategy:
- **Small/latency-bound** (B·T ≤ ~10k): reference issues ~28 kernels/call (12 conv + 4 cat + 8 mask-mul + 4 add). Dominant cost is launch overhead + HBM round-trips of `192×T` intermediates. **Win = collapse to a handful of fused launches and skip cat/mask/x0-copy overhead.** Geomean is heavily influenced by these many small cases, so latency wins matter a lot.
- **Large/compute-bound** (B·T ≥ ~200k): must feed the tensor cores efficiently (tf32 `tl.dot`) and minimize HBM traffic of the `768×T` intermediates. cuDNN is strong here; matching/beating needs good tiling + fusion of the 3 convs along T with halos.

Geomean speedup is the metric and every selected workload must pass correctness, so I must be robust across *all* shapes, not just the big ones. A regression on any tiny case hurts geomean as much as a big case.

## 3. Numerical analysis & risk

- Everything is float32 in/out. Tolerances per workload: `max_atol ∈ [0.0094, 0.013]` (grows with size), `max_rtol = 1e-5`, `required_match_ratio = 0.98`. So 2% of elements may exceed tolerance, and the absolute floor (~0.01) is generous.
- **Reference precision**: PyTorch defaults `torch.backends.cudnn.allow_tf32 = True` and `torch.backends.cuda.matmul.allow_tf32` historically False — but `F.conv1d` on H100 through cuDNN will typically use **TF32**. The golden output is therefore already ~TF32-accurate, and the atol values (scaling up with N) are consistent with TF32-level accumulation error being baked into the tolerance. Implication: a *more* accurate implementation (full fp32) trivially fits inside atol, and a TF32 `tl.dot` implementation should also fit.
- **Magnitude estimate**: `x0 ~ N(0,1)`; weights kaiming `std=sqrt(2/fan_in)`. conv0 pre-ReLU ~ `std≈1` (fan_in 480). After ReLU ~ half-normal. conv1 sums 960 products of (~O(1))·(std≈0.045) → output `std≈1.4`. conv2 sums 3840 terms → `S` per element `O(1–3)`. Final `out1 = x1 ± S`, `O(1–4)`.
  - tf32 relative error ~`2^-11 ≈ 5e-4`. On magnitudes ~2–4 → absolute error ~1e-3, comfortably under atol 0.01 for the vast majority of elements; the 0.98 match ratio absorbs the tail. **tf32 is expected to pass.**
- **Precision knob** (`tl.dot(input_precision=...)`): start `"tf32"` (fast). Escalation ladder if any workload fails correctness: `"tf32x3"` (≈fp32, ~3× dot cost) → `"ieee"` (true fp32, slowest). Choose per-need; conv1 is the accuracy-sensitive one (largest K) if escalation is required.
- **ReLU** is exact — no risk.
- **Zero-padding**: `padding=2` must be *zero* fill at the T boundaries (matches `F.conv1d`). In T-tiled kernels this is masked loads returning `0.0` for `t<0` or `t≥T`. A wrong padding value corrupts the first/last 2 columns → could still pass 0.98 ratio for large T but will fail tiny T (T=128) where 4/128 columns ≈ 3% > 2%. Must get padding exactly right; validate on the T=128 case.
- **Bias**: added once per conv output (conv2 uses the summed 4 biases). Adding bias in fp32 in the epilogue — no risk.
- **Mask**: guaranteed ones by `get_inputs`, but I will still multiply by mask in the epilogue (cost ~ one `[B,96,T]` read/mul, negligible) so correctness does not silently depend on that assumption; broadcast over the 96 channels from `[B,1,T]`.
- **Determinism / layout**: output must be `[B,192,T]` contiguous float32. Lower 96 channels = exact copy of input (a masked copy). No transpose in the returned tensor.

## 4. Triton design space

Common: each conv is an **implicit GEMM**. For conv `Cin→Cout`, k=5, the contraction is `K=Cin·5`; the "N" axis is the flattened `(B,T)` position axis; "M" is `Cout`. The k-window is handled either by (a) an inner loop over the 5 taps accumulating `W_k @ x[:, t+k-2]`, or (b) implicit im2col over `K=Cin*5`. Zero-padding via masked loads on the shifted T index.

Data layout note: within a batch, memory is `[C, T]` row-major → a channel row is contiguous in T; loading a `[Cin, BLOCK_T]` tile plus a ±2 halo in T is coalesced. Batch is the outer stride, so I flatten grid over `(B, T-tiles)`.

### Axis A — fusion granularity (increasing complexity / on-chip reuse)
1. **A0 (baseline, safest):** 3 separate conv kernels (conv0→ReLU epilogue, conv1→ReLU epilogue, conv2→residual+sign+mask epilogue), intermediates `H0,H1` in HBM (`768×T`). Fuses away *all* cat/mask/x0-copy overhead and the 4→1 launch collapse already. Establishes correctness + a real speedup baseline.
2. **A1:** fuse the residual add + reverse-sign + mask + `x1` load into conv2's epilogue (in A0 already); additionally fuse the `x0` lower-half copy as a cheap standalone kernel or `torch` metadata copy of the input slice.
3. **A2 (T-tiled full fusion):** one kernel per `(B, T-tile)` computing conv0→ReLU→conv1→ReLU→conv2→residual, keeping the 768-channel intermediates in SMEM/registers, loading `x0` with a ±6 halo (2+2+2). Eliminates HBM traffic of `H0,H1` (~2×402 MB per intermediate at the largest shape). Biggest potential win for large workloads but hardest; risk of register/SMEM pressure with 768 channels — may need to tile Cout of conv1 and re-loop.
4. **A2′ (partial fusion):** fuse conv0+conv1 (keep H1 resident), separate conv2. Or fuse conv1+conv2. Compromise between A0 and A2.

### Axis B — grouped conv1
conv1 is 4 independent `192→192` convs. Options: (b1) grid axis over group index with per-group weight pointer; (b2) treat as block-diagonal and skip cross-group MACs (mandatory — never compute the zero off-diagonal blocks). This keeps conv1 FLOPs at the true `4·192·192·5`, not `768·768·5` (16× more). **Must implement as grouped, not dense.**

### Axis C — GEMM tiling / occupancy
- Block sizes: `BLOCK_N` (positions) e.g. 64/128/256; M is small (96/192/768) — likely load full M or tile 64/128. `num_warps ∈ {4,8}`, `num_stages ∈ {2,3,4}`. Autotune over a small curated set keyed on N-regime (small vs large) to avoid overfitting/compile blowup.
- For small N (≤ a few k) prefer few CTAs but enough to fill SMs; for the two huge shapes prefer classic GEMM tiling with software pipelining and tf32 `tl.dot`.

### Axis D — precision
`tl.dot(input_precision="tf32")` default; escalate only if correctness fails (see §3).

### Axis E — reverse handling
Single kernel with a `REVERSE`/sign `constexpr` or a runtime scalar `sign = +1/-1` multiplied into `S` before the residual add. No separate code path needed. Pass `sign` as an arg → same compiled kernel serves both.

### What I will NOT do
- No torch/cuDNN conv fallback, no CPU/NumPy path (contract forbids; invalid submission).
- No dense computation of the block-diagonal conv1 (16× waste).
- No reliance on mask being ones for *correctness* (apply it), though I rely on `x0` being constant (that is guaranteed by the algebra of the reference, not by input data).

## 6. Validation strategy
- **Primary correctness/perf signal**: `./scripts/evaluate_candidate.sh feedback cNNN` (full 16-workload set = 1 eval; budget 100). It reports per-workload pass/fail (atol/rtol/0.98-ratio) and speedup vs reference.
- **No direct torch/CUDA execution here** — I cannot self-check numerics locally except through the evaluator and through profiling (`ncu_profile.sh` runs the benchmark python). So c001 is deliberately conservative to spend the *first* eval on a correct build.
- **Boundary focus**: the T=128, B=1 case is the padding/edge stress test and the extreme latency case; the B=64,T=8192 case is the compute/HBM stress test. Both must pass and not regress.
- **Profiling discipline**: use `ncu-report-skill` workflow only through `./scripts/ncu_profile.sh`; ensure no evaluation is running concurrently (foreign process on the locked GPU → controller discards eval, return code 3, wasted budget). Profile only between evaluations to locate the conv1/large-shape bottleneck and guide C-axis tuning.
- **Record-keeping**: append one JSON object per evaluated candidate to `candidates.jsonl` (parent, source hash, hypothesis, validation, per-workload result, geomean, decision, cumulative eval count, skill usage); never rewrite earlier records; new ID for any source/config/launch change.
