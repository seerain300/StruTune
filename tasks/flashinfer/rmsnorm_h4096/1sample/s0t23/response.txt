We’re consistently correct, but the last run showed a regression to ~1.02x. The computation has two clear parts:
- Per-row reduction: inv_rms[row] = rsqrt(mean(x[row]^2) + EPS).
- Elementwise application: out[row, col] = hidden[row, col] * inv_rms[row] * weight[col].

Since the reduction depends on the entire row, we cannot fuse it with the elementwise pass without extra memory traffic. Performance hinges on:
- Efficient per-row reduction with coalesced loads, float32 accumulation, rsqrt, and chunked traversal.
- Efficient elementwise application with minimal grid size and sufficient parallelism (warps/stages) to keep the GPU busy.

Observations from prior runs
- A strong ~1.37x speedup was achieved when:
  - Reduction kernel: one program per row, BLOCK_SIZE=1024, num_warps=8, num_stages=2, simple while loop over columns.
  - Elementwise kernel: 2D grid with BLOCK_SIZE=4096 for H >= 4096, num_warps=16, and grid=(B, cdiv(H, 4096)) => for H=4096, grid=(B, 1). This matches the entire row per block and was faster than a single-block-per-row approach in some environments.

Plan
- Keep the reduction kernel unchanged: it’s robust and previously fast for H=4096.
- Revert the elementwise kernel launch to the 2D pattern that worked best: choose BLOCK_SIZE based on H, then launch with grid=(B, cdiv(H, BLOCK_SIZE)). Avoid grid=(B, 1) for H >= 4096 because it can reduce parallelism and occupancy on some devices. Use:
  - H >= 4096: BLOCK_SIZE=4096, num_warps=16.
  - H >= 2048: BLOCK_SIZE=2048, num_warps=8.
  - Else: BLOCK_SIZE=1024, num_warps=4.
- Keep all math in float32 in-kernel; cast to original dtype at the end to preserve numerics.
- Avoid any incorrect pointer arithmetic by using row_base = hidden_ptr + row * H and simple offsets (inputs are contiguous).

Final code
```python
import torch
import triton
import triton.language as tl


# Reduction kernel: per-row inv_rms = rsqrt(mean(x^2) + EPS)
@triton.jit
def _row_rms_inv_kernel(
    hidden_ptr,            # *const fp16/bf16/fp32, shape [B, H]
    inv_rms_ptr,           # *float32, shape [B]
    B: tl.int32,           # batch size
    H: tl.int32,           # hidden size
    EPS: tl.float32,       # epsilon
    BLOCK_SIZE: tl.constexpr,
):
    row = tl.program_id(0)
    if row >= B:
        return

    # Base pointer for this row (assuming contiguous [B, H] with stride(1) == 1)
    row_base = hidden_ptr + row * H

    sum_sq = 0.0
    col = 0
    while col < H:
        offs = col + tl.arange(0, BLOCK_SIZE)
        mask = offs < H
        x = tl.load(row_base + offs, mask=mask, other=0.0)
        x_f32 = x.to(tl.float32)
        sum_sq += tl.sum(x_f32 * x_f32, axis=0)
        col += BLOCK_SIZE

    mean = sum_sq / H
    inv_rms = tl.rsqrt(mean + EPS)
    tl.store(inv_rms_ptr + row, inv_rms)


# Elementwise apply: out[row, col] = hidden[row, col] * inv_rms[row] * weight[col]
@triton.jit
def _apply_two_scales_kernel(
    hidden_ptr,    # *float32, shape [B, H]
    inv_rms_ptr,   # *float32, shape [B]
    weight_ptr,    # *float32, shape [H]
    out_ptr,       # *float32, shape [B, H]
    B: tl.int32,
    H: tl.int32,
    BLOCK_SIZE: tl.constexpr,
):
    row = tl.program_id(0)
    col_block = tl.program_id(1)
    if row >= B:
        return

    col_start = col_block * BLOCK_SIZE
    offs = col_start + tl.arange(0, BLOCK_SIZE)
    mask = offs < H

    # Load the row slice of hidden
    row_base_hidden = hidden_ptr + row * H
    x = tl.load(row_base_hidden + offs, mask=mask, other=0.0)

    # Load row's inv_rms and weight slice
    inv_rms_row = tl.load(inv_rms_ptr + row)
    w = tl.load(weight_ptr + offs, mask=mask, other=1.0)

    # Compute out = x * inv_rms_row * w
    out = x * inv_rms_row * w

    # Store
    row_base_out = out_ptr + row * H
    tl.store(row_base_out + offs, out, mask=mask)


def run_triton(hidden_states, weight):
    # Cast inputs to float32 for computation
    hidden = hidden_states.contiguous().to(torch.float32)
    weight = weight.contiguous().to(torch.float32)
    B, H = hidden.shape
    device = hidden.device

    # 1) Per-row reduction to compute inv_rms
    inv_rms = torch.empty((B,), dtype=torch.float32, device=device)
    _row_rms_inv_kernel[(B,)](
        hidden, inv_rms, B, H, 1e-5,
        BLOCK_SIZE=1024, num_warps=8, num_stages=2
    )

    # 2) Elementwise apply: 2D grid over rows and column blocks
    if H >= 4096:
        BLOCK_SIZE_E = 4096
        num_warps_e = 16
    elif H >= 2048:
        BLOCK_SIZE_E = 2048
        num_warps_e = 8
    else:
        BLOCK_SIZE_E = 1024
        num_warps_e = 4

    out_f32 = torch.empty((B, H), dtype=torch.float32, device=device)
    grid_apply = (B, triton.cdiv(H, BLOCK_SIZE_E))
    _apply_two_scales_kernel[grid_apply](
        hidden, inv_rms, weight, out_f32,
        B, H,
        BLOCK_SIZE=BLOCK_SIZE_E,
        num_warps=num_warps_e, num_stages=2
    )

    # Cast back to original dtype
    return out_f32.to(hidden_states.dtype)


# Optional: original Model using Triton path
class Model(torch.nn.Module):
    def forward(self, hidden_states, weight):
        return run_triton(hidden_states, weight)


class ModelNew(torch.nn.Module):
    def forward(self, hidden_states, weight):
        return run_triton(hidden_states, weight)
```

Why this should restore performance
- The reduction kernel is simple and robust: one program per row, coalesced loads, float32 accumulation, and rsqrt. It previously yielded strong speedups for H=4096.
- The elementwise kernel uses a 2D grid over (rows, column blocks) with BLOCK_SIZE chosen to cover the row efficiently. For H >= 4096, BLOCK_SIZE=4096 with num_warps=16 and grid=(B, cdiv(H, 4096)) (often 1) maximizes occupancy and parallelism compared to a single-block-per-row approach in some environments. For smaller H, it uses 2048/1024 with appropriate warps and num_stages=2 for pipelining.
- We avoid any incorrect pointer arithmetic by using row_base = hidden_ptr + row * H and direct offsets (inputs are contiguous), ensuring correct loads/stores.

This reverts to the launch configuration that previously achieved ~1.37x and should bring performance back above ~1.30x while maintaining correctness across all workloads.
