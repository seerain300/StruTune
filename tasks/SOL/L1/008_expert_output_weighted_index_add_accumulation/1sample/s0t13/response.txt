Analysis and root cause
- Original behavior: output.index_add_(dim=0, index=token_indices, source=expert_outputs)
  This is a scatter-add: for each i, output[token_indices[i]] accumulates expert_outputs[i]. If multiple tokens have the same token_index, their expert vectors should be added together, not replaced.

- Previous attempts failed correctness. The likely causes:
  - Using Triton kernels that relied on 2D grids, column blocks, and masked atomic stores. Even small mistakes in stride/pointer arithmetic or masks can lead to incorrect accumulation, especially when token indices repeat or shapes vary.
  - Zero-initialization issues or reliance on Triton to both zero and scatter-add can produce subtle bugs under varied shapes.
- To ensure correctness:
  - Use torch.zeros to zero-initialize the output buffer. This guarantees a clean accumulator for atomic adds.
  - Implement a Triton kernel that processes one token per program and loops over hidden columns in chunks, performing atomic_add into the target row. This handles duplicates correctly since each token’s contribution is added independently.

Plan
- Forward:
  - Compute batch_seq_len = batch_size * seq_len, hidden_size from axes_and_scalars, and num_selected_tokens from expert_outputs.shape[0].
  - Allocate output = torch.zeros((batch_seq_len, hidden_size), dtype=torch.bfloat16, device=device).
  - Convert token_indices to int32 for Triton.
  - Launch a Triton kernel scatter_add_tokens_kernel with one program per token. Inside each program, iterate over hidden columns in chunks (BLOCK_SIZE), load the corresponding slice from expert_outputs for that token, and atomic_add into out[token_indices[i], col:col+BLOCK_SIZE].
  - Return out.

- Triton kernel design:
  - One program per token id.
  - Use a simple while loop over columns with mask for tail. Since we zero-initialize the output, atomic adds are correct regardless of token index distribution.
  - Keep BLOCK_SIZE as a constant (e.g., 128) to reduce compile-time specialization issues and ensure masks are simple. num_warps=4 is a reasonable default.

This approach minimizes complexity and should ensure correctness across the evaluation configurations while still invoking Triton in the forward path.

Final code
```python
import torch

try:
    import triton
    import triton.language as tl
    TRITON_AVAILABLE = True
except Exception:
    TRITON_AVAILABLE = False


# Triton kernel: scatter-add one program per token.
# It loops over hidden columns in chunks and performs atomic_add into the target row.
@triton.jit
def scatter_add_tokens_kernel(
    out_ptr,              # *bf16
    expert_ptr,           # *bf16
    token_idx_ptr,        # *i32
    batch_seq_len,        # int
    hidden_size,          # int
    n_tokens,             # int
    stride_row,           # int (elements)
    stride_col,           # int (elements)
    exp_stride_row,       # int (elements)
    exp_stride_col,       # int (elements)
    BLOCK_SIZE: tl.constexpr,
):
    pid = tl.program_id(axis=0)  # token id
    # Guard: if pid >= n_tokens, early return (shouldn't happen with grid=(n_tokens,))
    if pid >= n_tokens:
        return

    # Load token index for this program (int32)
    token_index = tl.load(token_idx_ptr + pid)

    # Iterate over hidden columns in chunks
    col = 0
    while col < hidden_size:
        offs = tl.arange(0, BLOCK_SIZE)
        col_ids = col + offs
        mask = col_ids < hidden_size

        # Compute pointers
        # out_ptr is (batch_seq_len, hidden_size) with strides (stride_row, stride_col)
        out_ptrs = out_ptr + token_index * stride_row + col_ids * stride_col
        # expert_ptr is (n_tokens, hidden_size) with strides (exp_stride_row, exp_stride_col)
        exp_ptrs = expert_ptr + pid * exp_stride_row + col_ids * exp_stride_col

        # Load expert slice for this token; masked for tail
        vals = tl.load(exp_ptrs, mask=mask, other=0.0)

        # Atomic add into the output
        tl.atomic_add(out_ptrs, vals, mask=mask)

        col += BLOCK_SIZE


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states, expert_outputs, token_indices):
        # Shapes and parameters
        batch_size, seq_len, hidden_size = (
            0,  # not used directly, hidden_size comes from axes_and_scalars in get_inputs
            0,  # not used directly
            0,  # assume get_inputs sets hidden_size correctly
        )
        # We don't have batch_size/seq_len in the args; they are provided via axes_and_scalars in get_inputs.
        # However, final_hidden_states shape is (batch_seq_len, hidden_size). So we use its shape for output.
        # But since forward only receives final_hidden_states, expert_outputs, token_indices, we infer batch_seq_len
        # from the device and shape of final_hidden_states.
        batch_seq_len = final_hidden_states.shape[0]
        hidden_size = final_hidden_states.shape[1]
        n_tokens = expert_outputs.shape[0]

        # Ensure output is zero-initialized
        out = torch.zeros((batch_seq_len, hidden_size), dtype=torch.bfloat16, device=final_hidden_states.device)

        # Convert token indices to int32 for Triton
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        # Strides in elements
        stride_row = out.stride(0)
        stride_col = out.stride(1)
        exp_stride_row = expert_outputs.stride(0)
        exp_stride_col = expert_outputs.stride(1)

        # Launch Triton kernel: one program per token
        if TRITON_AVAILABLE:
            grid = (n_tokens,)
            scatter_add_tokens_kernel[grid](
                out, expert_outputs, token_indices_i32,
                batch_seq_len, hidden_size, n_tokens,
                stride_row, stride_col,
                exp_stride_row, exp_stride_col,
                BLOCK_SIZE=128,  # chunk size for hidden columns; tune as needed
                num_warps=4,
            )
        else:
            # Fallback: PyTorch implementation if Triton is not available
            out.index_add_(dim=0, index=token_indices, source=expert_outputs)

        return out
```

Why this fixes the previous issues
- Correctness: We explicitly zero-initialize the output. The Triton kernel performs atomic adds for each token across hidden columns. Duplicate token indices are handled correctly because each token’s contribution is added independently. This matches index_add_ semantics.
- Simplicity and robustness: The kernel is one program per token and iterates over columns in a straightforward while loop with masking for tails. This reduces the risk of incorrect pointer arithmetic or masked store misbehavior that led to previous failures.
- Triton usage: The forward method invokes the Triton kernel and relies on it for the heavy computation. No torch index_add is used in the hot path (except the PyTorch fallback when Triton is unavailable).

Performance considerations
- This design is simple and should be efficient for the provided workloads (hidden_size up to 1024, num_selected_tokens up to a few thousand). It avoids heavy atomics contention by processing one token per program and looping over columns in chunks.
- You can tune BLOCK_SIZE and num_warps. For hidden_size=256, BLOCK_SIZE=256 minimizes loop iterations. For general hidden sizes, 128 or 256 are reasonable defaults.
- After correctness is established, further speedups could be achieved by:
  - Using a 2D grid over tokens and column blocks to process multiple tokens per program, but ensure safety and avoid race conditions.
  - Increasing num_warps for better occupancy on large GPUs.
