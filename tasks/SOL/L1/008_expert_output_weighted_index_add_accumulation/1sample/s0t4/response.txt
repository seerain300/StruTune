Diagnosis
- The original PyTorch code performs output.index_add_(dim=0, index=token_indices, source=expert_outputs). This is a scatter-add along rows: for each i in [0, num_selected_tokens), output[token_indices[i]] += expert_outputs[i].
- The previous Triton attempt tried to use one program per row with atomic adds. While this conceptually can work, it was complicated and error-prone across varied shapes (e.g., hidden_size, seq_len) and token distributions. The evaluation reported “RUNTIME_ERROR” for multiple workloads, which likely stems from kernel logic or stride/pointer math issues under different configurations. Even minor mistakes in pointer arithmetic or masking can cause Triton to misaddress memory and produce incorrect results or crashes.
- To ensure robustness, we should match the reference behavior more directly: use a Triton kernel that processes one token per program, loops over hidden-size in column blocks, and performs atomic_add into the destination row. This avoids per-row kernel complexity and ensures that for any distribution of token indices, contributions are accumulated correctly.
- Additionally, the output must be zero-initialized before the scatter-add. We should ensure the Triton zero-init kernel is actually launched and operates correctly over any hidden_size.

Plan
- Define two Triton kernels:
  1) zero_init_kernel: zero-initializes the output tensor of shape (batch_seq_len, hidden_size) in bfloat16. We will do a 2D grid over rows and column blocks, writing zeros for all valid (row, col_block) pairs. This is simple and robust. It is actually launched from ModelNew.forward.
  2) scatter_add_atomic_kernel: For each token i (one program per token), load its expert vector (experts[i, :]) and perform atomic_add into out[token_indices[i], :] across hidden_size in column blocks. This matches index_add_ semantics. It is actually launched from ModelNew.forward.
- Ensure dtypes:
  - expert_outputs and final_hidden_states are bfloat16. Triton supports bf16. Atomic add on bf16 is supported on modern GPUs.
  - token_indices are converted to int32 for Triton.
- Generality:
  - The kernels use runtime shape parameters (batch_seq_len, hidden_size, num_selected_tokens) and BLOCK_SIZE for columns. We use masks to handle the last partial block when hidden_size is not divisible by BLOCK_SIZE.
- Performance:
  - The scatter-add kernel does O(n_tokens * hidden_size) atomic adds. This is comparable to PyTorch’s index_add and, for the provided sizes, should be fine. The zero-init kernel is O(batch_seq_len * hidden_size) and simple.
  - num_warps can be tuned (e.g., 4–8). BLOCK_SIZE=128 or 256 are reasonable defaults; we’ll use 128.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def zero_init_kernel(
    out_ptr,  # *ptr to output
    out_stride0,  # stride along rows
    out_stride1,  # stride along cols
    n_rows,  # batch_seq_len
    n_cols,  # hidden_size
    BLOCK_SIZE: tl.constexpr,
):
    # 2D grid: (n_rows, ceil_div(n_cols, BLOCK_SIZE))
    row = tl.program_id(0)
    col_block = tl.program_id(1)
    start_col = col_block * BLOCK_SIZE
    cols = start_col + tl.arange(0, BLOCK_SIZE)

    # Bounds mask for columns
    mask_cols = cols < n_cols

    # Compute base pointer for this row and column block
    # out_ptr is laid out as [row, col], strides provided
    base_ptr = out_ptr + row * out_stride0 + cols * out_stride1

    # Write zeros for valid columns
    tl.store(base_ptr, 0.0, mask=mask_cols)


@triton.jit
def scatter_add_atomic_kernel(
    out_ptr,  # *ptr to output
    out_stride0,  # stride along rows
    out_stride1,  # stride along cols
    experts_ptr,  # *ptr to expert_outputs
    experts_stride0,  # stride along rows of experts
    experts_stride1,  # stride along cols of experts
    token_indices_ptr,  # *ptr to token_indices (int32)
    n_rows,  # batch_seq_len
    n_cols,  # hidden_size
    n_tokens,  # num_selected_tokens
    BLOCK_SIZE: tl.constexpr,
):
    # One program per token
    pid = tl.program_id(0)
    if pid >= n_tokens:
        return

    # Load token index (int32)
    token_idx = tl.load(token_indices_ptr + pid)

    # Bounds check: token_idx must be in [0, n_rows)
    # Triton doesn't support dynamic break; we rely on host to provide valid indices.
    # If needed, you can mask out-of-range indices, but the harness ensures validity.

    # Loop over columns in blocks and atomic add
    for start in range(0, n_cols, BLOCK_SIZE):
        cols = start + tl.arange(0, BLOCK_SIZE)
        mask = cols < n_cols

        # Load expert row slice
        expert_row_ptr = experts_ptr + pid * experts_stride0 + cols * experts_stride1
        exp_vals = tl.load(expert_row_ptr, mask=mask, other=0.0)

        # Compute destination pointers
        out_row_ptr = out_ptr + token_idx * out_stride0 + cols * out_stride1

        # Atomic add into output
        tl.atomic_add(out_row_ptr, exp_vals, mask=mask)


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Shapes
        batch_seq_len = final_hidden_states.shape[0]
        hidden_size = final_hidden_states.shape[1]
        n_tokens = expert_outputs.shape[0]

        # Output tensor on same device and dtype (bfloat16)
        out = torch.empty(batch_seq_len, hidden_size, dtype=torch.bfloat16, device=final_hidden_states.device)

        # Choose a column block size; 128 is a good default
        BLOCK_SIZE = 128

        # 1) Zero-initialize output with Triton kernel
        grid_zero = (batch_seq_len, triton.cdiv(hidden_size, BLOCK_SIZE))
        zero_init_kernel[grid_zero](
            out, out.stride(0), out.stride(1),
            batch_seq_len, hidden_size,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,
        )

        # 2) Scatter-add with Triton kernel
        # Ensure expert_outputs and token_indices are on the same device
        # Convert token indices to int32 for Triton
        token_indices_i32 = token_indices.to(torch.int32).contiguous()

        grid_scatter = (n_tokens,)
        scatter_add_atomic_kernel[grid_scatter](
            out, out.stride(0), out.stride(1),
            expert_outputs, expert_outputs.stride(0), expert_outputs.stride(1),
            token_indices_i32,
            batch_seq_len, hidden_size, n_tokens,
            BLOCK_SIZE=BLOCK_SIZE,
            num_warps=4,
        )

        return out
```

What changed and why this should fix failures
- We now have two Triton kernels:
  - zero_init_kernel is actually launched to zero-initialize the output. This ensures atomic_add operates on a zero accumulator, matching index_add_ semantics.
  - scatter_add_atomic_kernel is actually launched to perform the scatter-add. One program per token, iterating over hidden_size in BLOCK_SIZE chunks, performs atomic_add into the correct row. This pattern is straightforward and handles any distribution of token indices correctly.
- The zero-init kernel uses a 2D grid over rows and column blocks, avoiding any single-program assumptions about row coverage. The scatter kernel uses a 1D grid over tokens, ensuring each token is processed exactly once.
- Dtypes are handled correctly: out and expert_outputs are bfloat16; token_indices are converted to int32 for Triton.
- The kernels use masks for partial column blocks, avoiding out-of-bounds accesses. We assume token indices are valid (as in the original get_inputs), which the evaluation harness guarantees.
