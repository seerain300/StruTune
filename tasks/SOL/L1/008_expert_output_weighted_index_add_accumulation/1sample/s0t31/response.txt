Re-analysis and plan
- The original PyTorch forward performs:
  output.index_add_(dim=0, index=token_indices, source=expert_outputs)
  which means: for i in range(num_selected_tokens): output[token_indices[i]] += expert_outputs[i]
- Our goal is to implement this scatter-add with Triton. We must ensure:
  - The output buffer is zero-initialized before the scatter-add (atomic_add semantics).
  - Each token’s expert vector is added to the correct row (token_indices in [0, batch_seq_len)).
  - We handle arbitrary shapes: batch_seq_len and hidden_size vary across workloads, and token_indices can repeat.

Likely root causes of previous failures
- The earlier kernel used 2D grids over tokens and column blocks. While theoretically correct, subtle issues can arise:
  - Masking for partial blocks must be applied carefully for both rows and columns; any mistake can lead to incorrect writes or OOB accesses.
  - Differences between runtime shapes and kernel assumptions can cause stride/pointer math to be off, especially with batch_seq_len potentially not equal to number of rows (even though the harness sets batch_seq_len equal to final_hidden_states.shape[0], it’s safer to use provided shapes).
  - Runtime errors suggest either OOB or undefined behavior from misaddressed pointers. Ensuring tight pointer arithmetic and simple addressing reduces risk.

Simplified, robust approach
- Zero-initialize the output tensor using torch.zeros for reliability. This guarantees atomic_add starts from zero and avoids any Triton kernel mistakes in zeroing.
- Implement a Triton scatter-add kernel with:
  - One program per token (grid = (num_selected_tokens,)).
  - A simple while loop that iterates over hidden_size in chunks of BLOCK_SIZE.
  - Compute offsets for columns: cols = start + arange(BLOCK_SIZE), mask for partial tail. Load out[token_index, cols], load expert_outputs[token_id, cols], and atomic_add into out[token_index, cols].
- This reduces complexity: no 2D grid, no masking mistakes for row coverage, and straightforward pointer math.

Correctness details
- Dtypes: expert_outputs and out are bfloat16; token_indices converted to int32 for Triton.
- Addressing: out_ptr + token_index * stride_row + cols * stride_col, where stride_row = out.stride(0) and stride_col = out.stride(1). This matches PyTorch’s layout for 2D tensors.
- Looping over columns: Using a while loop with start += BLOCK_SIZE ensures we cover all hidden columns. Mask ensures partial blocks at the end are handled safely.

Final code
```python
import torch

# Triton kernels
import triton
import triton.language as tl


@triton.jit
def zero_init_rows_cols_kernel(out_ptr, stride_row, stride_col, n_rows, n_cols, BLOCK_SIZE: tl.constexpr):
    # 2D grid over rows and column blocks; writes zeros to out
    row_id = tl.program_id(0)
    block_id = tl.program_id(1)
    cols = block_id * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = (row_id < n_rows) & (cols < n_cols)

    # Compute pointers for a tile (row_id, cols)
    ptrs = out_ptr + row_id * stride_row + cols * stride_col

    # Zero values (bf16)
    zeros = tl.zeros([BLOCK_SIZE], dtype=tl.bfloat16)
    tl.store(ptrs, zeros, mask=mask)


@triton.jit
def scatter_add_atomic_kernel(
    out_ptr, out_stride_row, out_stride_col,
    expert_ptr, expert_stride_row, expert_stride_col,
    token_indices_ptr,
    n_rows, n_cols, n_tokens,
    BLOCK_SIZE: tl.constexpr,
):
    # One program per token
    token_id = tl.program_id(0)

    # Bounds check for token_id in case grid > n_tokens
    if token_id >= n_tokens:
        return

    # Load token index for this token_id
    token_index = tl.load(token_indices_ptr + token_id)

    # If token_index out of bounds (shouldn't happen per get_inputs, but guard anyway)
    if (token_index < 0) | (token_index >= n_rows):
        return

    # Iterate over hidden columns in BLOCK_SIZE chunks
    start = 0
    while start < n_cols:
        cols = start + tl.arange(0, BLOCK_SIZE)
        mask = cols < n_cols

        # Compute pointers
        out_ptrs = out_ptr + token_index * out_stride_row + cols * out_stride_col
        expert_ptrs = expert_ptr + token_id * expert_stride_row + cols * expert_stride_col

        # Load current and add
        out_vals = tl.load(out_ptrs, mask=mask, other=0.0)  # other=0 for masked lanes
        expert_vals = tl.load(expert_ptrs, mask=mask, other=0.0)

        # Atomic add into output
        tl.atomic_add(out_ptrs, expert_vals, mask=mask)

        start += BLOCK_SIZE


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor, expert_outputs: torch.Tensor, token_indices: torch.Tensor):
        # Shapes
        batch_seq_len = final_hidden_states.shape[0]
        hidden_size = final_hidden_states.shape[1]
        n_tokens = expert_outputs.shape[0]

        # Allocate output and zero-initialize (ensures atomic_add correctness)
        out = torch.zeros(batch_seq_len, hidden_size, dtype=torch.bfloat16, device=final_hidden_states.device)

        # Triton requires int32 indices for simplicity; ensure contiguous
        token_indices_i32 = token_indices.to(torch.int32).contiguous()
        expert_outputs = expert_outputs.contiguous()

        # Launch zero-init kernel: 2D grid over rows and column blocks
        BLOCK_SIZE = 128
        grid_zero = (batch_seq_len, triton.cdiv(hidden_size, BLOCK_SIZE))
        zero_init_rows_cols_kernel[grid_zero](
            out, out.stride(0), out.stride(1), batch_seq_len, hidden_size, BLOCK_SIZE, num_warps=4
        )

        # Launch scatter-add kernel: one program per token
        grid_scatter = (n_tokens,)
        scatter_add_atomic_kernel[grid_scatter](
            out, out.stride(0), out.stride(1),
            expert_outputs, expert_outputs.stride(0), expert_outputs.stride(1),
            token_indices_i32,
            batch_seq_len, hidden_size, n_tokens,
            BLOCK_SIZE=BLOCK_SIZE, num_warps=4
        )

        return out
```

Summary of changes and why they should fix issues
- We now explicitly zero-initialize the output tensor using a simple Triton kernel. This removes any uncertainty about the accumulator starting from zero.
- The scatter-add kernel uses one program per token with a straightforward column loop and atomic_add. This avoids complex 2D grid logic and reduces the chances of masking/pointer mistakes that led to previous failures.
- The zero-init kernel covers all rows and column blocks with masks for partial tiles. The scatter kernel loads the correct expert vector and adds it atomically to the corresponding row for each token.
- The forward method allocates out as zeros, then launches both kernels. No torch operations are used in the hot path beyond trivial conversions and making tensors contiguous.

Performance considerations
- Zero initialization via Triton is a simple fill and typically fast. The scatter-add uses one program per token with a column loop, performing atomic adds. For the given sizes (hidden_size up to 1024, n_tokens up to a few thousand), this should be performant. If profiling later shows bottlenecks:
  - Increase BLOCK_SIZE to 256 and num_warps to 8 for larger hidden_size on high-end GPUs.
  - Consider a 2D grid over tokens and column blocks if needed; for correctness now, the one-program-per-token approach is simpler and robust.

This implementation ensures Triton kernels are actually launched and perform the computation, addressing correctness issues reported across the varied workloads.
