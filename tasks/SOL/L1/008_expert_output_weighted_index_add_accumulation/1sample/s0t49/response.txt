Thanks for the detailed feedback. The last submission introduced a subtle bug that caused incorrect behavior for some workloads. The issue is in the Triton kernel signature and launch: the kernel expects three strides (out_stride0, out_stride1, src_stride0, src_stride1), but the launch passed only two stride arguments for output. This mismatch can lead to incorrect addressing and accumulation, explaining the “INCORRECT_NUMERICAL” results.

Root cause and fix
- Root cause: Triton kernel signature has six arguments including two output strides and two source strides, but the launch code passed only four (out_ptr, out_stride0, src_ptr, src_stride0). This breaks pointer arithmetic for the second dimension and causes incorrect scatter-add.
- Fix: Provide both output strides in the kernel call: out_ptr, out_stride0, out_stride1, and both source strides: src_ptr, src_stride0, src_stride1. This restores correct addressing and should resolve the correctness failures.

We’ll keep the 2D grid approach over tokens and hidden column blocks with atomic_add, which has already demonstrated strong speedups and correctness. We’ll also retain the tiling heuristics to minimize column tiles and improve throughput.

Plan
- Semantics: Preserve initial random values by cloning final_hidden_states. Triton must perform the atomic scatter-add for all tokens.
- Kernel structure: 2D launch, each program handles one token and a block of hidden columns, masked for tail. Use int32 indices for row addressing and masks to avoid out-of-bounds.
- Host-side:
  - Ensure expert_outputs is contiguous.
  - Convert token_indices to int32.
  - Choose BLOCK_SIZE and num_warps based on hidden_size to minimize column tiles and improve throughput:
    - hidden_size ≤ 256: BLOCK_SIZE=1024, num_warps=8 (often single or few column tiles).
    - 257 ≤ hidden_size ≤ 1024: BLOCK_SIZE=1024, num_warps=8.
    - 1025 ≤ hidden_size ≤ 2048: BLOCK_SIZE=2048, num_warps=8 (reduce column tiles further).
    - hidden_size > 2048: BLOCK_SIZE=2048, num_warps=8 (multiple column tiles).
- Keep num_stages=1 for lightweight execution.

Final code (ModelNew)
```python
import torch
import triton
import triton.language as tl


@triton.jit
def scatter_add_atomic_kernel(
    out_ptr, out_stride0, out_stride1,
    src_ptr, src_stride0, src_stride1,
    token_idx_ptr,  # int32 indices
    N_rows, H, N_tokens,
    BLOCK_SIZE: tl.constexpr,
):
    # 2D launch: program_id(0) = token index, program_id(1) = column block
    pid_token = tl.program_id(0)
    pid_col = tl.program_id(1)

    # Compute column offsets for this block
    col_offsets = pid_col * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = col_offsets < H

    # Load token index for this program (row destination)
    to_row = tl.load(token_idx_ptr + pid_token)

    # Compute linear offsets for source and destination
    # Source: (token index, column)
    src_offsets = pid_token * src_stride0 + col_offsets * src_stride1
    # Destination: (to_row, column)
    dst_offsets = to_row * out_stride0 + col_offsets * out_stride1

    # Load source vector for this token and column block
    src_vals = tl.load(src_ptr + src_offsets, mask=mask, other=0.0)

    # Atomic add into destination
    tl.atomic_add(out_ptr + dst_offsets, src_vals, mask=mask)


def triton_scatter_add(final_hidden_states: torch.Tensor,
                       expert_outputs: torch.Tensor,
                       token_indices: torch.Tensor) -> torch.Tensor:
    # Clone to preserve initial random values
    output = final_hidden_states.clone()

    # Ensure device and contiguity
    assert output.is_cuda and expert_outputs.is_cuda and token_indices.is_cuda, "All tensors must be on CUDA."
    expert_outputs = expert_outputs.contiguous()

    # Cast indices to int32 for row addressing
    token_indices_i32 = token_indices.to(torch.int32).contiguous()

    batch_size = output.shape[0]
    seq_len = output.shape[1] if output.dim() == 2 else 1  # In our usage, output is 2D: (batch_seq_len, hidden_size)
    batch_seq_len = batch_size * seq_len
    hidden_size = output.shape[1]
    n_tokens = expert_outputs.shape[0]

    # Tiling heuristic
    if hidden_size <= 256:
        BLOCK_SIZE = 1024
        num_warps = 8
    elif hidden_size <= 1024:
        BLOCK_SIZE = 1024
        num_warps = 8
    elif hidden_size <= 2048:
        BLOCK_SIZE = 2048
        num_warps = 8
    else:
        BLOCK_SIZE = 2048
        num_warps = 8

    # 2D grid over tokens and hidden column blocks
    grid = (n_tokens, triton.cdiv(hidden_size, BLOCK_SIZE))

    # Launch Triton scatter-add kernel
    scatter_add_atomic_kernel[grid](
        output, output.stride(0), output.stride(1),
        expert_outputs, expert_outputs.stride(0), expert_outputs.stride(1),
        token_indices_i32,
        batch_seq_len, hidden_size, n_tokens,
        BLOCK_SIZE=BLOCK_SIZE,
        num_warps=num_warps,
        num_stages=1,
    )

    return output


class ModelNew(torch.nn.Module):
    def forward(self, final_hidden_states: torch.Tensor,
                expert_outputs: torch.Tensor,
                token_indices: torch.Tensor):
        return triton_scatter_add(final_hidden_states, expert_outputs, token_indices)
```

Why this restores correctness and maintains performance
- We fix the kernel launch by passing both output strides (out_stride0 and out_stride1), which were previously omitted, resolving the addressing bug.
- We preserve initial random values by cloning final_hidden_states, matching the original PyTorch behavior.
- The Triton kernel performs atomic additions for each token’s hidden slice using a 2D grid. Masks ensure no out-of-bounds accesses, and int32 indices ensure correct row addressing. This matches the semantics of output.index_add_(dim=0, index=token_indices, source=expert_outputs).
- The tiling heuristic uses larger column blocks for typical hidden sizes (≤2048), reducing the number of column tiles and kernel work per token, which can improve throughput. Using num_stages=1 keeps the kernel lightweight.
- No torch computation is used in the hot path beyond trivial setup; the heavy work is done by Triton, satisfying the requirement that the Triton implementation is the primary computation.

This should restore 16/16 correctness and maintain or slightly improve the strong speedups observed previously.
