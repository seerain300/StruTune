- The original PyTorch code behavior:
  - It generates a tensor topk_idx with shape (batch_size, seq_len, num_experts_per_tok), dtype int32, on the provided CUDA device.
  - In run, it flattens this tensor to 1D of length N = batch_size * seq_len * num_experts_per_tok.

  - It computes expert_offsets via histogram:
    - counts[i] = number of occurrences of i in flat for i in [0..255]
    - offsets[0] = 0

- The evaluation requirement is strict: all computation (no torch operations like torch.argsort, torch.cumsum, reductions) must be implemented inside @triton.jit kernels and actually launched from ModelNew.forward. The previous submissions failed correctness on multiple workloads, which suggests the custom sorting kernel had subtle logical errors and was not a robust fit for arbitrary N. Implementing a bitonic or odd-even sort in Triton is doable but easy to get wrong, especially with masking and vectorized pairing.

Key insight to fix correctness robustly:
- If we cannot reproduce torch.argsort exactly in Triton without risking correctness, the safest way to ensure correctness while still using Triton is to compute the histogram and the offsets (which is trivial and small) in Triton, and rely on torch.argsort for the permutation. However, since the evaluator prohibits torch.argsort, we must find a way to implement the sort in Triton.
- Given the evaluator’s repeated “INCORRECT_NUMERICAL” and not “runtime error,” it points to logical incorrectness (wrong permutation) rather than out-of-bounds or kernel crashes. The most robust sorting network for power-of-two sizes and easy to implement correctly in Triton is bitonic sort. In the provided workloads, N (which equals batch_size * seq_len * num_experts_per_tok) tends to be power-of-two (e.g., 2048, 2048, 1024, 4096, etc.), which is favorable for a bitonic sort. We can implement a stable bitonic sort in Triton for these power-of-two N and return the permutation. For non-power-of-two N, we can pad to next power-of-two and mask.

1) Implement a Triton bitonic sorting kernel that:
   - Takes a 1D int32 values array of length N (flattened topk_idx) and a 1D int32 indices array of length N. It will output the sorted permutation (sorted_token_indices).
   - Operates on the entire N if N is a power-of-two (which the evaluator’s shapes typically are). For non-power-of-two N, we can pad by adding a large sentinel so padded positions sort to the end; however, to maximize correctness, we’ll only run the kernel when N is a power-of-two.    - We will implement a stable bitonic sort: for comparator pairs where value_left != value_right, swap if value_left > value_right. For equal values, do not swap to preserve original order (stable).
2) Implement Triton histogram kernel with atomic adds to build counts[0..255] from the flattened indices.
3) Implement Triton inclusive prefix sum over counts to produce offsets[0..256].
4) In ModelNew.forward:
   - Flatten topk_idx to int32 1D tensor.
   - If N is a power-of-two, launch the bitonic Triton kernel to produce sorted_token_indices. Else, if the code were allowed to use PyTorch, torch.argsort would be used. If N is not power-of-two, we can still run the bitonic kernel but pad with a large value; the fallback safe behavior is that padded values are larger than any valid index (255), so they end up at the end.    - Launch prefix-sum kernel to compute offsets.

5) Performance considerations:
   - Bitonic sort is O(N log^2 N). For typical N up to 4096, this is fine. It avoids correctness pitfalls from odd-even variants and is straightforward to implement correctly.
   - Histogram and prefix sum are O(N) and O(256), respectively, very light.
   - We choose num_warps based on BLOCK for decent throughput; BLOCK is a power-of-two (e.g., 4096) and masks out lanes >= N.
