Root cause, strict requirements, and plan
- The original Model.forward simply calls run(topk_idx). The run function:
  - Flattens topk_idx into a 1D tensor flat of length N = batch_size * seq_len * num_experts_per_tok.
  - sorted_token_indices = flat.argsort(stable=True). This returns a permutation of [0, N-1], dtype int64 by default in PyTorch.
  - expert_offsets = torch.bincount(flat.long(), minlength=256).cumsum(0). Since flat is int32 from get_inputs, flat.long() is int64 before bincount, so counts are int64 and the cumsum is int64. Output shape is (257,).

- The evaluator previously rejected attempts that used torch.bincount, torch.cumsum, or torch.argsort in the host. It also flagged dtype mismatches and runtime errors. To pass:
  - Use Triton kernels for all numeric computation: no torch.bincount, no torch.cumsum, no torch.argsort.
  - Return exactly the same outputs as the original:
    - sorted_token_indices: torch.int64, shape (N,)
    - expert_offsets: torch.int64, shape (257,)

- Triton implementation strategy:
  1) Argsort permutation via Triton counting sort:
     - The generator creates expert indices in [0, 255] (num_experts=256), so values are bounded. We can implement a stable argsort in Triton using a counting-sort approach:
       - Histogram of flat values (int32) in bins [0..255].
       - Compute exclusive prefix sums of the histogram to get starting positions for each bin.
       - Write out positions for each value: sorted_token_indices[pos_out] = original index; increment starting position for that bin. This produces a stable order: for equal values, the original order is preserved as we process tokens in original order.
     - We use a single Triton program with a large BLOCK (e.g., 1024) and loop over tokens. Since N is at most a few thousand in provided workloads, this is fine. If N exceeded BLOCK, we could extend to a multi-block two-pass scan, but not needed here.

  2) Bincount via Triton:
     - Implement a Triton kernel that does an O(N) histogram across the 256 bins using atomic_add. Given values are in [0, 255], this matches torch.bincount(flat.long(), minlength=256) without needing to pad.

  3) Prefix sum via Triton:
     - Implement an inclusive prefix sum of the 256 counts vector in Triton, writing directly to an int64 output vector of length 257. We avoid torch.cumsum entirely.

- Dtypes and shapes:
  - sorted_token_indices must be int64 (to match PyTorch’s default argsort).
  - expert_offsets must be int64 (to match torch.bincount(...).cumsum(0)). We will compute counts in int32 for performance and then convert to int64 before the Triton prefix sum. The prefix sum output will be int64.

- Performance considerations:
  - For the given workloads (N up to ~8192), a single Triton program looping over tokens is efficient. The sorting by counting is O(N) with 256 atomics per token; bincount is O(N) atomics; prefix sum is O(256). All on the GPU, no host reductions.

@triton.jit
def bincount_i32_minlen256(x_ptr, counts_ptr, N: tl.int32, BLOCK: tl.constexpr):
    # Perform per-element atomic add into counts[0..255] for x_ptr values (int32)
    # x_ptr points to int32 values; counts_ptr is int32
    for offset in range(0, N, BLOCK):
        offs = offset + tl.arange(0, BLOCK)
        mask = offs < N
        # Load values; other=0 to ignore out-of-range
        vals = tl.load(x_ptr + offs, mask=mask, other=0)
        # Atomic add counts for valid lanes
        # Note: Triton atomic_add requires pointer and value; here we atomically add 1 per valid lane.
        for i in range(BLOCK):
            if mask[i]:
                # atomic add 1 into counts[vals[i]]
                tl.atomic_add(counts_ptr + vals[i], 1)

    # We implement a scalar loop in a single program. L is passed as int32. We assume L=257.
    # Note: Triton supports scalar loops with runtime bounds. We use y_ptr[offset] = inclusive sum up to offset.

    # We need to avoid direct pointer indexing with runtime offset inside Triton in a vectorized way.
    # A robust approach is to use scalar loop and update a running sum, writing to offsets[offset].
    # Triton allows this pattern.

    running = tl.zeros((), dtype=tl.int32)
    # We'll write offsets as int64 by casting. Triton has tl.cast. We loop and write scalar.
    for offset in range(0, L):
        val = tl.load(counts_ptr_i32 + offset)
        running += val
        # offsets_ptr_o64 is int64; we store running (int32) cast to int64
        tl.store(offsets_ptr_o64 + offset, tl.cast(running, tl.int64))
