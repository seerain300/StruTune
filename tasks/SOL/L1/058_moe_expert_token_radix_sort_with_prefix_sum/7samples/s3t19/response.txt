  - Inputs: topk_idx shape (batch_size, seq_len, num_experts_per_tok). We flatten to a 1D tensor flat of length N.
  - sorted_token_indices = torch.sort(flat, stable=True).indices: 1D tensor of length N, the permutation that would sort the values with stable tie-breaking by original index.

- Why previous attempts failed:
  - The last submission tried a Triton bitonic sort but encountered runtime errors. Triton requires constexpr parameters for certain constructs (like loop bounds), and passing dynamic values or improper constexpr usage can lead to compilation/runtime issues in the evaluator. Additionally, the previous version used torch.cumsum for offsets; we must avoid any torch reductions in the host code.
  - An earlier submission had decoy kernels (defined but not launched), which the evaluator flagged.

- Strategy to fix correctness and adhere to Triton-only:
  - Remove torch.sort from host code. Implement a Triton bitonic sorting network that produces a stable argsort indices. We pad N to the next power-of-two B and use a fixed comparator schedule. The kernel will:
    - For each original index i in [0..N-1], compute its rank among the elements, with stable tie-breaking by original index when values are equal. Specifically:
      - For each j in the network, determine whether i and j form an ascending/descending pair. If ascending, lower value wins; if equal, lower original index wins. If descending, higher value wins; if equal, higher original index wins. This is achieved by combining the comparator’s dir (ascending or descending) with stable tie-breaks.
      - Maintain a boolean array has[i] to mark whether i is still available for placement. After each comparator stage, the “winner” (the index that keeps its value) is computed and its position pos[w] is reserved via atomic add, then the permutation[out[i]] is set to i for those not yet placed. This places each index i at its correct sorted position, producing the argsort permutation.
    - We pass B as a constexpr meta-parameter to Triton to satisfy loop bounds. We compute B = next power-of-two of N in host code, ensure N <= 2^B (we use B = 1 << ceil(log2(N))).
  - Histogram and offsets:
    - Implement a Triton histogram kernel that does atomic adds into an int32 array of size 256 (num_experts). We pass num_experts as a constexpr to Triton.
    - Implement a Triton inclusive prefix-sum kernel to compute cumulative sums per expert. We pass num_experts as constexpr and use iterative doubling to perform the scan in-place on the histogram.

- Ensuring no decoy kernels:
  - Define Triton kernels and invoke them from ModelNew.forward with explicit grid and meta-parameters. No torch.sort, torch.cumsum, torch.bincount in host code.

This approach avoids the runtime errors by using Triton’s constexpr-friendly loops and ensures that all computation is performed inside Triton kernels. While bitonic sort is O(N log^2 N), it’s parallelizable and should be fine for the provided workloads. If runtime issues persist in the evaluator due to constexpr handling, we can add a robust fallback to torch.sort in forward; however, that would violate Triton-only. Here we prioritize Triton-only and correctness.
